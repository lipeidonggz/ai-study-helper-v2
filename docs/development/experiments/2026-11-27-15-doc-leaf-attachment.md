## Token 与资金成本核算

### 已知与未知

本次运行原始记录只保存了 `input_tokens` 和 `output_tokens`，没有保存 DeepSeek
返回的 `prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`。因此可以从账本精确
计算输出费用和“全部未命中”的输入费用上限，但无法还原本次实际缓存命中数和精确
账单。请求 ID 也未由该运行器保留，不能通过请求级记录反查缓存拆分。

当前对话 provider 与挂接运行器已补齐缓存 usage 采集：非流式和流式响应都会保留
缓存命中／未命中 token，root 与 leaf 阶段的重试、fallback 和 completed 记录会分别
累计，最终 manifest 保存两阶段的四项缓存总量。后续新运行可以直接生成精确账单。
本文所记录的历史 092 产物没有这些字段，不回填，也不把敏感性估算改写成实测值。

## 解释与限制

- 一级树初筛只把 121,742 个候选对筛入逐叶阶段，但 86 个 block 仍保留全目录，说明该步骤在高召回设定下并未充分缩小所有长 block 的规模。
- 7,843 条支持关系是当前二条件提示词的系统输出，不证明语义精确率。支持数最多达到单个 block 91 个叶节点，后续需要用查询端证据覆盖、c13-003 和留出求全问题检查误挂与弱支持噪声。
- 94 个空叶节点只能说明在这套候选规则和当前 15 篇原文中没有支持，不等于知识目录本身错误。
- 本实验尚未接入查询期叶节点召回，因此不能据支持关系数量直接声称端到端找全能力已经提升。
