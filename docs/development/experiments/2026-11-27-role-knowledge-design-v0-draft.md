## 1 文档目的

### 1.1 要解决的问题

前面的设计主要从“知识对象之间是什么关系”出发组织知识。关系观察轴适合筛选某类关系证据，但仍有两个缺口：

1. 用户可能首先要求枚举领域中的对象或方法，例如“AI Agent 的工程方法论都有哪些”；
2. 同一个词在不同文档和问题中可能有不同含义。例如，“隔离”可能分别指沙箱、虚拟机等实现机制，资源访问边界，防止数据泄漏的安全目标，或一类控制策略。预先固定概念本体和关系目录，会迫使同一知识被过早放入错误分类，并持续扩大分类负担。

本设计换一个知识组织起点：不从语料主题聚类和通用关系本体出发，而从“谁要用这个领域的知识完成任务”出发，先确认使用角色，再生成该角色的主要任务和任务树。任务树描述使用需求，不能直接充当知识内容目录；系统先独立生成该角色应当掌握的一级知识框架，再使用任务树检查履职覆盖缺口。

这里还有一个关键解耦：系统先生成一套与当前知识库内容无关的领域知识框架，再把知识库中的原文证据挂接到框架叶节点。“内容无关”是指框架生成不读取当前知识库的文档、主题、统计或已有抽取结果，而不是脱离领域和角色；领域名称与角色视角仍然决定框架范围。这样既保留角色和任务提供的多视角查漏能力，也避免让当前语料中有哪些内容反过来限制系统应该寻找哪些知识。

这种先框架、后挂接的顺序还有两个直接价值：

1. 知识库证据挂接时可以发现知识库缺口。每个叶节点都表达一个可独立判断覆盖的知识范围；一旦挂接完成，没有证据、证据很少或只覆盖部分典型情形的叶节点都会显式暴露出来。是否补齐这些缺口取决于该知识库准备用于什么任务，但缺口本身可以被稳定识别和记录。
2. 问答时可以根据框架给出知识库覆盖边界。若用户的求全问题属于当前领域，而知识库在某些叶节点上缺少内容或内容不足，主 Agent 可以依据节点证据状态提示用户“当前知识库未覆盖哪些方面”，而不是根据知识库碰巧有没有内容来决定问题能扩展到多大；框架只用于提示覆盖缺口，不能用框架中的先验知识替代原文证据回答。

### 1.2 核心命题

本设计当前采用以下推导链：

```text
知识库领域
→ 使用角色候选
→ 用户确认角色
→ 主要任务候选（多轮独立生成并归并）
→ 角色任务树
→ 一级知识框架候选（多轮独立生成并归并）
→ 基于角色任务的覆盖审查与 LLM 修复闭环
→ 一级知识框架冻结
→ 每个一级分支独立展开为知识主题树
→ 冻结角色知识框架与叶节点目录
→ 查询时按一级分支并行召回叶节点
→ 原文证据挂接、覆盖复核与回答
```

核心命题是：

> 对一个声明范围内的知识库领域，可以先多轮生成并归并使用角色候选，由用户确认实际要覆盖的角色；再为该角色生成、归并主要任务并拆成任务树。知识主题的主干不从任务步骤生长，而由该角色应掌握的一级知识框架多轮生成后按知识身份归并得到。任务树用于逐项审计该框架是否包含履职所需知识，并由 LLM 修复器补齐真实缺口。一级框架冻结后，每个一级分支独立展开；叶节点只表示可独立命名、检索和判断证据覆盖的领域知识范围。查询时，主 Agent 对每个一级分支并行执行一次叶节点召回，返回集合用 `required` 与 `optional` 表达回答优先级。召回结果不是最终答案，下一步仍需挂接原文 block、复核证据覆盖，并对主题外内容进行兜底检索。

该设计不假设同一领域只有一棵稳定目录，也不假设单次生成能完整覆盖角色知识。多轮生成解决候选发现，语义归并解决重复与粒度，任务覆盖审查解决履职缺口，逐分支展开解决单次生成规模过大，逐分支召回解决查询时的全目录输入过载。任何单次运行或单次测试问题都不能证明领域语义已经完整。

### 1.3 设计来源：人类知识传递方式

本设计确实借鉴了人类传递知识的基本方式。一本书、课程或教程通常先设定目标读者，也就是目标角色；再选择一条主线组织领域知识，形成目录；目录中的每一项则对应一个知识主题。

本设计把这一结构映射为：

```text
目标读者 → 使用角色
知识组织主线 → 角色知识框架
履职查漏 → 主要任务与任务树
目录项 → 知识主题
```

借鉴的不是某一本现成书籍的目录，而是这种“先明确谁使用，再确定如何组织知识”的方法。工程化后有三个区别：

- 同一个角色允许通过多次独立生成发现不同组织视角，再按知识身份归并，而不要求跨次目录逐字相同；
- 角色知识框架承担知识发现和组织，任务树承担履职覆盖审查，其他角色可以提供额外发现视角，但不能直接决定当前角色的主题名称；
- 查询时按一级分支并行召回叶节点，角色和任务不作为每次查询的必经定位链路。

### 1.4 与 15 和 15.1 的关系

本设计不立即替换 15 或 15.1。三者关系如下：

- 15 号设计以知识对象域和关系分面共同组织知识；
- 15.1 在 15 号模型内部继续设计关系观察轴与二级关系；
- 本文提出另一条竞争路径：使用角色生成领域知识框架，使用任务树审查知识覆盖，关系视角降为可选的生成、抽取和查询透镜；
- 知识主题树与关系观察轴可以共享原文证据，但承担不同职责，不能相互冒充。

本文重点验证：双分面是否必须是主要组织方式，以及“使用角色 → 知识框架 → 任务覆盖审查 → 叶节点召回”能否提供更直接的找全覆盖骨架。

### 1.5 非目标

本文当前不承诺：

- 枚举一个领域的全部现实角色；
- 证明每个知识领域都存在唯一正确的知识框架；
- 直接生成未经原文支持的领域真理；
- 用主题综合页替代原文证据；
- 首版完成跨角色知识主题归一化；
- 首版把任务节点中的动作、交付物或完成条件直接改写为知识主题；
- 首版在任务树与知识主题之间设置独立中间语义层，或要求用户直接在界面上维护领域问题清单；
- 在真实语料和独立找全问题验证前替换 13、14 或 15.1 的实现路径；
- 把本设计与 Microsoft GraphRAG 的既有机制等同。

## 2 设计依据

### 2.1 为什么从使用角色出发

知识库并不是对领域世界的穷尽描述，而是为特定使用方式提供证据。相同领域在不同使用位置会产生不同的知识关注点：

- Agent 架构师需要决策循环、状态、工具边界和失败恢复；
- 安全工程师关注信任边界、越权、注入和爆炸半径；
- 评测人员关注任务设计、指标、基准和回归；
- 产品人员关注能力边界、成本、用户预期和采用条件。

这些需求不能只靠固定关系类别推导。先识别使用角色，可以把“知识库为什么需要这些主题”显式化。

### 2.2 为什么用任务树而不是关键决定

“关键决定”可以作为任务分析中的辅助说明，但首版不作为独立生成层级。原因如下：

- 决定与任务通常多对多，强行建立“任务 → 决定 → 问题”的完备映射成本高；
- 同一决定可能横跨多个任务，也可能只是某个任务内部的判断点；
- 模型很容易生成泛化决定，例如“如何保证安全”，却没有更接近可回答问题的语义；
- 找全问题最终需要的是能够支撑独立判断和证据选择的知识范围，而不是一组抽象决定。

任务树负责把角色职责拆成可独立完成、可检查结果的实际工作，并保存完成条件、纳入范围与排除边界。它回答“角色需要实际完成哪些工作”，但任务标题、完成条件和场景走查要求仍混合了动作、交付物、验证步骤与领域知识。中间任务可以是目标分解或汇总节点；跨子任务的检查、综合、权衡、冲突修复和最终决策属于实际工作，必须成为显式子任务，不能只藏在父任务描述中。

任务树不直接生长知识目录。它的稳定职责是充当履职覆盖审计锚点：知识框架先由角色视角独立形成，再由任务树逐项检查每项任务及其关键判断所需的知识范围是否存在。这样既能发现只按工作任务拆分时容易遗漏的概念、机制和横向边界，也避免把“写报告、做评审、形成清单”等动作误写成知识主题。

### 2.3 为什么持久化内容节点只放知识主题

角色和任务都被当前使用方式绑定。如果把角色或任务直接写成最终树路径，一次角色或任务调整就会重写用户看到和查询路由的知识结构，并容易把一次性需求误当成领域知识。

因此：

- 可长期保存的内容节点只表达知识主题及其范围；
- 角色和主要任务作为知识框架的生成与覆盖审查依据，不成为知识主题名称；
- 多个任务可以共同要求同一知识范围，同一任务也可以由多个知识范围共同支撑，不建立机械的一对一映射；
- 知识节点是否属于同一身份，依据研究对象、核心问题和知识边界共同判断，不能仅按标题相似或共享上位类别合并；
- 父节点是知识范围的组织节点，叶节点是默认的证据挂接与独立覆盖判断单位；任何非叶节点的覆盖，均由该节点所属的全部后代叶节点汇总得到。

### 2.4 为什么仍需要原文证据

知识主题只能说明“这里应该讨论什么”，不能证明知识库中的结论真实、完整或适用于当前上下文。证据挂接必须保留 block、章节路径、文档来源、原文片段和挂接理由。

生成式改写可以形成主题概览和路由说明，但最终回答仍必须回到原文证据。

### 2.5 与 GraphRAG 的边界

Microsoft GraphRAG 的基础索引流程不要求用户先输入一组角色和场景：

```text
文档 → text units → 实体与关系抽取 → 社区 → 社区报告
```

GraphRAG 的可选 `prompt-tune` 会从语料 chunk 中推断领域、生成一个 persona、一个社区报告角色、实体类型和领域适配提示词。这些角色用于改写抽取和摘要提示词，不成为最终图中的节点，也不是一组知识库使用角色。

因此，本设计可以参考 GraphRAG 的“编译时引入使用语义”思路，但不能把它解释为 GraphRAG 已经提供了“角色／场景驱动的知识目录”。本设计的角色、任务、问题和最终知识主题仍是独立设计。

核对来源：

- [Microsoft GraphRAG · Auto Prompt Tuning](https://microsoft.github.io/graphrag/prompt_tuning/auto_prompt_tuning/)：该步骤是可选能力；
- [Microsoft GraphRAG · `prompt_tune.py`](https://github.com/microsoft/graphrag/blob/7f996cf5/graphrag/api/prompt_tune.py)：实现中生成 `domain`、`persona`、`community_reporter_role` 和索引提示词。

## 3 核心概念

### 3.1 知识库领域卡

知识库领域卡是领域身份锚点，不是项目章程，也不是一次填完的配置向导。必填字段只有一个：

| 字段 | 说明 |
| --- | --- |
| 领域名称 | 例如“AI Agent” |
| 领域说明 | 选填的用户可理解解释，只用于展示、人工确认或需要消歧的交互；不进入角色知识主题框架生成及其覆盖审查 |

以 AI Agent 为例，系统可以为用户展示如下可选解释：

```text
领域名称：AI Agent
领域说明：AI Agent 是一类以语言模型或类似模型作为决策核心，能够结合上下文，
并调用工具、检索、其他 Agent 或外部环境，在多步执行中推进目标的软件系统。
自治程度可以不同，不要求必须是多 Agent 系统。
```

系统负责生成 `domain_id` 和可选的候选展示解释。领域名称必须能够明确识别领域；领域名称有歧义时，系统先让用户完成规范化消歧，再把选中的规范名称用于生成。常见别名、知识库边界、目标用户、用途和粒度等均为选填。知识库快照、文档范围、语言和时间边界属于 collection 元数据。

领域卡不固化用户目的。用户目的变化时，应调整使用角色、任务或主题选择，而不是修改领域身份。

### 3.2 使用角色卡

“使用角色”是一类带着具体任务使用当前领域知识的人或明确职能主体。职业名称只用于识别，不能代替任务说明。角色卡有“候选态”和“确认态”两种生命周期形态：候选态用于发现、比较和归并角色；用户确认角色后，才生成完整主要任务，并在审核后进入任务树。

| 字段 | 适用形态 | 说明 |
| --- | --- | --- |
| 角色标识 | 两种形态 | 宿主分配的稳定 ID |
| 角色名称 | 两种形态 | 用户可识别和选择的职业、岗位或职能名称 |
| 区分性任务 | 候选态必填 | 用于识别角色和与相邻角色区分的少量代表性任务；严格为 2～4 项，不是完整职责清单，不展开步骤或子任务 |
| 主要任务 | 确认态必填 | 用户确认角色后多轮生成并归并的完整主要职责结果；覆盖该角色承担的通用职业原型职责和领域限定新增职责，不展开步骤或子任务 |
| 已有知识 | 可选的两种形态 | 默认概念背景和术语理解，只辅助后续问题深度 |

角色卡是知识库的可选配置。未选择角色时，系统可以保留全部有效候选，但不能静默只选一个默认角色。

角色名称只用于识别和选择，`reason` 说明它为什么与相邻角色不同，两者都不能代替任务。候选阶段的区分性任务只用于判断“这是不是一个独立角色”以及“能否与邻近角色合并”，不得作为任务树输入，也不得要求模型在一次生成几十个角色时同时穷尽每项职责。用户确认角色后，系统再以角色名称、领域卡、区分性任务和可选已有知识为上下文，多轮生成主要任务候选并按职责结果归并；用户审核通过的主要任务才是任务树展开的第一级输入。

角色卡不额外保存职责描述或岗位概述；能够形成可完成结果的职责必须直接表达为主要任务。任务树负责把每项已确认主要任务展开到可独立完成、可检查结果的实际工作粒度。

### 3.3 角色任务树

角色任务树把角色卡中的主要任务展开为可审核层级。每个任务节点包含
`task_key`、`source_primary_task_id`、`task`、`completed_when`、`inclusions`、
`exclusions`、`split_basis` 和 `children`。

已审核主要任务本身是自包含的任务语义契约，`task`、`completed_when`、
`inclusions` 和 `exclusions` 都必须在上游生成并经过审核。任务树的根节点是无损继承
节点：宿主绑定根节点的 `task_key` 和 `source_primary_task_id`，再以已审核主要任务覆盖
根节点的 `task`、`completed_when`、`inclusions` 和 `exclusions`，并对这些字段逐字校验
一致。任务树阶段只生成根节点的 `split_basis`、`children`，以及所有子节点的任务语义
字段和 `children`。根任务键是宿主冻结身份，不得由模型自由改写为 `root` 或其他局部
占位名。

主要任务的 `reason`、`support_runs`、`merge_type` 和 `granularity_reason` 属于归并来源
与审核元数据，通过 `source_primary_task_id` 查找，不复制到任务树根节点。任务树不保存
名为 `source_primary_task_reason` 的派生字段，避免同一理由出现第二份可漂移副本。

任务树不是最终知识框架，也不要求每个任务都有子节点。拆分停止条件不是固定层级，而是每个叶节点已经对应一项可独立完成并检查结果的实际工作，且不会把两个需要分别完成的工作混在同一范围内。

中间任务可以只是汇总任务，只要其完成条件能够说明子任务如何共同完成整体目标。若父任务仍包含未落到子任务中的实际工作，包括一致性检查、综合判断、冲突修复或最终取舍，必须把它拆成显式子任务。完整任务树共同作为角色知识框架的任务覆盖审查锚点；父任务和叶任务分别依据自身任务合同检查知识覆盖，知识主题本身不从任务步骤复制。

### 3.4 角色知识框架与知识节点

角色知识框架是一棵从岗位角色履职视角组织的领域知识树。第一阶段只生成一级知识范围；一级目录冻结后，再对每个分支独立展开。每个节点包含：

| 字段 | 说明 |
| --- | --- |
| `node_id` | 宿主分配的稳定标识；模型不自行生成最终路径编号 |
| `title` | 脱离父路径后仍可独立识别的知识范围名称 |
| `description` | 直接说明该范围研究什么、包含哪些知识内容、与相邻范围的主要边界；不写学习动作或工作任务 |
| `exclusions` | 容易与当前节点混淆但不属于当前节点的相邻知识；没有明确边界时可以为空数组 |
| `children` | 当前知识范围内的下层知识主题 |

每个节点必须表示领域知识范围，不能表示工作任务、实施步骤、项目安排、交付物、产品方案或代码实现。节点可以较宽，但必须具有统一知识身份；当范围内仍包含两个或更多可以分别命名、分别检索、分别判断证据覆盖的知识身份时，必须继续生成子节点。

叶节点不以固定深度或“绝对原子”定义。一个范围如果只能作为同一知识身份的定义、范围、作用、边界、条件或代价出现，应留在该节点的 `description` 中；如果能脱离父路径独立命名并作为独立检索目标，就应形成叶节点。系统不保留独立 `aspects` 层：叶节点是原文证据挂接和独立覆盖判断的单位；任何非叶节点的覆盖，均由该节点所属的全部后代叶节点汇总得到。

### 3.5 一级目录与逐分支展开

一级目录定义整套角色知识框架的顶层知识疆域，但不在同一次调用中展开完整树。生成流程分为两个阶段：

1. 一级目录阶段只生成该角色有效履职所需的一级知识范围，不生成任何下级节点；
2. 展开阶段对每个已经冻结的一级节点分别调用一次模型，只生成该节点内部的子树，不允许改写一级节点或侵入相邻一级分支。

一级节点可以较宽，但必须具有统一知识身份。系统不预设一级节点数量，也不要求所有分支具有相同深度或相同子节点数量。先冻结一级目录再展开，是为了缩小单次生成任务，避免模型在一次调用中同时承担全局覆盖、多级组织和叶节点粒度判断。

### 3.6 候选生成、归并与任务覆盖闭环

单次一级目录生成只提供候选，不直接成为正式框架。系统先执行少量独立生成，再按知识身份归并；归并必须支持同义合并、上下位收束和宽节点拆分，并为每个输入候选记录明确去向，不能静默丢弃低频有效范围。

归并后的框架使用角色已审核的主要任务执行覆盖审查。覆盖审查只判断每项任务完成及其关键判断所需的知识范围是否已经由现有节点明确承载，不把任务名称改成知识名称，也不要求任务与节点一一对应。存在 `partial` 或 `missing` 时，由 LLM 根据完整框架、任务和结构化审查结果修订一级分类；宿主只做确定性校验和应用。修订后重新执行完整任务覆盖审查，直到所有任务通过或触发显式迭代上限。

### 3.7 知识主题树与冻结版本

一棵知识主题树表示一个明确角色、主要任务版本和知识框架修订版下的组织结果。树内父子边表示知识范围包含关系，不表示任务先后、学习顺序或组织流程；节点无环，叶节点默认不直接挂接原文证据以外的派生结论。

冻结版本至少绑定领域名称、角色名称、主要任务版本、任务树版本、一级目录生成提示词、归并提示词、覆盖审查提示词、修复提示词、展开提示词、模型与 thinking 配置、原始输出和审查记录。任何一级节点、子树或叶节点目录的变化都形成新版本，不静默覆盖旧版本。

### 3.8 叶节点目录

查询前，宿主从冻结角色知识框架中生成叶节点目录。每个叶节点至少包含：

```text
leaf_id
完整路径
标题
description
exclusions
```

查询召回只使用 `leaf_id`、完整路径和标题；`description`、`exclusions` 属于知识框架内部语义，不进入叶节点召回输入，以免模型依赖未在查询时提供的长文本补洞。父节点和中间节点提供路径语境，不是召回候选或证据挂接单位。

### 3.9 查询覆盖检查表

查询覆盖检查表是某一次求全类查询的检查记录。它记录本次选择了哪些叶节点、每个叶节点属于哪个一级分支、该分支为何有或没有选择、哪些叶节点获得原文证据、哪些方面仍可能存在缺口，以及是否执行了主题外兜底检索。

查询覆盖检查表不是知识库的全局覆盖率，也不是给用户看的答案。主 Agent 在查询时临时形成的覆盖方面只作为检索参考和缺口诊断，不能证明当前知识库语义上已经完整。

## 4 角色知识框架生成流程

### 4.1 角色知识框架生成流程总览

本章描述从领域和角色到暂定冻结角色知识框架的生成链。它回答哪些阶段必须按顺序执行、每个阶段留下什么产物，以及生成阶段何时允许读取当前语料。

```text
领域名称
  ↓
多轮独立生成使用角色候选及区分性任务
  ↓
归并角色候选并由用户选择、拆分或调整
  ↓
为每个确认角色多轮生成主要任务候选
  ↓
按职责结果归并主要任务候选并由用户审核
  ↓
生成并审核角色任务树
  ↓
为当前角色多轮独立生成一级知识框架候选
  ↓
按知识身份归并一级知识框架
  ↓
使用完整角色任务树执行覆盖审查
  ↓
LLM 根据结构化缺口修复一级框架并复审
  ↓
冻结一级目录
  ↓
逐一级分支独立展开为知识主题树
  ↓
结构校验、知识质量审查和冻结记录
  ↓
可供证据挂接的角色知识框架与叶节点目录
```

主路径的生成单位是“角色当前的一级知识框架”。任务树提供履职覆盖审查，不复制成知识路径。一级目录先冻结再展开，避免单次调用同时承担全局覆盖、多级组织和叶节点粒度判断。知识主题只有通过结构校验、任务覆盖闭环和相应质量审查后，才能形成可供证据挂接的冻结版本。

模型提示词只描述模型实际可见的输入和需要执行的判断。知识库、测试问题、金标准、外部资料等数据是否进入上下文，由宿主的输入装配、版本绑定和校验负责；不得把这些宿主边界写成模型无法执行的“不要读取”指令。

#### 4.1.1 当前探索性回放概览

截至 2026-11-23，已在固定样本 `AI Agent`／`系统架构师` 上完成一轮贯穿全链路的探索性回放。模型主要为 `deepseek-flash`、温度为 `0`；各阶段实际 thinking、输出上限和提示词版本以对应实验记录为准。关键数据如下：

| 阶段 | 回放规模 | 代表性结果 | 说明 |
| --- | --- | --- | --- |
| 角色候选生成与归并 | 3 次独立生成、1 次归并 | 分别生成 28／30／21 个候选，共 79 个；归并为 40 组 | 79 个来源均恰好出现一次；架构师组已人工审核 |
| 主要任务生成与归并 | 3 次独立生成、1 次归并 | 分别生成 10／12／11 项，共 33 个来源；归并为 13 项主要任务 | 33 个来源均有明确去向；语义审查仍需结合角色边界问题审核 |
| 单根任务拆成任务树 | 同一根任务 3 次独立生成 | 节点数 30／24／26，叶节点数 21／16／18 | 三次根节点字段均无损继承；差异主要集中在停止拆分的位置 |
| 一级知识框架候选生成 | 8 次独立生成 | 每次 13～18 个一级节点，平均 16.5 个；合计 132 个候选 | 8/8 结构合法；14 个核心知识主干每次都有等价入口 |
| 一级知识框架归并 | 132 个候选归并一次 | 形成 22 个一级节点 | 95 个等价、5 个下位包含、32 个拆分；0 个来源丢失 |
| 任务覆盖审查与修复 | 13 项任务、3 轮审查 | `covered` 依次为 9、7、13 | 最终新增 K23、K24，一级节点由 22 个变为 24 个 |
| 逐一级分支展开 | 24 个一级分支 | 23 个批量调用全部首次成功；合并 K08 首轮结果后共 847 个节点、620 个叶节点 | 最大深度 3；0 个重试、0 个规范化标题完全重复、0 个单子节点容器 |

这组数据用于建立直观规模感，不是产品常数。角色、主要任务和任务树部分来自当前字段契约的直接回放；一级框架生成提示词与 §4.6.4 的 SHA-256 一致。部分归并、覆盖和展开数据来自随后又做过文案收敛的版本，因此可以证明方法可运行、调用规模可处理，不能替代当前版本在新领域的逐字等价回放。完整记录见[角色知识框架两阶段分层生成实验](2026-11-23-角色知识框架两阶段分层生成.md)。

冻结前的主要阶段产物如下：

| 产物 | 作用 | 是否可使用当前语料或外部资料 |
| --- | --- | --- |
| 角色候选集及归并结果 | 发现和合并使用角色，携带区分性任务和区别理由 | 否 |
| 确认角色快照 | 用户确认角色名称、区分性任务和已有知识后的版本 | 否 |
| 主要任务候选集 | 为确认角色多轮独立生成的职责结果候选，保留每轮来源和未决边界 | 否 |
| 主要任务归并结果 | 按职责结果合并、拆分和标记待审单例的规范化候选 | 否 |
| 确认主要任务集 | 用户审核后的自包含职责结果，包含任务、完成条件、包含范围和排除范围 | 否 |
| 角色任务树 | 从主要任务展开可执行叶任务、汇总层级和任务边界 | 否 |
| 一级知识框架候选集 | 多份独立生成的一级知识范围，每个候选保留运行来源 | 否 |
| 归并后一级目录 | 按知识身份归并、并记录全部候选来源去向的一级知识框架 | 否 |
| 覆盖审查与修复记录 | 任务覆盖判断、缺口、完整修订版本、复审结果和停止原因 | 否 |
| 展开后的角色知识框架 | 每个一级分支经独立调用展开并完成结构校验的知识树 | 否，进入证据挂接后绑定快照 |
| 叶节点目录 | 从冻结框架提取的路由候选集合，供查询期逐分支召回 | 否，查询时绑定当前框架版本 |

模型返回的局部键只用于当前响应。跨运行合并前由宿主用运行 ID 加命名空间；用户确认后再分配稳定 ID。所有版本都必须保留实际模型、thinking 状态、提示词版本、token、原始输出和校验结果。

### 4.2 输入边界

角色候选生成使用领域卡中的领域名称和选填领域说明，不读取当前知识库内容。主要任务、任务树和角色知识框架生成使用已经审核的上游产物，不读取当前知识库的文档标题、章节标题、正文、block 或已有知识主题，也不引入外部综述、工程手册、岗位目录或其他参考资料。

这项边界用于防止生成结果被现有语料覆盖范围限制，并把偶然结构固化为领域结构。知识库语料只在角色知识框架冻结后进入证据挂接。最终验收问题、金标准答案和其他测试样本不得进入角色、任务、任务树、知识框架生成或覆盖修复。

具体输入如下：

| 阶段 | 允许输入 |
| --- | --- |
| 角色候选生成 | 领域名称、选填领域说明 |
| 主要任务生成 | 确认角色、角色名称、区分性任务、可选已有知识 |
| 任务树生成 | 角色名称、已审核主要任务、可选已有知识 |
| 一级知识框架生成 | 规范领域名称、角色名称 |
| 一级框架归并 | 同一领域、同一角色的全部候选一级框架及来源标识 |
| 任务覆盖审查 | 领域名称、角色名称、当前一级知识框架、角色任务树及版本标识 |
| 框架修复 | 领域名称、角色名称、主要任务、当前框架、结构化覆盖审查结果 |
| 一级分支展开 | 领域名称、角色名称、框架总范围、全部一级节点紧凑目录、当前目标一级节点 |

初始知识框架生成、归并和任务覆盖审查都不接收领域卡中的选填领域说明。领域说明只用于展示、人工确认或规范名称消歧。语言模型无法可靠地只把它用于消歧，它会同时携带具体对象、组成关系和隐含边界，从而显著改变知识框架的广度与展开形状。

查询期发现的知识框架优化反馈不能直接进入当前角色、任务树或知识框架版本。经审核需要修改上游结构时，必须创建新的版本化离线修订，记录来源反馈标识，并从受影响的最上游层重新生成、重新审核其全部下游产物；旧版本及其下游追溯关系保持不变。

### 4.3 从领域生成使用角色候选

系统只依据领域名称和领域说明，多轮独立生成候选角色卡。每张卡给出角色名称、2～4 项区分性任务和区别理由，用这些信息识别角色、解释其与邻近角色的差别，并支持后续归并。候选阶段不要求覆盖该角色的全部职责，不展开步骤、子任务或知识点，也不输出 `completed_when`。完整主要任务必须等用户确认角色后单独生成。

候选角色直接使用用户能够识别和选择的职业、岗位或明确职能名称。首次生成不预设固定职业清单，也不把领域说明中显式提到的对象或活动当作候选全集。

同一领域至少进行多次独立生成，再按知识使用职责是否实质相同合并候选：

- 名称不同，但区分性任务所表达的角色职责实质相同，可以合并；
- 名称相同，但区分性任务表达出明显不同的知识使用职责，应拆分；
- 只有职位名称相近、上下游协作或共同主题，不足以合并。

为什么把完整性要求后移：在 AI Agent 领域让一次调用同时发现几十个角色并穷尽各角色职责时，模型会退化为模板化输出。同一提示词回放中，34 个角色全部恰好生成 5 项任务，另一轮 21 个角色全部恰好生成 4 项任务。阶段拆分实验随后使用已发现的架构师和开发岗位候选，只向确认角色生成器提供两项代表性任务，模拟候选阶段的区分性任务输入；架构师三轮分别生成 9、9、8 项主要任务，开发岗位三轮均为 9 项。两者都稳定补出了职业原型的通用职责和 Agent 领域新增职责，没有再出现整轮所有角色任务数一致的同构现象。该对照验证了“确认后再生成完整任务”的阶段拆分，但尚未直接回放本版 §4.3.1 的区分性任务输出契约，且只覆盖同一领域的两个角色，不能据此证明跨领域稳定性。

当前基线要求角色候选生成和归并开启模型推理。该结论来自 AI Agent 单领域实验：`deepseek-flash`、`temperature=0` 下，关闭 thinking 的一次合法生成得到 12 个角色卡候选；开启 thinking 的三次合法生成分别得到 26、30、38 个候选，并出现最终用户、客服运营、采购、监管、培训等不同方向。归并阶段关闭 thinking 时连续出现来源候选静默遗漏，开启 thinking 的五轮回放均覆盖全部来源候选。该证据仍只覆盖单模型、单领域，必须按 §9 的 Gate A 做跨领域对照，不能表述为普遍规律。

当前 §4.3.1 已审核。按该版本回放 3 次，3/3 结构合法，分别生成 28、30、21 个候选角色；79 个来源候选均包含 2～4 项区分性任务，且没有输出完整主要任务或完成条件。三轮候选交给当前 §4.3.2 做 1 次 thinking 归并后，79 个来源全部且仅分配一次，形成 40 组，没有新增、遗漏、重复或未知来源。该结果证明当前字段契约可以贯通到归并器；§4.3.2 提示词已确认，架构师组已人工审核通过，但一次归并仍不足以证明全部归并边界、跨领域场景稳定。

角色候选首版继续采用“多轮独立生成，再归并”的方式。新实现只依据本节输入边界、结构化输出和审核契约，不把任何既有实验代码结构视为实现基线。

### 4.5 确认角色后生成主要任务并拆成任务树

确认角色后的处理分成三个明确阶段：

1. 主要任务候选生成：以领域名称、领域说明、角色名称、区分性任务和可选已有知识为输入，多轮独立生成包含任务、完成条件、包含范围和排除范围的候选主要任务，并允许模型提出无法确定的组织职责边界；
2. 主要任务归并：把多轮任务候选视为同等来源，按职责结果归并为规范化、自包含的主要任务集；宿主另行完整保留各轮的未决覆盖问题，两者一起交用户审核；
3. 任务树生成：只使用用户审核通过的完整主要任务，把每个主要任务作为独立根任务生成一棵子树；不同根任务可以并发调度，但不得合并进同一次模型调用。区分性任务不再作为任务树输入，也不能限制主要任务数量。

每个确认角色独立生成任务树，角色内的每个已审核主要任务也独立调用。单次调用只接收一个根任务及其继承上下文，避免多个根任务共同消耗输出预算或相互稀释语义注意力。

节点单位是可独立完成并检查结果的实际工作，不是文档、Schema、矩阵或最终交付物。拆分依据如下：

- 能形成两个可分别完成、分别检查结果，并且完成其中一个不能推出另一个也完成的工作时，必须拆分；
- 只有当节点属于一项可独立完成的实际工作，或必须作为一个分类、比较、目标或权衡集合整体完成时，才保留为叶节点；
- 共享文档、Schema、矩阵、证据或最终交付物，不构成停止拆分的理由；
- 中间节点可以是汇总任务或组织任务，不要求在子任务之外承担独立实际工作；允许根任务直接连接多个叶节点；
- 若一致性检查、综合判断、冲突修复或最终取舍需要实际执行，必须建立显式子任务，不得只藏在父任务的 `completed_when` 或 `inclusions` 中；
- 固定深度、固定分支数、树形美观都不是任务树质量目标；
- 知识主题不从任务步骤直接生成；完整任务树只用于检查角色知识框架的履职覆盖。

重复生成出现不同的合法拆分边界时，不选“最佳一次”，也不要求人工选择。正式流程每次根任务调用只接受结构合法、根节点继承字段与已审核主要任务逐字一致且语义覆盖成立的快照，并把该次实际输出作为版本化任务树保存；后续重新生成形成新的候选版本。

任务树审查重点：

| 审核项 | 判断问题 |
| --- | --- |
| 角色一致性 | 任务是否确实服务于该角色的知识使用职责 |
| 可完成性 | 是否说明了什么结果出现时该工作实际已经完成 |
| 汇总覆盖 | 汇总任务的完成条件是否能由子任务共同满足，是否仍有实际工作只存在于父任务描述中 |

### 4.6 角色知识框架的候选生成、归并与冻结

#### 4.6.1 目标与输入边界

角色知识框架回答的是：在指定领域中，从某个岗位角色的履职视角出发，应当组织哪些知识范围，以及这些范围如何逐层展开。知识框架首先独立于当前角色任务形成，再由任务树检查是否漏项，避免工作任务和交付步骤在首轮就压过知识结构。

一级目录生成、归并和任务覆盖审查只使用规范领域名称与角色名称。领域名称界定知识疆域，角色名称界定履职视角。领域卡中的选填领域说明只用于展示、人工确认或规范名称消歧，不进入这些生成与审查调用。

不提供领域说明是本阶段的刻意约束，不是遗漏。领域说明通常是对领域范围的概括，带有较强的知识先验；实验对照显示，它会把生成结果进一步拉向说明中已经点名的主题，使未被点名的知识疆域被压缩、合并或不再展开，反而削弱本阶段发现尽可能广的知识范围的能力。知识广度改由多轮独立生成、按知识身份归并和后续任务覆盖修复共同保障，而不是由一份预写摘要限定。

生成阶段不读取当前知识库、测试问题、金标准答案或外部资料。任务树由上游独立生成，并在 §4.7 作为覆盖审查锚点使用。

#### 4.6.2 一级候选结构

一级知识框架阶段只输出一级知识范围，不输出任何下级节点：

```json

  "domain": "领域名称",
  "role": "角色名称",
  "framework_scope": "该角色在本领域中有效履职所需掌握的知识范围概述",
  "first_level_nodes": [
    {
      "title": "一级知识范围标题",
      "description": "该范围是什么、包含哪些知识内容，以及这些内容为何构成同一知识范围",
      "exclusions": []
    }

```

一级节点可以较宽，但必须具有统一知识身份。每个一级节点必须：

1. 是领域知识范围，不是工作任务、实施步骤、项目安排、交付文档或产品方案；
2. 标题在脱离角色和父路径后仍能识别所指知识；
3. `description` 明确知识内容和范围，不以“基础知识”“相关内容”代替；
4. `exclusions` 只记录真正容易混淆的相邻知识，没有边界时允许为空数组。

候选阶段不读当前语料，也不使用最终测试问题验证覆盖面。候选出现与否只作为知识发现证据，不作为领域完备性证明。

#### 4.6.3 多轮生成、归并与候选去向

单次一级目录生成只提供候选。当前实验基线独立生成多次后归并；运行次数不是产品常量，停止增加次数应以主干是否稳定、归并复杂度、覆盖审查收益和成本共同判断。

归并必须同时支持：

- 同一知识身份的合并；
- 上位范围对下位范围的收束；
- 一个宽节点拆成多个知识身份；
- 低频有效范围的保留；
- `needs_review` 显式暴露不确定项。

两个候选节点属于同一知识身份，必须同时满足“核心研究对象基本一致、核心问题基本一致、主要知识边界基本一致”。仅共享领域、岗位用途、上位类别、应用场景或标题措辞不足以合并。每个输入候选节点必须在来源账本中有一条明确去向：`equivalent`、`contained`、`split` 或 `needs_review`，不得静默丢弃。

归并输出必须通过结构校验：候选去向完整，所有 `source_node_id` 只出现一次，所有 `target_node_id` 存在，每个归并节点至少被一个候选引用，节点 ID 唯一，字段与类型合法。无法可靠归并的项进入显式审核，不由宿主自行猜测。

#### 4.6.4 一级知识框架生成提示词

```text
你是一位知识框架设计专家。

给定一个领域和一个岗位角色，请识别该岗位角色在该领域中有效履行职责所
必须掌握的知识范围，并为这些知识生成一级目录。

【任务】
识别该岗位角色在该领域中有效履行职责所必须掌握的知识，并且只生成一级
目录。一级目录用于界定整套框架的大类知识范围，不是最终叶节点，也不在
这一步继续展开。

【一级节点要求】
1. 每个一级节点必须是知识范围，不能是工作任务、实施步骤、项目安排、
   交付文档或产品方案。判断一项知识是否应纳入，依据是它是否是该岗位在
   该领域中有效履行职责所必须掌握的知识，不要求它属于狭义的领域核心知识。
2. 标题应清楚、稳定，脱离父路径后仍能独立识别所指的领域知识范围。
3. description 用一到三句话说明该范围是什么、主要包含哪些知识内容，以及
   这些内容为什么构成同一个知识范围。不要只复述标题，也不要用空泛的
   “基础知识”“相关内容”等措辞代替知识范围。
4. exclusions 只记录确实容易与该一级范围混淆、但不属于该范围的相邻知识；
   没有这种相邻知识时返回空数组。
5. 各一级节点应共同覆盖该岗位角色有效履行职责所必需的主要知识范围，
   不能只列出少量示例，也不能只覆盖该领域内部的技术构成。
6. 一级节点可以是有内部结构的知识范围，但必须具有统一的知识身份；不能把
   互不相干的知识仅因为同属该领域就合并成一个节点。
7. 各一级节点之间不能是同一知识身份的重复表述、同义改名或简单上下位重复。
8. 不预设一级节点数量。节点数量由该角色需要掌握的知识范围决定。

【输出要求】
只输出符合下方输出契约的 JSON，不输出 Markdown、解释或额外文字。
domain 和 role 必须与输入逐字一致。first_level_nodes 中每个对象只有
title、description 和 exclusions 三个字段，不得输出 children 或其他层级。

【输出契约】
{
  "domain": "领域名称",
  "role": "角色名称",
  "framework_scope": "该岗位角色在该领域中有效履行职责所必须掌握的知识范围概述",
  "first_level_nodes": [
    {
      "title": "一级知识范围标题",
      "description": "该知识范围是什么、主要包含哪些知识内容，以及这些内容为什么构成同一个知识范围",
      "exclusions": []
    }
  ]
}
```

用户消息只提供：

```text
领域名称：{{domain_name}}
角色名称：{{role_name}}
```

不提供领域说明、任务树、知识库内容、测试问题或金标准答案。

#### 4.6.5 一级知识框架归并提示词

```text
你是一位知识框架归并专家。

给定同一个领域、同一个岗位角色下的多份候选知识框架，请将全部候选的一级
知识范围归并为一套规范化框架。候选来自多次独立生成，各份结果地位相同，
出现次数不表示正确性，也不得作为删除低频知识的依据。

【输入】
输入包含：
- domain_name：领域名称；
- role_name：岗位角色名称；
- candidate_frameworks：多份候选框架，每份包含 run_id、
  framework_scope 和 first_level_nodes；
- first_level_nodes 中每个候选节点包含 source_node_id、title、
  description 和 exclusions。

【任务】
根据各候选节点所描述的知识身份，生成一套不重复、同层级、可供后续继续
展开的一级知识范围。

归并后的每个一级节点必须是知识范围，不能是工作任务、实施步骤、项目安排、
交付物或产品方案。一级节点应具有相对完整的知识身份，不得退化为孤立事实或
过窄的知识片段。

【判断知识身份的方法】
1. 两个候选节点属于同一知识身份，必须同时满足：核心研究对象基本一致、
   试图回答的核心问题基本一致、主要知识边界基本一致。只满足其中一项或两项
   时属于部分重叠，不构成同一知识身份。
2. 标题同义、近义、缩写展开、中英文译法不同，或仅更换了组织措辞的，属于
   同一知识身份。
3. 两个节点只因为共享领域名称、岗位用途、上位类别、横向主题或同一应用场景，
   不构成同一知识身份。上位标签相同不是知识身份相同的证据。
4. 上位范围与下位范围不是重复。若下位范围属于某个一级范围，应将其知识身份
   保留在该一级范围的 description 中，不把上下位节点并列成同级节点。若下位
   范围的核心问题不同，并且需要成为独立的高层检索入口，则保留为独立节点。
5. 同一个候选节点包含多个互不从属、需要分别检索的知识身份时，应拆分到多个
   归并节点，不能为了少生成节点而强制合并。
6. description 中列举多个具体内容，不代表必须拆分。只有这些内容分别形成
   独立知识身份，并且需要成为不同的高层检索入口时，才进行拆分。

【归并要求】
1. 候选框架中的全部知识身份都必须有明确去向：进入某个归并节点、作为该节点
   的组成部分被明确保留，或进入 review_items。不得静默丢弃。
2. 低频出现的有效知识同样需要保留。一个范围只出现一次，不是删除它的理由。
3. 归并后的 description 必须综合各候选的有效信息，不能只采用出现次数最多的
   表述。被合并的主要知识身份及关键内容应在 description 中继续可见，避免后续
   展开时丢失。
4. exclusions 只记录真正容易与当前一级范围混淆、但不属于该范围的知识边界。
   合并相互冲突的 exclusions 时，按知识身份和职责范围判断，不使用简单多数投票。
5. 一级节点数量不设目标。数量由归并后的知识范围决定，不得为了凑数拆分，也
   不得为了控制数量而合并不同知识身份。
6. framework_scope 应概括归并后框架覆盖的完整知识范围，不能只复述其中少数
   一级节点。

【来源映射】
为每个输入候选节点在 merge_ledger 中记录且仅记录一条去向：
- equivalent：候选节点与归并节点属于同一知识身份；
- contained：候选节点是某个归并节点的下位知识范围；
- split：候选节点包含多个知识身份，分别进入多个归并节点；
- needs_review：无法可靠判断其归属，不得通过丢弃解决。

target_node_ids 使用归并节点的 node_id。split 可对应多个 node_id；
needs_review 没有可靠目标时返回空数组。
reason 用一句话说明判定依据。

【输出要求】
只输出符合下方输出契约的 JSON，不输出 Markdown、解释或额外文字。
domain 和 role 必须与输入逐字一致。
first_level_nodes 中每个对象只包含 node_id、title、description 和 exclusions。
merge_ledger 必须覆盖全部输入候选节点。
每个 first_level_nodes 的 node_id 必须至少被 merge_ledger 引用一次。
所有 node_id 在各自集合内必须唯一。

【输出契约】
{
  "domain": "领域名称",
  "role": "岗位角色名称",
  "framework_scope": "归并后框架覆盖的知识范围概述",
  "first_level_nodes": [
    {
      "node_id": "K01",
      "title": "一级知识范围标题",
      "description": "该知识范围是什么、包含哪些主要知识内容，以及这些内容为什么构成同一知识身份",
      "exclusions": []
    }
  ],
  "merge_ledger": [
    {
      "source_node_id": "输入中的原值",
      "relation": "equivalent",
      "target_node_ids": ["K01"],
      "reason": "该候选与目标节点研究同一组对象和核心问题。"
    }
  ],
  "review_items": [
    {
      "source_node_ids": ["输入中的原值"],
      "reason": "无法可靠判断归属的具体原因。"
    }
  ]
}
```

#### 4.6.6 归并后的结构校验与知识质量审查

宿主先执行确定性结构校验：候选来源账本覆盖全部输入，节点 ID 唯一，字段与类型合法，所有候选去向可解析，所有目标节点至少被一个候选引用。结构失败不得通过删除非法项或补写节点掩盖。

结构合格后，独立执行知识质量审查，至少检查：

- 节点是否均为领域知识范围，而不是任务动作、交付物或组织流程；
- 同级节点是否存在同义重复或简单上下位重复；
- 宽节点是否混入多个互不从属、需要分别检索的知识身份；
- `description` 是否说明知识内容和边界，而不是空泛分类名；
- `exclusions` 是否只包含真正相邻而不属于当前范围的知识；
- `review_items` 是否确实无法可靠归并，而不是把疑难项推给人工。

知识质量审查不负责判断框架是否覆盖角色职责。履职覆盖统一在 §4.7 使用已审核任务树执行。

#### 4.6.7 实验回放与阶段结论

2026-11-23 使用 §4.6.4 当前提示词（SHA-256 `9ef4d2cc0b1fc9b4e7e8837cd5c0dda53b8cdc28d409272b035f1c3ed46e2ec6`）对同一领域和角色独立生成 8 次。单次输出 13～18 个一级节点，平均 16.5 个，合计 132 个候选；输出 token 平均 6,173.75，平均耗时约 33.71 秒。8 次均结构合法，没有截断、重复标题、`children` 或非法字段。

这组样本给出了两个相反但同样重要的信号：

- 14 个核心知识主干在 8 次中均形成了直接或等价入口，包括 Agent 概念与架构范式、模型与推理服务、规划决策、工具调用、记忆与上下文、RAG、多 Agent、运行时与沙箱、编排调度、评估、可观测性、安全治理、人机交互、应用与领域建模。核心面并不是完全随机生成的。
- 外围范围的组织仍不稳定。数据架构只有 4 次明确单列，协议版本与企业集成只有部分样本明确，LLM Judge 偏差与校准、Agent 前沿范式在 8 次中没有稳定入口。只增加重复生成次数不能保证低频知识自动出现，也不能从 8 份结果中事后挑一份作为“最完整”结果。

132 个候选随后按知识身份归并。历史身份契约回放形成 22 个一级节点，来源账本为 95 个等价归并、5 个下位包含、32 个拆分，0 个来源丢失，输出 38,882 tokens，耗时 166.78 秒。首版归并曾把安全与隐私／合规误合成一个节点；收紧知识身份判断后稳定拆开，但又出现 K01、K04、K08、K19 四个需要继续审查的宽合并。这说明归并必须同时保留来源账本和语义质量审查，结构合法、来源完整并不等于知识边界已经正确。

阶段结论是：单次生成的 13～18 个一级入口足以形成候选主干，但不能直接冻结；多轮生成负责发现，归并负责去重和恢复边界，任务覆盖修复负责履职缺口。22 个和 24 个都是固定样本上的回放结果，不设为目标节点数。

### 4.7 基于任务树执行覆盖审查与 LLM 修复

任务树用于检查归并后的一级知识框架是否遗漏了角色完成实际工作所必需的领域知识。覆盖审查只输出逐任务判断、匹配路径和结构化缺口，不直接把任务名称改成知识节点，也不由审计器、实验助手或人工逐分支编写补丁。

审查发现 `partial` 或 `missing` 后，由独立 LLM 修复器读取完整框架、角色任务和结构化审查结果，输出一份完整修订框架。宿主只执行确定性校验和应用，随后重新审查全部任务。这个“审查 → 完整修订 → 全量复审”循环是发现和补齐知识缺口的唯一正式路径。

#### 4.7.1 任务覆盖审计提示词

```text
你是一个角色知识框架的任务覆盖审计器。

【输入】
1. domain：领域名称。
2. role：当前知识主题框架所服务的角色。
3. framework_version：待审计角色知识框架的版本标识。
4. knowledge_framework：当前一级知识框架。每个节点包含 node_path、title、description、exclusions 和 children；任务覆盖审查发生在逐分支展开之前，children 可以为空数组。
5. task_tree：当前角色的任务树。每个任务节点包含 task_key、task_path、task、completed_when、inclusions、exclusions 和 children。

【任务】
逐个审计 task_tree 中的任务节点，判断 knowledge_framework 是否提供了完成该任务所需的领域知识组织路径。

本审计只判断角色知识框架是否提供了完成任务的领域知识，不判断当前知识库中是否已经有足够原文证据，也不判断任务目前是否已经执行。

【判断口径】
1. 一个任务可以由一个知识主题路径直接覆盖，也可以由多个知识主题路径共同覆盖。不要要求存在与任务同名的节点。
2. covered：knowledge_framework 中存在一个或多个清楚可路由的知识主题路径，合起来覆盖了任务完成所需的核心知识对象、边界和关键类别。具体项目事实可以留待执行时补充，不因此判为 partial。
3. partial：存在部分相关知识主题，但缺少会实质影响任务完成的关键知识范围、知识类别、机制、条件或边界。
4. missing：knowledge_framework 中没有清楚可路由的知识主题路径能够支撑该任务所需的核心领域知识。
5. retrieval 衡量主 Agent 只依据节点标题、路径、description 和 exclusions 找到相关知识的难度：easy、moderate、hard。
6. matched_paths 必须逐字使用 knowledge_framework 中已有的完整节点路径。只能返回实际支撑任务的路径，不得为了显示覆盖而选择只在措辞上相似的节点。
7. 如果任务需要组合多个知识主题才能完成，matched_paths 必须给出完整组合，并在 reason 中说明每个路径分别提供哪部分知识。
8. 父任务与子任务分别依据自身的 task、completed_when、inclusions 和 exclusions 判断。不能因为没有逐一检查父任务，就直接用子任务覆盖结果替代父任务结论；也不能因为部分子任务 covered，就把父任务自动判为 covered。
9. gap 只在 partial 或 missing 时填写，必须描述缺失的领域知识范围。不得把审计 gap 改写成建议新增的节点、任务步骤、项目事实、待办事项或框架更新方案。
10. gap_type 取值：none、knowledge_missing、granularity_insufficient、routing_ambiguous、task_contract_error。task_contract_error 表示任务本身不是可由领域知识支撑的合理任务，不能把它伪装成知识缺口。
11. 只依据输入的领域、角色、知识框架和任务树判断，不假设输入中没有给出的知识库内容、项目现状、用户状态或外部资料。
12. 只输出符合输出契约的 JSON，不输出 Markdown、代码块或额外说明。

【输出 JSON】
{
  "framework_version": "必须逐字复制输入中的 framework_version",
  "framework_assessment": "对当前角色知识框架任务支撑情况的整体判断",
  "tasks": [
    {
      "task_key": "输入任务键",
      "task_path": ["从根任务到当前任务的完整路径"],
      "status": "covered | partial | missing",
      "retrieval": "easy | moderate | hard",
      "matched_paths": ["逐字引用 knowledge_framework 中的完整节点路径"],
      "reason": "这些路径分别提供了哪些知识，或为什么不足以支持任务",
      "gap_type": "none | knowledge_missing | granularity_insufficient | routing_ambiguous | task_contract_error",
      "gap": "缺失的领域知识范围；covered 时为空字符串"
    }
  ],
  "summary": {
    "covered": 0,
    "partial": 0,
    "missing": 0
  }
}
```


#### 4.7.3 修复闭环、校验与停止语义

每次修复必须返回完整框架，不得只返回局部节点补丁。宿主至少校验：

- `domain`、`role` 与输入一致；
- 原有 `node_id` 全部存在且没有重复；
- 新增 `node_id` 格式合法且全局唯一；
- 每个节点只有 `node_id`、`title`、`description`、`exclusions` 四个字段；
- 标题和描述非空，`exclusions` 为字符串数组；
- 修订后没有删除原节点；
- 相对上一版本的新增、修改和未变节点均有审计记录。

修订后必须重新执行完整任务覆盖审查，不能只复审本轮报告的缺口。闭环结束状态只能是：

```text
completed
no_framework_change
no_coverage_progress
iteration_limit
call_failed
```

只有全部任务为 `covered` 时才允许 `completed`。达到最大修复轮次、修订没有变化或覆盖没有进展时，必须显式失败并保留全部输入、输出、审查结果、提示词版本和 token 记录，不能把未完成状态记为成功。

#### 4.7.4 实验回放与阶段结论

2026-11-23 先在 13 项已审核一级任务上做了两次同输入覆盖审查。两次均没有 `missing`，但第一次为 8 项 `covered`／5 项 `partial`／5 个缺口，第二次为 9 项 `covered`／4 项 `partial`／3 个缺口。“架构需求追溯与质量属性验收基线”两次都被识别为缺口；其余边界存在裁量差异。单次审查因此只能作为修复输入，不能直接当作最终质量结论。

首次自动闭环从第二次审查结果开始，共执行 3 轮审查：

| 轮次 | 覆盖结果 | 审查暴露的主要缺口 | 修订结果 |
| --- | --- | --- | --- |
| 1 | 9 `covered`／4 `partial`／0 `missing` | 架构需求追溯；失败分类、检测信号与可恢复性判定；跨团队设计交接与例外治理 | 修改 K13、K19、K20 的 description 和边界 |
| 2 | 7 `covered`／6 `partial`／0 `missing` | 审计事件与追踪架构；策略执行点与工具调用网关架构 | 新增 K23、K24，并澄清 10 个既有节点的边界和交互 |
| 3 | 13 `covered`／0 `partial`／0 `missing` | 无 | 达到 `completed`，停止修订 |

闭环总耗时 280.865 秒；除复用的首轮审查外，新增调用合计输入 44,795 tokens、输出 54,083 tokens。最终一级框架从 22 个节点变为 24 个，13 项任务共组合引用 23 个一级节点，没有形成任务到节点的一对一映射。

最值得保留的实验现象是：第 1 轮修订后，第 2 轮 `covered` 反而从 9 降到 7。这不是覆盖退化，而是更完整的节点描述让审查发现了此前没有识别的审计和策略执行知识身份。因此闭环不能要求每轮指标单调上升，只能以最终固定点和全部任务覆盖为准；同时，单次收敛不能证明跨次稳定。

这轮回放使用的是 13 项已审核一级任务，不是后来定义的完整任务树输入。因此它证明了“审查 → 完整修订 → 全量复审”的闭环能够发现并补齐真实缺口，但当前完整任务树契约仍需按 §9 重放，不能把历史数字直接视为最终质量。

### 4.8 逐一级分支展开知识主题树

任务覆盖闭环通过后，一级目录冻结。宿主对每个一级节点分别发起一次展开调用。每次只展开当前节点，不修改其他一级节点，也不重新设计一级目录。

输入包含规范领域名称、角色名称、框架总范围、全部一级节点的紧凑目录，以及当前目标一级节点。其他一级节点只用于识别知识边界，不传入其内部子树。模型返回以目标节点为根的完整子树。

#### 4.8.1 一级分支展开提示词

```text
你是一位知识框架展开专家。

给定一个领域、一个岗位角色、整套一级知识目录，以及其中一个已经冻结的目标一级
节点，请只展开目标节点，生成它内部的一棵知识树。

【输入】
- domain_name：领域名称；
- role_name：岗位角色名称；
- framework_scope：整套一级知识框架的范围；
- first_level_directory：全部一级节点的紧凑目录；
- target_node：本次需要展开的一级节点，包含 node_id、title、description 和 exclusions。

【任务】
1. target_node 是本次输出树的根。其 title、description 和 exclusions 已经冻结，
   不得改写。
2. 根据 target_node 的 title、description 和 exclusions 识别其内部包含的知识
   身份，并生成完整后代树。
3. first_level_directory 只用于识别本目标节点与相邻一级范围的边界，不得把其他
   一级节点的内部知识写入当前树。
4. 不限制固定层级和固定节点数量。是否继续拆分由节点内部是否仍包含多个可独立识别
   的知识身份决定。

【知识节点要求】
1. 每个节点必须表示领域知识范围，不能是工作任务、实施步骤、执行动作、项目安排、
   交付文档、产品方案或代码实现。
2. title 必须脱离父路径和节点编号后仍能识别所指的知识范围，不得使用“概述”
   “相关内容”“其他知识”等无法独立定位的标题。
3. description 直接说明该范围是什么、包含哪些知识内容、与相邻范围的主要边界。
   不要使用“需要理解”“用于学习”等学习动作句式代替知识内容。
4. exclusions 只记录确实容易与该节点混淆、但不属于该节点的相邻知识或属性；没有
   这种边界时返回空数组。
5. 同一棵输出树中不得出现重复或仅更换措辞的同义节点。
6. 不得把多个互不从属、需要分别检索的知识身份仅通过标题中的“与”、顿号或其他
   并列表达塞进同一个节点。

【父子结构】
1. 父节点与子节点之间必须是知识范围的包含关系，不是执行先后、学习顺序或组织流程。
2. 子节点应共同覆盖父节点承诺的主要知识范围，兄弟节点之间应尽量边界清楚。
3. 一个非叶父节点必须至少有两个子节点。
4. target_node 的 description 只用于定义整棵子树共同的范围和边界，不作为需要在
   后续单独挂接原文证据的知识项。其范围内如果存在总览、定义、分类关系、组成关系、
   共同原理等能够独立检索并需要证据支持的总括性知识，必须作为子节点输出，不能因为
   已经出现在父节点 description 中就省略。
5. 叶节点的 children 返回空数组。

【叶节点判定】
1. 不使用固定深度，也不追求绝对逻辑原子。
2. 一个知识身份应能脱离父路径独立命名，并可作为独立知识节点被检索。
3. 如果一个范围包含两个或更多可以分别命名、分别检索的知识身份，应继续拆分为
   子节点。
4. 如果内部内容只是同一知识身份的定义、范围、作用、边界、条件、代价等属性，
   不应拆成兄弟节点，而应写入该节点的 description。
5. 不同分支可以根据实际知识结构使用不同深度。

【输出要求】
只输出符合下方输出契约的 JSON，不输出 Markdown、解释或额外文字。
parent_node_id 必须与 target_node.node_id 逐字一致。
每个节点只包含 title、description、exclusions、children 四个字段。
exclusions 必须是字符串数组，数组中的每一项不能为空；没有需要说明的边界时返回
空数组。

【输出契约】
{
  "parent_node_id": "输入中的 target_node.node_id",
  "children": [
    {
      "title": "直接子知识范围标题",
      "description": "该范围包含的知识内容及主要边界",
      "exclusions": ["确实容易混淆的相邻知识"],
      "children": []
    }
  ]
}
```

#### 4.8.2 展开校验与拼装

宿主在拼装前必须校验：根对象只含 `parent_node_id` 和 `children`，根 ID 与目标一级节点一致；每个节点只含 `title`、`description`、`exclusions`、`children`；标题和描述非空；`exclusions` 为字符串数组且元素非空；叶节点 `children` 为空数组；非叶节点至少有子节点；同一子树不存在规范化后完全相同的标题；模型没有改写目标一级节点；JSON 未截断且没有非法额外字段。

通过校验后，宿主按先序分配路径标识，例如 `K08.01`、`K08.01.02`。路径标识只由宿主生成，不交给模型。任何截断、非法 JSON、字段缺失或结构失败都记为该分支显式失败，不生成空子树，也不把失败分支伪装成叶节点。全部一级分支展开通过后，才形成可供证据挂接的完整角色知识框架。

#### 4.8.3 叶节点颗粒度审计与拆分修复

§4.8.2 的宿主校验只能证明树结构合法，不能证明叶节点已经满足“一个可独立命名、检索和判断证据覆盖的知识身份”这一语义条件。当前展开提示词已经在生成时要求继续拆分包含多个可分别检索身份的宽叶节点，Gate D 也将复合叶节点列入验收项；但一级分支展开之后尚无独立、全量执行的叶节点颗粒度审查与拆分修复闭环，历史回放只对四个宽分支做了语义抽查。

这个缺口不能被证据挂接阶段替代。挂接阶段判断“当前 block 能否支持给定叶节点”，不会重新决定叶节点是否过粗；当证据只支持叶节点的一部分组成时，挂接器只能在错误粒度上作出保守拒绝。`K21.06.04 Agent 应用成熟度与采纳准备度` 同时包含数据成熟度、流程标准化、治理能力、人才与运营准备、试点到规模化判断依据，却在当前框架中作为叶节点存在，就是代表性失败样本。

正式冻结知识框架前，需要增加独立的叶节点颗粒度审查：对全部叶节点判断其是否仍包含两个或更多可分别命名、分别检索、分别判断证据覆盖的知识身份；需要拆分时由 LLM 返回完整替换子树，宿主重新执行结构与路径校验，并重新检查相关任务覆盖。定义、范围、作用、边界、条件、代价等同一知识身份的属性仍留在 `description`，不得把属性机械拆成子节点。

本轮需要解决的是这个审计与修复闭环本身，而不是继续修改证据挂接提示词。至少要明确以下问题：

1. **审计输入**：每个待审叶节点提供完整路径、标题、description 和 exclusions；是否需要同时提供同一父节点下的兄弟节点标题，作为判断“独立知识身份”还是“同一身份属性”的上下文，需要实验确定。
2. **拆分判据**：两个或更多知识身份可以分别命名、分别检索、分别判断证据覆盖时必须拆分；定义、范围、作用、边界、条件、代价、属性或同一机制的不同侧面不因此自动成为兄弟节点。标题只是线索，不能仅凭“与”、顿号或多个名词机械判断。
3. **输出与修复**：审计器需要给出可解释的 `keep`、`split` 或 `uncertain` 决定。`split` 不能只给建议标题，应由 LLM 返回完整替换子树；宿主负责结构、路径、层级和字段校验，并重新检查相关任务覆盖。人工逐分支补丁不是正式修复路径。
4. **执行范围与批次**：当前 620 个叶节点都必须进入审计，可以按父分支或相邻路径分批调用，但不能只用若干个宽分支的抽样结果作为全量门禁。批次组织必须避免只给叶标题造成上下文不足，也要避免把过多叶节点放进一次调用引发相互竞争。
5. **失败语义**：结构非法、调用失败或语义不确定时必须显式保留未决状态并保守处理，不能把未拆分叶节点默认为通过，也不能把失败分支从冻结框架中静默丢弃。

本轮验收至少包括：

- `K21.06.04` 这类明确包含多知识身份的叶节点得到正确拆分，而不是通过挂接提示词把部分支持误判为整节点支持；
- 只有单一知识身份的叶节点不被机械拆成一堆属性节点；
- 当前知识框架全部叶节点都有审计结论，未决项和失败项没有被静默算作通过；
- 拆分后的框架重新通过任务覆盖检查，没有因为拆分造成原有履职知识缺口；
- 单叶证据挂接提示词保持冻结；拆分前后用同一组固定 block 和叶节点对照，确认问题缓解来自知识粒度而不是挂接提示词变化。

#### 4.8.4 实验回放与阶段结论

2026-11-23 先在宽节点 K08“Agent 运行时、编排与执行控制”上做单分支回放。首次调用即结构合法：输入／输出为 6,639／9,286 tokens，耗时 49.612 秒，得到 5 个直接子节点、21 个后代节点、16 个叶节点，最大深度 2；根节点原样保留，没有重试、重复标题或单子节点容器。

随后对其余 23 个一级节点执行批量展开，并发度为 15。23/23 全部首次通过结构校验，0 次重试，批量耗时 161.674 秒，合计输入 152,235 tokens、输出 325,804 tokens。复用已审核的 K08 子树后，24 个一级分支形成：

| 指标 | 结果 |
| --- | ---: |
| 一级根节点 | 24 |
| 后代节点 | 823 |
| 叶节点 | 620 |
| 分支节点 | 203 |
| 包含一级根的总节点 | 847 |
| 最大深度 | 3 |
| 深度 1／2／3 节点 | 178／565／80 |

结构层面，23 个批量分支和 K08 均一次合法，说明“先冻结一级目录，再逐分支展开”能把原本过大的单次生成任务拆成可并行、可校验的调用。规模差异也很大：K17、K23、K14、K07 分别产生 66、56、50、45 个后代节点，而 K02、K20 各产生 21 个；不能用固定节点数或固定深度压平分支。

语义抽查又说明结构通过不等于可以冻结。数据血缘同时出现在 K10 和 K17，成本事件在 K23 与 K14 之间存在边界重叠，K23 的事件分类还暴露出配置变更和知识数据变更可能遗漏，K14 存在标题与描述范围不一致。阶段结论是：逐分支展开的调用边界和规模已经验证可行，但完整框架仍需知识质量审查和跨分支边界修复；“847 个节点、620 个叶节点”是一次回放结果，不是生成目标。

以上覆盖与展开数字来自此前一版提示词和 13 项一级任务样本。当前 §4.7 已改为完整任务树覆盖，§4.8.1 的展开提示词也做过文案收敛，因此跨领域和当前逐字版本的稳定性仍应由 §9 的独立 Gate 验证。

## 5 知识库证据挂接

本章描述冻结知识框架之后如何把知识库原文接入框架。这里不重新生成或改写知识主题，也不把整个知识库“塞进”框架；挂接的基本关系是一条原文 block 对一个或多个叶节点提供证据，以及由此形成的叶节点与祖先节点覆盖状态。当前主方法固定为两级：先使用一级、二级、三级标题骨架排除整棵明确无关的一级树，再对保留一级树下的每个 `block × leaf` 执行单叶证据判定。一级树初筛只缩小最终判定范围，不能直接形成挂接关系；证据去重、覆盖状态、容错协议和跨 block 验证仍待完成。

### 5.1 挂接单位

挂接时以完整 block 及其文档、章节上下文为判断单位。知识主题只有叶节点承载原文证据；父节点和中间节点承担知识导航与范围说明，其证据覆盖由该节点所属的全部后代叶节点汇总得到，不直接重复挂接同一原文块。

一个 block 可以支持多个叶节点，一个叶节点也可以由多个 block 支持。具体挂接必须保留 `block_id`、冻结知识框架版本、叶节点 ID、原文引文、文档与章节路径、判断理由和挂接版本。模型输出不得引入输入中不存在的叶节点 ID。

### 5.2 已确定的判断边界

单叶挂接要回答的是一个存在性问题：当前 block 中是否存在至少一条可逐字提取、仅凭当前 block 即可成立、并直接支持该叶节点知识身份的证据。它不是要求枚举 block 内所有可能相关内容，也不是要求为 block 完成完整语义标注。只要一条合规证据已经足以证明支持，就应判为支持；叶节点整体是否覆盖充分，留给多个 block 汇总后的覆盖判断。

- 模型对 block 与叶节点返回 evidence 数组，宿主以数组是否为空派生“支持／不支持”二值挂接；不输出“部分支持”作为运行时结果。人工金标准与离线灰区评价另采用 `no_support`、`weak_support`、`direct_support` 三档。`weak_support` 不是模型新增的输出等级，也不是运行时必须落库的关系强度；叶节点整体覆盖是否充分，仍属于跨 block 的覆盖判断；
- 不能只按标题关键词匹配；原文没有出现主题标题词，但只要它直接回答了该叶节点的知识范围，仍应挂接；
- 一个具体案例、机制、规则、边界、分类或关系，可以作为独立证据支持叶节点，不要求覆盖该叶节点的全部类型和变体；
- 原文只与叶节点共享领域词、上位概念、邻近问题或背景时，不构成支持；
- 不得使用原文块之外的知识补造对象、机制、关系和因果；
- 一个 block 可以同时支持多个叶节点，不能只选“最相关”的一个；
- 叶节点 ID、引文和字段结构必须由宿主确定性校验，非法输出显式失败，不静默删除后继续挂接；
- 父节点不作为默认证据挂接单位，以免同一证据在祖先链上重复存储或掩盖叶节点漏挂。
- 单叶挂接调用向模型提供 block 的 `section_path`、`text`，以及 leaf 的 `path`、`title`、`description`、`exclusions`；`block_id` 和 `leaf_id` 由宿主在调用外绑定；
- `leaf.path` 与 `leaf.title` 共同规定证据必须满足的知识关系。原文只说明某个对象存在、被实现、具备能力或产生效果时，不得据此推断该对象参与了路径和标题所指的阶段、过程、职责或关系；后者必须由原文直接陈述。`leaf.description` 只用于确认该身份的具体范围，不得扩张或改写 `leaf.path`／`leaf.title` 规定的关系；
- 一条 evidence 表示一个连续 quote，可以包含多个陈述，不要求拆成原子事实；同一 quote 同时构成多个支持类型时，用 `support_types` 数组返回全部成立类型；
- `support_types` 用来限定什么形态的陈述能够构成支持，并帮助审核返回的 `quote` 与理由是否自洽；它不是要求对 block 做穷尽类型标注。类型集合不要求覆盖叶节点的全部方面，未返回次要证据也不构成漏挂；
- 单叶挂接的当前验收条件是：模型输出可解析且宿主结构合法；evidence 非空时至少一条 quote 直接支持该知识身份并逐字存在于 block 中，evidence 为空时派生为不支持；返回的证据不得依赖原文未陈述的关系。语义评价在离线层对照人工三级金标准：`direct_support` 必须判支持，`no_support` 应判不支持，`weak_support` 单独观察。当前不验收 block 内全部相关证据是否列全、全部支持类型是否列全，或叶节点全部方面是否都有证据。

知识库证据挂接是整个流程中计算成本最高的阶段之一。首版把模型任务限定为判断“当前 block 能否支持当前叶节点”并给出足够成立该判断的证据，不要求模型承担 block 完整标注、跨 block 证据补齐或叶节点覆盖审计。证据遗漏只有在跨 block 聚合后影响叶节点覆盖时，才作为覆盖问题处理。

### 5.3 一级树标题骨架初筛

一级树初筛的目标不是选择“最相关”的一级树，而是只排除已经能够确定“整棵一级树下的所有叶节点都不可能从当前 block 获得直接证据”的一级树。凡是不确定、只命中一个小分支、只在更深层叶节点中可能相关的范围，都默认保留。误排除会造成不可恢复漏挂，因此高召回优先；误保留留给后续单叶判定拒绝。

每次调用发送一个 block 和当前知识框架的全部一级树标题骨架。每个一级节点只包含 `root_id` 和 `title`，二级节点只包含 `title` 和它直接三级子节点的标题；不发送一级、二级、三级节点的 `description`、`exclusions`，也不发送更深层叶节点。当前框架的该骨架包含 24 个一级标题、178 个二级标题和 565 个三级标题，另有 80 个更深层叶节点不进入此调用。

```json
{
  "block": {
    "section_path": ["文档标题", "章节标题"],
    "text": "当前 block 的完整原文"
  },
  "roots": [
    {
      "root_id": "K08",
      "title": "一级知识范围标题",
      "children": [
        {
          "title": "二级知识范围标题",
          "children": ["三级知识范围标题一", "三级知识范围标题二"]
        }
      ]
    }
  ]
}
```

输出必须覆盖全部 `root_id` 且每项恰好出现一次，每项只包含 `root_id`、`is_retained` 和不超过 80 字的 `reason`。宿主检查 JSON、字段、根节点覆盖、未知或重复 ID；保守语义还要求模型不能因为一级范围较宽、block 未覆盖全部标题、标题没有出现原词或看不到更深叶节点而排除。人工确认的应保留一级树只在宿主侧评分，不进入提示词。

`b00008` 上使用该标题骨架执行 50 次独立回放，50/50 次结构合法，6 个已知应保留一级树全部保留，平均保留 10.6 个一级树，一级候选精确率 56.6%；平均单次输入约 10,918 token、输出约 1,060 token。该结果支持把一级树初筛作为当前主步骤：在 `b00008` 本轮回放中，它把后续验证范围缩小到 10 个一级分支、253 个叶节点。该 253 是 `b00008` 的样本级候选集，不是 620 叶全量目录；其他 block 必须重新初筛并形成自己的叶节点候选集。只有单一 block 证据仍意味着跨 block 泛化是待验证风险，并必须采用失败回退，但不改变当前主路径选择。

#### 5.3.1 一级初筛提示词

当前有效实验提示词的规范化 UTF-8 SHA-256 为 `219f18c9e5539c10a90358637c92b1d5bbc8d6dd1d7f17f0243f7ecd6bde7dd8`。

```text
你是知识树一级候选筛选器。你会收到一个 block 和该领域全部一级知识树。

你的任务不是判断哪些一级树最相关，而是只排除已经可以确定“整棵一级树下的所有知识
叶节点都不可能从当前 block 获得直接证据”的一级树。这是后续叶节点挂接的高召回前置
步骤，误排除会造成不可恢复的漏挂，因此必须保守。

【输入】
- block.section_path：原文所在章节路径；
- block.text：本次唯一可用的原文；
- roots：全部一级候选范围。每项包含 root_id、title 和 children；children 中的每个
  二级节点包含 title，并可能包含 children，后者是该二级节点的直接三级子节点标题。
  输入最多提供到三级标题，不提供节点描述，也不提供更深层叶节点。

评价，就保留这个一级树。

1. block 提供的只是具体产品案例、实现、条件或效果，但可能支持某个上位知识叶节点；
2. 当前 block 只覆盖一级树中的一个小分支；
3. 下级标题提示了可能范围，但需要查看更深层叶节点定义才能进一步确认；
4. 你只能在“该一级标题及全部已提供的下级标题所指的知识范围，都与当前 block 无关或
   明确冲突”时排除。

原词，或你没有看到更深层叶节点就排除。候选是否最终成立由后续叶节点验证器决定。

【输出】
只输出一个 JSON 对象，不得输出 Markdown 或 JSON 之外的说明。

decisions 必须覆盖 roots 中的所有 root_id，每项恰好出现一次。字段顺序固定为
root_id、is_retained、reason。reason 用不超过 80 字说明为何保留或排除。

    }
  ]

```

### 5.4 单叶最终判定方法与宿主校验

当前最终判定采用“一次调用只判断一个 block 与一个叶节点”的方法。一级树初筛先用一个 block 与全部一级树标题骨架缩小范围，但它只输出需要继续验证的一级树，不能直接形成带证据的挂接关系。未被初筛排除的一级树，其叶节点必须继续拆成 `block × leaf` 的独立调用，避免同一批叶节点互相竞争。

每次调用只发送以下用户消息；`block_id` 和 `leaf_id` 由宿主在模型调用之外绑定，不进入提示词：

```json
{
  "block": {
    "section_path": ["文档标题", "章节标题"],
    "text": "当前 block 的完整原文"
  },
  "leaf": {
    "path": ["一级知识范围", "中间知识范围", "叶节点标题"],
    "title": "叶节点标题",
    "description": "叶节点的完整知识范围说明",
    "exclusions": ["确实相邻但不属于当前叶节点的知识"]
  }
}
```

提示词不得接收领域名称、角色名称、用户问题、答案组、金标准、其他叶节点或当前知识库中的其他原文。模型只能依据当前 block 和当前叶节点的路径、标题、描述与排除边界判断支持关系。

宿主至少执行以下确定性检查：

1. 输出必须是单个 JSON 对象，且顶层只能包含 `evidence` 数组；
2. 宿主以 `evidence` 是否非空派生运行时可挂接结果：非空即支持，空数组即不支持；模型不再输出 `is_supported` 或外层不支持理由；
3. 每条 evidence 必须且只能包含 `quote`、`support_types`、`target`、`reason`；`target` 用于显式记录本条证据支持的叶节点范围或方面，宿主不据此二次推断挂接结果；
4. 每条 evidence 的 quote 必须是 `block.text` 中的连续逐字原文，不得翻译、拼接或用省略号跨段；
5. `support_types` 必须是非空、不重复的数组，每个成员只能来自九类支持类型；
6. 每条 quote 必须能直接证明该 evidence 的每一种 `support_types` 和 reason；
7. JSON、字段、引文或叶节点身份不合法时显式失败并保留原始输出，不静默删除非法项后继续挂接。

以上检查只验证 evidence 结构与宿主派生结果。离线评测另将派生结果与人工三级金标准对照，不能把 `weak_support` 塞回模型输出契约，也不能因为模型返回非空 evidence 就自动把该关系记录为 `direct_support`。运行时关系与离线评审等级的字段和写入责任见 §5.6。

当前校准配置为 `deepseek-flash`、temperature 0、关闭 thinking、最大输出 4,096 token、并发 25。模型 ID、并发和输出上限是实验配置，不是对所有部署永久固定的产品参数；提示词、模型 ID 和关键参数必须进入 trace。


### 5.6 已验证的判断边界

证据支持存在天然灰区。一个 block 可能只是支持目标知识的一个弱实例，也可能只与目标知识共享领域和背景，却不能回答目标知识身份。把这些情况强行压进二元正负例会放大人工标注抖动，也会让提示词为个案反复收紧。因此，模型输出继续保持二值，评价侧改用三级金标准。

#### 5.6.1 三级人工金标准与灰区评价

每个 `block × leaf` 的人工金标准使用 `gold_support_grade` 表示：

| 等级 | 含义 | 挂接策略 |
| --- | --- | --- |
| `no_support` | 不相关，或虽然主题相关但不能回答目标知识身份 | 不挂接 |
| `weak_support` | 部分支持、弱实例或处于可入可不入的灰区 | 可以挂接；运行时仍只记录二值支持关系，不要求额外标记弱支持 |
| `direct_support` | 原文直接支持目标知识身份 | 必须挂接 |

`no_support` 可进一步记录诊断原因，但原因不改变等级，也不拆成额外指标：

- `non_support_reason=unrelated`：原文与目标知识范围无关；
- `non_support_reason=related_but_not_target`：原文主题接近，但不能回答目标知识身份。

模型只输出 evidence 数组，宿主按 evidence 是否为空派生二值挂接结果。`weak_support` 不得成为模型新增的“部分支持”输出，也不得由模型返回 evidence 后自动推断。离线评审记录使用概念字段 `gold_support_grade`；当前 `b00008` 的 253 叶评测产物中对应 JSON 字段名为 `support_grade`。`weak_support` 命中的叶节点可以按普通支持关系挂接，不要求运行时另记 `support_strength` 或把关系标记为弱支持；该等级只用于离线灰区指标。

评价指标分为硬指标和灰区观察，不能把 `weak_support` 同时算作正例和负例：

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 必挂召回率 | `direct_support` 判定中模型判支持的次数 ÷ `direct_support` 全部判定次数 | 直接衡量不可接受的漏挂 |
| 硬负例误挂率 | `no_support` 判定中模型判支持的次数 ÷ `no_support` 全部判定次数 | 直接衡量明确无关内容的误挂 |
| 灰区支持率 | `weak_support` 判定中模型判支持的次数 ÷ `weak_support` 全部判定次数 | 只观察模型对边界样本的倾向 |
| 硬精确率 | `direct_support` 中判支持的次数 ÷（`direct_support` 中判支持的次数 + `no_support` 中误判支持的次数） | 衡量硬正负例合并后的支持准确性 |
| 硬 F1 | 仅用 `direct_support` 与 `no_support` 计算，`weak_support` 不进入分子或分母 | 版本比较的硬指标 |

灰区还需要报告稳定性：所有回放轮次都支持记作“稳定支持”，所有轮次都拒绝记作“稳定拒绝”，其余记作“摇摆”。稳定性用于发现知识身份或提示词语义是否真正不稳定，不作为单次通过门槛。三级主口径不再把 `unrelated` 和 `related_but_not_target` 拆成额外数值等级；这两种原因用于根因定位，继续细分只会增加主观判断负担。

这一评价方式与信息检索中的分级相关性、语义歧义软标签和选择性预测思路一致，可参考 [TREC 2021 Deep Learning Track](https://trec.nist.gov/data/deep2021.html)、[Stanford IR Book 的相关性判断讨论](https://nlp.stanford.edu/IR-book/html/htmledition/assessing-relevance-1.html)、[AmbiFC](https://aclanthology.org/2024.tacl-1.1/) 和 [ACL 2023 selective prediction](https://aclanthology.org/2023.acl-long.437/)。这些资料只支持“分级和灰区应显式建模”的方法判断，不替代本项目自己的固定样本评审。

`support_type` 必须锚定目标知识身份本身，或锚定 `title`、`description`、`path` 明确包含的组成部分；不能只锚定与目标场景相关的外部对象、机制或结果。`evaluation` 只有在原文明确建立指标、判据或标准与目标知识对象或其组成部分之间的评价关系时才成立，单独出现数值、效果或普通判断不够。`support_type` 当前仍用于证明支持关系自洽，不作为二值门禁或穷尽标签。

上述失败把下一问题定位到知识框架：证据只支持粗叶节点中的一个组成部分时，挂接提示词不应代替叶节点粒度审查决定该粗节点是否成立。详细逐轮结果、提示词版本、哈希和产物位置见[知识库证据挂接实验](2026-11-24-知识库证据挂接.md)。

### 5.7 叶节点挂接产物与持久化边界

本节确定固定 15 篇文档快照上的全量叶节点挂接结果如何保存。当前只冻结“不可变挂接账本 → 派生运行时索引”的两阶段方向，不在首次全量验证前冻结正式 SQLite schema。叶节点挂接关系与原 Profile Knowledge Map 属于不同数据域，不能写入 `wiki-knowledge-maps` 的 `map.json`，也不能复用 `BlockAspectSupport`。

两者不能混用的原因是：`BlockAspectSupport` 表示一个原始 block 对 Profile 知识地图中 `TopicAspect` 的支持关系；叶节点挂接表示一个原始 block 对角色知识框架叶节点的支持关系。它们绑定不同的知识身份、版本和查询路径，合并后会破坏范围校验，并使框架或地图任一版本变化时难以判断哪些关系失效。

#### 5.7.1 逻辑关系与运行状态

叶节点挂接的逻辑对象为 `BlockLeafSupport`，即在某个固定快照和固定角色知识框架 revision 下，一个 block 支持一个叶节点的二值关系。一个 block 可以支持多个叶节点，一个叶节点也可以被多个 block 支持。每条关系可以包含多条 evidence，但同一 `framework_revision_id + block_id + leaf_id` 只形成一条逻辑支持关系。

模型输出、宿主校验和离线评审仍遵守 §5.6：运行时只以 evidence 是否非空派生支持／不支持二值结果；`no_support`、`weak_support`、`direct_support` 只存在于离线评测金标准，不得写入产品挂接账本，也不得成为运行时证据强度字段。

一次挂接运行的 manifest 状态至少包括：

| 状态 | 含义 | 能否设为活动版本 |
| --- | --- | --- |
| `building` | 正在生成或校验，产物不完整 | 否 |
| `sealed_complete` | 输入范围、逐 block／叶节点覆盖和全部输出均已校验完成 | 是 |
| `partial` | 部分 block、叶节点或模型输出未完成，仅供诊断 | 否 |
| `failed` | 运行失败，不能作为挂接结果使用 | 否 |

活动指针只在 `sealed_complete` 后原子更新。新运行失败或仍为 `partial` 时，不得覆盖既有活动指针；读取方发现所选快照、角色知识框架 revision 与活动指针不一致时必须显式失败，不能静默换用其他版本或退回全扫描。

#### 5.7.2 不可变挂接账本

每次运行在数据根目录下使用独立运行目录，不原地追加或覆盖已完成产物：

```text
<data_root>/wiki-leaf-attachments/<snapshot_id>/
  active-attachment.json
  <attachment_run_id>/
    manifest.json
    supports.jsonl
    block-coverage.jsonl
    leaf-coverage.jsonl
    conflicts.jsonl
```

`active-attachment.json` 是快照级活动指针，至少记录 `attachment_run_id`、`framework_revision_id`、manifest 内容 hash 和发布时间。运行目录创建后视为不可变；重试、提示词变化、模型参数变化或框架修订都必须生成新的 `attachment_run_id`。

`manifest.json` 至少绑定：

- `schema_version`、`attachment_run_id`、运行状态和创建／封存时间；
- `snapshot_id`、文档数、block 数和输入清单 hash；
- 角色知识框架 ID、`framework_revision_id` 和框架内容 hash；
- 单叶挂接提示词版本及 SHA-256；
- 一级树标题骨架初筛提示词／策略版本及 SHA-256；
- 模型 ID、temperature、thinking 配置、最大输出 token 和其他影响结果的参数；
- block 覆盖数、叶节点评估数、支持关系数、无支持 block 数、空叶节点数和冲突数；
- 各账本文件的内容 hash。

`supports.jsonl` 每行一条 `BlockLeafSupport`，至少包含：

```json
{
  "support_id": "bls_<stable-hash>",
  "snapshot_id": "s_...",
  "framework_revision_id": "kf_...",
  "block_id": "b...",
  "leaf_id": "K01.07.03",
  "evidence": [
    {
      "quote": "block.text 中的连续逐字原文",
      "support_types": ["definition"],
      "target": "被该 quote 支持的叶节点范围或方面",
      "reason": "该 quote 如何以所选支持类型支持 target"
    }
  ]
}
```

`support_id` 必须由 `framework_revision_id + block_id + leaf_id` 稳定派生，使同一逻辑关系可去重、可重建，并能检测错误挂接。evidence 可按实现需要追加 `quote_start`、`quote_end` 或 `quote_sha256`，但这些辅助字段不能替代逐字 quote 校验。

#### 5.7.3 覆盖与冲突账本

支持关系只记录肯定关系，不把完整 block × leaf 否定矩阵写入活动运行时索引。为了证明运行范围完整并支持失败闭环，另用覆盖账本记录：

- `block-coverage.jsonl`：每个 block 的一级分支初筛结果、实际评估叶节点数、支持叶节点数、是否无任何支持叶节点，以及未完成原因；
- `leaf-coverage.jsonl`：每个叶节点的候选 block 数、实际评估 block 数、支持 block 数、是否为空叶节点；
- `conflicts.jsonl`：quote 校验失败、叶节点身份或范围不合法、范围不完整、模型输出冲突、重复回放不稳定、证据互相冲突等需要人工或后续策略处理的情况。

未挂接 block 指完成规定评估范围后没有得到任何叶节点支持的 block；空叶节点指完成规定评估范围后没有任何支持 block 的叶节点。二者必须能由覆盖账本恢复，不能用“没有出现在 `supports.jsonl`”代替完整性证明。

首次 15 篇实验如需保留逐对否定结果或原始模型输出，应放入运行诊断产物或现有 trace／artifact 机制，并明确标记为不可用于运行时查询。即使保留，也不得把全部否定关系复制进活动索引。原始 prompt、输入、模型输出、usage、校验结果和失败重试继续由 trace 关联 `attachment_run_id`，不在挂接账本中重复保存大段 trace 数据。

#### 5.7.4 运行时索引与正式 schema

活动挂接账本确认 `sealed_complete` 后，可以编译独立、可重建的运行时索引，至少提供：

- `block_id → leaf_ids`；
- `leaf_id → block_ids`；
- 空叶节点集合；
- 冲突证据集合；
- 账本版本、快照和框架 revision 校验信息。

运行时索引是派生产物，不是事实源；删除后必须能从不可变账本重建。向量数据库只保存向量检索数据，不能承担挂接关系真值。15 篇首次全量挂接和端到端验证稳定前，不新增或迁移正式产品 SQLite 表，也不把当前 JSONL 字段直接视为最终数据库 schema。查询链路可以先通过活动指针读取账本或临时编译索引；只有框架、挂接和查询闭环稳定后，才依据真实规模、访问模式和迁移成本决定正式存储介质。

### 5.8 待协作确定的问题

证据挂接设计还需要共同确定：

1. 一级、二级、三级标题骨架初筛能否在未参与调参的多个 block 上稳定做到不误排除正例，以及初筛失败、超时或结构非法时如何保守回退到全目录；
2. 多叶节点同时支持、重叠引文和同义证据的存储与去重方式；
3. 叶节点与父节点的派生覆盖状态，以及“知识库没有证据”和“挂接漏挂”如何区分；
4. 残差 block 的复核、重试和人工检查边界；
5. 文档增量、框架版本变化和局部重新挂接的失效与回滚协议。
6. `condition`、`evaluation` 与 `instance` 的语义边界。`K21.06.03` 已确认其人工金标准支持类型为 `instance`：原文是 Claude Code 实际进行组织可行性判断的案例，而不是只陈述一个抽象条件。2026-11-25 的旧 R2 回放中有 8 次支持主要返回 `condition`，说明模型仍偏向描述“可行性依据”，与负责人要求的“可识别的评估应用案例”存在类型偏差；该偏差不影响 `direct_support` 定级，也不作为挂接门禁。其他方法、评估与实例之间的通用边界仍需在未参与调参的样本上校准，不能把本样本的结论扩大成所有类型的固定映射。
7. 知识节点的支撑义务与部分覆盖策略。当前“命中 `leaf.description` 中任一合法具体方面即可”的规则对可列举范围、类别实例、过程关系、规则映射等节点可能成立，但会把架构、范式、体系结构和边界类节点中的一个组成机制误当成整体知识身份。`b00007` 复核中，Reflexion 的自主控制循环被用于支持 `K01.05.05 自主型Agent体系结构`，动态记忆、反思和动作空间又被用于支持 `K01.04.05 认知架构`；临时增加“具体方面本身必须仍完整表达叶节点知识身份”的约束后，前者首次被拒绝，但后者仍然误支持，说明只改 target 抽取句不足以形成通用规则。后续需要把节点要求的证明义务显式区分，例如“任一合法方面”“必须证明类别实例”“必须证明整体组成关系”“必须呈现过程关系”“一个映射实例即可”“必须完成比较”“必须说明边界与职责归属”，但仍需在代表性叶节点和未参与调参的 block 上验证，不能先固定成一整套类别或逐叶硬编码。该问题登记为 [BL-0021](../backlog.md)。
8. 按支持类型与问题意图选择返回证据的策略。当前挂接阶段只判断“某条原文能否支持叶节点”，尚未决定叶节点已经挂接大量证据后，回答时应该向用户返回多少、哪些证据。支持类型最初用于说明挂接证据以什么形态支持叶节点，并不表示同一叶节点下的所有支持证据都应等权进入回答；知识库扩大后，它还应成为查询期决定哪些证据进入回答的依据。一个知识节点可能挂接几十或上百条支持证据；这些证据不应等量返回，也不能用一个固定 top-k 截断。候选策略至少需要同时考虑支持类型、问题意图、证据唯一性、代表性与多样性、冲突、权威和成本：同一叶节点有 100 条 `instance` 支撑时，通常只需选择少量有代表性或覆盖不同侧面的实例；`definition` 支撑可能需要返回全部不同定义与边界差异，尤其不能因预算静默丢掉冲突定义；当用户明确问“所有例子”“有哪些”“分别是什么”时，`instance` 也必须扩大覆盖并显式报告缺口。`condition`、`mechanism`、`method`、`evaluation` 等类型也可能因问题不同而有不同的全量或抽样义务。后续应把“离线证据挂接关系全集”和“单次回答证据包”分开设计：挂接关系继续可追溯地保留，查询期再做有解释的证据选择，输出已选数量、省略数量和选择理由，禁止用固定数量上限冒充语义覆盖。该问题登记为 [BL-0022](../backlog.md)。

在这些问题确认前，单叶挂接仍属于候选设计；任何新调度或覆盖规则都不得根据单块、单主题样本固化。

## 6 查询与检索

### 6.1 查询路径总览

求全类问题采用“按一级分支隔离的叶节点召回”，而不是把整棵知识框架一次交给模型：

```text
用户问题
→ 规范化问题与资料范围
→ 读取当前冻结角色知识框架的叶节点目录
→ 对每个一级分支并行执行一次叶节点召回
→ 宿主校验每个分支的 JSON、叶节点 ID 和分支归属
→ 合并 required／optional 叶节点
→ 按叶节点读取已挂接原文证据
→ 主题外兜底检索与新增证据复核
→ 回答或声明部分覆盖
```

每个分支调用只看到当前一级分支和该分支下的叶节点，不看到其他分支的候选结果。这样可以避免模型先做一次容易漏项的一级分支筛选，也避免一次输入全部叶节点造成注意力稀释。分支之间并行执行，任何一个分支返回空数组都不是失败。

### 6.2 召回输入

叶节点目录中的每个候选只提供：

```json
{
  "leaf_id": "K08.01.02",
  "path": ["AI Agent 运行时、编排与执行控制", "执行隔离机制", "工作区隔离"],
  "title": "工作区隔离"
}
```

召回时向模型提供当前用户问题、当前一级分支、该分支叶节点目录。不提供：

- `domain_name`、`role_name`；
- 叶节点 `description`、`exclusions`；
- 其他一级分支及其叶节点；
- 已选叶节点、测试问题、金标准、答案组名称或外部资料。

路径用于补充叶节点的知识语境，不能作为候选输出。模型只能返回叶节点 ID，不能返回父节点、内部节点、其他分支节点或自行构造的编号。

### 6.3 分支叶节点召回提示词

```text
你是一个叶节点知识召回器。每次调用只处理一个一级知识分支。

你会收到：
- question：用户要完整回答的问题；
- first_level_branch：本次允许检查的一级知识分支；
- leaf_directory：该分支下全部叶节点的 id、完整路径和标题。

【任务】
找出为了完整回答用户问题，本分支内所需的所有叶节点。必须逐项检查
leaf_directory，不能只根据一级分支标题判断整个分支无关，也不能看到第一个相关叶节点
就停止。

【选择规则】
1. 只能返回 leaf_directory 中逐字存在的 leaf_id，不得编造或改写编号。
2. 祖先路径只用于理解叶节点的知识语境，不是候选知识节点；不得输出父节点或路径编号。
3. 对相关叶节点给出层级：
   - required：如果不召回该叶节点，用户问题中至少一个明确方面会缺答案，或者答案会
     不完整。reason 必须写出会缺少的具体知识内容，不能只写“支撑理解”“提供基础”
     “帮助定位”“便于建模”等泛化作用。
   - optional：能提供例子、背景、相邻视角或扩展知识，但不召回不会导致核心答案缺失。
     这类叶子可以返回，但不能算作满足必要知识覆盖。
4. 只根据叶节点的完整路径和标题判断它能否实际帮助回答问题；不要仅因问题与叶节点
   共享关键词就选择，也不要把路径或标题中偶然出现的一个词当成完整选择依据。
5. 同一个 leaf_id 只返回一次；不同叶节点即使表达相近或重叠的知识，也不要自行做跨
   节点互斥选择或合并，节点级重复留到后续证据块关联阶段处理。
6. 本分支只能提供部分答案时，返回本分支确实相关的叶节点，不要推测其他分支内容。
7. 如果逐项检查后本分支没有任何叶节点能帮助回答，返回空数组。
8. 选择应尽量少而完整：漏掉一个确有回答价值的叶节点比多返回一个边界叶节点更严重，
   但明显无关或只提供泛化背景的叶节点不要加入。

【输出】
只输出 JSON，不得输出 Markdown 或额外说明：
{
  "selected_leaves": [
    {
      "leaf_id": "目录中的叶节点 id",
      "tier": "required 或 optional",
      "reason": "该叶节点能回答哪个必要方面，不超过50字"
    }
  ],
  "branch_reason": "本分支整体为何相关或为何为空，不超过100字"
}
```

用户消息只序列化 `question`、`first_level_branch` 和 `leaf_directory`，不附加问题特例、已有选择结果或其他一级分支信息。

### 6.4 required 与 optional 的含义

`required` 表示优先召回集：不选它会使问题至少一个明确答案方面缺失，或使答案明显不完整。它不是数学意义上的最小必要集，也不承诺三个运行必然完全相同。

`optional` 表示扩展候选：可以提供例子、背景、相邻视角或补充知识，但不进入核心必要覆盖的判断。最终证据读取可以先处理 `required`，再用 `optional` 补足深度、案例或边界；不能把 `optional` 自动当成无关项。

召回结果不输出全局连续排名。当前不使用 1～N 名次，因为“多直接构成某类知识边界”无法形成稳定、可重复的提示词规则。`required`／`optional` 是当前已经验证可用的有限分层。

#### 6.4.1 查询期叶节点召回也必须高召回

查询期叶节点召回服务于完整回答，不应优化成“返回最少的正确节点”。漏掉一个承载必要答案方面的叶节点，可能直接造成最终答案缺项；多召回一个扩展节点通常只会增加证据读取和筛选成本。因此该阶段的基本取舍是：在保持叶节点目录身份边界的前提下，优先避免漏召回，允许返回一定数量的 `optional` 或冗余候选，再由证据挂接、证据覆盖和回答阶段做降权或剔除。

`required` 和 `optional` 都是候选，不是“保留”和“删除”的区别。`required` 表示优先检查集，`optional` 表示仍应检查的扩展集；下游不能因为计算预算先到就把 `optional` 静默丢弃。固定 top-k、单一相关度阈值或过早的一级分支筛选都不能作为求全质量停止条件。当前逐分支输入完整叶节点目录、分支并行、不允许一次筛选一级分支，正是为避免前期一次误判造成不可恢复漏项。

高召回不等于无条件膨胀。叶节点仍必须来自当前冻结目录，非法 ID、父子混淆和跨分支返回仍然阻断；多召回候选应在证据读取后按证据覆盖、问题相关性和回答贡献降级。评价上应主要看金标准知识面的叶节点集合召回、最终可用证据召回和假完整率；冗余叶节点数量作为成本与噪声诊断，不能用精确率优化反向牺牲必要覆盖。

### 6.5 分支结果校验与合并

每个分支返回后，宿主至少校验：

1. JSON 合法且未截断；
2. `selected_leaves` 是数组，`branch_reason` 是非空字符串；
3. 每个选择项只有约定字段，`tier` 只能是 `required` 或 `optional`；
4. `leaf_id` 在该分支目录中存在且只出现一次；
5. 不得出现父节点、内部节点、其他分支叶节点或编造编号；
6. 空数组是合法的“本分支无相关叶子”；
7. 未知 ID、父子节点混淆、重复叶节点或非法字段必须使该分支显式失败，不得静默删除后继续计分。

全部分支成功或按明确失败语义记录后，合并所有分支的叶节点。跨分支出现相近节点时不在召回阶段做互斥合并，留到证据块挂接与去重阶段处理。

### 6.6 证据读取、兜底与停止

叶节点召回只回答“应该检查哪些知识范围”，不证明当前知识库中一定有证据。系统随后按叶节点读取已挂接原文 block，并执行主题外兜底检索：

- 某个叶节点没有证据，不等于整个问题无答案；
- 找到若干机制或对象不代表已经找全；
- 求全类查询必须检查未被选中叶节点、挂接错误叶节点和被遗漏 block 中的相关内容；
- 停止前至少完成一轮“叶节点召回 → 证据读取 → 主题外补充 → 新增证据复核”；
- 新一轮检索不再带来新的相关原文 block 时才能结束；
- 只能形成部分覆盖或无法验证是否有主题外内容时，必须显式记录限制；
- 资源和 token 上限只作为异常保护，不作为质量停止条件。

叶节点召回与证据挂接是两段不同判断。前者判断“用户问题可能需要哪些知识范围”，后者判断“这段原文是否能为某个叶节点提供可用于回答的证据”。一次召回结果不能替代后者，也不能单独宣称当前快照已经找全。

### 6.7 分支并行召回探索结论

当前固定样本使用 24 个一级分支、620 个叶节点，每次只输入一个分支，24 路并发，`deepseek-flash`，关闭 thinking。对完整问题“除了沙箱、虚拟机和出口控制，AI Agent 还有哪些隔离或控制边界？请分别说明各限制什么。”连续运行三次：

| 运行 | required | optional | 合计叶节点 |
| --- | ---: | ---: | ---: |
| 1 | 126 | 47 | 173 |
| 2 | 128 | 60 | 188 |
| 3 | 131 | 50 | 181 |
| 均值 | 128.33 | 52.33 | 180.67 |

三次 required 并集为 149 个叶节点，其中 109 个三次均为 required，18 个两次为 required，22 个一次为 required。结果显示单次集合存在波动，但主召回面稳定，已满足继续进入证据挂接和覆盖复核的需要。

已知分级偏差包括：上下文与记忆生命周期相关叶节点可能被稳定放入 `optional`，任务分配约束、群体决策等弱边界叶节点可能被提升为 `required`。这些问题不再通过继续优化叶节点排序解决；它们留到证据挂接、叶节点证据覆盖和最终回答缺项复核中处理。

因此本轮停止继续探索叶节点名次和二次必要性判定。24、620、24 路并发是当前验证配置，不是对所有领域永久固定的产品参数；正式实现应由当前冻结框架的分支数和叶节点规模决定并发与输入装配。

### 6.8 找全的适用范围

本设计中的“找全”是：在固定知识库快照和声明资料范围内，尽可能找出所有能用于回答当前问题的原文内容。它不是证明现实领域知识已经完整。

最终召回范围同时受到当前知识框架版本、叶节点召回质量、证据挂接质量、原文索引能力和主题外兜底过程影响。任何一步缺失都可能造成假完整，因此必须保留逐分支召回、证据挂接和兜底检索的 trace。

端到端完整召回至少由两段高召回共同组成：查询期召回回答所需的叶节点，以及证据挂接期让这些叶节点能够读取到相关原文。少量单点漏挂可以通过相邻知识节点召回、多叶证据和主题外兜底争取补偿，但不能因此把该漏挂从指标中删除；同理，节点召回率较高也不能掩盖所选节点没有证据。两段必须分别报告，并最终以回答证据召回率和假完整率判定是否找全。

评测时，答案组名称和金标准叶节点只能存在于隐藏 fixture 或评测器中，不能出现在运行时问题文本、分支描述、叶节点目录或召回提示词中。运行时由模型独立选择叶节点，评测器事后映射到答案组。

## 7 关系观察轴的位置

关系观察轴和角色知识框架不是必须同时物化的两套永久结构。

### 7.1 生成期

关系视角可以帮助模型检查问题答案方面。例如生成“工作区隔离”相关主题时，可以检查机制、限制对象、条件、作用、来源和例外。关系视角只作为生成透镜，不直接决定最终主题节点。

### 7.2 证据挂接期

证据挂接可以使用关系定义、纳入条件和排除边界作为判断原文证据的辅助视角，但不必把全部关系轴写入每个 block。关系抽取结果不是叶节点集合，也不得替代叶节点级证据覆盖。

### 7.3 查询期

关系视角可以作为动态查询投影，例如在一个主题中进一步查找机制、条件、限制、作用和例外。只有在多个查询中稳定复用且显著改善召回或精度时，才考虑物化为持久索引。

### 7.4 核心分工

```text
使用角色：确定知识框架的职业视角
任务树：展开实际工作，并作为履职覆盖审查锚点
角色知识框架：组织和路由领域知识
叶节点：默认的查询召回、证据挂接和覆盖判断单位
关系视角：检查某类关系证据是否遗漏的辅助透镜
原文 block：最终事实与引用依据
LLM：语境消歧、路由、动态组合和答案综合
```

## 8 与其他知识组织路径的比较

| 路径 | 优势 | 主要风险 |
| --- | --- | --- |
| 纯主题或社区检索 | 实现简单，适合普通主题问答 | 缺少明确覆盖契约，跨主题找全不稳定 |
| 单一路径 LLM Wiki | 页面组织自然，回源链清晰 | 页面目录依赖生成结果，未知主题可能没有入口 |
| 固定关系观察轴 | 横切主题，可执行关系枚举 | 领域对象枚举不足，概念角色和多义性处理成本高 |
| 使用角色驱动的知识框架 | 角色视角明确，任务覆盖可审计，一级分支可并行召回，叶节点可直接挂接证据 | 依赖角色与任务质量，框架构建包含多次生成、归并、修复和展开调用 |

本设计当前不宣称优于其他方案，只把它作为最值得优先验证的候选路径。

## 9 验证设计

### 9.1 独立样本原则

用于生成角色、主要任务、任务树和知识框架的输入，与最终测试问题必须分开。`c13-003` 可以用于召回和回答验证，但不能反向进入角色的知识框架生成、任务覆盖修复或叶节点标题设计。

运行时不得向召回模型提供答案组名称、隐藏金标准叶节点或预先整理好的答案维度。金标准只存在于隐藏 fixture、评测器和事后映射中。

### 9.2 Gate A：角色、主要任务与任务树

验证：

- 多轮角色候选能够通过归并和用户审核形成可区分角色；
- 确认角色后能够生成完整主要任务，并通过职责边界审核；
- 每个主要任务都能拆成可独立完成、可检查结果的任务树；
- 任务树根节点完整继承主要任务字段，没有改写或丢失；
- 完整任务树可以被用作知识框架覆盖审查锚点。

通过条件：角色、主要任务和任务树均有版本化审核记录，失败语义明确，未决项没有被静默删除。

### 9.3 Gate B：一级知识框架生成与归并

验证：

- 一级生成是否只输出一级知识范围，没有提前展开或生成任务动作；
- 多份候选是否覆盖角色的主要知识主干，并暴露低频有效范围；
- 归并是否支持同义合并、上下位收束、宽节点拆分和低频保留；
- `merge_ledger` 是否覆盖全部输入候选，是否有静默丢失；
- 同一输入重复运行是否出现不可解释的大幅分支波动；
- 结构失败、截断和非法字段是否显式失败。

数量、深度和跨次目录相似度只用于诊断，不作为唯一质量目标。通过条件是：结构合法、知识身份边界可解释、候选去向完整，并且没有已知阻断性重复或漏项。

### 9.4 Gate C：任务覆盖审查与 LLM 修复闭环

验证：

- 覆盖审查是否独立判断 `covered`、`partial`、`missing`；
- `matched_paths` 是否引用真实节点，`gap` 是否只描述缺失知识而不是任务步骤；
- LLM 修复是否保留已有节点 ID，并以完整框架返回修订；
- 修复后是否重新审查全部任务，而不是只复审原缺口；
- 是否区分没有变化、没有进展、迭代上限和调用失败；
- 是否出现灾难性节点膨胀、任务式节点或为了通过覆盖而堆砌宽泛分类。

通过条件是：所有任务达到 `covered`，或以明确失败状态保留未通过任务和证据。平均节点数、单轮时长和 token 只用于诊断，不参与“是否覆盖”的语义判定。

### 9.5 Gate D：一级分支展开

验证：

- 每个调用是否只展开一个冻结一级节点，且目标节点字段原样保留；
- 是否存在任务动作、交付物或实现步骤式知识节点；
- 同级节点是否有重复、同义或简单上下位重复；
- 对全部叶节点检查是否可脱离父路径独立识别，是否存在明显应继续拆分的复合叶节点；可以按批调用，但不能只用抽样结果代替全量门禁；
- 非叶节点是否有有意义的多个子节点；
- 子树是否侵入相邻一级分支；
- JSON 截断、字段缺失和非法节点是否显式失败。

通过条件是：所有一级分支完成结构校验，全部叶节点完成颗粒度审查，明显复合叶节点已经拆分或保留为有依据的显式例外，并且流程没有依赖模型一次生成整棵树。

### 9.6 Gate E：叶节点目录与证据挂接

叶节点目录必须从冻结框架确定性提取，包含稳定的 `leaf_id`、完整路径、标题、描述和排除边界。验证：

- 叶节点 ID 与路径唯一，父节点没有混入候选；
- 所有查询召回 ID 都能映射回当前框架版本；
- 原文证据只挂接叶节点，任何非叶节点的覆盖均由该节点所属的全部后代叶节点汇总得到；
- 一个 block 能挂接多个叶节点，没有按关键词强行唯一化；
- 非法 ID、无法定位的引文和越界字段显式失败；
- 证据挂接提示词与具体协议经负责人审核后，再做正式样本验证；
- 挂接质量按必挂召回率、硬负例误挂率、灰区支持率和灰区稳定性分别报告，不使用把灰区同时算作正负例的单一总体准确率掩盖边界样本。

证据挂接尚未完成协作设计，因此当前 Gate E 只确认目录和数据结构可支持后续验证，不宣称挂接质量已经验收。

### 9.7 Gate F：叶节点分支召回与回答闭环

验证：

- 每个一级分支是否独立调用，输入中没有其他分支结果；
- 是否只提供 `leaf_id`、完整路径和标题；
- `required` 是否覆盖问题核心答案面，`optional` 是否保留扩展线索；
- 金标准回答所需知识面的叶节点集合召回是否优先得到满足；冗余候选数量和 required 精确率只作为噪声与成本诊断，不能以漏掉必要知识面换取更高精确率；
- 空分支是否合法，非法 ID 和非法 tier 是否阻断；
- 三次重复运行的集合召回和稳定性是否可接受；不要求三次返回完全相同的节点集合，重点是金标准必要知识面没有因运行波动而漏掉；
- 召回叶节点是否能通过证据挂接找到支持原文；
- 最终进入回答上下文的金标准支持 block 是否完整，遗漏是否被主题外兜底发现；
- 主题外兜底是否找到未召回但仍相关的 block；
- 是否存在显著误支持或覆盖漏项；单条 evidence 的类型偏差不作为挂接门禁；
- 回答是否保留条件、例外、限制对象和来源。

Gate F 按“节点集合召回 → 可用证据召回 → 回答覆盖”分层判定。前一层通过不能替代后一层；最终回答漏掉任一明确答案方面都属于假完整，即使总体节点精确率或平均 F1 较高。当前 `c13-003` 三次回放的结果记录在 §6.7。该结果足以支持继续进入证据挂接，不继续以全局排序或 required 精确率优化作为主目标。

### 9.8 建议指标

- 一级分支覆盖主干率和低频有效范围保留率；
- 归并来源账本完整率、静默丢失数和错误合并数；
- 任务覆盖率：`covered` 任务占比，`partial` 不计为覆盖；
- 修复轮次、完整框架变化幅度和失败停止原因；
- 叶节点数量、深度分布、复合叶节点率和重复叶节点率；
- 单个一级分支召回成功率、空分支率和非法输出率；
- 查询期金标准必要知识面的叶节点集合召回率、漏项数、required 召回率、required 多次运行稳定率；
- required 精确率、optional 扩展率和多余叶节点数，只作为噪声与成本诊断；
- 按叶节点的可用证据召回率、最终回答证据召回率和假完整率；
- 必挂召回率（只统计 `direct_support`）、硬负例误挂率（只统计 `no_support`）、灰区支持率与灰区稳定性（只统计 `weak_support`）；
- 硬 F1（只使用 `direct_support` 与 `no_support`）、证据挂接率、主题外补充召回增量和最终假完整率。

这些指标按用途区分。节点数量、平均覆盖率、token 和延迟只能作为诊断，不得替代语义审核，也不能为了让单个固定样本通过而调整。

### 9.9 `c13-003` 专项验证

`c13-003` 用于验证跨分支求全召回和后续证据闭环。当前问题为：

```text
除了沙箱、虚拟机和出口控制，AI Agent 还有哪些隔离或控制边界？请分别说明各限制什么。
```

验证重点不是要求返回某个固定节点集合，而是：

1. 多个一级分支能够返回不同的隔离或控制边界；
2. `required`／`optional` 能帮助后续证据读取确定优先级；
3. 上下文与记忆生命周期等边界即使被标成 `optional`，仍能在扩展证据阶段参与复核；
4. 主题外兜底能够发现没有被叶节点召回覆盖的相关原文；
5. 最终回答不是只有机制清单，还应说明各自限制什么；
6. 评测器在事后把叶节点映射到隐藏答案组，运行时输入不包含答案组名称。

### 9.10 总体闭环与显著提升判定

`c13-003` 是角色知识框架、叶节点召回、原文证据挂接和回答链路的总闭环验收点，不作为单个组件的替代指标。判断整条路径是否相对既有检索基线取得显著提升时，必须固定 snapshot、知识框架、地图、Profile、模型、提示词、上下文预算和用例 revision，在同一组隐藏金标准上比较核心证据覆盖、指定 block 召回、精确率、无关 token、最终回答假完整率、硬失败、token 与延迟。任何上游节点数量、Wiki 主题数量或召回候选数量都不能单独证明显著提升；只有最终可用证据和回答覆盖改善且噪声、成本未出现不可接受退化时，才能把该次结果称为闭环提升。

## 10 风险与被推翻条件

### 10.1 主要风险

- LLM 枚举的角色集中在常见职业，遗漏非典型但真实的知识使用方式；
- 候选阶段要求同时穷尽每个角色的职责，导致模型按固定任务数输出模板化角色；
- 两到四项区分性任务不足以区分职责相近的角色，导致归并阶段误合并；
- 把区分性任务直接当作完整主要任务，导致任务树漏掉职业原型职责；
- 角色划分过粗，任务树混合多个独立职责；
- 角色划分过细，主题生成和检索成本大幅上升；
- 任务拆分停在抽象岗位描述，无法用于覆盖审查；
- 知识主题范围过度泛化，角色知识框架变成通用分类目录；
- 知识主题仍隐含角色或任务路径，导致使用方式变化时结构脆弱；
- 不同角色生成大量近义知识框架，增加重复挂接和检索；
- 多轮候选归并静默丢失低频但有价值的知识范围；
- 任务覆盖审查把任务名称机械复制成知识节点，或修复器为了通过审查堆砌宽泛分类；
- 一级分支展开时产生任务动作、空泛容器或复合叶节点；
- 把单次叶节点未命中当作知识框架缺失，导致查询噪声被固化为知识结构；
- 未审核反馈直接修改活动知识框架，造成版本漂移和历史结果不可复现；
- 评测问题反向进入生成链路，造成评测污染和虚假提升；
- 把叶节点召回当作内容边界，漏掉没有挂接或没有叶节点匹配的相关 block；
- 把主 Agent 查询时临时形成的覆盖清单当成知识库内容已经全部召回的证明；
- block 挂接只按关键词匹配，丢失隐含表达；
- 叶节点 `description` 不足以独立表达语义，系统又通过单例特例补洞，造成路由偏差和过拟合；
- 真实复合问题被错误拆成多个互不相关的叶节点，最终回答失去统一综合入口；
- 综合页比原文流畅，但事实性或条件完整性下降；
- 主 Agent 过早相信单个一级分支，漏掉跨分支证据；
- 当前快照为空的合理叶节点被误删除；
- 把 GraphRAG 的 persona 机制误当作角色目录机制，导致错误类推。

### 10.2 设计被推翻或调整的条件

出现以下证据时，应调整或否决本设计：

- 角色和任务生成高度同质，不能提供比普通主题检索更好的覆盖；
- 人工审核无法形成稳定、可区分的任务树和知识框架；
- 知识框架生成大量依赖角色名称，无法形成领域可复用节点；
- 证据挂接召回或精度显著低于现有关系轴方案；
- 动态扩展无法识别单分支缺口，假完整率不可接受；
- 为维持覆盖需要持续编写大量个案规则，收益低于维护成本；
- 任务覆盖闭环长期无法收敛，或只能通过大量节点膨胀和任务式节点通过；
- 逐分支召回无法发现跨分支边界，且主题外兜底持续承担主要召回；
- 完整框架和逐分支调用成本超过其覆盖与可解释收益。
