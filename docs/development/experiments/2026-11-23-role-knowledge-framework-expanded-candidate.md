# 角色知识框架展开与架构师覆盖候选实验

- 状态：探索中，待人工审核
- 日期：2026-11-23
- 领域：AI Agent
- 角色：系统架构师
- 后续方向：首版不预生成持久化跨分支导航容器，先验证查询期跨分支路由，并用真实 trace 驱动版本化演进
- 关联设计：[16 · 使用角色驱动的领域知识组织](../../design/16-使用角色驱动的领域知识组织.md#4b-角色知识框架驱动的知识组织探索候选)

## 1. 结论

本轮不再把“多轮生成后收敛为唯一稳定目录”作为目标。实验目标是找到一个同时满足以下条件的工作候选：

1. 知识范围已经展开到可检索层级；
2. 能覆盖系统架构师已审核主要任务的绝大部分领域知识；
3. 查询时能够从少量主路径路由到具体知识节点；
4. 允许其他合法组织方式存在，不追求跨次标题一致。

当前 449 节点版本是手工补丁候选，不是可接受的自动修复产物：它以第二版展开结果中的 415 节点框架为底稿，再由实验助手手工编写六组子树并交给一次性脚本应用。这些子树不是 LLM 修复生成结果；实验中没有产生可审查的“候选分支”，也不存在“人工复核补丁”。两次独立 LLM 覆盖审计都判定 13 项已审核主要任务全部覆盖；11 个代表性问题的目录路由分别为 11/11 和 10/11，唯一一次 `ambiguous` 出现在跨分支的“工程方法论”问题上。

这个结果支持把该版本作为**工作候选**继续做证据编译和查询实验，但还不能证明：

- 它已经覆盖 AI Agent 架构师的全部知识；
- 它比其他合法组织框架更接近唯一正确目录；
- 它已经覆盖当前 15 篇知识库中的全部可回答问题；
- LLM 覆盖审计可以替代人工领域判断。

## 2. 实验边界

框架生成输入只有：

```text
领域：
AI Agent

角色：
系统架构师
```

没有输入：

- 当前知识库文档或标题；
- 架构师完整任务树；
- 测试问题或金标准答案；
- `prior_knowledge`；
- 已生成框架的归并结果。

任务和测试问题只用于生成后的独立审计，不参与首轮框架生成。这样可以把“框架本身的领域组织能力”和“任务查漏补缺能力”分开观察。

固定配置：

| 项目 | 值 |
| --- | --- |
| 模型 | `deepseek-flash` |
| temperature | `0` |
| thinking | 开启 |
| 最大输出 | 60,000 tokens |
| 生成提示词版本 | `v2-expanded` |

## 3. 展开前后结果

### 3.1 首版三层约束不足

最初三次独立生成都只达到深度 2：

| 运行 | 一级分支 | 总节点 | 叶节点 | 最大深度 |
| --- | ---: | ---: | ---: | ---: |
| 运行 1 | 12 | 88 | 76 | 2 |
| 运行 2 | 15 | 106 | 91 | 2 |
| 运行 3 | 14 | 119 | 105 | 2 |

语义覆盖基本稳定，但大量叶节点仍是“知识库与检索增强架构”“失败处理、重试与补偿”“弹性、容错与限流”这类复合知识范围。它们可以用于人工阅读，却不足以直接承担检索路由与证据覆盖判断。

### 3.2 强制展开后

第二版提示词增加了以下主要契约：

- 叶节点必须是单一、可直接检索并独立判断证据覆盖的知识主题；
- 节点只要包含两个或更多可分别命名、检索或判断覆盖的范围，就必须继续展开；
- 叶节点不能把多个并列范围用“与”、顿号等方式合并；
- 整套框架至少三层。

| 展开运行 | 一级分支 | 总节点 | 叶节点 | 最大深度 | 输出 tokens | 耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 展开运行 1 | 13 | 415 | 334 | 3 | 20,996 | 99.3 秒 |
| 展开运行 2 | 13 | 546 | 447 | 3 | 40,237 | 139.9 秒 |

结论不是“节点越多越好”。两次展开证明复合节点可以继续打开，但也显示生成规模会从约 100 节点跃升到 400～550 节点，因此需要后续的任务覆盖与路由审计来约束真实需要。

## 4. 为什么选择 415 节点版本

两套展开框架在任务覆盖和目录路由上各有强弱，没有哪一套在所有指标上占优：

| 版本 | 节点 | 初始覆盖审计 | 初始代表性查询路由 | 主要问题 |
| --- | ---: | --- | --- | --- |
| 415 节点版本 | 更小 | 10 项覆盖、3 项部分覆盖 | 7 项路由、1 项含糊 | 工具调用网关、架构治理、跨团队交接缺口明确 |
| 546 节点版本 | 更大 | 11 项覆盖、1 项部分、1 项缺失 | 7 项路由、1 项缺失 | 跨团队交接没有主路径；整体规模更大 |

选择 415 节点版本作为工作底稿的理由是：

1. 它的输入和输出成本约为另一版本的一半；
2. 初始代表性查询路由没有比另一版本更差；
3. 已有“企业架构与落地治理”主分支，适合承载架构治理、需求基线、跨团队交接等架构师专有知识；
4. 缺口集中且可以解释，适合验证“任务查漏补缺”机制；
5. 组织方式本来不要求唯一，选择更小且结构可修补的版本比继续寻找“最佳一次”更有工程价值。

### 5.2 实验助手手工补丁（错误路径证据）

以下六组子树不是任何正式上游阶段的产物。审计器只输出失败任务、命中路径、理由和 `gap` 文本；实验助手随后越过修复生成和独立审查，自行判断知识分类和挂接位置，把整棵子树直接写进一次性脚本。没有修复提示词、修复生成输出、独立审查结果或人工复核记录；系统中也从未存在“候选分支”或“人工复核补丁”。它们只能作为观察结构变化对覆盖和路由影响的错误路径样本，不能视为自动修复能力证据：

| 实验助手硬编码子树 | 声称解决的缺口 | 实验助手给出的放置理由 |
| --- | --- | --- |
| 架构需求与质量属性基线 | 原框架只有分散的质量指标，没有需求范围、质量场景、验收阈值和需求追踪主路径 | 属于企业级架构治理的前置输入 |
| 系统蓝图与组件契约建模 | 原框架有架构风格，却没有组件职责、数据所有权、控制/数据流和接口契约的统一入口 | 属于总体架构蓝图，不归入某个具体架构风格 |
| 工具注册、发现与调用网关 | 原框架有工具契约和沙箱，但缺少注册发现、统一网关、副作用分级、配额和重复调用防护 | 是工具行动与外部集成中的控制面 |
| 多步失败恢复与补偿编排 | 原框架有重试、幂等和降级，但缺少部分成功、连锁失败、补偿回退和恢复一致性 | 属于可靠性工程中的多步副作用问题 |
| 架构决策与演进治理 | 原框架有架构评审和版本治理，但没有 ADR、假设/风险、变更影响、例外和技术债 | 是从“评审活动”到“可追踪治理机制”的补齐 |
| 跨团队架构对齐与设计交接 | 原框架没有设计交接、咨询/例外入口和实施反馈闭环 | 属于架构落地治理中的组织协同范围 |

## 6. 覆盖审计

### 6.1 审计方法

使用已审核的 13 项 AI Agent 系统架构师主要任务作为任务侧基线。模型同时看到：

- 任务及其完成条件、包含范围和排除边界；
- 候选框架中全部节点的完整路径、描述和排除边界。

模型对每项任务输出：

- `covered｜partial｜missing`；
- `easy｜moderate｜hard` 检索可达性；
- 逐字引用框架路径；
- 覆盖理由与具体缺口。

本轮没有审计任务树下级节点。当前 13 个根任务中只有 `decision_loop_control_architecture` 具备当前契约下的任务树，旧产物的任务键和字段契约不一致，不能拿来补做本轮审计。因此下文的 `13/13 covered` 只表示 13 个根任务在当前审计判定下可由框架支持，不能表述为完整任务树覆盖。

覆盖定义是“存在清楚可达且包含任务核心知识对象、边界和关键类别的主路径”，不是要求框架代替架构师完成任务。

### 6.2 结果

最终候选连续执行两次独立审计：

| 审计 | 覆盖结果 | 检索可达性 | 输出 tokens |
| --- | --- | --- | ---: |
| 审计 1 | 13/13 覆盖 | 10 项 easy、3 项 moderate | 10,909 |
| 审计 2 | 13/13 覆盖 | 11 项 easy、2 项 moderate | 6,748 |

两项核心架构任务的最终路由已经收敛到单一主路径：

| 任务 | 路由结果 |
| --- | --- |
| 架构需求与质量属性基线 | `企业架构与落地治理 / 架构需求与质量属性基线` |
| 总体架构蓝图与组件契约 | `Agent体系结构与设计模式 / 系统蓝图与组件契约建模` |

这比补丁前依赖多个分散分支拼接更适合检索。补丁前，第一项在第一套框架中被判 `covered/moderate`，但匹配了 9 条分散路径；第二项同样被判 `covered/moderate`，匹配了 9 条分散路径。主路径建立后，检索判断不再需要先猜测这些分散知识如何组合。

## 7. 查询路由审计

### 7.1 问题集

使用 11 个代表性问题，覆盖架构师框架的宽、窄与横切查询：

1. 架构需求和质量属性场景如何定义；
2. 如何描述总体架构、组件职责、数据所有权和控制/数据流；
3. AI Agent 工程方法论有哪些；
4. AI Agent 中的隔离和控制边界有哪些；
5. 决策循环状态及转移条件；
6. 上下文将满时如何压缩、摘要和检索；
7. 工具调用的最小权限、沙箱和人工审批；
8. 提示注入下的信任边界与防护机制；
9. 多 Agent 职责、协作和失败隔离；
10. 任务成功率、时延、安全性和成本如何评测；
11. 架构决策记录、风险验证、变更评审和技术债如何治理。

### 7.2 结果

| 问题 | 审计 1 | 审计 2 |
| --- | --- | --- |
| 架构需求与质量属性 | routed，3 条路径 | routed，1 条路径 |
| 总体架构蓝图 | routed，4 条路径 | routed，1 条路径 |
| 工程方法论 | routed，8 条路径 | ambiguous，只定位到提示工程和工程成熟度 |
| 隔离和控制边界 | routed，5 条路径 | routed，5 条路径 |
| 决策循环 | routed，7 条路径 | routed，4 条路径 |
| 上下文压缩与检索 | routed，7 条路径 | routed，3 条路径 |
| 工具权限与沙箱 | routed，7 条路径 | routed，5 条路径 |
| 提示注入 | routed，6 条路径 | routed，5 条路径 |
| 多 Agent | routed，8 条路径 | routed，4 条路径 |
| 评测 | routed，5 条路径 | routed，4 条路径 |
| 架构治理 | routed，5 条路径 | routed，4 条路径 |

对于“AI Agent 中的隔离和控制边界”，两次审计都稳定选择了五类入口：

- 工具行动与外部集成 / 执行环境；
- 安全对齐与治理 / 权限与访问控制；
- Agent体系结构与设计模式 / 分层Agent架构 / 治理层；
- 安全对齐与治理 / 对齐与行为约束 / 安全护栏；
- 多Agent系统 / 多Agent安全与评测 / Agent权限隔离。

这说明框架没有把“隔离”误锁成单一安全主题，也没有因为找不到一个名为“隔离”的节点而失败；它可以接受“隔离”是跨多个知识分支的跨切面语义。

## 8. 关键问题审查

### 8.1 展开是必要的，但不能把叶节点数量当目标

深度 2 的结果语义上像一份目录，深度 3～4 之后才具备具体路由入口。反过来，415 与 546 节点版本比较也说明：更多节点不一定带来更高覆盖，反而会扩大上下文与路由候选。

判断展开是否足够的标准应是：

1. 叶节点是否对应单一可检索知识范围；
2. 任务是否能够到达具体知识而不是停在宽泛一级分支；
3. 继续拆分的子范围是否真的能分别承载证据。

### 8.2 任务覆盖审计能发现结构缺口，但会波动

同一框架在不同轮审计中对“多步失败恢复”出现过一次 `covered`、一次 `partial`。实验助手回看任务语义后，把补偿与回退编排手工加入了脚本。这属于已否决的修复方式，只能说明：

- 不能让单次 `covered` 直接冻结框架；
- 审计分歧应回到任务完成条件和节点边界，而不是直接投票；
- 正式流程应由多次独立审计、独立的 LLM 修复审查和自动仲裁处理分歧，不能把人工抽查当作规模化兜底。

### 8.3 审计“覆盖”不等于框架里有一个同名节点

补丁前的总体蓝图任务可以通过多个领域节点组合回答，所以被判为覆盖；但对检索来说，这种覆盖需要主 Agent 先知道要跨 9 条路径拼接。建立 `系统蓝图与组件契约建模` 主路径后，领域覆盖没有增加很多全新知识，检索稳定性却明显提高。

这说明框架评价至少有两个维度：

- 领域内容是否存在；
- 是否提供了清楚、低成本、可解释的检索入口。

### 8.4 “工程方法论”暴露了纯树结构的限制

“AI Agent 的工程方法论都有哪些”是典型的横切问题。相关方法分散在提示工程、推理策略、上下文管理、RAG、工具调用、规划、评测、架构模式等分支中。严格树只能：

- 让查询路由到多个分支，再由主 Agent 汇总；
- 或新增一个与其他分支重叠的“工程方法论索引”节点；
- 或允许导航容器通过引用连接多个既有一级分支，而不复制知识身份。

本轮没有为通过这个问题而新增重复节点。后续讨论确认：首版先不预生成持久化导航容器，而是允许主 Agent 仅依据现有知识框架选择多个分支、逐层展开并执行主题外兜底；真实 trace 中同类访问意图重复出现且形成稳定路由缺口后，再决定调整知识树或物化只引用既有主题的导航视图。

### 8.5 目录规模与路由成本还没有达到生产结论

把全部 449 个节点连同描述送入一次评审，覆盖审计约使用 23.6k 输入 tokens，查询路由约使用 20.4k 输入 tokens。对云端模型可以运行，但不能直接作为每次查询的默认成本。

候选查询方式应是分层路由：

1. 先用 13 个一级分支选择知识域；
2. 再展开选中分支的二级节点；
3. 最后读取必要叶子与证据。

分层路由是否损失召回、跨分支问题是否会被过早剪枝，尚未验证。

### 8.6 叶节点边界仍不完整

449 节点中 334 个原始叶节点的 `exclusions` 为空。描述提供了主要边界，但在相邻主题高度接近时，仍未系统记录“什么不属于我”。当前实验没有因此产生块级证据挂接，但进入编译阶段后，可能出现同一 block 在相邻叶子间反复摇摆。

### 8.7 标题并非唯一身份

候选中仍有一个重复标题“Agent身份认证”出现在两个路径下。路径可以区分身份，但标题级检索和多路径返回需要显式带路径，不能只返回标题。

## 9. 需要设计决定的问题

| 问题 | 当前建议 | 理由 |
| --- | --- | --- |
| 是否接受 449 节点候选作为架构师工作底稿 | 不建议 | 该版本由实验助手手工加入子树，不能证明自动修复能力；两次根任务覆盖审计只作为结构变化观察，不能替代 LLM 修复闭环 |
| 是否继续追求跨次唯一稳定的目录 | 不建议 | 组织方式天然多样，目标是检索可用和覆盖充分 |
| 是否首版预生成跨分支导航容器 | 建议首版不做；先验证查询期跨分支路由，并用 trace 驱动离线演进 | “工程方法论”等问题横跨多个一级分支，但预生成容易形成空泛索引和重复节点 |
| 是否要求每个叶节点都有排除边界 | 建议至少对相邻易混主题强制要求 | 当前 334 个叶节点无排除边界，进入证据挂接前风险较高 |
| 任务覆盖审计是否由一次判断生效 | 不建议 | 已观察到同一版本出现一次覆盖、一次部分覆盖；应由多次独立审计、独立 LLM 复审和自动仲裁消除分歧 |
| 是否马上执行全目录路由优化 | 暂不建议 | 先验证分层路由和跨分支导航容器，再决定是否压缩目录 |

## 10. 当前建议

保留原始 415 节点版本作为自动修复实验的固定输入。449 节点手动补丁版本只保留为错误路径对照，不直接作为下一轮证据编译和查询实验的工作底稿；只有通过 LLM 修复生成、独立 LLM 审查、确定性应用和全任务重新审计的新版本才进入候选。

下一步应按以下顺序进行：

1. 实现 LLM 修复生成器、独立修复审查器和确定性应用器；任务覆盖失败后自动生成并应用结构化更新，不再由实验助手或人工编写补丁分支；
2. 验证查询期跨分支路由；首版不预生成持久化导航容器，真实 trace 重复暴露稳定缺口后再做版本化评审；
3. 对相邻和高风险叶节点补充排除边界；
4. 在固定 15 篇知识库快照上做节点到 block 的证据挂接；
5. 用 `c13-003` 和至少一个不参与调参的任务问题验证“一级路由 → 二级展开 → 叶子证据”的完整链路；
6. 再评估 449 节点是否过大，而不是提前按固定节点数裁枝。
