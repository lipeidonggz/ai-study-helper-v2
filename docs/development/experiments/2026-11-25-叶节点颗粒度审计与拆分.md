- 状态：BR-1 至 BR-9 已完成；已确认 b00008 不挂接 BR-8 的任一候选叶节点
- 日期：2026-11-25
- 关联设计：[16 使用角色驱动的领域知识组织](../../design/16-使用角色驱动的领域知识组织.md)
- 关联实验：[知识库证据挂接实验](2026-11-24-知识库证据挂接.md)

## 1 实验目的

前序实验已经证明，冻结角色知识框架后，单叶证据挂接能够完成大部分支持判定，但知识框架本身仍可能留下复合叶节点。复合叶节点会让“支持其中一部分”被错误当成“支持整个知识身份”，也会降低检索命中后的证据完整性。

本实验检查展开后的叶节点是否仍包含两个或更多可分别命名、分别检索的知识身份，并在需要时直接生成可替换的子树。首轮只处理 `K21` 一个一级分支，不扩展到全部 620 个叶节点。

本实验不重新设计一级目录，不修改一级、二级非叶节点，不改证据挂接提示词，也不把一次模型输出直接视为正确知识。重点回答四个问题：

1. 一次输入一个完整一级分支，模型能否覆盖并审计全部现有叶节点；
2. 模型能否同时识别真实复合叶节点和避免机械拆分单一知识身份；
3. 直接返回替换子树，是否比先逐叶判断、再另行生成子树更稳定和更省调用；
4. 如果一支一批仍不稳定，失败来自分支规模、输入信息不足、拆分判据，还是模型本身。

## 3 实验边界

### 3.1 本轮做什么

- 每次输入一个完整一级分支；
- 只审计该分支当前的叶节点；
- 每个现有叶节点得到一个 `keep` 或 `split` 决定；
- `split` 在同一输出中返回完整替换子树；
- 由宿主检查结构、覆盖、路径和节点数量，不直接接受模型输出；
- 首轮只处理 `K21`，结果稳定后再设计其他一级分支的批次。

### 3.2 本轮不做什么

- 不逐叶调用，也不先做 `keep / split / uncertain` 两阶段；
- 不在这一轮重新生成一级目录或修改非叶节点；
- 不把模型新建的子树直接写回正式知识森林；
- 不用 `K21.06.04`、证据挂接、审批或安全样本给模型提示；
- 不以节点增加数量判断拆分成功，也不以固定叶节点数为目标；
- 不在只有 `K21` 单分支证据时宣称全目录审计协议成立。

`uncertain` 不作为模型可返回的第三态。模型必须在 `keep` 与 `split` 中选择；结构非法、调用失败、无法覆盖全部叶节点或人工无法确认语义时，由宿主记为未决，不能默认 `keep` 通过。

## 4 调用契约

### 4.1 模型配置

首轮计划配置如下，实际运行值必须在产物 manifest 中记录：

| 配置 | 计划值 |
| --- | --- |
| 模型 | `deepseek-flash` |
| thinking | 关闭 |
| temperature | `0.0` |
| 最大输出 token | `16384` |
| 最大并发 | `1` |
| 单次超时 | `180s` |
| 首次运行次数 | 1 |
| 稳定性回放触发条件 | 首次结构合法且人工未发现系统性粒度错误后，再跑 3 次 |

### 4.2 输入结构

每次调用序列化以下对象。除字段名和结构用例外，不向提示词加入任何领域特定节点示例。

```json
{
  "domain_name": "AI Agent",
  "role_name": "系统架构师",
  "framework_scope": "该岗位角色在领域中有效履行职责所需掌握的知识范围",
  "first_level_directory": [
    {
      "node_id": "一级节点ID",
      "title": "一级节点标题"
    }
  ],
  "target_branch": {
    "node_id": "本次审计的一级节点ID",
    "title": "标题",
    "description": "描述",
    "exclusions": [],
    "children": []
  }
}
```

`target_branch` 必须包含完整当前子树，不能只传叶标题。`first_level_directory` 只提供全部一级节点 ID 和标题，用于识别当前分支与相邻一级范围的边界。

### 4.3 输出结构

模型只输出一个 JSON 对象：

```json
{
  "branch_id": "本次输入的一级节点ID",
  "decisions": [
    {
      "leaf_node_id": "当前叶节点ID",
      "action": "keep",
      "reason": "一句话说明为何该范围只包含一个知识身份",
      "replacement_children": []
    },
    {
      "leaf_node_id": "另一个当前叶节点ID",
      "action": "split",
      "reason": "一句话说明为何其中包含多个可独立检索的知识身份",
      "replacement_children": [
        {
          "title": "替换子树直接子节点标题",
          "description": "该知识范围的内容与边界",
          "exclusions": [],
          "children": []
        }
      ]
    }
  ]
}
```

替换节点只返回 `title`、`description`、`exclusions`、`children`。节点 ID 与完整路径由宿主按原树路径重新分配。模型不得为替换节点编造 ID，也不得修改原叶节点的 `title`、`description` 和 `exclusions`；原叶节点只在应用结果后获得新的子节点。

## 5 审计与拆分提示词

状态：待负责人审核。审核通过前不得调用模型。

### 5.1 系统提示词

```text
你是一位知识节点颗粒度审计专家。

给定一个领域、一个岗位角色、整套一级知识目录，以及其中一个一级分支的完整
知识树，请只审计该分支当前的叶节点，并直接返回每个叶节点应保持还是应拆分的
决定。对需要拆分的叶节点，同时生成可替换其叶节点身份的完整下级子树。

【输入】
- domain_name：领域名称；
- role_name：岗位角色名称；
- framework_scope：该岗位角色在领域中需要掌握的知识范围；
- first_level_directory：全部一级节点的 node_id 与 title；
- target_branch：本次待审计的一级分支完整子树。

【审计范围】
1. 只审计 target_branch 中 children 为空的当前叶节点。
2. 每个当前叶节点必须且只能出现一次决定，顺序与输入树中的遍历顺序一致。
3. 不属于当前叶节点的节点不输出决定，也不得修改其标题、描述和排除项。
4. 不重新划分一级目录，不重命名原叶节点，不改变已有父子关系。
5. first_level_directory 只用于识别当前分支与其他一级范围的边界。

【知识身份判据】
1. 不使用固定深度，也不追求绝对逻辑原子。
2. 一个知识身份应能脱离父路径独立命名，并可作为独立知识节点被检索。
3. 如果一个范围包含两个或更多可以分别命名、分别检索的知识身份，应继续拆分为
   子节点。
4. 如果内部内容只是同一知识身份的定义、范围、作用、边界、条件、代价等属性，
   不应拆成兄弟节点，而应写入该节点的 description。
5. 不同分支可以根据实际知识结构使用不同深度。
6. 一个知识对象只回答一个主问题；同一主问题下的维度、指标、条件、方法和示例
   属于该知识身份，并列的不同判断目标必须拆为不同叶节点。

【替换子树要求】
1. split 时，replacement_children 是该原叶节点的直接下级子树，不是新的
   一级或二级节点。
2. replacement_children 至少包含两个节点。若只能形成一个新节点，应保留原叶
   节点并输出 keep。
3. 每个新节点只包含 title、description、exclusions、children 四个字段。
4. title 必须脱离父路径仍可独立识别知识范围；不得使用“概述”“相关内容”
   “其他知识”等无法定位的标题。
5. description 直接说明该范围包含什么知识、主要边界是什么，不得用学习任务或
   执行动作代替知识内容。
6. exclusions 只记录确实容易与该节点混淆但不属于它的相邻知识；没有这种边界
   时返回空数组，不得为了填充而编造排除项。
7. 替换子树共同覆盖原叶节点承诺的知识范围，既不能漏掉原范围中的主要知识，
   也不能把范围外知识塞入。
8. 任何带 children 的新节点至少有两个直接子节点。没有子节点的节点必须返回
   children: []。
9. 同一替换子树中不得出现重复标题、仅更换措辞的同义节点，或父子范围倒置。

【输出要求】
1. 只输出一个符合输出契约的 JSON，不输出 Markdown、解释或额外文字。
2. branch_id 必须与 target_branch.node_id 逐字一致。
3. decisions 必须覆盖全部当前叶节点，不得遗漏、重复或加入未知 node_id。
4. action 只能是 keep 或 split。
5. keep 时 replacement_children 必须为空数组。
6. split 时 replacement_children 必须是至少包含两个节点的有效子树数组。
7. reason 用一句话说明触发 keep 或 split 的主要依据，不展开分析过程。
8. 字符串必须使用合法 JSON 转义；不得输出注释、尾逗号或额外字段。

【输出契约】
{
  "branch_id": "输入中的 target_branch.node_id",
  "decisions": [
    {
      "leaf_node_id": "输入中的当前叶节点 node_id",
      "action": "keep 或 split",
      "reason": "一句话依据",
      "replacement_children": [
        {
          "title": "直接下级知识范围标题",
          "description": "该知识范围的内容与边界",
          "exclusions": [],
          "children": []
        }
      ]
    }
  ]
}
```

### 5.2 提示词设计约束

- 不出现 `K21`、`K21.06.04`、成熟度、审批、沙箱、证据挂接或其他测试样本；
- 不把“必须拆分某个复合节点”写成提示，避免用目标样本调参；
- 本轮逐字复用一级分支展开提示词的“叶节点判定”，不额外加入“判断证据覆盖”
  等审计专属条件，先验证同一判据在不同调用边界下是否一致；
- 把定义、范围、属性、条件等明确留在 `description`，抑制属性级碎拆；
- 用“至少两个子节点”抑制无意义容器，而不是限制整棵树的最大深度或节点数；
- 要求逐叶覆盖，避免分支级调用只挑少数显眼节点处理。

## 6 宿主校验

模型输出不能直接修改知识森林。宿主至少执行以下检查：

| 检查 | 失败语义 |
| --- | --- |
| JSON 可解析且只含约定字段 | 本次运行结构失败 |
| `branch_id` 与输入根 ID 一致 | 拒绝整份结果 |
| 决定集合与 28 个当前叶节点一一对应 | 缺失、重复或未知 ID 均为失败 |
| `keep` 的替换子树为空 | 拒绝该决定 |
| `split` 的替换子树至少两个直接子节点 | 拒绝该决定 |
| 新节点字段完整，空排除项合法 | 拒绝该决定 |
| 新非叶节点至少两个子节点 | 拒绝该决定 |
| 新子树无空标题、空描述、重复标题和父子倒置 | 拒绝该决定 |
| 非叶原节点、根节点和原叶节点字段未被改写 | 拒绝整份结果 |
| 没有截断、额外 Markdown 或额外字段 | 本次运行结构失败 |

宿主应用 `split` 时，原叶节点保留原 `node_id`、`title`、`description` 和 `exclusions`，新子节点路径按原路径递归追加新序号。路径分配、重试和写回均不属于本实验首轮范围。

## 7 评估指标

### 7.1 机械指标

| 指标 | 定义 |
| --- | --- |
| 叶节点决定覆盖率 | 唯一且有效的叶节点决定数 / 28 |
| 结构合法率 | 通过全部宿主结构检查的运行数 / 总运行数 |
| 非叶节点稳定率 | 未被改写的原有非叶节点数 / 8 |
| 拆分叶节点数 | `split` 的原叶节点数 |
| 新增叶节点数 | 应用替换子树后新增的叶节点总数 |
| 新增最大深度 | 替换子树相对原叶节点增加的最大层级 |
| 调用成本 | 输入 token、输出 token、缓存命中 token 与实际耗时 |
| 原始产物完整性 | 请求、返回、解析结果和错误均落盘 |

### 7.2 语义指标

| 指标 | 定义 |
| --- | --- |
| 应拆漏拆 | 人工复核确认包含多个独立知识身份，但模型返回 `keep` 的原叶节点数 |
| 过度拆分 | 原叶节点只含一个知识身份，或被拆成属性、执行步骤、测试题粒度的数量 |
| 错拆边界 | 新子节点越过原叶节点范围，或与其他分支已有知识身份直接冲突的数量 |
| 子树覆盖 | 替换子树是否共同覆盖原范围的主要知识内容 |
| 边界清晰度 | 新兄弟节点能否仅凭标题和描述区分 |
| 可检索性 | 每个新叶节点能否被一个自然领域问题直接命中，而不是必须依赖父路径补全语义 |

首轮没有完整的 28 叶人工金标准，因此不预先报告“拆分准确率”。`K21.06.04` 只用于定向复核，其他拆分按候选逐项核对。只有在负责人确认一组固定应拆、不应拆样本后，后续运行才能计算稳定口径的召回率或精确率。
