## 1 实验目标

本实验用于反复校准“冻结知识框架之后，如何判断一段知识库原文是否能够支持某个叶节点”的挂接协议。实验对象包括候选叶节点的输入方式、支持判定、理由与引文输出、宿主校验、重试与残差处理，以及文档或框架变化后的局部重算语义。

本实验不重新生成知识框架，也不把检索召回结果当作证据挂接结果。需要分别回答两个问题：

1. 这段原文能否直接支持该叶节点所表示的知识范围；
2. 当前知识库中是否还存在能够支持该叶节点但尚未挂接的其他原文。

第 1 个问题属于证据挂接；第 2 个问题属于覆盖复核。任何一次模型调用都不能单独证明叶节点已经获得完整覆盖。

### 2.1 英文原文

```text
Claude Code runs on a user's machine and has access to their filesystem, shell, and network. Without this, coding agents have limited usefulness, so it’s imperative to find a way to grant that access safely.
One approach is to rely on a human-in-the-loop. This is only a tractable solution for Claude Code because the average user is a developer who’s familiar with coding environments: they can read bash, they understand what rm -rf does, and they already run npm install from untrusted sources several times a week. All that means that when an “allow this” dialog pops up, they are highly likely to have the expertise to accurately evaluate what the agent is attempting to do and the risk involved. Given this, Claude Code launched with the simplest possible defense: allow reads, require approval for write, bash, and network access.
However, as mentioned, approval fatigue showed up within weeks. Ironically, this meant that a feature originally designed to provide oversight could arguably have the opposite effect—some users might simply stop paying attention. As a first step to mitigate incautious approvals, we shipped an OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) that hardens the boundary: reads are allowed, writes are allowed inside the workspace, but network is denied by default. Within the sandbox, the agent runs largely without interruption. The result was an 84% reduction in permission prompts, and we open-sourced the runtime, so the boundary is auditable.
```

## 4 迭代规则

### 4.1 一次只验证一个主要变量

每个实验轮次先写清要推翻或验证的假设，再执行回放。提示词、候选目录、输入上下文、输出结构、模型配置和运行次数都属于变量；同一轮不得同时修改多个互相纠缠的主要变量。确需同时修改时，必须拆成可辨识的对照组。

### 4.2 多次独立回放

默认每个配置并行运行 3 次，用于观察集合与理由的基本波动；当某个叶节点的挂接结论在 3 次之间不稳定，或准备据此固化规则时，扩展到 10 次。次数变化必须记录原因，不能只保留最终挑选的一次结果。

### 4.3 逐项而不是整体判断

每次回放至少记录：

- 模型选择了哪些叶节点；
- 对每个叶节点给出的理由和引文；
- 宿主判定为正确支持、误挂、漏挂、待定还是无证据；
- 判定依据来自原文哪一句；
- 同一叶节点跨运行是否稳定。

不能只比较“这次选了 17 个、上次选了 18 个”。多一个节点可能是合理扩展，也可能是误挂；少一个节点可能是已找全，也可能是漏挂，必须逐项查看。

### 4.4 结论进入设计的门禁

实验结果先记录在本文件中，只有经负责人确认的协议判断才写入设计文档。单次运行、单个叶节点或单个 block 上偶然正确，不算门禁通过。

#### E-1.1 输入与输出契约

每次调用只序列化一个 block 和一个叶节点：

```json
{
  "block": {
    "section_path": [
      "How we contain Claude across products",
      "Patterns for containing agents",
      "Pattern 2: The human-in-the-loop sandbox (Claude Code)"
    ],
    "text": "完整英文原文"
  },
  "leaf": {
    "path": ["一级节点", "二级节点", "叶节点"],
    "title": "叶节点标题",
    "description": "叶节点完整描述",
    "exclusions": ["排除项"]
  }
}
```

`block_id` 和 `leaf_id` 由宿主在调用之外绑定和保存，不提供给模型。一次调用已经只有一个 block 和一个叶节点，模型不需要使用数据库标识完成判断。

支持时输出为：

```json
{
  "is_supported": true,
  "evidence": [
    {
      "quote": "从 block.text 中逐字复制的连续原文",
      "support_types": ["capability", "instance"],
      "reason": "该证据为何分别构成数组中的每一种支持类型"
    }
  ]
}
```

一个 `evidence` 元素表示一个连续证据单元，通过 `support_types` 数组记录该证据同时成立的全部支持类型。本轮诊断开放 `definition`、`structure`、`capability`、`mechanism`、`condition`、`method`、`instance`、`effect`、`evaluation` 九类支持类型。一个连续证据单元可以包含多个陈述，不要求拆成原子事实；同一段连续原文同时构成多种支持类型时，不拆成多个 evidence，而是在 `support_types` 中列出全部成立类型。`quote` 必须逐字存在于 `block.text`，不得翻译、改写、拼接或使用省略号跨段连接。不支持时 `evidence` 为空数组。

支持时不输出外层 `reason`，由每个证据元素自己的 `reason` 说明支持依据。不支持时没有证据元素可承载理由，因此必须输出外层 `reason`。

#### E-1.2 提示词

```text
你是知识库证据挂接判定器。每次只判断一个 block 是否能为一个叶节点提供支持。

你会收到一个 block 和一个 leaf：
- block.section_path：原文所在章节路径；
- block.text：本次唯一可用的原文；
- leaf.path、leaf.title、leaf.description、leaf.exclusions：叶节点的完整知识范围。

【leaf 的含义】
leaf 是知识框架中的一个终端知识范围。它描述某一类应被掌握的知识，不是任务、
待输出成果或测试问题。你的判断目标是：block 中是否存在能够用于回答该知识范围内
问题的证据。

【支持判定】
同时满足以下三个条件才判为支持：
1. 相关性：原文陈述的对象、关系或问题落在 leaf 的知识范围内；
2. 实质性：原文提供至少一种下方支持类型所描述的内容，而不是只出现相关词；
3. 自足性：仅凭当前 block 就能得到该支持判断，不需要补充 block 之外的知识。

只要 block 对 leaf 的某一个方面形成上述支持，就不要求覆盖 leaf 的全部方面。
任一条件不满足，即判为不支持。

【目标知识身份】
以 leaf.title 标识核心知识身份，leaf.description仅用于明确leaf.title的含义，不参与支持类型判断；
leaf.exclusions 排除的内容不算。

leaf.path 和 leaf.title 共同规定证据必须满足的知识关系。原文只说明某个对象存在、
被实现、具备能力或产生效果时，不得据此推断该对象参与了 leaf.path/title 所指的
阶段、过程、职责或关系；后者必须由原文直接陈述。leaf.description 用于确认该身份
的具体范围，不得扩张或改写 leaf.path/title 规定的关系。

description 中列举的方面、边界、条件、组成、作用、实例等，都属于该核心知识身份，
不得把其中一项改写成另一个被判断的目标身份。判断 support_types 中的每个类型时，证据描述的功能、
机理、结构、条件、方法或效果也必须归属于该核心知识身份。

只出现相关术语，或陈述的是其他知识身份和背景，不算相关。

【支持类型】
- definition：说明目标知识对象是什么、指称哪类对象，或它与相邻概念的边界。
- structure：说明目标知识对象内部由哪些部分、角色或层级构成，以及这些部分的组成关系。
- capability：目标知识对象自身能执行什么动作、提供什么功能，或能对其他对象实施什么允许、拒绝和限制规则。
- mechanism：说明目标知识对象借助什么作用过程、因果链条或工作原理产生功能或变化。
- condition：目标知识对象之外的某个事实必须先成立，目标知识对象才能成立、运行或被使用。
- method：说明建立、操作、使用或处理目标知识对象所采用的方法、步骤、策略或流程。
- instance：说明目标知识对象的具体实例、案例、实现、产品或场景。
- effect：目标知识对象产生、导致、避免或改变的结果、变化或影响。
- evaluation：说明评价目标知识对象时可使用的指标、判据、标准、权衡或优缺点结论。

不满足任何上述类型的陈述不要选择，也不得为了使用某个类型而强行归类。若 block 中
没有任何陈述满足上述类型，则判为不支持。

【证据单元】
每个 evidence 元素表示一个连续证据单元，可以包含多个共同支持当前 leaf 的陈述，
不要求拆成原子事实。quote 只能逐字复制 block.text 中的连续原文，不得翻译、改写、
拼接或用省略号跨段连接。若同一判断需要多个互不相邻的原文，分别输出多个 evidence
元素；同一段连续原文同时构成多种支持类型时，不拆成多个 evidence，而是在该元素的
support_types 中列出全部成立类型。每条 quote 必须能够直接证明该元素 support_types
中的每一种类型和 reason。不得使用 block 之外的知识。
每个 evidence 的 support_types 必须是非空且不重复的数组，每个成员必须且只能来自上方
```

#### E-1.4 宿主校验与评估

每次调用至少执行以下检查：

1. 输出是 JSON 对象；`is_supported` 是布尔值，`evidence` 是数组；
2. 支持时，对象恰好包含 `is_supported` 和 `evidence`，且 `evidence` 非空；
3. 不支持时，对象恰好包含 `reason`、`is_supported` 和 `evidence`，`reason` 是非空字符串，且 `evidence` 为空；
4. 每个证据元素恰好包含 `quote`、`support_types`、`reason`，且三个字段均合法；
5. 每个 `support_types` 都是非空、无重复的数组，每个元素必须且只能是九类已定义支持类型之一；
6. 每条 `quote` 都是 `block.text` 的逐字连续子串；
7. `is_supported` 与 `evidence` 是否为空一致；
8. 二值判定与人工金标准一致；
9. 结构合法、二值判断正确且 quote 逐字存在时，记为当前 `support_contract_pass`；
10. 对所有证据元素的 `support_types` 取并集并统计 `legacy_type_contract_pass`，仅作为类型诊断，不阻断挂接；
11. 正例逐项审核至少一条证据是否直接满足叶路径、标题和描述规定的知识身份，是否存在原文未陈述的关系补造。

本实验分别统计宿主合法率、二值一致率和当前挂接契约通过率。通过率之外还要逐项查看理由和引文，既避免模型碰巧选对二值判定，也检查支持证据是否直接成立。类型契约单独统计，不能用它把二值正确的挂接重新判成失败。

提示词中的字数只用于引导模型保持输出简洁，不属于宿主合法性门禁。宿主只检查字段类型和非空，不检查 `reason` 的字符数或 token 数，避免因为合理但略长的解释把整个调用判为失败。

#### E-1.5 当前边界

E-1 只验证单条支持关系能否被识别。它不能证明全目录候选、分支路由、叶节点形式精简、批量成本、叶节点整体证据覆盖或增量重算有效；这些实验必须在 E-1 结论明确后分别设计。

#### E-1.9 核心目标收敛与关系约束回放

此前“所有直接相关证据均已召回”的说法会把单叶挂接扩张成 block 完整语义标注。证据挂接是当前流程中调用成本最高的阶段，要求模型穷尽证据和支持类型既会增加成本，也会诱导模型为了“列全”而用叶节点标题补造原文没有直接陈述的关系。本轮将目标收敛为：

> 当前 block 中是否存在至少一条能够直接支持当前叶节点的证据？

据此，`evidence` 的职责是证明支持判断成立，不是完整标注 block；`support_types` 的职责是限定支持形态并约束证据与理由自洽，不要求类型穷尽。叶节点整体是否覆盖充分，属于多个 block 汇总后的覆盖判断。

为防止“对象相邻”被误当成“关系成立”，脚本的【目标知识身份】增加了以下约束：

```text
leaf.path 和 leaf.title 共同规定证据必须满足的知识关系。原文只说明某个对象存在、
被实现、具备能力或产生效果时，不得据此推断该对象参与了 leaf.path/title 所指的
阶段、过程、职责或关系；后者必须由原文直接陈述。leaf.description 用于确认该身份
的具体范围，不得扩张或改写 leaf.path/title 规定的关系。
```

### E-7：单叶最终挂接主路径

#### E-7.1 主路径决定

负责人已确定最终挂接不再使用多叶分批输入。此前 E-5 的跨树叶批量和相邻叶竞争实验保留为失败探索记录，不再作为待修复或待产品化的主链路。

主路径调整为：

1. E-4 的三级标题一级去除继续保留，用于把全目录一级树缩减为后续候选范围；
2. 对去除后保留的每个叶节点，各自发起一次独立支持判定；
3. 每次调用只输入一个 block 和一个完整叶节点；不输入其他叶节点，不允许其他叶节点的判断改变当前结果；
4. 每个叶节点独立解析、独立校验、独立记录语义失败或结构失败；一个叶节点失败不导致同批其他叶节点失效；
5. 当前不使用 thinking；先测现有单叶提示词和输出上限下的原始稳定性，不先引入重试、提示词改写或特殊节点豁免。

E-5.4 已经提供的单叶参考结果是：253 个叶节点、并发 25，总窗口 13.762 秒；输入／输出 token 为 387,864／22,658，热缓存下费用约 ¥0.1484；召回 16/17，精确率 53.3%。唯一漏挂 `K18.03.01` 的模型语义决定实际为支持，失败来自 JSON 语法错误。紧邻的另一轮为 17/17 召回、50.0% 精确率。因此单叶方案的下一问题不是叶间竞争，而是单叶输出契约和运行间稳定性。

与已否决的 253 叶分批相比，单叶当前样本的费用由约 ¥0.0881 增至 ¥0.1484，增加约 68.4%；但实际窗口由 29.0 秒降至 13.8 秒，并且消除了整批结构失败和语义近邻干扰。保留一级去除后，单叶总成本预计约 ¥0.153～¥0.163、总窗口约 18 秒；若不做一级去除而直接判定 620 叶，成本约 ¥0.364、时间约 34 秒。因此一级去除在单叶主路径下仍有明显经济价值。

下一项实验固定 `b00008`、253 个保留叶节点、并发 25 和当前单叶提示词，完整运行 10 轮，共 2,530 次独立调用；结果见 E-7.2。验收时分别统计：

- 每轮 17 个正例是否全部召回；
- 语义支持决定的逐叶证据契约通过率；
- JSON 解析失败、字段语法失败和证据失败；
- 支持精确率与每轮误支持集合；
- 每轮输入／输出 token、缓存命中和总耗时。

该轮只测原始方案，不预先加入失败重试。若结构失败复现，再基于具体错误确定单叶级重试或修复协议。

#### E-7.2 单叶 10 轮稳定性回放

## 8 当前结论

目前已经确认 A1：block 与叶节点的运行时关系采用二值支持，不设置 `partial` 输出。A44 进一步确认人工金标准和离线灰区评价使用 `no_support`／`weak_support`／`direct_support` 三档；`weak_support` 只用于离线评价，不是模型的部分支持输出，也不要求运行时落库为弱支持。叶节点整体是否覆盖充分，属于跨 block 的覆盖判断，不能写回单条挂接关系。

同时新增 A8：支持关系记录领域无关的 `support_type`，本轮诊断开放完整九类：`definition`、`structure`、`capability`、`mechanism`、`condition`、`method`、`instance`、`effect`、`evaluation`。九类分别指向目标知识对象的定义、组成、能力、机理、条件、方法、实例、效果与评价知识。控制方向必须从目标知识对象出发：外部事实限制目标对象属于 `condition`，目标对象控制其他对象属于 `capability`。该枚举仍需通过正例和反例回放验证，不能把类型标签当作支持强度或叶节点覆盖状态。

新增 A9：一条连续证据可以同时成立多个 `support_type`，输出字段因此使用 `support_types` 数组。证据原子性不是目标；同一段原文构成的全部成立类型应在同一条 evidence 中返回，不为类型差异拆分，也不强制模型在多类型之间只选一个。

新增 A10：当前阶段继续向挂接模型提供完整叶节点 `description`。`support_types` 允许出现语义偏差，不作为挂接门禁；单叶挂接以二值判断正确、至少一条直接证据、关系成立和 quote 逐字存在为验收重点，不要求穷尽 block 内证据或叶节点方面。类型准确率单独记录，只有在下游确实把 `support_types` 用于路由、覆盖或回答组织时，才升级为阻断条件。

新增 A11：`leaf.path` 与 `leaf.title` 共同规定证据必须直接满足的知识关系；对象存在、被实现、具备能力或产生效果，不能替代原文对该对象参与特定阶段、过程、职责或关系的直接陈述。`leaf.description` 只确认范围，不扩张关系。该约束用于抑制邻近知识误支持，但不能宣称已经消除全部误判。

新增 A12：N6“在环审查与采样复核”的原人工金标准错误。`allow this` 对话框请求人类评估 Agent 操作及其风险，构成对工具调用的在环审查请求；同一 block 可以同时支持 P4 的审批交互和 N6 的审查交互。修正金标准后，12 个探针各运行 20 次，二值判断和当前挂接契约均为 240/240 通过。

新增 A13：单 block 多叶候选路由采用“必须成为候选”的高召回门禁，语义只是“存在一条具体线索即交给后续单叶验证器”，不要求候选已经成立或覆盖叶节点全部内容。当前固定版本在 500 次独立回放中 N6 为 `499/500`，其他 6 个正例为 `500/500`；把“必须”改为“应当”会使 N6 降至 `2/100`，因此“必须”保留。候选阶段向模型提供完整 `description`，当前不提供 `exclusions`；去掉描述会使 N6 与 K23 的误判同步失稳。

新增 A14：候选阶段允许保留 N3 这类高语义相关但最终不支持的候选。当前 500 次回放中 N3 均进入候选，K12、K23 均未进入；候选集合精确率为 87.5%。该误召回由 E-1 单叶验证器拒绝，不以提高候选器精确率为目标破坏 N6 的稳定性。

| --- | --- | --- |
| `no_support` | 不相关，或相关但不能回答目标知识身份 | 不挂接 |

| `direct_support` | 原文直接支持目标知识身份 | 必须挂接 |

模型输出不增加“部分支持”等级，仍只输出 `is_supported=true/false`。三级只属于人工金标准与离线评价，`weak_support` 不要求写入运行时支持关系。`weak_support` 不进入硬 F1 的分子或分母，必须单独报告灰区支持率与稳定性。

评价口径如下：

| 指标 | 定义 |
| --- | --- |
| 必挂召回率 | `direct_support` 中模型判支持的次数 ÷ `direct_support` 全部判定次数 |
| 硬负例误挂率 | `no_support` 中模型判支持的次数 ÷ `no_support` 全部判定次数 |
| 灰区支持率 | `weak_support` 中模型判支持的次数 ÷ `weak_support` 全部判定次数 |
| 硬 F1 | 只使用 `direct_support` 与 `no_support`，不使用 `weak_support` |

灰区稳定性按每个叶节点的多次回放分类：全部支持为“稳定支持”，全部拒绝为“稳定拒绝”，其余为“摇摆”。这类分类只用于判断灰区和知识身份是否需要继续拆分，不能把“摇摆率低”当作硬召回通过。

#### A48：稳定负例逐项审计起点与 K01.07.03 叶子定义问题

模型把它判为 structure 或 definition，理由概括为“运行在用户机器并依赖文件系统、shell 和网络，界定了系统与外部环境的边界”。与此同时，allow／deny 和沙箱规则也被解释为“边界输入输出关系”或“职责划分”。

人工复核认为，原叶子存在明显语义歧义：Agent系统边界与外部依赖边界 同时可以指向架构职责边界、外部资源访问边界、安全边界、集成边界或审批控制边界；原描述中的“划分、输入输出关系、责任范围”也没有提出一个足够单一的主问题。于是模型容易从原文抓取 machine、filesystem、shell、network、allow、deny 和 boundary 等显眼词语，把访问能力误当作职责边界知识。

    {
