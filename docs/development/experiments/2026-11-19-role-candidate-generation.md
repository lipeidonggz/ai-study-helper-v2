# 角色候选生成提示词三次回放

## 文档定位

本文验证实验时版本的 16 号设计角色候选生成提示词。该版本扩大了角色出现位置的枚举范围，并删除了重复宿主输入隔离职责的“禁止读取当前知识库或外部资料”规则。实验只检查候选生成的结构合法性和单轮覆盖，不评价归并质量，也不证明角色集合完整。

注意：该实验运行的是“候选阶段同时输出完整主要任务”的旧提示词。后续设计已改为候选阶段只输出 2～4 项区分性任务。当前 16 号设计 §4.3.1 与本实验提示词不再相同；实验时的精确提示词保存在对应原始结果的 `system_prompt` 和 `user_prompt` 字段中，本文以下记录保持历史原样。

## 固定条件

- 模型：`deepseek-flash`
- temperature：0

- 最大输出 token：60,000

- 生成提示词：实验时版本；精确文本见原始结果的 `system_prompt` 和 `user_prompt`，现行契约见 [16 号设计 §4.3.1](../../design/16-使用角色驱动的领域知识组织.md)

## 初步结论

扩大角色位置枚举后，单轮候选能够覆盖比软件开发生命周期更宽的职责范围。当前主要问题不是缺少明显的职责方向，而是候选数量、命名粒度和岗位组合方式仍明显波动：同为 25～42 个候选，不同运行会选择不同的拆分方式，并产生大量近义或上下位角色。

因此下一步应保留三次原始候选，先按“主要任务是否产生相同问题需求”进行归并和来源全覆盖校验，再判断哪些角色方向是稳定需求，哪些只是名称抖动。不能直接用精确名称命中率代替语义稳定性。

## 阶段拆分结论

确认角色后单独生成主要任务，能够明显降低“为整轮所有角色套用相同任务数量”的问题：本次各轮任务数为 9、9、8，不再出现整轮全部 4 项或 5 项的同构结果。三次都补出了角色发现阶段容易遗漏的通用架构师职责，同时保留了 Agent 特有的决策循环、上下文、工具、权限和不可控行为边界。

当前证据支持把主要任务完整性要求放到角色确认之后。角色候选阶段仍应保留少量区分性任务用于识别和归并，但不能把候选任务当作最终任务树输入。该拆分已由沛东确认并同步进入 16 号设计 §3.2、§4.3、§4.5、§4.8～§4.9、§9.2 Gate A 和决策 `16-D16`。

### 初步语义复核

以下合并与当前区分性任务基本双向对应：

- Agent 系统架构师的三个称谓；
- Agent 应用开发工程师的三个称谓；
- 产品经理、评测工程师、平台／运行时、运维／可观测性；
- 检索、上下文、记忆和数据／知识工程；
- 治理／合规、审计、采购、标准、培训、伦理、交互等方向的同义候选。

需要继续审阅的边界：

- `Agent 工具/API 提供者` 被并入工具集成工程师组。三者当前都围绕机器可用工具契约、错误语义、权限和幂等性，按“问题需求是否相同”可以成立；但提供方还承担 API 兼容性和对外服务责任，是否应单独成组需要人工判断；
- `Agent 数据/知识工程师`、`Agent 知识与检索工程师` 和 `Agent 上下文与记忆工程师` 被合并为一个较宽的“知识与检索工程”组。它们的当前三项任务高度重合，因此合并有依据，但可能掩盖知识库治理、记忆策略和检索算法之间的后续任务差异；
- `Agent 安全工程师/红队` 因同时包含安全设计和攻击验证，未与纯红队组或纯安全对齐组合并，保留为单例。当前归并契约不允许一个来源候选进入多个组，因此该处理与结构规则一致，后续可由用户选择是否拆分；
- 安全对齐研究、安全对齐工程、纯红队和事故响应保持分组，当前理由能够区分研究发现、控制设计、攻击验证和事件处置。

针对第一个边界又做了一次局部归并回放：只输入 `Agent 工具与 API 集成工程师`、`Agent 工具与协议集成工程师` 和 `Agent 工具/API 提供者` 三个候选，提示词及其他配置不变。结果是 3 个来源形成 2 组：两个集成工程师合并，`Agent 工具/API 提供者` 单独成组。模型给出的拆分理由是提供方还需要从被调用方评估既有 API 的滥用风险和兼容性影响，这会形成集成方没有的独立问题需求。

该单次成功不能证明模型在局部输入下已稳定执行第 4 条排除规则。随后使用同一提示词和同一三个候选继续回放时，一次仍拆成两组，另外四次均合并为一组，累计只有 1/5 次拆出提供方。因此，此前“局部输入会稳定纠正全局注意力漂移”的推断不成立；当前证据支持的是同一提示词在 temperature 0 下仍存在输出不稳定性。

局部回放原始结果：`backend/.runtime/role_merge_v1_20261119T133224950932Z/results.json`。

### 三个边界联合局部回放

把三个边界涉及的 14 个角色一次性输入同一版 §4.3.2，配置仍为 `deepseek-flash`、temperature 0、thinking 开启。结构结果合法：14 个来源形成 7 组，其中 4 组发生合并、3 个单例，没有遗漏、重复、新增或未决问题。

与人工预期相比，联合输入暴露出两个问题：

1. 工具边界再次把 `Agent 工具/API 提供者` 并入两个集成工程师。相同提示词和相同三个候选在单独输入时能够正确拆开，说明该边界至少对输入组成和候选上下文敏感，尚不稳定。
2. 知识与检索边界的三个来源继续合并为“知识与检索工程”，而 `企业知识库与数据治理专员` 保持单例。这个结果与当前任务描述基本一致：前者偏检索、上下文和记忆机制，后者偏知识源准入、权限映射、版本、删除和访问审计。
3. 安全边界把 `Agent 安全工程师/红队`、`Agent 红队测试专家` 和 `Agent 安全红队/安全研究员` 合并，把 `Agent 安全对齐工程师` 和 `Agent 对齐与安全研究科学家` 保持单例。混合安全候选同时包含防护设计和红队验证，但当前契约要求一个来源只能进入一个组，模型按红队验证将其合并，仍然掩盖了独立的防护设计问题需求。

联合回放说明，当前单标签分组模型无法稳定表达“一个来源同时对应两个合理角色组”的混合候选。`Agent 安全工程师/红队` 是直接证据：完整防护设计与纯攻击测试都有独立问题需求，但组输出只能二选一，或者被迫塞入一个较宽的组。后续应评估允许一个来源候选映射到多个语义组，或要求先把混合候选拆成原子角色，再进入一对一归并。

原始结果：`backend/.runtime/role_merge_v1_20261119T133358529425Z/results.json`。

### 工具与安全 10 个角色的联合回放

去掉知识与检索边界后，只把工具接口 3 个角色和安全 7 个角色一次性输入。配置仍为 `deepseek-flash`、temperature 0、thinking 开启。10 个来源形成 6 组，结构合法，没有遗漏、重复、新增或未决问题。

结果如下：

- 工具接口 3 个来源仍全部合并为“Agent 工具与 API 集成工程师”，没有拆出工具/API 提供方；
- 安全侧的 `Agent 安全工程师/红队` 单独成组，理由是它同时具有防护设计和攻击验证，和纯控制设计或纯红队都不能双向对应；
- `Agent 对齐与安全研究科学家` 和 `Agent 安全对齐工程师` 分别单列；
- 两个纯红队候选合并；
- 两个事故响应与取证候选合并。

与 14 个角色的联合输入相比，安全侧结果从“混合安全候选被并入红队”变为“混合安全候选保持单例”，说明该边界对同时出现的其他候选组敏感。仅去掉知识／检索组就改变了安全组边界，因此当前全局一次性归并不能视为稳定。

工具边界则仍然错误：仅输入三个工具角色时能正确拆成两组，但加入安全候选后再次合并成一组。两种输入规模下都开启 thinking，因此这不是 thinking 开关造成的差异。

结论：当前 §4.3.2 在单次回放中完成了结构闭环，语义结果总体可用，但不是稳定性结论。至少还需要在固定 79 个来源候选上重复归并 3 次，比较分组数量、组边界变化及人工复核结果后，才能判断是否可以提交审核。

## 参与方位置实验

工具集成方与 API 提供方多次被合并，暴露出一个候选卡未显式表达的维度：相同活动可能处于不同的参与方位置。例如双方都“设计 schema 和权限”，但集成方代表 Agent 消费外部接口，提供方则代表外部服务治理契约、兼容性、配额和滥用风险。

为隔离该维度，冻结上面三个边界涉及的 14 个来源候选，不重新生成角色，只在实验输入中人工增加 `participant_position`，并在直接归并提示词中增加规则：相同活动如果参与方地位不同，并因此产生不同的责任对象、风险承担方或交付结果，不得合并。

| 实验 | 输出结构 | 结果 |
| --- | --- | --- |
| 三个工具候选 | 直接归并 | 3/3 次均为两个 Agent 侧集成角色合并、API 提供方单列 |
| 三个边界全部 14 个候选 | 直接归并 | 3/3 次均为相同 9 组：4 个合并组、5 个单例组、0 个遗漏、重复或未决 |

14 个候选三次的稳定分组为：

- `Agent 工具与 API 集成工程师` + `Agent 工具与协议集成工程师`；
- `Agent 工具/API 提供者` 单例；
- `Agent 知识与检索工程师` + `Agent 上下文与记忆工程师` + `Agent 数据/知识工程师`；
- `企业知识库与数据治理专员` 单例；
- `Agent 安全工程师/红队` 单例；
- `Agent 红队测试专家` + `Agent 安全红队/安全研究员`；
- `Agent 对齐与安全研究科学家` 单例；
- `Agent 安全对齐工程师` 单例；
- `Agent 事故响应与取证分析师` + `Agent 安全事件响应工程师`。

该实验只验证了“显式参与方位置 + 对应归并规则”这一机制，参与方位置由人工提供，不能证明候选生成模型能够自动产出正确字段。基于这一结果，16 号设计已把 `participant_position` 加入候选角色卡契约，下一步需重新运行候选生成并逐角色检查字段质量。

因此，本轮结论是：参与方位置可以作为候选卡必填字段，不需要再退回人工补写或单角色推导实验。单轮没有同时出现工具供需双方不构成字段失败，也不能据此否定三次独立生成方案；下一步应以三次候选的整体为输入检查归并覆盖、错误合并和漏并，而不是把单轮角色数量或精确名称重合率当作候选阶段质量指标。

## 归并阶段自行推测参与方位置

为检验“参与方位置能否由归并模型从候选职责中重新推断”，复用冻结的 14 个来源候选，但不再提供人工或候选生成阶段的 `participant_position`，同时隐藏 `reason` 和 `prior_knowledge`。归并输入只保留候选名称和区分性任务，要求模型先逐候选输出 `inferred_participant_position`，再依据推测位置、责任对象、风险承担方和交付结果决定归并。

提示词 SHA-256：`41e32804a1144595f64f1e31b51c2190f8e21cd3bd27d803bc058dbd75b3f1d6`。使用 `deepseek-flash`、temperature 0、thinking 开启，独立回放 3 次。

| 回放 | 结构状态 | 推测位置 | 位置未决 | 分组数 | 合并组 | 单例组 | 工具提供方结果 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 合法 | 14/14 | 0 | 7 | 5 | 2 | 并入工具集成组 |
| 2 | 合法 | 14/14 | 0 | 7 | 5 | 2 | 并入工具集成组 |
| 3 | 合法 | 14/14 | 0 | 8 | 5 | 3 | 正确单独成组 |

与人工提供参与方位置时的稳定 9 组结果相比，自行推测没有得到改善：三次分别为 7、7、8 组，且没有任何一次完整复现人工边界。具体错误集中在两个边界：

- 工具提供方在 2/3 次被并入工具集成组。模型通常把三者都推测成“工具/API 提供与集成方”，并将负责现有 API 兼容性和滥用风险解释成同一提供侧的内部差异。只有第 3 次明确把 `现有 API` 推断为“外部 API/工具提供方侧”，才正确拆开。
- `Agent 安全工程师/红队` 在 3/3 次被并入 `Agent 安全对齐工程师`。模型把前者的主位置判为安全工程，把红队任务降为次要活动，于是选择保留工程侧合并，掩盖了人工基线中混合角色的独立问题需求。

该结果支持一个更具体的根因假设：候选卡中的参与方位置和区分性任务并不总能相互推出。尤其当任务只写“设计 schema、权限、错误语义”等共同活动，而不明确谁消费、谁提供、谁承担兼容性风险时，归并模型自行推测也会得到同一参与方。继续增加“自行推测”步骤不能替代候选任务中的责任边界表达。

## 最终处置

参与方位置方向到此停止，不进入当前实现。角色合并只在用户确认角色时进行一次，少量错误合并可由人工直接纠正；继续修改候选任务、增加归并推测步骤或调优稳定性，成本高于人工纠正收益。

当前有效契约已经回退：候选生成不再输出 `participant_position`，只输出角色名称、2～4 项区分性任务和区别理由；归并提示词恢复为最初版本，只比较区分性任务能否双向对应。上面的字段生成、人工位置和模型自行推测实验仅作为历史证据保留，不代表当前接口。
