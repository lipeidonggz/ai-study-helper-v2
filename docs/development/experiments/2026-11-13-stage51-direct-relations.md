# 原文关系抽取探索：历史、当前基线与后续计划

## 文档定位

本文是阶段 51 关系抽取探索的统一入口。阅读时应先看本节的当前结论，再按需查看下文的实验
证据。下面的历史章节保留了当时使用的提示词、数字和结论，用来解释方法为什么演进到今天；
其中过期口径不能覆盖本节定义的当前基线。

当前要解决的问题不是“让一次模型调用判断出原文中的所有关系”，而是：给定完整原文块和一个
通用功能关系类别，判断该块是否明确表达了这个关系，并返回最小、逐字可核验的原文证据段。
后续编码、提示词评审和实验设计都应以本节的当前方法为前提。

## 一、当前结论

### 1.1 已采用的方法

当前采用“块级输入、单关系调用、统一定义契约”的方法：

1. 输入单位是 canonical collection 快照中的一个完整原文 block，不先拆句，不先抽候选词面，
   也不向模型注入其他关系类别。
2. 每次模型调用只判断一个关系类别，输出二元结果和证据段；当前已验证的关系是“约束”。
3. 每个关系类别由一张关系卡描述。关系卡至少包含关系标识、中文名称、唯一的关系定义，以及
   可选的“证据与推断边界”。
4. 关系定义是正向语义的唯一来源。“证据与推断边界”只能收缩判断，说明哪些核心要素必须由
   原文明确表达、哪些内容不能反推；它不能增加定义之外的正面判定条件。
5. 当前不把正例、反例、纳入条件、领域关键词或邻接关系映射写入在线提示词。正反样本应作为
   离线测试夹具，用于验证关系卡是否稳定，不能提前泄露给被测模型。
6. 模型返回证据段时，`quote` 必须是当前 block 中逐字存在的连续片段。空结果和格式失败必须
   分开统计；格式失败不能计为“不存在”，也不能由运行时静默修复。
7. 查询侧上游负责判断应选择哪些关系入口。若一个问题需要多个关系，可分别发起多次单关系
   调用，但不在同一个提示词里同时注入多个关系让模型竞争。

### 1.2 当前“约束”关系卡

当前关系卡是：

```text
关系标识：constrain
关系名称：约束

定义：
原文表示因为某个目标或者原因（可为显式的或者根据上下文自然推测的隐式表达的），
通过明确的机制、条件或动作，把某个对象、行动或状态的可发生、可执行、可访问、可观察
或可影响范围限定为更小的一部分。

证据与推断边界：
目标或原因可以根据完整块上下文推断；但限制范围所用的机制、条件或动作，被限定的对象或
状态，缩小后的范围，以及“范围被缩小”这一关系本身，必须由原文明确表达。仅说明降低风险、
建立防护、存在边界或限定文章讨论范围，不能据此反推约束。
```

该定义于 2026-11-16 根据 D04 人工复核补充“可影响范围”。本文后续历史实验章节中出现的旧版
“适用、可见等范围”表述保留其当时实验语境，不代表当前关系卡。

这里两个字段的职责必须严格区分：

- “定义”回答什么情况属于该关系，是唯一的正向判定来源；
- “证据与推断边界”回答在原文证据上最多允许推断多远，只能提供必要的负向限制。

若定义与边界发生冲突，该关系卡无效，应先修订并回放，不能要求模型自行选择服从其中一条。

### 1.3 当前结果

三波主实验都固定使用 `deepseek-flash`、temperature 0、thinking disabled 和单关系输入，
并使用同一定义的主口径。句子级基线沿用早期并发配置；两波块级运行使用每篇文档内部并发 12。
结果如下：

| 路线 | 判断单位 | 有效“存在” | c13-003 block 覆盖 | 当前判断 |
| --- | --- | ---: | ---: | --- |
| 句子级单关系 | 句子 | 463/526 | 66/68 | 召回高，但明显过切、过标，不继续作为主路线 |
| 块级单关系基线 | 完整 block | 387/526 | 59/68 | 明显减少切分误报，但仍会宽解释设置和选择 |
| 块级＋证据与推断边界 | 完整 block | 327/526 | 单次对照约 55/68 | 精确性方向继续改善，11 个 c13 语义组仍全部可达 |

- 15/15 篇、526/526 个 block 完成；
- 有效“存在”327 块；
- 有效“不存在”195 块；

60 个精确命中，但逐条检查显示大部分旧命中来自举例、能力、用途、流程步骤、参数选择或实验
结果被宽泛解释为范围约束。第三波同时暴露出少量稳定性波动和个别定义边界，详见 §1.4。

### 1.3.1 关系卡重构的 D04 行为等价回放

为把约束专用探针改为可复用的关系卡方式，当前脚本把关系标识、中文名称、定义和证据与推断
边界集中到 `RelationCard`，判断逻辑改为从关系卡读取这些字段。`scripts/wiki_constrain_block_level_probe.py`
通过 `--relation-card constrain` 选择当前卡；除关系卡字段外，提示词外壳、完整 block 输入、
单关系二元判断、证据逐字校验和模型调用参数均保持不变。

重构后先对 D04 的 26 个 block 逐个重建提示词，并与旧基线的已保存提示词直接比较：

- 26/26 个提示词逐字相同；
- 26/26 个提示词 SHA-256 相同；
- 因而本次新运行不存在由提示词文本变化引入的语义差异。

固定 `deepseek-flash`、temperature 0、thinking disabled 和每篇并发 12，新旧运行对比如下：

| 指标 | 旧基线 | 关系卡方式 |
| --- | ---: | ---: |
| block 数 | 26 | 26 |
| 存在 | 22 | 21 |
| 不存在 | 4 | 5 |
| 格式或证据校验失败 | 0 | 0 |
| 调用失败 | 0 | 0 |
| 证据段 | 25 | 24 |
| 唯一证据段 | 25 | 24 |
| 输入 token | 16,964 | 16,964 |
| 输出 token | 2,805 | 2,807 |

旧基线产物为
`backend/.runtime/constrain_block_level_guarded_full_20261115_162222/D04`，关系卡方式产物为
`backend/.runtime/constrain_relation_card_d04_20261116_082045/D04`。

逐块比较结果：

- 响应类型和存在性一致 25/26；
- 证据 quote 列表完全一致 25/26；
- 25 个一致 block 的证据数量也全部一致。

唯一差异是 D04 `b00020`：旧运行判为存在并返回
`tool calls route through proxies that enforce network and file policy...`，新单次运行判为不存在。
由于两者提示词逐字相同，该差异不能归因于关系卡重构。为确认波动来源，随后用同一关系卡、同一
提示词、同一模型和参数对该 block 连续调用 10 次，结果为 7 次存在、3 次不存在、0 次格式失败；
7 次存在均返回同一句证据。稳定性回放产物为
`backend/.runtime/constrain_relation_card_b00020_stability_20261116_082129/results.json`。

因此，本次可以确认关系卡重构与旧版在 D04 上行为基本一致，剩余一项差异是 `deepseek-flash`
在 temperature 0 下已有的判断波动，而不是关系卡字段装载、提示词拼接或解析校验造成的变化。
该结论只证明重构等价，不改变前文关于模型稳定性和关系定义边界的结论。

### 1.3.2 输入 token 缓存顺序优化

DeepSeek 的[上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)只识别从第 0 个
token 开始的相同前缀，缓存以 64 token 为存储单元，且属于尽力而为机制。响应中的
`prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens` 可以直接用于验证是否真的命中。按本次实验
时的[模型价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)，`deepseek-flash` 在高峰
时段缓存命中输入为 0.04 元/百万 token，未命中输入为 2 元/百万 token。

旧顺序在关系卡后立即注入原文 block，导致公共任务规则、证据边界和 JSON 输出结构全部位于变量
内容之后，无法进入跨 block 的公共前缀。`stable-prefix-v2` 保持任务规则、关系名称、定义、证据
与推断边界和输出结构的文字不变，只调整顺序：

```text
旧顺序：固定标题 → 关系卡 → 原文 block → 任务规则 → 输出格式
新顺序：固定标题 → 关系卡 → 任务规则 → 输出格式 → 原文 block
```

在同一“约束”关系下，所有 block 共用新顺序中 block 之前的完整前缀。D04 的 26 次请求在新旧
顺序下的普通输入 token 总数均为 16,964，说明这一变化只是重排，没有通过增加提示词内容换取缓存。

探索中还试过两版更激进的重排，均未采用：一版把具体关系措辞改为通用“判断目标”表达，D04 四次
有效存在数降到 20、18、18、16；另一版把任务规则前置、只把 JSON 输出格式留在原文 block 后，
首轮有效存在数降到 18。这说明不能只按缓存前缀长度重排，任务规则相对原文 block 的位置会实质
影响抽取；当前采用的版本只把 block 移到末尾，其他契约文字保持不变。

为排除历史缓存干扰，缓存实验为每种顺序生成独立批次前缀，并分两步运行：先处理 D04 前 13 个
block 形成公共前缀，再处理此前从未发送过的后 13 个 block。执行 3 组独立试验，每组预热和测量
都使用同一批次前缀。结果如下：

| 试验 | 旧顺序测量命中 | 旧顺序命中率 | 新顺序测量命中 | 新顺序命中率 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 0 / 8,306 | 0% | 3,328 / 8,332 | 39.94% |
| 2 | 0 / 8,306 | 0% | 3,328 / 8,332 | 39.94% |
| 3 | 0 / 8,306 | 0% | 3,328 / 8,332 | 39.94% |

新顺序的测量批输入比旧顺序多 26 token，仅来自实验批次标签长度差异，不是产品提示词差异。
3 次试验都得到完全相同的缓存命中数。按上述高峰价格计算，仅看输入费用时，新顺序在未见过的新
block 批次上的费用从 0.016612 元降到 0.01014112 元，降幅约 39.0%。缓存是尽力而为机制，因此
39.94% 是该固定实验条件下的实际命中率，不是对所有语料的保证。

重排后的抽取效果用 D04 全部 26 个 block 各跑 4 次对照。旧顺序 4 次的有效存在数依次为
21、21、22、22，新顺序 4 次均为 22。旧顺序有 4 个 block 在 4 次中不稳定，新顺序没有出现过
存在性翻转。两边都命中 22/26 个 block，但具体集合有 4 个差异；对照 c13-003 的 D04 单篇金标准，
旧顺序覆盖 20/22 个已知相关 block，新顺序覆盖 21/22，双方都保持 6/6 个必需证据组可达。所有
运行均为 0 个格式或校验失败、0 个调用失败。

因此当前采用 `stable-prefix-v2` 作为默认提示词顺序，并保留 `legacy` 作为对照入口。结论边界是：
本次只验证了“约束”关系和 D04；缓存命中已经真实发生，但抽取效果不能仅凭这一篇文档宣称在所
有关系和 50 篇扩大语料上完全不变。

### 1.3.3 跨关系交错时缓存是否仍然有效

上一节的 39.94% 只回答“同一张关系卡连续处理多个 block”。关系卡的名称、定义和证据边界会随
关系变化，因此还需要验证一个关键问题：如果实际按“块在外层、关系在内层”执行，使不同关系的
请求交错出现，此前缓存的单关系前缀是否仍然可用。

为了不改动正式基线，新增实验探针
`scripts/wiki_prompt_cache_topology_probe.py`，固定使用“约束、使能、要求”三张关系卡和 D04
的 10 个代表性 block。每个 block 对三种关系各执行一次，共执行三种顺序：

| 顺序 | 调用组织 | 提示词中的稳定前缀 |
| --- | --- | --- |
| 关系在外层 | 同一关系的 10 个 block 连续执行，再切换下一关系 | 关系卡、任务规则和输出格式 |
| 块在外层，关系卡在前 | 同一 block 依次执行三种关系，再切换下一 block | 仍为关系卡、任务规则和输出格式；任务规则位于原文块前 |
| 块在外层，原文块在前 | 同一 block 依次执行三种关系，再切换下一 block | 公共开头、原文块；关系卡和关系专用规则位于原文块后 |

每种顺序执行 30 次请求，并使用独立批次前缀隔离历史缓存。首次冷缓存结果如下：

| 顺序 | 输入 token | 缓存命中 token | 命中率 |
| --- | ---: | ---: | ---: |
| 关系在外层 | 20,551 | 6,912 | 33.63% |
| 块在外层，关系卡在前 | 20,701 | 6,912 | 33.39% |
| 块在外层，原文块在前 | 20,671 | 2,048 | 9.91% |

使用同一批次前缀和相同提示词立即回放一次，得到热缓存结果：

| 顺序 | 输入 token | 缓存命中 token | 命中率 |
| --- | ---: | ---: | ---: |
| 关系在外层 | 20,551 | 14,590 | 70.99% |
| 块在外层，关系卡在前 | 20,701 | 14,838 | 71.68% |
| 块在外层，原文块在前 | 20,671 | 14,592 | 70.59% |

该实验只有三张关系卡，不能直接代表完整 40 个关系下的调用规模。缓存总收益首先取决于实际可复用
片段有多长，而不是只在“关系在外层”和“块在外层”之间选边。对单关系调用，设：

- `R` 为原文块前的完整规则前缀 token 数；
- `B` 为当前原文块 token 数；
- `C` 为所有关系逐字共用的公共开头 token 数；
- DeepSeek 以 64 token 为缓存存储粒度。

“关系卡在前”的最大命中约为 `floor(R / 64) * 64`；“原文块在前”约为
`floor((C + B) / 64) * 64`。一次完整处理中，前者按每个关系跨多个 block 重复，后者按每个
block 跨多个关系重复。当关系数和 block 数都较大时，重复次数的差异会抵消，平均每次请求的命中
大小仍主要由上述两个前缀长度决定。

2026-11-16 对当前三张关系卡做了空原文块 token 计数：

| 关系卡 | 不含原文块的规则 token |
| --- | ---: |
| 约束 | 440 |
| 使能 | 415 |
| 要求 | 421 |

三张提示词在关系名称出现前只有 20 个字符逐字相同，少于一个 64 token 缓存单元。因此当前不同
关系不会共享很大的公共规则前缀，而是各自形成约 415～440 token 的缓存簇。

同一快照中的原文块规模为：

| 样本 | 中位数 | 平均值 | 最大值 |
| --- | ---: | ---: | ---: |
| D04 的 26 个 block | 252 | 212.5 | 323 |
| 全部 15 篇的 526 个 block | 199 | 194.8 | 518 |

因此当前规则前缀通常大于单个原文块前缀。“关系卡在前”多数时候能命中 384 token；原文块直接
前移后，若公共开头不足 64 token，则多数块只能命中 128～256 token。这解释了本次三关系实验
中块前移没有获得缓存优势，而不是说明完整 40 个关系下块前移一定无效。只有当 `C + B` 稳定超过
`R` 时，块前缀才会成为更大的可复用单元。

如果要让“原文块在前”真正占优，需要把关系无关的安全、证据、输出和质量规则整体前置，并且把
关系卡、关系名称和关系专用判断全部后置，以扩大 `C`。这属于提示词语义契约重排，不能只靠移动
原文块完成。另一种显著降低 token 的方式是一次请求注入多个关系，但这会增加模型注意力压力；
现有双关系实验已经观察到关系互相干扰，必须单独验证。

这组结果说明：

1. DeepSeek 可以保留多张关系卡各自的前缀。关系请求交错后，再回到某个关系时仍可命中该关系
   之前形成的缓存前缀，不会因为相邻请求属于其他关系而自动失效。
2. 热缓存稳定后，“关系在外层”和“块在外层、关系卡在前”的命中率基本相同，没有观察到块在
   外层带来的额外缓存收益。
3. 把原文块直接前移后，首次冷缓存命中率反而明显更低；热缓存后回升到与其他顺序基本相同。
   在当前三关系、每块各调用一次的样本里，原文块前缀小于规则前缀，因此块前移没有提高命中。
4. 三种顺序的普通输入 token 总量基本相同，缓存只改变命中／未命中的计费构成，不会减少模型
   实际接收的总输入 token。

该实验还暴露了缓存落盘的时序：公共前缀需要多次请求后由供应商识别并落盘，缓存构建耗时为秒级，
不是当前请求结束就能立刻被并行请求复用。因此并发启动同一 block 下的全部关系调用，不能假定
它们会自动共享该 block 的前缀。

行为方面，三个配置均为 30/30 次结构可解析。热缓存回放中的 `present=true` 次数分别为
23、22、21，但这只是三张关系卡、十个 block 的单轮结果，且关系在外层与块在外层的关系卡前
配置拥有逐字相同的提示词集合，因此差异同时受调用顺序和模型既有波动影响，不能据此判定提示词
重排等价。原文块前移方案目前只能保留为候选，不能替换正式提示词基线。

尚未验证的部分是完整 40 个关系、更多文档和多次回放的长期缓存命中。当前可以确认的是：单关系
39.94% 不能直接外推到跨关系场景；但跨关系交错本身也不会把多关系缓存压缩成单一前缀。真正要
比较的是各方案在一次完整语料处理中的累计命中、未命中、输出 token、延迟和抽取稳定性。

### 1.4 第三波结果的人工核验

对第三波中最容易造成错误漏抽的样本，使用完全相同的提示词各回放 10 次：

| block | 回放结果 | 当前结论 |
| --- | ---: | --- |
| D10 `b00021` | 0/10 | `The plan must be a sequence of valid actions` 是任务提示中的格式要求，不是可供检索的系统功能关系；接受为不存在 |
| D10 `b00040` | 9/10 | `requires only one parameter` 是明确接口约束；全库单次漏掉属于稳定性问题，不是定义系统性排除 |
| D15 `b00002` | 8/10 | Stop hook 的条件门控有较高概率判为存在；全库单次漏掉属于稳定性问题 |
| D06 `b00017` | 2/10 | `obeys permissions and security policies` 是否构成范围缩小存在解释空间 |

D06 的主体是 Agents SDK 使用案例，`obeys their internal permissions and security policies`
只是一句附带安全修饰。它没有说明权限如何划分、边界是什么、哪些对象不可访问、由什么机制
执行。即使严格语义上可以讨论它是否受策略约束，该块对 c13-003 的隔离和控制边界问题也没有
足够的证据价值。因此当前接受该块判为不存在，不因它增加专门规则。

为确认模型是否普遍漏掉权限和安全管理，本轮还对全部 526 个 block 做了关键词候选扫描。命中
权限、策略、访问控制、授权、允许列表、审批、确认、护栏或凭证等表达的块共 56 个：46 个判为
存在，9 个判为不存在，1 个格式失败。详细描述工具权限、挂载允许列表、网络默认拒绝、域名
允许列表和沙箱访问边界的块基本都被识别为约束。未命中的 9 个中，除 D06 外主要是护栏校验、
权限模式选择、参考文献或只把 permissions 当作优化组件名称的内容，不构成系统性的权限管理
漏抽。

### 1.5 当前能确认与不能确认

可以确认：

1. 完整 block 比句子级切分更适合作为关系判断单位，能保留跨句关系并减少从句和任务指令的
   过度多标。
2. 多关系联合注入会相互干扰；每次只注入一个关系时，目标关系的判断明显更稳定。
3. 对“约束”而言，“目标可以隐含，但范围缩小关系本身必须明示”的要求没有误伤固定正例，
   并把输出格式、权限模式等设置类误报压低到 0/10。
4. 权限、允许列表、访问控制和沙箱等详细机制没有被系统性漏抽。D06 是一个证据价值不足的
   边界样本，不是“权限管理整体无法抽取”的证据。
5. 只依赖“约束”一个入口，c13-003 的 11 个语义组仍全部可达；这证明组级入口没有被当前
   保守化破坏，但不等于 68 个金标准 block 已全部找全。

尚不能确认：

1. 第三波相对第二波精确率提高了多少。当前没有对全部旧命中、新命中和未命中建立独立真值，
   只能依据抽样和逐项差异判断方向。
2. c13-003 最终能否稳定找全。第三波对照中有 4 个金标准 block 从存在变为不存在，虽仍保持
   11 个语义组可达，但需要继续判断它们是旧误报还是实际漏抽。
3. 10 次回放能代表长期稳定性。`deepseek-flash` 在 temperature 0 下仍存在结果波动，窄样本
   的 10 次只是当前证据，不是确定性保证。
4. 同一模板能否直接推广到其余 39 个关系。当前只完成了“约束”的充分走查；其他关系还需要
   各自确定定义和证据边界，并用独立样本验证。
5. 当前方法在 50 篇或更大规模上的成本、延迟和精度。现阶段不能因为 526 块回放成功就直接
   扩大到 50 篇验收。

## 二、来龙去脉

### 2.1 已被排除或降级为主路线之外的思路

| 思路 | 实验观察 | 当前处理 |
| --- | --- | --- |
| 用一组预先设计的通用关系在一次调用中尽量全覆盖 | 容易受当前技术语料和设计者先验影响，且关系越多越难保持区分度 | 不再把“一次抽全”当主目标；关系集合只作为可用检索入口，具体调用逐个验证 |
| 同时注入多个关系类别 | 目标句通常仍能被识别，但加入任一第二类型都会提高整块抽取密度并引入额外关系；关系之间存在相互干扰 | 不再使用多关系联合判定；需要多个入口时拆成多次单关系调用 |
| 两阶段“先发现候选，再分类” | 在同一调用或同一上下文内仍保留多类型竞争，不能解决联合注入的扩张；其主要价值是单关系时改善候选召回 | 不作为当前主方法；候选发现不能代替单关系明示性判断 |
| 先抽候选词面或候选概念，再判断关系 | 候选抽取错误会直接导致关系漏抽；名词候选与最终关系对象并不等价 | 当前直接从完整 block 判断关系；暂不把候选词面设为必经阶段 |
| 逐句直接关系抽取 | 句子级“约束”命中 463/526 块、c13 金标准 66/68，但大量从句、条件和任务指令被放大 | 不再作为主路线；仅保留为基线，用于说明切分过细的代价 |
| 通过大量类别样例、关键词清单或个案例外修补提示词 | 容易按样本表面特征过拟合，破坏跨领域泛化，且很难保证多个规则之间一致 | 在线提示词不放大规模例；样本留作离线测试，定义和边界必须整体评审 |

这些路线不是在所有子任务上都毫无价值。例如，单关系下的候选发现可能提升某些关系的召回；
但当前需要先确认“一个关系是否能被稳定、可审计地判断”，因此不把它们放在主调用链上。

### 2.2 三波关键实验

第一波是句子级单关系抽取。它把原文切成句子，每句判断是否存在指定关系。该路线证明模型
能在细节层面找到大量候选，但也说明切分本身会破坏跨句语义，并把被动条件、例子和任务指令
当成关系实例。

第二波把输入改回完整 block，要求模型返回最小连续证据段。它与第一波使用同一关系定义、
同一模型和单关系输入口径，主要只改变了判断粒度和证据输出方式。结果全库命中从 463 降到
387，c13 金标准从 66/68 降到 59/68，说明块级上下文减少了片断性误报，但仍有把比较和配置
选择解释为约束的宽解释。

第三波保持完整 block 和原定义，只增加“范围缩小关系本身必须由原文明确表达，不能从比较、
使能、重要性、选择或设置反推”的通用证据边界。8 个固定样本各执行 10 次：5 个固定正例仍
为 10/10，输出格式和权限模式两个设置类样本从基线 6/10、1/10 降到 0/10。随后进行 526 块
全量单次回放，得到 §1.3 的结果，并对可疑漏抽做 §1.4 的复核。

## 三、当前方法的详细设计

### 3.1 调用单位与输入

调用单位是一个完整 block。输入必须来自不可变 collection 快照，并保留：

- block ID；
- 文档身份和标题；
- 章节路径；
- 完整原文；
- 快照与提示词版本。

输入前不拆句、不抽候选词、不附加领域本体，也不把其他 block 的正文拼入。允许使用当前
block 内部的上下文判断代词、条件和相邻句关系；禁止使用模型外部知识补写原文没有表达的事实。

### 3.2 关系卡

每个关系类别对应一张可版本化关系卡，最小字段为：

| 字段 | 作用 | 约束 |
| --- | --- | --- |
| 关系标识 | 稳定引用该关系 | 使用实现标识，不随中文名称变化 |
| 中文名称 | 面向人阅读 | 与设计术语表一致 |
| 关系定义 | 正向语义的唯一契约 | 只写判定所必需、可跨领域解释的含义 |
| 证据与推断边界 | 说明允许推断的范围和必须明示的核心要素 | 只能收缩定义，不得增加新的正向条件 |

当前不在关系卡中放：

- 正例和反例；
- 纳入条件；
- 领域关键词；
- 邻接关系的完整定义；
- “如果不是本关系就输出另一个关系”的多分类映射。

正例、反例和邻接关系对照属于离线验证资产。它们用于回答两个问题：定义是否覆盖应命中的
语义，边界是否能排除最接近的误报。测试样本对被测模型保密，避免模型按样本表面措辞匹配。

### 3.3 单次提示词的固定结构

所有类别共用固定提示词外壳，只替换该次调用的关系卡：

1. 先放所有不随 block 变化的公共外壳和关系卡；
2. 声明任务：判断完整原文 block 是否表达当前关系；
3. 注入关系名称、定义和证据与推断边界；
4. 要求原文中任意一处明确表达即可，不要求整个 block 的主要目的属于该关系；
5. 要求返回最小连续证据段，允许一句或相邻多句；
6. 要求证据逐字复制，不得翻译、概括或改写；
7. 给出固定的 `present=true/false` JSON 输出结构；
8. 最后才注入当前 block，使 provider 能从第一个 token 起复用尽可能长的缓存前缀。

先给出带槽位的固定模板。花括号中的内容由当次关系卡和当前 block 注入：

```text
你是原文块关系判定器。

判断目标：

{关系名称}：{关系定义}

任务：

1. 判断这个完整原文块是否表达了上述“{关系名称}”含义。
2. 不要求整个块的主要表达目的就是{关系名称}；只要块中有一处明确表达了该含义，就可以判定为存在。
3. 可以使用原文块内部的上下文。一个{关系名称}可以由一句表达，也可以由相邻多句共同表达。
4. 只依据原文块判断，不为覆盖全文而补充关系。
5. 如果存在{关系名称}，返回支持该判断的最小连续证据段。一个证据段可以包含一句或多句；
   一句话已经足够时，不要返回整个块。
6. 如果同一个块中存在多个彼此独立的{关系名称}，可以返回多个证据段；
   如果多个句子共同表达同一个{关系名称}，应合并为一个连续证据段。
7. evidence_spans 中的 quote 必须逐字复制原文，携带原文标点和语序，不得翻译、概括或改写。
8. 每个证据段的 reason 只说明该连续证据段如何表达上述{关系名称}定义，不新增定义之外的判断要求。
9. {证据与推断边界}

只输出一个 JSON 对象。

存在{关系名称}时：

{
  "relation": "{关系标识}",
  "present": true,
  "evidence_spans": [
    {
      "quote": "逐字复制的原文证据段",
      "reason": "该连续证据段如何表达{关系名称}"
    }
  ]
}

不存在{关系名称}时：

{
  "relation": "{关系标识}",
  "present": false,
  "evidence_spans": [],
  "reason": "原文块为什么没有表达该关系"
}

下面是需要判断的完整原文块：

"""
{当前完整原文块}
"""
```

各槽位的来源如下：

| 槽位 | 来源 | 当前“约束”关系卡的取值 |
| --- | --- | --- |
| `{关系名称}` | 关系卡中文名称 | `约束` |
| `{关系定义}` | 关系卡的正向定义 | `原文表示因为某个目标或者原因（可为显式的或者根据上下文自然推测的隐式表达的），通过明确的机制、条件或动作，把某个对象、行动或状态的可发生、可执行、可访问、可观察或可影响范围限定为更小的一部分。` |
| `{证据与推断边界}` | 关系卡的证据与推断边界 | `目标或原因可以根据完整块上下文推断；但限制范围所用的机制、条件或动作，被限定的对象或状态，缩小后的范围，以及“范围被缩小”这一关系本身，必须由原文明确表达。仅说明降低风险、建立防护、存在边界或限定文章讨论范围，不能据此反推约束。` |
| `{关系标识}` | 关系卡的稳定实现标识 | `constrain` |
| `{当前完整原文块}` | collection 快照中的一个完整 block | 按本次调用动态注入，不来自关系卡 |

把上述“约束”关系卡代入模板后，完整提示词如下。运行时 `<当前完整原文块>` 会替换为该次
调用的一个完整 block 原文：

```text
你是原文块关系判定器。

判断目标：

约束：原文表示因为某个目标或者原因（可为显式的或者根据上下文自然推测的隐式表达的），通过明确的机制、条件或动作，把某个对象、行动或状态的可发生、可执行、可访问、可观察或可影响范围限定为更小的一部分。

任务：

1. 判断这个完整原文块是否表达了上述“约束”含义。
2. 不要求整个块的主要表达目的就是约束；只要块中有一处明确表达了该含义，就可以判定为存在。
3. 可以使用原文块内部的上下文。一个约束可以由一句表达，也可以由相邻多句共同表达。
4. 只依据原文块判断，不为覆盖全文而补充关系。
5. 如果存在约束，返回支持该判断的最小连续证据段。一个证据段可以包含一句或多句；
   一句话已经足够时，不要返回整个块。
6. 如果同一个块中存在多个彼此独立的约束，可以返回多个证据段；
   如果多个句子共同表达同一个约束，应合并为一个连续证据段。
7. evidence_spans 中的 quote 必须逐字复制原文，携带原文标点和语序，不得翻译、概括或改写。
8. 每个证据段的 reason 只说明该连续证据段如何表达上述约束定义，不新增定义之外的判断要求。
9. 目标或原因可以根据完整块上下文推断；但限制范围所用的机制、条件或动作，被限定的
   对象或状态，缩小后的范围，以及“范围被缩小”这一关系本身，必须由原文明确表达。
   仅说明降低风险、建立防护、存在边界或限定文章讨论范围，不能据此反推约束。

只输出一个 JSON 对象。

存在约束时：

{
  "relation": "constrain",
  "present": true,
  "evidence_spans": [
    {
      "quote": "逐字复制的原文证据段",
      "reason": "该连续证据段如何表达约束"
    }
  ]
}

不存在约束时：

{
  "relation": "constrain",
  "present": false,
  "evidence_spans": [],
  "reason": "原文块为什么没有表达该关系"
}

下面是需要判断的完整原文块：

"""
<当前完整原文块>
"""
```

换成其他关系时，只替换关系名称、定义、证据与推断边界和输出中的关系标识；固定外壳、完整
block 输入、最小连续证据段要求和 JSON 结构保持不变。

公共指令中不使用“选择最合适的关系”这类多分类措辞。当前调用的输出空间只有“是／否”，
关系入口选择由上游负责。

### 3.4 输出与校验

存在关系时，返回一个或多个证据段，每段包含：

- 原文连续片段；
- 该片段为何表达当前关系的简短理由。

不存在时，返回空证据和简短理由。运行时至少执行以下校验：

1. JSON 根对象和字段类型正确；
2. 关系标识与本次调用一致；
3. `present` 为布尔值；
4. 存在时至少有一个合法证据段，不存在时不得携带证据；
5. 每个证据段理由非空；
6. 每个 `quote` 必须是当前 block 的逐字子串；
7. 引用不能因解码、换行或模型改写而失真。

校验失败是独立状态，不是关系不存在。不得自动截断、纠正引文或把失败样本从统计中删除；
需要重跑时保留原始失败记录和重跑记录。

### 3.5 关系入口与查询侧

单次调用只回答一个关系，因此查询侧必须先把问题映射到一个或多个关系入口。当前尚不规定
最终查询解析算法，只确定以下边界：

- 不把 40 个关系同时塞入一次判定；
- 不把“能力切面”“功能关系”“实体”当成同义概念；
- 不为了召回某个固定问题，在查询时为某个类别增加专用映射；
- 若一个问题确实需要多个关系，可以并行发起多次单关系调用，再在证据块层合并；
- 关系调用命中不等于最终答案相关，查询侧仍需根据证据方面和边际增量筛选。

## 四、后续工作

后续必须按以下顺序推进，避免重新陷入“针对单个案例反复调提示词”的路径。

1. **冻结当前“约束”卡。** 暂时保留名称、定义和证据与推断边界三个语义要素，不增加正例、
   纳入条件或新的个案例外。任何修改都生成新版本并重新回放固定样本。
2. **完成剩余 4 个 c13 block 的审计。** 对第三波由存在变为不存在的 D01 `b00006`、
   D01 `b00016`、D02 `b00014`、D04 `b00003`，结合完整上下文判断是旧误报、应改归其他
   关系，还是当前方法的真漏抽。
3. **固化关系卡数据模型和测试夹具。** 在线提示词只包含定义和证据边界；正反例进入版本化
   测试集，覆盖法律、临床医学、历史和当前技术语料。先验证定义能否区分，再讨论算法优化。
4. **建立近邻关系对照。** 下一批优先验证“要求、禁止、阻止、分离”与“约束”的单关系边界，
   因为它们是当前最容易混淆的相邻语义。每个关系独立调用，再比较同一测试句上的结果。
5. **先做小规模模板一致性验证。** 选择 5 个左右代表关系，用完全相同的公共外壳和各自
   关系卡运行固定样本。只有当单关系结果稳定后，才扩展到 40 个关系。
6. **重新做 526 块单次回放。** 模板稳定后保持 snapshot、模型、并发和输出校验不变，观察全库
   命中分布、格式失败和关系间重复；不能再用单次结果直接宣称精确率提升。
7. **回到 c13-003 验收。** 按 11 个语义组和题面要求检查证据覆盖，不把“每组至少有一个
   block”当作最终找全通过。必须分别记录可用证据、不足、缺失和错归关系。
8. **规模扩展门槛。** 只有在当前 15 篇上的模板、校验、人工抽查和 c13 证据覆盖得到确认后，
   才进入 50 篇扩大验收；此前不把 526 块跑通视为产品级检索成功。

## 实验三：同时注入 decrease 和 forbid

为了验证“任意第二个类型都会触发抽取范围扩张”，将第二个类型换成在该块几乎没有明确
禁止语义的 `forbid`。连续运行 10 次：

| 项目 | 结果 |
| --- | ---: |
| 目标句判为 `decrease` | 10/10 |
| 目标句判为 `forbid` | 0/10 |
| 空返回 | 0/10 |
| 包含额外关系 | 8/10 |
| 关系数序列 | `4,2,2,2,1,2,2,2,2,1` |
| 输入 token | 1135 |
| 输出 token | 111～459 |

虽然模型从未输出 `forbid`，额外关系仍然是 `decrease`：

| 原文句 | 模式 | 次数 |
| --- | --- | ---: |
| `Locally, ... can guard against malicious tool outputs` | `decrease` | 8/10 |
| `defenses can be added higher up the chain by limiting ...` | `decrease` | 1/10 |
| `When environmental defenses aren’t available, the model layer has to ...` | `decrease` | 1/10 |

这说明额外扩张并非只由 `enable` 的语义启动造成。加入第二个类型后，即使该类型完全不匹配，
模型仍会提高整块的抽取密度并把更多句子映射到原本就存在的 `decrease`。

## 对照结论

| 指标 | 只有 `decrease` | `decrease + enable` | `decrease + forbid` |
| --- | ---: | ---: | ---: |
| 目标关系召回 | 20/20 | 10/10 | 10/10 |
| 目标关系误判为其他类型 | 0/20 | 0/10 | 0/10 |
| 空返回 | 0/20 | 0/10 | 0/10 |
| 含额外关系的运行 | 1/20 | 10/10 | 8/10 |
| 每次关系数 | 通常为 1，1 次为 2 | 2～5，平均 3.3 | 1～4，平均 2.0 |

主要结论：

1. 加入第二个关系类型没有抢走目标关系，目标句在三种配置下都稳定判为 `decrease`。
   单类型复跑中额外关系由 0/10 变为 1/10，说明“完全不扩张”不是确定性保证。
2. 任意第二个类型都可能触发块级抽取范围扩张。`forbid` 在该块没有输出任何实例，
   但仍使 8/10 次运行额外返回了 `decrease`，因此这不是 `enable` 独有的语义启动。
3. `enable` 的扩张更强：10/10 次出现额外关系、每次最多 5 条；`forbid` 为 8/10、
   每次最多 4 条。当前 10 次样本只能说明方向，不能证明稳定的比例差异。
4. 关系方向和 participant 端点必须属于同一个语义框架。`decrease(..., defenses)` 与
   proposition“增加防御”方向不一致；若要表达最终风险下降，证据应出现明确的被降低对象，
   或由 `decrease` 的定义明确允许“降低后者作为威胁所造成的风险、危害或影响”。实验一至
   三仍采用旧定义，因此该条在当时只能视为端点方向不确定。
5. 单类型前后两批合计 20 次仅额外抽取 1 次，仍明显低于双类型配置，但单次 10 次
   不能证明其额外关系比例恒为 0。
6. 先前 5 次统计曾把输出摘要中的整数 `relations` 当作关系数组，导致空结果被误计为
   一条关系；本文件中的结果均已改为逐次读取完整关系数组后重新统计。

## 实验四：同一调用内先发现候选、再分类（方案 B）

实验目标是验证：如果一次调用先发现类型无关的关系候选，再只对已有候选分类，能否阻止
第二个关系类型扩大抽取范围。候选发现与分类仍在同一个模型调用和同一个上下文内完成。

连续运行 10 次，结果如下：

| 候选数 | 6～7 |
| 最终关系数 | 2～3 |

每次均稳定抽取目标关系：

额外关系主要来自以下两个候选：


### 只注入 decrease 的对照

使用完全相同的两阶段输出结构和原文块，只注入 `decrease`，连续运行 10 次：

| 项目 | 结果 |
| --- | ---: |
| 目标句判为 `decrease` | 10/10 |
| 候选数 | 4/4/4/4/4/4/4/4/4/4 |

```text
  the environment and model defenses,
```

### 在旧定义下的判断

方案 B 没有实现候选发现与关系类型集合的隔离：

1. 只注入 `decrease` 时，候选固定为 4 个。
2. 加入 `enable` 后，候选扩大到 6～7 个，最终关系扩大到 2～3 条。
3. 因此，即使输出结构上先列 `candidates`、再列 `relations`，候选发现仍受同一上下文中
   的关系类型定义影响。两阶段只是输出字段顺序，不是独立的发现阶段。
4. `decrease + enable` 的额外关系 10/10 次出现，高于方案 A 中单类型对照的 1/20；
   方案 B 没有消除扩张，只把扩张限制到了候选集合内。
5. 若要让候选发现真正不依赖允许类型，必须把发现与分类拆成两次调用，确保第一次调用
   的上下文完全不出现关系类型定义；同一次调用内仅靠步骤文字无法建立这种隔离。
6. 这里“候选发现受类型集合影响”不等于“新增结果一定是假关系”。当时被计为额外关系的
   `decrease(defenses, malicious tool outputs)` 在实验五修订定义后成为有效关系。因此，
   方案 B 作为“完全隔离类型影响”的机制仍不成立，但作为一种提高关系召回的两阶段输出
   结构，可以继续评估。

## 实验六：v12 两类型下的候选与分类

固定 `decrease + enable`、两阶段结构，连续运行 10 次，使用默认最多 2 次重试。结果如下：

| 项目 | 结果 |
| --- | ---: |
| 成功完成 | 2/10 |
| 校验失败 | 8/10 |
| 成功轮中的目标 `decrease` | 2/2 |
| 成功轮中的防御 `decrease` | 2/2 |
| 成功轮中的 `enable` | 1/2 |
| 成功轮中的其他关系 | 0/2 |
| 成功轮候选数 | 5、7 |
| 成功轮关系数 | 2、3 |

两次成功输出均只包含预期关系：

```text
decrease(Granularly limiting tool permissions, the blast radius)
decrease(the environment and model defenses, malicious tool outputs)
```

其中一次另外输出了：

```text
enable(
  limiting the tool's capabilities and access,
  defenses
)
```

其命题明确对应原文“通过限制工具能力和访问权限，可以在链条更高层添加防御”，是有效关系。
在成功响应中没有观察到额外错误关系。但 8/10 次失败使当前结果不足以证明多类型下的误发现率。

### 失败根因

另做 10 次关闭重试的诊断，仍为 2 次成功、8 次失败。8 次失败错误完全相同：

```text
ValueError:candidate_participants_too_few:4
```

捕获的失败响应中，候选索引 `4` 为：

```text
candidate_id: c5
proposition: 防御措施应当相互重叠并互为补充。
source_span: Defenses should overlap and complement each other.
participants: Defenses
```

该候选没有被最终 `relations` 引用，本身也不是一个具有两个可识别端点的关系；但当前
`_validate_staged_relations` 候选发现阶段要求每个候选至少有两个参与者，因此一个未被分类的
候选会令整份响应失败。开启重试后，模型仍重复产生相同候选，所以 2 次重试也没有恢复。

该问题不是“候选错误导致错误关系发布”，而是“未使用的候选错误阻断了整次抽取”：

1. 候选发现阶段会枚举关系表达和一些单对象陈述；
2. 分类阶段可以只选择其中一部分候选；
3. 当前校验却在分类前要求所有候选都必须满足最终关系的两端点约束；
4. 结果是一个不会被发布的候选使可能有效的两条关系也一起丢失。

### 当前结论

1. 两类型下，加入 `enable` 确实仍会扩大候选集合；成功轮候选数为 5～7。
2. 成功轮的最终关系都有效，没有观察到“多候选导致错误关系发布”的样本。
3. 但当前 B 的主要问题已经是候选校验失败率 8/10，而不是额外关系本身。
4. 在修复候选容错前，不能得到可靠的多类型误发现率，也不应继续扩大样本。
5. 下一步应先决定：未分类候选是否允许只有单参与者，或是否在发现阶段直接丢弃这类候选。

### 候选参与者校验修正

根据“暂时漏掉也可以”的取舍，候选参与者最低数量从 2 改为 1。编译器版本升为
`stage51-direct-relations-subset-prototype-v13`，提示词版本仍为
`stage51-direct-relations-v12`。

使用此前稳定触发 `candidate_participants_too_few:4` 的同一输入，重新执行
`decrease + enable` 两阶段回放，并关闭重试：

| 项目 | 结果 |
| --- | ---: |
| 最终状态 | `succeeded` |
| 实际尝试 | 1 |
| 候选数 | 8 |
| 关系数 | 2 |
| 单参与者候选 | `c5: Defenses` |
| 校验错误 | 无 |

`Defenses should overlap and complement each other` 现在允许以 `Defenses` 单个参与者保留，
不会再因为该候选未展开而丢弃同响应中的其他合法关系。本次只验证候选校验修正，不据此评价
新的多类型成功率或误发现率。

| 独立的 `enable` | 3/10 |
| 未观察到其他关系 | 10/10 |
| 输出 token | 675～1089 |

各轮关系组合：

| 关系组合 | 次数 |
| --- | ---: |
| 目标关系 + 独立防御关系 | 2 |
| 目标关系 + 独立防御关系 + 独立 `enable` | 3 |
| 目标关系 + 合并候选中的防御关系 | 5 |

其中 `T` 为目标关系，`D` 为独立防御关系，`E` 为独立 `enable`，`C` 为合并了防御与
`enable` 两个子句的候选。

### 合并候选问题

5/10 次运行把两个独立子句合并成一个候选，例如：

```text
source_span:
Locally, the environment and model defenses can guard against malicious tool outputs,
but defenses can be added higher up the chain by limiting the tool's capabilities and access.

proposition:
在本地，环境和模型防御可以防范恶意的工具输出，但可以通过限制工具的能力和访问权限
在链条更高处增加防御。

pattern:
decrease

participants:
the environment and model defenses
malicious tool outputs
limiting the tool's capabilities and access
```

这条关系正确包含了防御语义，但 `decrease` 只覆盖第一个子句；第二个子句实际表达：

```text
enable(
  limiting the tool's capabilities and access,
  defenses
)
```

由于两个子句被合成一个候选，且只输出 `decrease`，第二个子句没有形成独立 `enable` 关系。
这不是补造了一条完全无关的假关系，而是候选原子性和关系分类同时出现了漏分。

### 分析结论

1. 候选参与者下限改为 1 后，原先 8/10 的整包失败被消除；10/10 均一次成功。
2. 多候选本身没有产生完全无关的额外关系；10/10 的最终关系都能在原文中找到直接依据。
3. B 仍然不能保证关系实例的原子性。5/10 将两个独立关系子句合并为一个候选，导致第二个
   关系未被分类。
4. 独立 `enable` 只出现 3/10；另外 5/10 被合并候选吞掉，2/10 完全没有抽取。因此当前
   `enable` 召回仍明显低于目标和防御关系。
5. 下一步应调整候选发现规则，使一个 candidate 只包含一个最小关系表达；遇到由 `but`、
   分号或并列结构连接且具有不同谓词或参与对象的关系子句时，应拆成多个 candidate。

## 实验八：证据区域候选与原子关系实例

实验七提出的“按从句拆候选”没有直接实施。修订后的候选表示的是“可能承载零个或多个
关系的连续证据区域”，不要求与最终关系一一对应。一个候选可以产生多个原子关系；每条关系
独立给出自己的 `source_span`、命题和参与对象。因此，候选合并不再被直接视为关系漏分，
真正需要观察的是第二阶段能否从同一证据区域完整枚举其支持的关系。

固定 `decrease + enable`，使用提示词 `stage51-direct-relations-v13` 和编译器
`stage51-direct-relations-subset-prototype-v14`，连续运行 10 次。每轮候选发现不参考
允许关系集合，只有第二阶段注入 `decrease + enable`。

| 最终关系数 | 2～3 |

### 候选发现结果

10 次运行都稳定发现了承载五条预期关系的相关证据区域：

- `c3`：`Granularly limiting tool permissions can help limit the blast radius.`
- `c4`：`An agent with read-only DB access ... can be deployed far more broadly ...`
- `c7`：同时包含环境／模型防御和 `defenses can be added ... by limiting ...` 的连续区域。

因此，本轮的漏项主要不是候选发现失败，而是第二阶段分类不完整：

1. `c3` 稳定被识别为 `decrease`，但从未额外输出其同时支持的 `enable`。
2. `c4` 每轮都成为候选，但从未输出只读数据库访问支持更广泛部署的 `enable`。
3. `c7` 每轮最多输出一个关系；8 次选择 higher-chain 的 `decrease`，7 次选择防御关系的
   `decrease`，只有 5 次同时输出两者，且从未输出 higher-chain 的 `enable`。

最近一次单轮输出中，`c7` 只产生了第一个子句的关系：

```text
decrease(
  the environment and model defenses,
  malicious tool outputs

```

第二个子句实际表达：

```text
enable(
  limiting the tool's capabilities and access,
  defenses can be added higher up the chain

```

### 判断

1. 候选表示成证据区域后，原先“一个复合候选导致校验失败”的问题已被消除；10/10 一次成功，
   且没有产生完全无关的关系。
2. 原子关系结构已经允许同一候选产生多个不同端点关系，但模型仍倾向于为每个候选选择一个
   最显著的关系，说明“允许输出多个”不等于“完整枚举所有支持关系”。
3. `limiting ... by ...` 仍明显受 `limiting` 的表面词义吸引，被判断为 `decrease`。这说明
   第二阶段需要更明确的关系方向和端点判定，而不应继续依赖对限制类词语的直觉映射。
4. 下一步暂不调整提示词。应先把“枚举不完整”和“关系方向误判”作为两个独立问题分别设计，
   避免再次把词面排除规则和结构要求叠加到同一轮修改中。

## 实验九：单一 decrease 关系类型下的证据区域分类

固定实验八的提示词 `stage51-direct-relations-v13`、编译器
`stage51-direct-relations-subset-prototype-v14`、两阶段结构和同一个原文块，只把允许关系集合从
`decrease + enable` 收窄为 `decrease`。连续运行 10 次，关闭重试。

### 汇总

| 项目 | 结果 |
| --- | ---: |
| 成功完成 | 10/10 |
| 每次实际尝试 | 均为 1 |
| 校验失败 | 0/10 |
| 候选数 | 3～4 |
| 最终关系数 | 均为 2 |
| 目标 `decrease` | 10/10 |
| 防御恶意输出的 `decrease` | 9/10 |
| higher-chain 被误判为 `decrease` | 1/10 |
| 只读数据库 agent 被抽取为关系 | 0/10 |
| 未预期额外关系 | 0/10 |
| 输入 token | 均为 1372 |
| 输出 token | 528～651 |

10 次运行时，`c1` 都对应目标句：

```text
decrease(
  Granularly limiting tool permissions,
  the blast radius
)
```

防御句在 9/10 中是第二条关系：

```text
decrease(
  the environment and model defenses,
  malicious tool outputs

```

第 10 次没有选择防御句，而是把 higher-chain 子句抽成了：

```text
decrease(
  limiting the tool's capabilities and access,
  defenses
)
```

模型给出的依据是“`by limiting the tool's capabilities and access` 表达限制工具能力与访问是
增加防御的手段”。这说明它看到了完整的工具手段和防御目标，但“limiting”的词面仍压过了
`by` 表达的使能方向，最终把“使增加防御成为可能”记为“减弱防御”。

### 候选变化

两类型实验八中每轮固定产生 8 个候选；本轮只注入 `decrease` 后，每轮只产生 3 个候选，
其中一轮额外产生环境防御缺失句，共 4 个。虽然两阶段提示词声称候选发现不参考允许关系
集合，实际输出仍然明显受其影响。

每轮稳定出现的三个候选是：

1. 目标句：`Granularly limiting tool permissions can help limit the blast radius.`
2. 只读数据库 agent 句：`An agent with read-only DB access ... can be deployed far more broadly ...`
3. 防御与 higher-chain 的连续证据区域。

只读数据库 agent 句 10/10 都进入了候选，但 10/10 都没有产生 `decrease`。higher-chain
虽然在 10/10 的候选区域内，真正被输出为 `decrease` 只有 1/10。

### 判断

1. 只注入 `decrease` 后，higher-chain 的稳定误判没有复现；1/10 属于低频但真实的语义方向
   错误，不能当作随机噪声忽略。
2. 两类型实验中的 8/10 higher-chain 误判，与同时注入 `enable` 有强相关。原因仍不能仅凭
   本组实验区分为“第二类型扩大了抽取范围”还是“模型在两个类型之间选择了 `decrease`”。
3. 单类型并没有自然恢复只读数据库 agent 的 `enable`，因为该配置根本没有注入 `enable`；
   同时该候选也没有被识别为任何 `decrease`，符合当前关系集合。
4. 候选阶段仍受完整提示词和类型集合影响。当前所谓“候选发现与分类”只是输出结构分开，
   不是模型推理上的严格两阶段隔离。
5. 当前不应通过加入 `limiting` 的词面排除规则来修第 10 次误判。需要先验证：当同一候选明确
   支持多个类型时，如何要求模型逐个类型独立判断，而不是选一个最显著的类型。

同一条原文块中，`Granularly limiting tool permissions can help limit the blast radius.`

| --- | ---: |
| `decrease + enable` | `decrease` 8/10，`enable` 0/10 |

| 仅 `enable` | `enable` 10/10 |

下按预期没有输出。该句是当前“联合类型输出减少独立关系”的最清晰样本。

### 类型隔离后的并集

如果分别执行单一 `decrease` 和单一 `enable`，再合并关系：

- 9/10 的 decrease 运行与 10/10 的 enable 运行合并后，可覆盖目标 `decrease`、第一句
  `enable`、只读数据库 agent 的 `enable`、防御 `decrease` 和 higher-chain `enable`
  五条预期关系。
- 1/10 的 decrease 运行会把 higher-chain 误判为 `decrease`，同时漏掉防御 `decrease`，因此
  该轮合并结果不完整。

这只是把两次独立实验的结果按理想方式合并，并未验证运行时的结果去重、同一候选在不同类型
调用中的稳定性以及 40 种类型全部执行的成本。不能据此直接宣称“逐类型调用已经可行”，但可以
确认它值得作为多类型联合输出受限时的下一项候选方案。

### 判断

1. 单一 `enable` 是本样本上目前最稳定的配置：三条目标关系全部 10/10，无额外关系。
2. 两类型联合输出并不是简单等于两个单类型输出之和。类型集合直接改变了模型对同一句的
   默认解释和候选裁剪，当前两阶段结构没有隔离这一影响。
3. `decrease` 对候选有收缩作用：只注入 `decrease` 时候选从 8 个降到 3～4 个。只注入
   `enable` 时仍稳定为 8 个，说明候选阶段的实际行为还受类型语义本身影响。
4. 下一项应优先验证逐类型抽取后的合并机制，还是继续修改联合提示词，需要先比较两条路线的
   调用成本、关系重复率和候选一致性；当前证据不足以直接确定。

### 三个缺失块的具体情况

#### `b00003`：风险类别与边界绕过语义

#### 应抽取为 `constrain` 的目标

| 原文句 | 是 | 否 | 观察 |

- 判“是”：`具体实现……主要表达一种机制性约束，属于 constrain。`

这说明原因前置并没有迫使模型指出“哪个对象原先可做什么、现在被缩小到哪一子集”。模型仍可
用“机制性约束”覆盖整句，或者用“方案描述”拒绝整句。

#### 不应抽取为 `constrain` 的句子

| 原文句 | 实是 | 实否 | 模型常见理由 |

| 跨平台 Agent 身份是一个开放问题 | 0 | 10 | 均为问题陈述 |
| Agent 应拥有自有身份，还是作为用户延伸并继承权限 | 0 | 10 | 均为待决问题 |

本轮结论：

1. `pattern` 改为是／否后，结构和判定完整性明显稳定，不能再把上一轮的 4 次最终失败归因于
   是／否字段本身。
2. 判定语义仍没有解决：身份方案句只有 1/10 判“是”，子 Agent 只返回结构化事实为 0/10。
3. 非目标句误报已明显下降，但最高的“高信任输出引入注入途径”仍有 3/10 被判为约束；这些
   “是”的共同理由是把条件机制或机制性后果直接称为约束。
4. 原因前置能暴露模型如何理解，但不能替代可操作判定标准。当前主要矛盾是“缩小了哪类对象的
   哪一个可行情景”没有被稳定识别，而不是输出字段顺序。

#### 待合并的提示词修改

- 第一句 `Models and products are advancing fast... our mitigations must keep pace...` 的
  预期判定为“否”。10 次中有 2 次判“是”，说明模型会把“要求／必要性”直接等同于约束。
- 条件本身不是约束：触发条件、前置条件、时间条件、风险发生条件或因果条件，只有同时明确表达
  边界、规则或机制把某个目标对象可行或可接受的情形缩小到一部分时，才可能构成 `constrain`。
- 要求本身也不是约束：`must`、`should`、`need` 等只表达能力、必要性或规范性强度，不能仅凭
  情态词判定 `constrain`；必须进一步指出被限制的对象及其被缩小的情形。
- 条件或要求可以作为命题中的证据背景保留，但不能因为句子包含条件或要求就自动发布约束关系。
- 当前实验只注入关系定义，没有注入源提示词中的“原文判定依据”和“排除边界”。下一步可把三者合并
  为一条可执行判定式：先识别被限制的对象或行动，再指出原文明确排除、禁止或缩减了哪一种原本
  可发生的情形；填不出“被排除／被缩减的情形”时判“否”。
- `缩小`应作为核心谓词，但不能把它实现为关键词匹配。`only`、`limited to`、`scoped-down`、
  `rather than`、`not`、`不得超出`等只是线索；必须能回指目标对象和被排除或缩减的具体情形。
- 单纯触发条件、前置条件、要求或建议默认判“否”；但不要把所有条件句绝对判“否”，因为
  `only when ... can ...` 这类表达仍可能同时给出明确的范围排除。
- 合并后的主定义不要枚举“可行、可接受、可访问、可输出”等具体范围类型；这些只是示例，写成列表
  会诱导模型把它们当成封闭集合。主定义应使用“适用范围”或“可能情形”这类上位表达：原文明确把
  某个对象或行动的适用范围限定为更小的一部分，并且至少能指出一种被排除、禁止或缩减的具体情形。
- 如需帮助理解，可在主定义之外标注“例如权限、访问、可见性、输出内容或行动方式，仅为示例而非
  范围限定”；但首批实验中优先保持主定义抽象，避免再次引入当前领域假设。

下一步应停止在 `b00021` 上继续堆措辞，优先验证两次独立调用：第一遍只发现候选，第二遍只
接收一个候选及必要上下文并做是／否判定；同时把候选参与者原文错误与关系语义判定错误分开
统计。此结论不需要另建实验文档，后续版本继续更新本节及其产物索引。

因此当前定义具备良好的上位关系召回能力，但 sentence 级结果仍需保留原文命题，供后续查询侧
按目标对象和作用范围重新判断，不能只依赖关系标签。

##### 本轮结论

1. 对全部金标准 block，当前定义已经达到 16/16、且全部 10/10 稳定覆盖，直接关系入口的召回

   它能够把候选空间从 26 个 block 扩成几乎全部 block，却不能在 block 级单独完成 c13-003
   的证据挑选。
4. 后续检索必须在“约束证据”之上继续判断约束对象、控制目标和适用边界是否与用户问题相关。

5. 当前定义可以作为后续实验基线，但还不应单独写成最终的 40 模式正式定义；需要先验证它与
   `使能`、`分离` 等其他关系的组合，是否会形成可用的查询侧选择空间。

## 约束关系验证结论

围绕 c13-003 对通用“约束”关系进行的跨块、跨文档验证表明，这一关系定义具有较高的跨领域
召回能力：统一按每块第一次运行、块内句子去重后，15 篇文档的 526 个块中有 449 个块抽出了
约束，共 1,043 条约束句子记录，全库完全相同句面去重后为 1,040 条，平均每个命中块 2.32 条；

作为不依赖具体领域的通用上位关系，有效把原文中的安全边界、权限范围、监督频率、工作区、

找准”。因此更合理的定位是：约束关系作为第一阶段的领域无关高召回入口，先把所有可能有关的

文档仅完成一次块级回放，跨文档结果可说明覆盖，但尚不能说明稳定率。

### 3 个“仅块级命中”的样本

- D08 `b00018`：`harness improvement ... but intelligence is still the core`；
- D15 `b00024`：`--output-format json` 和 `--output-format stream-json` 限定输出格式；

逐项复核：

- D08 `b00018`：块级判断错误。`better deployment` 与 `intelligence is still the core` 是在比较部署能力和模型核心能力，没有主动缩小适用范围。
- D15 `b00024`：块级判断错误。`--output-format json` 是在选择输出表示，原文没有明确把某个适用或可见范围收窄；它更接近“用于”。否则任意格式选择、参数设置或模式选择都会被吸收到“约束”。

### “范围收紧必须显式”的十次对照

根因假设：模型把定义中“目标或原因可以隐含”扩大成“范围缩小关系本身也可以由上下文反推”，于是把比较、使能、重要性、选择参数和设置模式解释为约束。

本轮只增加一条通用语义要求，约束定义不变：

> 目标或原因可以根据完整块上下文推断；但限定动作、被限定对象、缩小后的范围以及“范围被缩小”这一关系本身，必须由原文明确表达，不能从比较、使能、重要性、选择或设置关系中反推。

固定样本包括 5 个正例和 3 个误报：
