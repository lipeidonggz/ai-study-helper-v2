# 5.1 术语与义项判断拆分及最终摘要实验

## 目的

验证把第一阶段模型职责从“术语资格、义项判断和局部摘要生成”收窄为“术语资格与义项归属”，
并把概念摘要统一推迟到义项归并完成后的效果。重点检查：

- 未在原文中显式定义的稳定技术术语是否仍能成为检索入口；
- 术语入口是否能继续形成概念义项，而不是停留在“仅提及”；
- 同一输入重复运行时，入口和义项数量是否比 v5 更稳定；
- 这种职责拆分带来的额外模型调用、token 和耗时是否可接受。

本实验是探索证据，不是产品化稳定性结论。固定输入只有一篇英文技术文章，尚未覆盖中文、混合
语言和未参与提示词调整的留出文档。

## 固定输入与配置

- 文档：`doc_fd4dec9976e041308e2b39ed797c75d1`，即《How we contain Claude across products》。
- 快照：`s51_7f7e71a6b581c451`，1 篇文档、26 个原文块。
- 模型：`deepseek-flash`，`temperature=0.0`。
- 并发：8。
- 最大输入字符：100,000。
- 最大输出 token：8,000。
- 最大重试：2。
- 运行日期：2026-11-12。

## 协议变化

- 术语与义项判断阶段不再返回局部摘要、局部义项标签或摘要依据。
- `resolved` 且没有 `existing_sense_id` 时，只表示该候选进入新建概念义项的归并候选。
- 新建义项即使只有一个草稿，也必须进入义项归并；由归并响应基于完整支持证据生成最终摘要。
- 同一原文块中的显式同指判断只返回关系两侧、证明文本和理由，不再顺带生成摘要。
- 已有地图中的摘要只用于候选导航，不能替代原文证据。

## 什么是“分量”和“分量请求合批”

这里的“分量”不是检索结果分组，也不是 Topic 或 Group，而是**义项归并阶段的一张临时计算图**
中的连通分量：

- 图中每个节点是一个待归并的临时概念义项草稿；
- 两个草稿只要共享至少一个规范化词面，就连成同一分量；
- 同块显式同指已经把不同词面合成同一个草稿，因此不需要在归并阶段再次猜测跨词面同义；
- 不共享词面的两个分量互不依赖，不能在一次归并判断中被合成同一个概念义项。

例如：

```text
block_01：isolation ...  → draft_01，词面 {isolation}
block_17：isolation ...  → draft_02，词面 {isolation}
block_24：logging ...    → draft_03，词面 {logging}

分量 A = {draft_01, draft_02}   # 共享 isolation
分量 B = {draft_03}             # 与 A 无共享词面
```

### 为什么会出现大量请求

新建概念义项必须由归并响应生成最终摘要，即使该分量只有一个草稿也不能跳过。一篇 26 块的文章
会产生数百个临时义项草稿，其中大量词面只出现一次，于是形成大量单草稿分量。拆分版按“一个分量
一次请求”执行，导致单篇产生 286 次归并请求。每次请求都要重复发送完整任务说明和规则，而这些
分量之间本来就没有依赖，固定请求开销被重复了数百次。

### 分量请求合批做什么

“合批”只合并请求的运输方式，不合并分量语义：

1. 按输入预算把多个互不依赖的分量装进同一次模型请求；
2. 每个草稿携带一个仅在该请求内有效的 `component` 序号；
3. 模型仍只能在同一 `component` 内判断哪些草稿表达同一义项；
4. 宿主校验每个输出组只能引用一个 `component`，并校验全部草稿恰好被完整分区一次；
5. 输出组一旦跨分量，整个响应无效并重试，不会采用“模型认为它们相同”的越界结果；
6. 单个分量自身超过输入护栏时仍整组保持未归并，不能拆开做部分归并。

因此，“分量合批”不等于放宽相似度、不再区分词面，也不等于把几百个义项一次性自由合并。它只是把
多个互不依赖的小任务放入同一个请求，减少重复的固定提示和网络往返。批次大小由实际 JSON 字符数
决定，不是按 topic、group、块或草稿数量设置质量阈值。

## 入口与摘要

第二次和第三次运行中，以下目标入口都同时形成术语和概念义项：

- `environment layer`
- `model layer`
- `egress`
- `containment`
- `sandbox`
- `isolation`
- `prompt injection`

第三次运行的摘要能覆盖职责差异，例如：

- `environment layer`：运行环境隔离与配置层次，并说明三种隔离模式。
- `model layer`：模型自身行为约束层，通过提示、分类器、探针和训练修改塑造行为。
- `egress`：数据或流量离开受控环境的路径，通过出站控制限制外部目的地和数据流出。
- `isolation`：虚拟机和沙箱边界内限制代理执行环境及其可见性。

第三次运行有 305 个术语，其中 285 个形成概念义项，20 个保持“仅提及”。未发现少于 12 个
字符的空摘要。

## 稳定性

第二次和第三次运行使用相同代码、模型、提示词和输入：

- 术语数：302 对 305。
- 概念义项数：284 对 285。
- 术语交集：248。
- 术语并集：359。
- 术语集合 Jaccard：0.691。

这比 v5 两次执行的 Jaccard 0.605 更高，但仍有明显条目漂移，不能据此宣布术语稳定性通过。
第三次运行仍有个别可疑入口，例如 `s able`、`addresses`、`approach`、`file`、`users` 等；
关键入口稳定存在不等于术语噪声边界已经解决。

## 成本

拆分后的主要成本从术语判断转移到义项归并。第三次运行的归并阶段：

- 286 次请求；
- 330,729 输入 token、26,607 输出 token；
- 50.31 秒墙钟时间，占总编译时间约 68%。

当前实现把每个互不依赖的归并连通分量分别发起请求，大量单草稿分量形成一次请求。下一项性能
优化已在第三次回放后实现并验证：在协议中显式标注互不依赖的分量，允许一次请求处理多个分量，
并由宿主校验任何输出分组都不得跨分量。两次成功回放的归并阶段为 6 和 8 次请求、17.20 和
24.90 秒；相比拆分版第三次的 286 次请求、50.31 秒，请求数下降约 97%，归并耗时下降约 51%～
66%。总编译耗时从 73.78 秒降到 39.79～46.87 秒，总输入 token 从 538,577 降到 296,843～
328,173。

两次分量合批回放均保留 `environment layer`、`model layer`、`egress`、`containment`、
`sandbox`、`sandboxes`、`isolation`、`prompt injection` 的术语和概念入口。两次术语集合交集
280、并集 384，Jaccard 0.729，高于职责拆分版两次的 0.691，但仍有明显漂移。第一次回放的
部分摘要偏短且中英文混用，第三次则更完整；这更像模型随机性而非合批截断，仍需更多样本确认。

## 结论

职责拆分达到了预期的质量方向：原先缺失的 `environment layer`、`model layer` 和 `egress`
现在可以稳定形成术语与概念入口，最终摘要也不再由局部判断顺手生成。与 v5 相比，术语和义项
数量更稳定，概念入口覆盖明显改善。

当前不能直接宣布方案通过，原因有三个：

1. 合批已把归并请求数从 286 降到 6～8，但总体术语与义项判断仍会发生结构输出失败；
2. 两次合批回放的术语 Jaccard 为 0.729，仍未解决入口漂移、作者名和截断片段噪声；
3. 尚未在未参与提示词调整的中文、英文和混合语言样本上验证。

建议保留职责拆分与分量合批作为候选主路径。下一步优先收敛术语与义项判断协议的结构输出和
入口稳定性，再在留出样本上复核质量和稳定性；在这些验证完成前，A6“单篇找全入口”不能标记通过。
