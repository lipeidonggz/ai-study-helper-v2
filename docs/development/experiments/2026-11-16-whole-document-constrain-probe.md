# 整篇文档约束抽取实验：D04 回归与 15 篇全库回放

## 文档定位

本文记录“整篇文档一次调用”与“逐 block 调用”的约束抽取对照，并固化 D04 人工审查形成的
局部回归标准。这里只研究 `constrain`（约束）一个关系，不修改 14 号设计或正式实现。

本文始终只保留当前版本。实验采用过但已废弃的跨块输出、独立判断区等协议不继续保留；它们不能
作为后续实现依据。

## 一、固定条件

- 快照：`s_6b787258ba7d700c`
- 文档：D04 `How we contain Claude across products`
- 文档规模：26 个 block，27,235 个原文字符
- 关系：`constrain`（约束）
- 模型：`deepseek-flash`
- 参数：temperature 0、thinking disabled、max tokens 6,000
- 逐块基线：`constrain_prompt_layout_v2_behavior_r01_20261116` 至 `r04_20261116`
- 无 candidate 的整篇基线：`constrain_whole_document_blocks_r01_20261116`
- candidate 审查版：`constrain_whole_document_closest_candidates_r01_20261116`

当前约束关系卡是：

```text
定义：
原文表示因为某个目标或者原因（可为显式的或者根据上下文自然推测的隐式表达的），
通过明确的机制、条件或动作，把某个对象、行动或状态的可发生、可执行、可访问、可观察
或可影响范围限定为更小的一部分。

证据与推断边界：
目标或原因可以根据完整块上下文推断；但限制范围所用的机制、条件或动作，被限定的对象或
状态，缩小后的范围，以及“范围被缩小”这一关系本身，必须由原文明确表达。仅说明降低风险、
建立防护、存在边界或限定文章讨论范围，不能据此反推约束。
```

人工审查发现原定义的“范围轴”不完整：`b00001` 明确表达通过控制运行环境来限制 Agent 的
相对损害范围，但原定义只列出适用、可见等范围。2026-11-16 已把“可影响范围”加入当前关系卡。
2026-11-16 已在修订后的定义上完成 D04 冻结回归和 5 次稳定性回放。16 个稳定正例在 5/5 次
运行中命中，7 个冻结负例在 0/5 次运行中命中。`b00025` 作为已知的宽召回误报在 4/5 次运行中
命中；当前接受该高召回偏差，不继续扩写约束定义来修补这一条。

## 二、当前输出协议

整篇请求一次输入全部 26 个 block。模型必须按原文顺序逐块输出：

```json
{
  "relation": "constrain",
  "blocks": [
    {
      "block_id": "b00001",
      "relations": [],
      "closest_candidates": [],
      "has_constraint": false,
      "reason": "该块没有约束的原因"
    }
  ]
}
```

字段约束：

- `relations` 只存放当前块内成立的关系证据；
- `closest_candidates` 只用于判否前复核，最多两条，每条必须包含逐字 `quote` 和具体 `why_not`；
- `has_constraint` 必须与 `relations` 是否为空一致；
- 所有 `quote` 必须是所在 block 的逐字连续子串；
- 不输出跨块关系；
- 每个 block 恰好出现一次，顺序必须与输入一致。

实现入口：[wiki_constrain_whole_document_probe.py](../../../scripts/wiki_constrain_whole_document_probe.py)。

## 三、对照结果

逐块数据取四轮平均。整篇数据均为单次运行，因此只能作为探索证据，不能直接用于稳定性结论。

| 指标 | 逐块四轮 | 整篇无 candidate | 整篇 candidate 审查 |
| --- | ---: | ---: | ---: |
| 模型调用数 | 26 | 1 | 1 |
| 命中 block | 22 | 9 | 15 |
| 证据段 | 28 | 11 | 24 |
| 输入 token | 16,964 | 7,217 | 7,460 |
| 输出 token | 2,952.75 | 1,905 | 4,680 |
| 总 token | 19,916.75 | 9,122 | 12,140 |
| 实际墙钟耗时 | 约 4.04 秒（12 并发） | 8.04 秒 | 21.14 秒 |
| 格式或调用错误 | 0 | 0 | 0 |

整篇 candidate 版命中：

```text
b00002 b00004 b00005 b00007 b00008 b00010 b00011 b00012 b00013
b00014 b00015 b00019 b00020 b00021 b00023
```

相对无 candidate 版，它恢复了此前重点漏掉的 `b00002`、`b00007`、`b00021`、`b00023`，并新增
`b00013`、`b00020`。c13-003 结果达到：

- 六个必需证据组：`6/6`；
- 已知相关 block：`15/22`；
- 返回的 15 个 block 全部落在已知相关集合内。

逐块版仍比 candidate 版多返回：

```text
b00001 b00003 b00006 b00009 b00016 b00017 b00018 b00022
```

这 8 个 block 不能直接视为 candidate 版的漏召回。人工审查表明其中大部分是背景、其他关系、
文章讨论范围或旧提示词的宽解释。

## 四、candidate 审查的作用

candidate 审查要求模型在判否前找出当前 block 中“最接近约束”的局部原文，并说明缺少哪个定义
要素。这改变了原先只对 block 主题作整体判断的行为。

本轮的 11 个判否 block 中，有 9 个返回了候选，共 10 条 `closest_candidates`。这说明模型并非
简单地把所有候选提升为关系：它仍能拒绝只表达背景、副作用或文章范围的句子，同时会重新检查
其中真正包含限制机制的句子。

主要代价是输出 token 和单篇耗时显著增加。candidate 版比无 candidate 版多输出 2,775 token，
总 token 增加约 33%，耗时从 8.04 秒增加到 21.14 秒。

## 五、人工审查后的局部回归标准

本节是本轮形成的人工判定集。它针对 D04 中的争议 block，只标注 `constrain`，属于开发回归集，
不是完整 D04 金标准，也不是独立验证集。

| block | 人工结论 | 判定理由 |
| --- | --- | --- |
| `b00001` | `present` | 通过控制运行环境限制 Agent 的相对损害范围；新定义的“可影响范围”覆盖该关系 |
| `b00003` | `absent` | 描述用户、模型和外部攻击三类风险，并说防御应用于三个组件；这是威胁模型和组成关系，没有限制具体行动范围 |
| `b00006` | `absent` | `Focusing on the environment layer` 是文章讨论范围，不是 Agent 的功能边界 |
| `b00009` | `absent` | 描述有经验用户减少逐步审批、只在 Agent 偏离时监督；这是用户监督行为，对象不是 Agent 能力 |
| `b00016` | `absent` | 中间人代理是事故修复手段，`custom allowlist proxy failed` 是经验总结；没有说明放行、拒绝或缩小后的范围 |
| `b00017` | `absent` | VM 隔离使 EDR 不可见，是隔离的副作用和可见性限制；更像 `separate`，不是主动约束 |
| `b00018` | `absent` | 表格总结 `guarded by gVisor／host infra／vsock／hypervisor boundary`；更像 `protect` 或 `separate`，不应放宽约束定义来命中 |
| `b00020` | `present` | 代理对工具调用执行网络和文件策略，明确限制工具调用的网络与文件访问；返回值检查另可作为 `observe` 候选 |
| `b00022` | `absent` | `We focus on containment in this piece` 限定的是文章讨论范围，不是系统功能范围 |

其中：

- `b00001` 依赖 2026-11-16 修订后的“可影响范围”定义，必须经过修订定义的新运行验收；
- `b00020` 在当前定义下成立，不需要通过扩宽定义来救回；
- `b00016`、`b00017`、`b00018` 不能为了增加 block 召回而混入 `constrain`；
- 一个 block 可以产生多个关系实例，但每个实例必须分别满足自己的关系定义。

## 六、冻结后的回归断言

修订约束定义并把 candidate 审查纳入正式探针后，至少应满足：

```text
b00001：constrain 命中
b00020：constrain 命中
b00003：constrain 不命中
b00006：constrain 不命中
b00009：constrain 不命中
b00016：constrain 不命中
b00017：constrain 不命中
b00018：constrain 不命中
b00022：constrain 不命中
```

该断言集只用于检查本次暴露出的定义边界，不能替代：

- D04 全 26 个 block 的逐块人工审查；
- `separate`、`protect`、`observe` 等其他关系的人工标注；
- 未参与调参的 held-out 文档和主题；
- 多种子、多次运行的稳定性验证；
- 真实问答的最终找全质量。

## 七、D04 当前结论

1. candidate 审查显著改善了整篇路线的局部召回，上一轮四个重点漏块全部恢复。
2. 整篇 candidate 版覆盖 c13-003 的全部六个必需证据组，但单次运行仍不能证明稳定。
3. 逐块多返回的 8 个 block 多数不是严格约束；不能用旧的宽口径 `known_relevant` 直接当作精度目标。
4. 已修订约束定义的适用范围并加入“可影响范围”，不是为单个 block 增加特判。
5. candidate 审查代价较高：总 token 约为无 candidate 版的 1.33 倍，单篇耗时约为 2.63 倍。
6. 在修订定义通过冻结回归和稳定性验证前，不应据此替换逐块路线或修改正式设计。

## 十、15 篇全库回放

### 固定条件

- 快照：`s_6b787258ba7d700c`；
- 文档：15 篇；
- block：526 个；
- 关系卡：当前带“可影响范围”的 `constrain`；
- 模型：`deepseek-flash`；
- 参数：temperature 0、thinking disabled、每篇最大输出 20,000 token；
- 并发：12 篇同时请求；
- 格式校验失败：保持同一提示词最多重跑 2 次；
- 实现入口：[wiki_constrain_whole_document_corpus_probe.py](../../../scripts/wiki_constrain_whole_document_corpus_probe.py)；
- 主运行产物：`backend/.runtime/constrain_whole_document_all15_retry2_20261116/result.json`。

### 执行结果

第一轮全库运行只得到 84 个命中块，且 4 篇因结构校验失败；它只保留为失败记录，不作为比较
基线。加入有限格式重跑后：

- 15/15 篇完成调用；
- 11 篇首次成功，2 篇有效判空，2 篇格式失败；
- 再用最多 5 次格式重跑时，D15 在第 4 次成功，D07 在累计 9 次尝试后仍未通过；
- 最终为 14 篇有效、1 篇未通过结构验收；
- 14 篇共 482 个 block，命中 122 个，命中率 25.31%；
- 122 个命中块产生 211 条证据段、420 个判否候选；
- 14 篇有效结果（含 D15 重跑）共使用输入 134,683 token、输出 89,286 token；
- 15 篇首次并发批次的墙钟耗时为 79.10 秒；D07／D15 恢复批次墙钟耗时 133.10 秒。

D07 的失败不是截断，也不是调用错误。`b00030` 与 `b00036` 的原文是被保存为字符串的
JSON／Markdown 片段，块内包含字面量 `\\n` 和 `\\\"`；模型返回解码后的文本，严格子串校验拒绝。
最终无效输出的块级诊断显示 7 个正判块、13 条关系，但不能计入正式命中。

### 三条路线对比

句子级和块级使用较早的约束定义；整篇级使用当前带“可影响范围”的定义。因此下表只比较模型
是否返回约束证据，不是 precision，也不能把定义差异解释成单一变量实验。

| 路线 | 判断单位 | 有效 block | 命中 block | 命中率 | 输入 token | 输出 token | 已知问题 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 句子级 | 句子 | 526 | 463 | 88.02% | 227,653 | 97,696 | 过切、过标严重 |
| 块级＋证据边界 | 完整 block | 526 | 327 | 62.17% | 333,905 | 54,066 | 4 个结构错误 |
| 整篇级 | 完整文档 | 482（14 篇） | 122 | 25.31% | 134,683 | 89,286 | D07 未验收；长文档明显漏抽 |

### 文档级结果

| 文档 | block | 句子级命中 | 块级命中 | 整篇命中 |
| --- | ---: | ---: | ---: | ---: |
| D01 | 24 | 22 | 14 | 7 |
| D02 | 18 | 16 | 13 | 12 |
| D03 | 17 | 13 | 11 | 7 |
| D04 | 26 | 24 | 22 | 17 |
| D05 | 19 | 17 | 14 | 15 |

| D08 | 39 | 32 | 22 | 11 |

整篇级没有占优：

1. 输入 token 比句子级少 40.8%，比块级少 59.7%，但没有保持相应证据覆盖。
2. 输出 token 高于块级，因为协议要求写全每块判断、理由和判否候选；总 token 并未随输入同比下降。
3. 短文档 D02、D03、D04、D05、D06、D15 仍能形成有意义的局部覆盖。
4. 长文档出现规模性崩塌：D11 从块级 48 降到 1，D13 从 60 降到 0，D09 从 18 降到 0，
   D14 从 17 降到 1。模型都返回了完整 block 记录，不是输出截断，而是把大部分块判成了无约束。
5. 因此“一次输入整篇文档”目前不适合作为找全主路线。它适合继续研究跨块判断或作为低成本
   旁路，但不能替代逐块抽取的证据覆盖基线。

### 当前结论

1. 20,000 输出上限足以避免本轮 15 篇的输出截断；最大输出实际约为 13,104 token。
2. 格式重跑能修复偶发 quote 与字段冲突，但无法修复嵌入 JSON 文本的转义表示差异；D07
   目前保留为明确未验收样本。
3. 全库结果否定了“整篇一次调用可以同时降低成本和保持召回”的假设。真正的问题是长上下文下
   模型对逐块判定的覆盖和敏感度明显下降，而不是 token 上限。
4. 下一步若继续整篇方向，应优先做长文档切片或分层审查；若目标是找全，仍应以逐块抽取为
   主基线，再研究如何降低逐块成本。

## 十一、D14 连续块批次回放

### 固定条件

- 快照：`s_6b787258ba7d700c`；
- 文档：D14《Building Effective AI Agents》，22 个 block；
- 关系卡：当前带“可影响范围”的 `constrain` 定义与证据推断边界；
- 模型：`deepseek-flash`；
- 参数：temperature 0、thinking disabled、每批最大输出 6,000 token；
- 批次：按原文顺序连续切分，分别为 `11+11` 和 `6+6+5+5`；
- 每批一次运行，每个方案只运行一次；批次之间不提供其他批次原文；
- 实现入口：[wiki_constrain_batched_document_probe.py](../../../scripts/wiki_constrain_batched_document_probe.py)；
- 运行产物：`backend/.runtime/constrain_batched_document_d14_2_4_20261116_125213/result.json`。

### 结果

人工确认的通用真约束为 `b00012`、`b00018`、`b00021`；其中与 c13-003 直接相关的为
`b00012`、`b00021`。

| 方案 | 批次 | 命中 block | 通用召回 | c13 相关召回 | 假阳性 | 输入 token | 输出 token | 总 token | 墙钟耗时 |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 整篇 1 批 | 22 | `b00021` | 1/3 | 1/2 | 0 | 5,035 | 3,819 | 8,854 | 14.43 秒 |
| 连续 2 批 | 11+11 | `b00007 b00008 b00009 b00010 b00012 b00013 b00015 b00020 b00021` | 2/3 | 2/2 | 7 | 6,258 | 3,545 | 9,803 | 10.29 秒 |
| 连续 4 批 | 6+6+5+5 | `b00007 b00008 b00009 b00010 b00011 b00012 b00013 b00015 b00021` | 2/3 | 2/2 | 7 | 8,652 | 4,075 | 12,727 | 5.85 秒 |
| 逐块 22 批 | 每批 1 | 17 个 block | 3/3 | 2/2 | 14 | 13,795 | 2,625 | 16,420 | 3.70 秒（12 并发） |

### 结论

1. 连续 2 批已经恢复 `b00012` 和 `b00021`，c13-003 相关召回从整篇的 1/2 恢复到 2/2；
   假阳性从逐块的 14 个降到 7 个。
2. 连续 4 批没有提高通用召回或降低假阳性，只增加 token；D14 上暂未看到相对 2 批的优势。
3. `b00018` 在 2 批和 4 批中都进入了 closest candidate，原文引用准确，但两次都被判为
   “商业模式说明，不是约束”。在 4 批方案中它已经是仅含 5 个 block 的批次首块，仍被拒绝，
   因此该漏抽不是候选发现或上下文长度问题，而是约束语义校验错误。
4. 本次每个方案只运行一次，只能作为方向性证据，不能据此确定批次数量或稳定性。

## 十二、主题独立候选发现规则回放

在不修改约束定义和证据边界的前提下，批处理提示词新增通用规则：候选发现不得根据文档主题、
批次主题或段落主旨预筛选，背景、示例、补充说明和弱主题关联句也必须进入候选检查。该规则只
用于本次 D14 连续 2 批和 4 批实验，不写入关系卡。

## 十九、结构化候选与 runtime 派生成立条件

### 任务拆分

为继续使用整篇一次输入，同时避免让模型直接给出最终 `has_constraint`，新增独立的
`--structured-candidate-judgment` 实验模式。该模式与默认整篇直接判断模式互斥，默认模式不变。

模型只逐块返回候选及以下字段：

- `quote`：当前 BLOCK 中逐字连续的原文；
- `limiter`：执行限制或缩小作用的具体机制、规则、条件、动作或配置；
- `target`：可能性、可接受性、可见性或可执行集合被缩小的对象、行动、状态、输入或结果；
- `excluded_case`：被排除、禁止、跳过、阻止或不再允许发生的一个具体情形；
- `reason`：原文如何分别支持上述结构字段。

模型不能输出 `has_constraint`、`present` 或 `relations`。runtime 仅在 `limiter`、`target`、
`excluded_case` 三者均非空时将该候选规范化为一条成立关系；缺任一字段时只保留为未成立候选。

结构化模式没有复用直接判断模式的证据边界。其候选边界只说明三个字段如何从原文确定、何时填
`null`，以及“常见做法／可选方案／仅被建议”等实践属性不影响候选保留；不再出现“能否判定为
约束”的最终分类要求。

## 二十、显式范围收紧边界下的结构化候选单次回放

第十九节的结构化模式允许模型从建议中补齐三个字段，导致 D14 单次产生 19 条关系。为恢复历史
实验中精度较好的“范围收紧必须显式”要求，把结构化模式自己的候选边界替换为：

1. `limiter` 必须是原文表达的具体机制、规则、边界、条件或配置，不能只是建议、重要性或
   “when needed／appropriate／beneficial”一类泛化决策准则；
2. `target` 必须被 `limiter` 实际约束；
3. `excluded_case` 必须由 quote 中的 `limiter` 直接推出，不能为了填满结构而虚构；
4. 比较、使能条件、重要性、适用场景、一般建议或方案选择，不能支撑候选；
5. 实践属性本身不影响判断，但表达中必须同时存在真实限制机制及其排除范围。

共享的 `constrain` 关系卡不变，只修改 `--structured-candidate-judgment` 的候选边界。D14 整篇
单次结果如下：

- 产物：`backend/.runtime/constrain_structured_candidate_d14_explicit_scope_20261116/`；
- prompt SHA-256：`5c9d2604132fbc9a9e76fa53af3e682e835a1269ba85f643ada159acec66aa1c`；
- 22 个 BLOCK 全部按顺序返回，格式校验成功，无调用失败；
- 命中 3 个 BLOCK、3 条关系、0 条缺字段候选；
- 输入 5,176 token，输出 1,571 token，总 6,747 token，耗时 7.81 秒。

三条关系分别是：

| block | 结构化候选 | 审核结论 |
| --- | --- | --- |
| `b00007` | `programmatic checks` 用于确保流程仍在正轨，排除流程偏离正轨 | 假阳性：原文只表达检查和确保，没有明确拒绝、阻止或排除具体情形 |
| `b00012` | `maximum number of iterations` 限制 agent 执行，排除超过上限的迭代 | 正确 |
| `b00021` | 工具始终要求绝对路径，排除相对路径 | 正确 |

`b00018` 仍返回空候选，未恢复“只对成功解决收费”；按当前优先级不作为本轮失败。三项目标关系
因此命中 2/3，三项目标之外另有 1 条关系。

### 本轮结论

显式范围收紧边界把上一节的 19 条关系收敛到 3 条，输出 token 从 3,624 降到 1,571，说明该
边界确实在抑制一般建议和设计指导被改写为约束。但 `b00007` 表明“检查、验证或确保某状态”仍
可以被模型补写成“排除状态不满足的情形”。若目标是只保留明确的控制边界，下一步边界还需要声明：

> 仅说明检查、验证、监控、确保或评估某个状态，不能仅因为检查失败后可能发现问题就建立约束；
> 只有原文明确表达拒绝、阻止、停止、限制或排除某个具体情形时，才满足 `excluded_case` 的
> 直接推出要求。

该结论仍是单次运行，不能据此证明稳定性。边界下一轮修改后应继续固定 D14 整篇回放，并同时
观察 `b00007` 是否消失、`b00012` 和 `b00021` 是否保持。
