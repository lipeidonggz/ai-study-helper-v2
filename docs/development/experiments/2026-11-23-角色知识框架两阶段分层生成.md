# 角色知识框架的两阶段分层生成思路

- 状态：首轮一级目录回放已完成，待审核；第二阶段尚未开始
- 日期：2026-11-23
- 关联设计：[16 使用角色驱动的领域知识组织](../../design/16-使用角色驱动的领域知识组织.md)
- 关联实验：[角色知识框架提示词减法实验](2026-11-23-role-knowledge-framework-prompt-reduction.md)

## 1 要解决的问题

S5 使用一次调用生成完整角色知识框架。五次同口径结果的总节点数为
360～734，三次较早结果的节点数也从 351 漂移到 507。数量漂移本身不能
单独证明失败，但同时出现的叶节点粒度变化、重复标题、标题可识别性和
`description` 契约不稳定表明：

> 单次调用同时承担了划分全局知识疆域、构造多层树、判断叶节点、生成
> 标题和描述、维持同级边界等多项强耦合决策，已经超过当前生成方式能够
> 稳定完成的范围。

因此本轮不继续通过增加提示词条款来约束完整树，而是缩小每次生成调用
负责的结构范围。

## 2 本轮假设

将完整框架生成拆成两个阶段：

1. 第一阶段只生成一级目录，不生成任何下级节点；
2. 第二阶段对每个一级目录分别调用一次模型，展开该分支的完整子树。

两个阶段使用同一套知识节点要求。确定性程序负责保存第一阶段的一级节点、
安排第二阶段调用，并原样拼装最终树。

本轮要验证的是：在节点语义要求不降低的前提下，按一级分支缩小单次调用
范围，能否显著降低完整树生成中的结构波动和粒度失控。

## 3 非目标

- 不把“每次生成相同的一级目录”作为成功条件。同一领域知识可以有多种
  合法组织方式。
- 不用更多提示词条款硬压节点数量。节点数量应由知识范围、可独立检索性
  和叶节点判据决定。
- 不在本轮同时引入任务树增补、证据挂接、跨次主题归并或查询路由实验。
- 不因采用分层生成，就默认 S5 的 `description` 模板问题已经解决。

## 4 总体流程

```text
领域名称 + 角色名称
→ 第一阶段：只生成一级目录
→ 检查一级目录的结构、字段完整性和主要知识覆盖
→ 第二阶段：逐一级目录独立展开子树
→ 确定性程序原样拼装完整框架
→ 跨分支审核与覆盖验证
```

首轮严格采用“一级目录一批、每个一级目录一批”的调用边界。暂不继续把
每个二级节点拆成独立调用。先验证一级分支是否已经足以把单次任务降到模型
可稳定完成的规模；如果某个一级分支仍然明显超载，再根据真实失败决定是否
递归拆分。

## 5 第一阶段：只生成一级目录

### 5.1 输入

```text
领域名称
角色名称
```

首轮不输入领域说明、角色任务树、知识库内容、测试问题或金标准。领域说明
是否限制知识广度已经由前序实验暴露；本轮不把这个变量重新混入分层生成实验。

### 5.2 输出

第一阶段只输出框架范围和一级节点，不输出 `children`：

```json
{
  "domain": "领域名称",
  "role": "角色名称",
  "framework_scope": "该角色在领域中需要掌握的主要知识疆域",
  "first_level_nodes": [
    {
      "title": "一级知识范围标题",
      "description": "该知识范围包含的内容及边界",
      "exclusions": [
        "确实容易与该范围混淆、但不属于该范围的相邻知识"
      ]
    }
  ]
}
```

这里的“一级节点”是尚未展开的知识范围，不是叶节点。第一阶段不得生成
二级、三级或更深节点，也不得把一级节点直接标记为已经完成拆分的知识主题。

### 5.3 一级节点必须满足的要求

- 一级节点是领域知识范围，不是工作任务、实施步骤、项目安排、交付物或
  产品方案；
- 标题能脱离父路径独立识别所指的领域知识范围；
- `description` 说明该范围需要掌握哪些领域知识以及主要边界，不能只复述
  标题；
- `exclusions` 只记录确实容易混淆的相邻知识，可以为空；
- 各一级节点共同覆盖该角色在领域中的主要知识疆域，不能只列几个示例分支；
- 一级节点允许是复合知识范围，但必须具有一致的知识身份，不能把互不相干
  的知识只是并列塞在一起；
- 不要求固定一级节点数量；数量由知识范围决定。

第一阶段完成后先做一次轻量检查，重点确认：

1. 是否出现工作任务、流程、交付物等非知识节点；
2. 是否漏掉明显的主要知识疆域；
3. 一级节点之间是否存在直接重复或明显包含关系；
4. 标题和描述是否足以说明每个一级范围。

首轮不为此再增加一个独立的 LLM 审查阶段。先由确定性检查和固定覆盖清单
暴露问题；如果一级目录本身已经无法形成可用覆盖面，再讨论是否需要生成后
审查。

### 5.4 一级目录生成提示词初稿

状态：待审核。提示词只向模型描述当前一次生成任务，不解释系统为什么采用
分层生成，也不带入 S5、测试能力项或项目过程信息。

#### 5.4.1 系统提示词

```text
你是一位知识框架设计专家。

给定一个领域和一个岗位角色，请识别该岗位角色在该领域中有效履行职责所
必须掌握的知识范围，并为这些知识生成一级目录。

【任务】
识别该岗位角色在该领域中有效履行职责所必须掌握的知识，并且只生成一级
目录。一级目录用于界定整套框架的大类知识范围，不是最终叶节点，也不在
这一步继续展开。

【一级节点要求】
1. 每个一级节点必须是知识范围，不能是工作任务、实施步骤、项目安排、
   交付文档或产品方案。判断一项知识是否应纳入，依据是它是否是该岗位在
   该领域中有效履行职责所必须掌握的知识，不要求它属于狭义的领域核心知识。
2. 标题应清楚、稳定，脱离父路径后仍能独立识别所指的领域知识范围。
3. description 用一到三句话说明该范围是什么、主要包含哪些知识内容，以及
   这些内容为什么构成同一个知识范围。不要只复述标题，也不要用空泛的
   “基础知识”“相关内容”等措辞代替知识范围。
4. exclusions 只记录确实容易与该一级范围混淆、但不属于该范围的相邻知识；
   没有这种相邻知识时返回空数组。
5. 各一级节点应共同覆盖该岗位角色有效履行职责所必需的主要知识范围，
   不能只列出少量示例，也不能只覆盖该领域内部的技术构成。
6. 一级节点可以是有内部结构的知识范围，但必须具有统一的知识身份；不能把
   互不相干的知识仅因为同属该领域就合并成一个节点。
7. 各一级节点之间不能是同一知识身份的重复表述、同义改名或简单上下位重复。
8. 不预设一级节点数量。节点数量由该角色需要掌握的知识范围决定。

【输出要求】
只输出符合下方输出契约的 JSON，不输出 Markdown、解释或额外文字。
domain 和 role 必须与输入逐字一致。first_level_nodes 中每个对象只有
title、description 和 exclusions 三个字段，不得输出 children 或其他层级。

【输出契约】
{
  "domain": "领域名称",
  "role": "角色名称",
  "framework_scope": "该岗位角色在该领域中有效履行职责所必须掌握的知识范围概述",
  "first_level_nodes": [
    {
      "title": "一级知识范围标题",
      "description": "该知识范围是什么、主要包含哪些知识内容，以及这些内容为什么构成同一个知识范围",
      "exclusions": []
    }
  ]
}
```

#### 5.4.2 用户输入模板

```text
领域名称：{{domain_name}}
角色名称：{{role_name}}
```

输入只提供领域名称和角色名称。提示词中的“领域知识组织专家”只是当前输出
任务需要的能力角色，不额外引入该领域或角色卡中的事实。

## 6 第二阶段：逐一级目录展开

### 6.1 调用边界

对第一阶段冻结后的每个一级节点分别发起一次独立调用。每个调用只负责展开
当前一级节点，不修改其他一级节点，也不重新设计一级目录。

每次调用输入包括：

```text
领域名称
角色名称
完整框架范围
所有一级节点的标题和描述
当前一级节点的完整输入记录
```

提供所有一级节点的紧凑目录，是为了让展开模型知道相邻分支的存在；不传入
其他分支已经生成的整棵子树，避免当前分支被无关局部结构牵制。

### 6.2 输出

每次只返回当前一级目录下的子树：

```json
{
  "parent": {
    "title": "当前一级知识范围标题"
  },
  "children": [
    {
      "title": "二级知识范围标题",
      "description": "该知识范围包含的内容及边界",
      "exclusions": [],
      "children": []
    }
  ]
}
```

返回结果只能为当前父节点增加后代，不能重写父节点的标题、描述或排除边界。
最终树由确定性程序按以下规则拼装：

- 第一阶段的一级节点字段原样保留；
- 当前一级节点接收它自己的 `children`；
- 其他一级节点和兄弟分支不因本次调用发生改变；
- 任一分支失败时保留明确失败状态，不做静默跳过或伪造空子树。

### 6.3 所有新节点必须满足的统一要求

第二阶段生成的每一个节点，与第一阶段的一级节点使用同一套基本字段和知识
性质要求：

- 节点表达领域知识范围，不是任务步骤或交付物；
- 标题脱离父路径后仍能识别其知识身份；
- `description` 说明知识内容和主要边界；
- `exclusions` 只记录真实的相邻边界，可以为空；
- 不生成重复、近义或没有实际知识内容的节点；
- 父节点与子节点之间是知识范围的包含关系，不是实施顺序。

同时增加展开阶段需要的结构性要求：

- 父节点范围内存在两个或更多可以分别命名、分别检索或分别判断覆盖的知识
  范围时，应继续拆成子节点；
- 叶节点只能表达一个知识对象、类型体系、机制、过程、条件、方法、判据、
  模式或案例类别；
- 不得用标题中的“与”、顿号或其他并列表达，把多个本应独立存在的知识范围
  藏在同一个叶节点中；
- 子节点应基本覆盖父节点承诺的知识范围，并尽量保持彼此边界清楚；
- 不要求固定层级和固定子节点数量，根据当前知识范围自然展开。

## 7 需要守住的关键不变量

1. **一级目录先冻结，再展开。**第二阶段不能因为局部展开困难而悄悄改写
   一级目录。
2. **节点要求不因拆分而降低。**不能把第一阶段做成只生成几个粗标题。
3. **每次调用有明确父范围。**不能在没有父节点上下文的情况下自由生成。
4. **宿主负责拼树。**模型只生成当前调用边界内的结构，不负责全局拼装。
5. **失败必须显式。**不能把超时、截断、非法 JSON 或空子树当作正常叶节点。

## 8 首轮验证设计

### 8.1 固定样本

继续使用：

```text
领域：AI Agent
角色：系统架构师
```

模型、温度、thinking、输出上限和输入模板按最终审核版本固定。每个结果
记录实际模型 ID、提示词版本与哈希、输入、原始输出、token 和耗时。

### 8.2 第一阶段

独立生成三组一级目录，不把三次结果先合并。记录：

- 一级节点数量；
- 覆盖固定 14 类知识中的多少类；
- 非知识节点、重复节点、明显包含关系和空泛标题数量；
- `description` 是否说明范围和边界，是否只是标题复述；
- 输入／输出 token 和耗时。

节点数不要求三次一致，但三组结果都必须在主要知识覆盖和节点契约上可用。
不应通过挑选节点最多的一组来掩盖覆盖缺口。

### 8.3 第二阶段

从三组一级目录中选取一组进行首轮分支展开。选择依据是结构、契约和覆盖，
不是节点数量或标题是否更接近某个人工答案。

首轮可以先展开全部一级目录中的二至三个代表分支，验证：

- 每次调用是否只展开当前父节点；
- 父节点字段是否被原样保留；
- 新建节点是否继续遵守统一节点要求；
- 子树内是否出现明显重复、复合叶节点或脱离父范围的内容；
- 单分支调用的 token、耗时和结构漂移是否明显小于 S5 的完整树调用。

如果代表分支稳定，再展开全部一级目录并拼装完整树。最终对完整树执行：

- 确定性的结构、路径和字段校验；
- 固定 14 类覆盖检查；
- 叶节点可拆分性、重复身份和相邻分支重叠检查；
- 与 S5 的五次结果做同领域对比。

### 8.4 成功信号

- 第一阶段能稳定产生覆盖主要知识疆域的一级目录，而不是退化为少量粗泛分类；
- 第二阶段单次调用不再同时承担全局覆盖、完整树组织和多级叶节点收敛；
- 拼装后的完整树在固定 14 类覆盖上不低于 S5 的可用结果；
- 复合叶节点、重复节点和描述模板化问题得到改善，且不是通过把节点普遍缩短为
  粗标题实现；
- 各分支失败可以定位到具体一级目录，而不是整棵树一起失效。

### 8.5 失败与调整条件

出现以下情况时，不继续增加提示词堆叠，先回到阶段边界分析：

- 第一阶段稳定漏掉多个主要知识疆域；
- 一级目录只能依靠大量非知识节点或任务名称来获得覆盖面；
- 各一级分支展开时重复生成相邻兄弟分支的内容；
- 某个一级分支仍然产生数百节点或持续截断，说明“一级分支”还不是合适调用边界；
- 拼装后节点看似更多，但完整覆盖、叶节点质量或描述质量没有改善；
- 第一阶段字段被第二阶段或宿主拼装过程无意改写。

其中“某个一级分支仍然过大”如果重复出现，下一轮再评估是否按二级节点递归
展开；本轮不预先增加这一复杂度。

## 9 当前需要审核的设计点

1. 是否接受第一阶段只输出一级节点，完全不生成 `children`；
2. 是否接受第二阶段向每个一级分支提供“所有一级节点标题和描述”的紧凑上下文；
3. 是否接受首轮由确定性程序原样拼树，且第二阶段不得改写父节点；
4. 是否接受先展开代表分支，再决定是否展开全部一级目录；
5. 一级节点和二级以下节点分别保留哪些统一要求、哪些展开要求只适用于第二阶段。

这五项确认后，再编写两个阶段的正式提示词并开始回放。

### 10.4 结果判断

这一轮的首要目标是把“完整树生成”缩小为“一级目录生成”。仅从当前三次回放看，目标成立：

1. **结构稳定性明显改善。**三次都一次返回合法 JSON，一级节点均为 14 个；没有截断、非法字段、重复标题或意外下级节点。
2. **输出规模显著收窄。**三次输出 token 为 5,514～6,528，耗时约 30～38 秒；S5 的完整树输出为 19,460～39,887 tokens，耗时约 90～169 秒。
3. **主要知识疆域基本齐全，但仍有明确缺项。**三次都形成了基础概念与体系结构、模型能力、规划决策、记忆与知识、工具交互、多 Agent、运行时、安全治理、评估可观测性、人机交互、部署性能和企业集成等主分支；固定 14 项中仍有少数范围没有明确的一级入口，详见 §10.6。
4. **描述契约明显好于 S5。**三次描述中位长度为 86.5～102 字，普遍用两句话说明知识范围、主要内容以及这些内容为何构成同一知识范围；不再是 S5 中大量单句“覆盖 A、B、C 等知识”的模板。三次都主动给出了每个一级节点的排除边界。
5. **组织方式仍有合理差异。**运行 1 单列通信协议和模型基础设施；运行 2 单列外部知识检索、数据反馈和部署性能；运行 3 单列状态持久化和工程化平台。它们对运行时、协议、记忆和外部知识等边界的切法不同，但没有哪一种已经表现出明确的错误。

### 10.5 尚未解决的问题

- 三次都恰好生成 14 个一级节点只是一个回放观察，不能据此把 14 固定为提示词目标或产品规则；
- 一级节点仍允许是较宽的复合范围，例如“安全、对齐、隐私与治理”；这是第一阶段的设计边界，是否适合检索要到第二阶段和任务覆盖审核时验证；
- 三次在“记忆与外部知识”“运行时与协议”“性能与可靠性”的归属上仍有差异，可能导致第二阶段不同分支之间出现重复或覆盖缺口；
- 描述虽然比 S5 完整，但仍有一部分主要靠连续性枚举知识面；目前没有证据要求继续加长描述，也不应把描述长度本身作为质量目标；
- 本轮只验证了一级目录生成，不能据此宣称两阶段完整框架已经可行。

当前结论：一级目录提示词初稿可以进入第二阶段试用，但完整框架验收前必须补查 §10.6 中的缺口。下一步应从一组一级目录中选择有代表性的分支，验证逐分支展开时是否继续满足统一节点要求，以及是否出现跨分支重复。

- 如果比较“单次一级目录的知识丰富度”，S5 的最佳单次结果更好；S5 多次

#### 10.10.5 方法判断

八样本结果说明：

1. **只增加重复调用次数，不能自动得到全面覆盖。**稳定主干会被反复生成，
   低频范围只靠采样偶然出现，另有一些范围八次都没有出现。
2. **最终方法不能是“从 N 个结果中挑一个”。**任何单次结果都会漏掉该角色的
   部分知识疆域，即使它结构最完整。
3. **也不能简单把所有结果首尾拼接。**132 个一级节点里有大量同义、上下位和
   不同粒度的表示，直接拼接会形成重复森林，无法作为检索入口。
4. **第一阶段需要“多视角生成 → 语义归并取并集 → 独立覆盖审查 → 针对缺口
   再生成 → 再归并”的闭环。**语义归并必须保留低频有效范围，而不是按多数投票
   删除少数项。
5. **覆盖审查不能只使用一张固定清单。**固定 14 项能检查已知缺口，却无法发现
   清单外的新知识范围。至少还需要按角色职责、问题类型和知识形态生成独立的
   覆盖视角。

因此当前结果支持把第一阶段改为“覆盖候选生成”，而不是“生成一棵框架”。后续
需要验证的关键问题是：如何把八份结果规范化为一张不重复、同层级、可检索且
尽量不漏项的知识范围并集，并让覆盖审查只补缺口，不凭单次输出重新洗牌。

### 10.11 一级知识框架归并提示词

多次生成只解决候选召回，不能直接得到一套框架。归并阶段的目标是把所有候选
节点按知识身份整理成一套规范化的一级目录，同时保留低频有效范围，并留下可
审计的来源去向。

归并不能只做标题相似度聚类。候选节点可能同义、上下位包含、部分重叠，也可能
一个宽节点内部包含多个互不从属的知识身份。因此，归并需要同时支持合并和拆分。

输入由宿主为每个候选节点分配稳定的 `source_node_id`，例如 `r01-n03`。归并
模型不得自行改写该标识，宿主可以据此检查每个输入节点是否都有明确去向。

#### 10.11.1 系统提示词

```text
你是一位知识框架归并专家。

给定同一个领域、同一个岗位角色下的多份候选知识框架，请将全部候选的一级
知识范围归并为一套规范化框架。候选来自多次独立生成，各份结果地位相同，
出现次数不表示正确性，也不得作为删除低频知识的依据。

【输入】
输入包含：
- domain_name：领域名称；
- role_name：岗位角色名称；
- candidate_frameworks：多份候选框架，每份包含 run_id、
  framework_scope 和 first_level_nodes；
- first_level_nodes 中每个候选节点包含 source_node_id、title、
  description 和 exclusions。

【任务】
根据各候选节点所描述的知识身份，生成一套不重复、同层级、可供后续继续
展开的一级知识范围。

归并后的每个一级节点必须是知识范围，不能是工作任务、实施步骤、项目安排、
交付物或产品方案。一级节点应具有相对完整的知识身份，不得退化为孤立事实或
过窄的知识片段。

【判断知识身份的方法】
1. 两个候选节点属于同一知识身份，必须同时满足：核心研究对象基本一致、
   试图回答的核心问题基本一致、主要知识边界基本一致。只满足其中一项或两项
   时属于部分重叠，不构成同一知识身份。
2. 标题同义、近义、缩写展开、中英文译法不同，或仅更换了组织措辞的，属于
   同一知识身份。
3. 两个节点只因为共享领域名称、岗位用途、上位类别、横向主题或同一应用场景，
   不构成同一知识身份。上位标签相同不是知识身份相同的证据。
4. 上位范围与下位范围不是重复。若下位范围属于某个一级范围，应将其知识身份
   保留在该一级范围的 description 中，不把上下位节点并列成同级节点。若下位
   范围的核心问题不同，并且需要成为独立的高层检索入口，则保留为独立节点。
5. 同一个候选节点包含多个互不从属、需要分别检索的知识身份时，应拆分到多个
   归并节点，不能为了少生成节点而强制合并。
6. description 中列举多个具体内容，不代表必须拆分。只有这些内容分别形成
   独立知识身份，并且需要成为不同的高层检索入口时，才进行拆分。

【归并要求】
1. 候选框架中的全部知识身份都必须有明确去向：进入某个归并节点、作为该节点
   的组成部分被明确保留，或进入 review_items。不得静默丢弃。
2. 低频出现的有效知识同样需要保留。一个范围只出现一次，不是删除它的理由。
3. 归并后的 description 必须综合各候选的有效信息，不能只采用出现次数最多的
   表述。被合并的主要知识身份及关键内容应在 description 中继续可见，避免后续
   展开时丢失。
4. exclusions 只记录真正容易与当前一级范围混淆、但不属于该范围的知识边界。
   合并相互冲突的 exclusions 时，按知识身份和职责范围判断，不使用简单多数投票。
5. 一级节点数量不设目标。数量由归并后的知识范围决定，不得为了凑数拆分，也
   不得为了控制数量而合并不同知识身份。
6. framework_scope 应概括归并后框架覆盖的完整知识范围，不能只复述其中少数
   一级节点。

【来源映射】
为每个输入候选节点在 merge_ledger 中记录且仅记录一条去向：
- equivalent：候选节点与归并节点属于同一知识身份；
- contained：候选节点是某个归并节点的下位知识范围；
- split：候选节点包含多个知识身份，分别进入多个归并节点；
- needs_review：无法可靠判断其归属，不得通过丢弃解决。

target_node_ids 使用归并节点的 node_id。split 可对应多个 node_id；
needs_review 没有可靠目标时返回空数组。
reason 用一句话说明判定依据。

【输出要求】
只输出符合下方输出契约的 JSON，不输出 Markdown、解释或额外文字。
domain 和 role 必须与输入逐字一致。
first_level_nodes 中每个对象只包含 node_id、title、description 和 exclusions。
merge_ledger 必须覆盖全部输入候选节点。
每个 first_level_nodes 的 node_id 必须至少被 merge_ledger 引用一次。
所有 node_id 在各自集合内必须唯一。

【输出契约】
{
  "domain": "领域名称",
  "role": "岗位角色名称",

    {
      "node_id": "K01",
      "title": "一级知识范围标题",
      "description": "该知识范围是什么、包含哪些主要知识内容，以及这些内容为什么构成同一知识身份",
      "exclusions": []
    }
  ],
  "merge_ledger": [
    {
      "source_node_id": "输入中的原值",
      "relation": "equivalent",
      "target_node_ids": [
        "K01"
      ],
```

#### 10.11.2 归并阶段需要验证的指标

- 来源账本是否覆盖全部输入节点，是否存在静默丢失；
- 同义节点是否被正确收敛，低频但有效的范围是否仍然存在；
- 宽节点是否发生错误合并，尤其是包含多个独立知识身份的节点；
- 下位范围是否被误提为一级节点，或上位范围是否吞掉了独立检索入口；
- 输出的一级节点是否仍保持同层级、可识别、可继续展开；
- 归并后的 description 是否保留了被吸收节点的关键知识内容；
- `review_items` 是否真正无法判断，而不是把疑难归并推给人工或宿主。

### 10.12 是否需要八次生成后归并

八次不是当前建议固定的产品参数。本轮回放八次，是为了测量同一提示词在不同
随机运行中的覆盖方差，判断继续增加次数是否仍然有明显收益，而不是证明八次是
正确数量。

目前证据表明：

1. 三次已经稳定形成主要知识主干；追加五次主要增加了低频范围和组织变体，
   全量 token、耗时和归并成本近似线性增加。
2. 八次仍然稳定漏掉部分范围。说明继续增加同提示词运行次数，不能替代独立的
   覆盖审查和缺口补生。
3. 八次也没有形成统计意义上的充分样本。把“八”直接固定成产品参数，只是把
   一个实验选择变成新的硬编码。
4. 当前八份结果仍有实验价值：它们可以用于验证归并提示词是否能正确处理同义、
   包含、拆分和低频保留。这个实验不要求未来每次都生成八份。

推荐把单次角色框架构建分为三步：

```text
基础候选生成（少量独立运行）
→ 按知识身份归并
→ 独立覆盖审查与缺口补生
→ 再次归并
```

在归并方法尚未验证前，暂不决定最终运行次数。若三份归并后的框架已经保留主要
主干，并由独立审查补齐低频范围，就没有必要再做八份同源生成。若后续对照显示
三份与五份在未审查前的召回存在显著差异，再按覆盖率、token、时延和归并复杂度
决定基数。停止条件应由覆盖是否收敛决定，而不是由运行次数决定。

#### 10.13.4 首次归并发现的问题

主要错误是 K16 把安全控制、隐私、法律合规和伦理责任合并为一个一级节点。
这些范围都属于横向治理，但依赖不同专业知识、不同评价依据和不同责任主体，
不能只因为共享“治理”语义就视为同一知识身份。

这个问题也说明当前提示词中的“同一知识身份”判断需要收紧为三个必要条件：

```text
两个候选范围属于同一知识身份，必须同时满足：核心研究对象基本一致、
试图回答的核心问题基本一致、主要知识边界基本一致。

两个范围只是共享领域名称、岗位用途、上位类别、横向主题或同一应用场景，
不构成同一知识身份。上位标签相同不是知识身份相同的证据。
```

该规则不列举任何具体横向类别，也不依赖组织责任划分，可以用于避免“横向大类
下的不同问题被一个容器吞掉”，同时避免为了拆分而把知识切得过碎。

其他需要后续处理的边界包括：

- K12 编排控制与 K17 可靠性都包含重试和补偿。前者应关注控制流机制，后者应
  关注故障与状态恢复，需要在展开时明确证据归属。
- K04 平台基础设施、K08 数据架构、K18 性能成本和 K19 部署运维在缓存、存储、
  弹性和 SLO 上存在交叠，需要以“资源供给”“数据资产”“非功能权衡”和
  “生命周期变更”区分。
- K06 提到提示注入的上下文边界，K16 处理提示注入的攻防与治理；前者是上下文
  装配机制，后者是安全控制，可以在排除边界中进一步说明。
- K14 没有出现 LLM Judge、评测偏差和评价器校准。归并不能凭空补齐候选中不存在
  的知识，这类缺口必须由独立覆盖审查处理。
- Agent 前沿范式与开放问题仍未出现，同样属于归并阶段无法自行发明的候选缺口。

#### 10.13.5 当前结论

归并方法本身基本成立：来源可追踪、低频项可保留、复合节点可拆分、单次组织偏差
可以被消除。当前首要问题不是归并结构，而是“横向关切下的独立知识身份”判断
还不够严格。

下一步应先针对 K16 增加上述通用边界并重放归并，确认安全和隐私／合规／负责任
AI 能稳定拆开。归并结果稳定后，再进入独立覆盖审查，检查 K14 等候选本身缺失的
知识范围。归并提示词不能承担发现候选完全未提及知识范围的职责。

### 10.15 基于已审核一级任务的覆盖审查提示词

归并后的知识框架只证明候选内容已被整理，不证明它覆盖角色职责。下一步使用
已经审核的 13 项 AI Agent 系统架构师主要任务作为覆盖锚点，检查每项任务完成
及关键判断所需知识是否已经在框架中明确存在。

这项审查只判断知识与任务的覆盖关系，不重写知识框架，不评价一级节点宽窄，
也不统计覆盖率平均值。宽节点只要在 title、description 或 exclusions 中明确
保留了任务所需的知识身份，就可以构成覆盖；只出现名称但没有知识边界的，不能
视为完整覆盖。

#### 10.15.1 系统提示词

```text
你是一位知识框架覆盖审查专家。

给定一个领域、一个岗位角色、该角色已经审核的一级任务，以及当前候选知识
框架，请逐项检查当前框架是否包含完成每项任务所必需的知识范围，并找出
遗漏的知识身份。

【输入】
输入包含：
- domain_name：领域名称；
- role_name：岗位角色名称；
- primary_tasks：已经审核的一级任务，每项包含 task_id、task、
  completed_when、inclusions 和 exclusions；
- knowledge_framework：当前候选知识框架，包含 framework_scope 和
  first_level_nodes；
- first_level_nodes 中每个节点包含 node_id、title、description 和
  exclusions。

【任务】
对 primary_tasks 中的每项任务执行覆盖审查：
1. 根据任务的 completed_when、inclusions、exclusions、任务本身和角色职责，
   推导完成该任务及其关键判断所必需的知识范围。
2. 检查当前知识框架的一级节点标题、description 和 exclusions，判断这些知识
   范围是否已经存在。
3. 为每项任务给出 covered、partial 或 missing，并记录提供覆盖的节点和缺失
   的知识身份。

【覆盖判断标准】
1. covered：完成该任务所需的主要知识身份都已经在当前框架中明确出现，并由
   title 或 description 清楚说明其知识范围。
2. partial：存在相关上位范围，但至少一个完成任务所必需的知识身份没有出现、
   只出现了名称却没有说明知识范围，或归属边界无法确定。
3. missing：当前框架没有任何节点覆盖完成该任务所需的主要知识身份。
4. 一级节点可以较宽。不能因为一个节点包含多个知识身份就判定 covered 或
   partial；应检查其 title、description 和 exclusions 是否完整保留了任务
   所需要的知识身份。
5. 一级节点较窄也不能自动判定 covered。必须确认该节点确实能够支持任务的
   全部主要知识需求。
6. 同一个知识身份可以支持多项任务。不要因为多个任务都需要它而生成多个重复
   缺口。
7. 不要求每项任务对应一个或多个独立一级节点。知识身份可以存在于宽节点的
   description 中，也可以跨越多个节点，只要范围明确且没有遗漏。
8. 任务名称是审查锚点，不是知识名称。不能直接复制任务名称作为缺口名称，也
   不能把工作任务、实施步骤、项目安排、交付文档或产品方案列为知识范围。
9. primary_tasks 是已经审核的职责边界。不要增加新的角色职责；发现跨任务
   共用的知识需求时，将其关联到所有确实需要它的 task_id。
10. 不要用固定知识清单代替判断，也不要因为某个知识范围出现次数少、看起来
    边缘或不属于领域技术内核，就认为它不必要。判断依据是它是否确实影响任务
    完成和关键判断。

【缺口判断】
一个缺口必须是尚未被现有框架完整表达的知识身份，不是某项工作动作，也不是
某次交付结果。

对每个缺口说明：
- 具体缺失什么知识范围；
- 为什么完成关联任务必须掌握它；
- 它涉及哪些 task_id；
- 是否能够归入现有节点，还是现有节点无法容纳而需要形成新的知识范围。

suggested_parent_node_ids 只记录确实能够容纳该知识身份的现有节点。没有合适
现有节点时返回空数组，不得为了维持一级节点数量而强行塞入。

如果框架中已经出现相关术语，但只有名称、没有可以继续展开的知识边界，应作为
partial 和缺口报告，不能视为已经覆盖。

【输出要求】
只输出符合下方输出契约的 JSON，不输出 Markdown、解释或额外文字。
domain 和 role 必须与输入逐字一致。
task_coverage 必须覆盖全部 primary_tasks，每项任务出现一次。
covered_by_node_ids 和 suggested_parent_node_ids 必须使用输入中已有的
node_id。
gap_register 中的 gap_id 必须唯一。
所有 task_coverage 中引用的 gap_id 必须存在于 gap_register。

【输出契约】
{
  "domain": "领域名称",
  "role": "岗位角色名称",
  "task_coverage": [
    {
      "task_id": "输入中的 task_id",
      "task": "输入中的 task",
      "required_knowledge": [
        "完成该任务及其关键判断所必需的知识身份"
      ],
      "status": "covered",
      "covered_by_node_ids": [
        "K01"
      ],
      "gap_ids": [],
      "reason": "说明现有节点为何已经完整支持该任务所需的主要知识范围"
    }
  ],
  "gap_register": [
    {
      "gap_id": "G01",
      "scope": "缺失的知识范围名称",
      "description": "该知识范围是什么、主要包含哪些内容、边界在哪里",
      "why_required": "为什么关联任务需要这项知识",
      "required_for_task_ids": [
        "输入中的 task_id"
      ],
      "suggested_parent_node_ids": [
        "K04"
      ],
      "placement": "existing"
    }
  ]
}
```

`placement` 只使用两个值：`existing` 表示可由一个或多个现有节点通过补充或
展开完整承载，`new_scope` 表示现有节点无法完整承载、需要增加新的知识范围。

### 10.16 基于任务覆盖的自动修订闭环

知识框架的覆盖质量不能靠人工逐条补节点，也不能把审查结果直接当成人工待办。这里
采用生成者—检查者闭环：

```text
当前一级知识框架
→ 基于已审核一级任务做覆盖审查
→ 若存在 partial/missing，将审查结论和缺口建议交给框架修订器
→ 修订一级知识分类
→ 用修订后的框架重新做覆盖审查
→ 直到全部任务 covered
```

覆盖审查器只负责判断任务所需知识是否已被框架明确表达，并提出缺口建议；框架修订器
只负责把这些建议落实到一级知识分类中。两者使用不同提示词和不同模型调用，避免同一
次调用既降低覆盖标准又重写框架。

首轮闭环采用保守的“只增补、不删减”约束：

- 现有 `node_id` 全部保留，允许修改 title、description 和 exclusions；
- 必要时新增一级节点，新 `node_id` 必须唯一；
- 不通过删除原有知识范围来制造表面覆盖；
- 修订结果必须通过宿主结构校验，才能进入下一轮覆盖审查。

终止条件：

1. 13 项任务全部为 `covered`，且 `gap_register` 为空，闭环成功；
2. 修订器返回的框架与输入完全相同，判定 `no_framework_change`；
3. 连续两轮覆盖审查仍停在同一组 partial/missing 任务和同一组缺口范围，判定
   `no_coverage_progress`；
4. 达到最大 6 轮仍不能全覆盖，判定 `iteration_limit`。

最大轮次只是异常保护和成本上限，不是用少生成节点来迎合覆盖率的调参旋钮。任何未
全覆盖的结束状态都必须显式失败，不能记为成功。

### 10.18 跨分支求全类问题目录导航

#### 10.18.5 对“运行时临时视角”假设的结论

结论是“部分支持，但不足以直接作为生产路径”：

- 支持部分：四类问题都能跨多个一级分支组合节点；Q1 能形成“治理与元数据、来源加工、
  入库版本、检索证据、审计追踪、删除治理”等临时主题组，说明查询时组合视角是可能的。
- 不支持部分：同一固定问题的关键组召回会随轮次和目录形态变化；单轮不能稳定做到
  找全。当前失败主因不是知识森林缺少知识，而是一次导航同时面对的候选过多、节点粒度
  不统一、输出约束过重。
- 四轮选择结果取并集可以补回多数漏组，但并集规模会膨胀到 59～157 个节点。直接依靠
  多轮并集提高召回，会把精度、上下文成本和后续证据挂接负担转移给下游。

因此，暂不据此启动 847 节点全局语义归并。更窄的下一步是验证分层导航：

1. 第一层只用标题让模型选择可能相关的一级分支和二级区域，不返回所有叶节点。
2. 第二层只把入选区域的子树交给模型做局部找全，并按问题生成临时主题组。
3. 第三层执行覆盖审计：拿“问题、已选区域、未选一级分支摘要”检查是否还有必要区域，
   只补漏而不重选全目录。
4. 第二层存在标题歧义时再按需提供 description；不默认对所有 847 个节点附带描述。
5. 对“必须找全”的问题，可以用 2～3 次独立导航形成共识，但应先在“所在一级/二级区域”
   层聚合，不能无约束合并全部叶节点。

只有分层导航仍稳定漏掉同一关键知识组，或证据挂接阶段证明跨视角重复节点持续挤占
Top-K 时，才重启跨树概念索引或语义归并的设计讨论。

### 10.19 叶节点级导航召回率与精确率重算

#### 10.19.1 评测规则

上一节按关键知识组计算覆盖，只能回答“有没有访问到相应语义区域”，不能区分模型返回了
一个精确叶节点，还是返回了一个包含大量无关后代的祖先节点。本轮把评测单位统一到叶节点：

1. 每个问题维护一个必须叶节点集合 `G`，其中只放回答该问题不可缺少的最低级节点。
2. 模型返回的任意节点 `x` 先投影为 `leaves(x)`：如果 `x` 是叶节点，集合只有它自己；
   如果 `x` 是祖先节点，集合包含它的全部后代叶节点。
3. 一次运行的有效返回叶集合 `U` 是所有返回节点的 `leaves(x)` 并集。父子节点同时返回时，
   通过集合并集去重，不重复计分。
4. `TP = |U ∩ G|`，`FP = |U - G|`，`FN = |G - U|`。
5. `召回率 = TP / |G|`，`精确率 = TP / |U|`，`F1 = 2TP / (|U| + |G|)`。
6. 返回集合恰好等于 `G` 时记为 `exact`；完整包含 `G` 且有多余叶节点时记为
   `complete_with_redundancy`；漏掉任一必须叶节点时记为 `incomplete`。
7. 未知节点、JSON 非法或响应截断使整次运行记为 `invalid`，召回率、精确率和 F1 都按
   0 计入四轮均值，不静默排除失败样本。

各指标的具体定义如下：

| 指标 | 定义与公式 | 回答的问题 | 解释边界 |
| --- | --- | --- | --- |
| 召回率（Recall） | `TP / size(G)`，即被返回集合覆盖的必须叶节点数除以必须叶节点总数 | 回答该问题所需的必须知识是否找全 | 只看漏没漏，不惩罚额外返回；返回整棵一级树也可以得到 1.0 |
| 精确率（Precision） | `TP / size(U)`，即返回叶节点中真正属于必须集合的比例 | 返回结果中有多少是确实需要的，多少是冗余 | 对祖先节点很敏感；返回父节点一次，仍会按其全部后代叶节点计算分母 |
| F1 | `2TP / (size(U) + size(G))`，等价于召回率与精确率的调和平均 | 用单一数值概括找全与纯度 | F1 不能替代“必须找全”门禁；高 F1 仍可能漏掉关键叶节点 |
| 多余叶节点（Extra Leaves） | `FP = size(U - G)`，即返回叶集合中不属于必须集合的叶节点数 | 相对最低必须集合多带出了多少无关知识单元 | 统计单位是叶节点，不是模型原始返回的 `node_ids` 数；一个父节点可能产生多个多余叶节点 |

其中 `size(X)` 表示集合 `X` 的元素个数；`|G|` 是必须叶节点数，`|U|` 是投影并去重后的
返回叶节点数。`U` 为空时精确率按 0 处理，不把空结果解释为“没有错误”。四轮汇总中的
平均值是四个独立运行结果的算术平均；
失败运行按召回率、精确率和 F1 为 0 参与平均，不会从分母中删除。

例如：必须集合 `G` 有 4 个叶节点，返回一个父节点和一个叶节点，投影并去重后
`U` 有 5 个叶节点，其中命中 3 个必须叶节点。此时 `TP=3`、`FP=2`、`FN=1`，
召回率为 `3/4=75%`，精确率为 `3/5=60%`，F1 为 `6/(5+4)=66.7%`，多余叶节点为 2。

该规则直接落实“祖先节点可以算召回，但会降低精确率”。例如返回一个一级根节点，虽然会
召回其下所有必须叶节点，但也会把整棵一级树中的其他叶子全部计为多余返回。

2. 精确命中为零不是指没有命中知识点，而是指模型几乎从不只返回必须叶节点。其典型行为是

### 10.20 一级分支隔离的叶节点并行选择

状态：提示词已经沛东审核，并完成首轮模型回放；首轮结果见 §10.20.6。

#### 10.20.1 本轮目标

本轮只验证一个最小问题：把 24 个一级分支完全隔离，每次调用只让模型看一个分支的
叶节点目录，能否得到较好的叶节点级召回与精确率。

本轮不引入以下机制：

- 不让模型先筛选一级分支；
- 不把父节点或祖先节点作为可选答案；
- 首轮不提供叶节点 description 或 exclusions；§10.20.7 的复验只补充 description；
- 不做跨分支漏项审计；
- 不做多次运行并集；
- 不引入 BM25、向量检索或候选回调。

这些机制只有在单次分支隔离叶子选择仍存在明确问题时再逐步加入。

#### 10.20.2 调用单元与输入

对每个固定问题、每个一级根节点分别调用一次。第一阶段固定为：

```text
4 个问题 × 24 个一级分支 = 96 次调用
```

同一问题的 24 个分支调用并行执行，分支并发上限固定为 24；不同问题暂时顺序执行，
避免一次启动 96 个请求。若供应商实际限流，必须记录实际并发、失败和重试，不得静默
降级成串行后仍宣称完成 24 路并行。

每次调用只包含：

```json
{
  "question": "用户原始问题",
  "first_level_branch": {
    "node_id": "K08",
    "title": "一级分支标题",
    "description": "一级分支完整描述",
    "exclusions": ["一级分支排除边界"]
  },
  "leaf_directory": [
    {
      "leaf_id": "K08.05.01",
      "path": "K08 > K08.05 > K08.05.01",
      "title": "代码执行沙箱",
      "description": "代码执行沙箱的知识范围、边界与治理要求"
    }
  ]
}
```

不提供 `domain_name` 和 `role_name`。用户问题本身已经表达领域语义，一级分支和叶节点
完整路径已经承载当前角色知识框架的观察视角。重复提供领域名、角色名不会提供新的选择
依据，反而可能强化模型对角色名称的先验联想，诱导它忽略框架中已经存在的相邻知识范围。

`leaf_directory` 只包含该一级分支下的真实叶节点。路径包含根、祖先和叶节点标题，
但祖先不是候选项，只用于恢复叶节点的知识语境。§10.20.6 的标题模式只提供 `leaf_id`、
完整路径和标题；§10.20.7 的复验增加叶节点 `description`，用于区分相邻叶子的细微
知识边界，仍然不提供 `exclusions`。当前森林总计 620 个叶节点，单个一级分支拥有
16～53 个叶节点，因此每次调用的候选规模可控。

#### 10.20.3 系统提示词

系统提示词：

```text
你是一个叶节点知识召回器。每次调用只处理一个一级知识分支。

你会收到：
- question：用户要完整回答的问题；
- first_level_branch：本次允许检查的一级知识分支；
- leaf_directory：该分支下全部叶节点的 id、完整路径、标题和 description。

【任务】
找出为了完整回答用户问题，本分支内所需的所有叶节点。必须逐项检查
leaf_directory，不能只根据一级分支标题判断整个分支无关，也不能看到第一个相关叶节点
就停止。

【选择规则】
1. 只能返回 leaf_directory 中逐字存在的 leaf_id，不得编造或改写编号。
2. 祖先路径只用于理解叶节点的知识语境，不是候选知识节点；不得输出父节点或路径编号。
3. 对相关叶节点给出层级：
   - required：如果不召回该叶节点，用户问题中至少一个明确方面会缺答案，或者答案会
     不完整。reason 必须写出会缺少的具体知识内容，不能只写“支撑理解”“提供基础”
     “帮助定位”“便于建模”等泛化作用。
   - optional：能提供例子、背景、相邻视角或扩展知识，但不召回不会导致核心答案缺失。
     这类叶子可以返回，但不能算作满足必要知识覆盖。
4. description 描述该叶节点整体覆盖的知识范围，不是候选证据。要结合 description
   判断它能否实际帮助回答问题；不要仅因问题与标题或 description 共享关键词就选择，
   也不要把 description 中偶然出现的一个词当成完整选择依据。
5. 同一个 leaf_id 只返回一次；不同叶节点即使表达相近或重叠的知识，也不要自行做跨
   节点互斥选择或合并，节点级重复留到后续证据块关联阶段处理。
6. 本分支只能提供部分答案时，返回本分支确实相关的叶节点，不要推测其他分支内容。
7. 如果逐项检查后本分支没有任何叶节点能帮助回答，返回空数组。
8. 选择应尽量少而完整：漏掉一个确有回答价值的叶节点比多返回一个边界叶节点更严重，
   但明显无关或只提供泛化背景的叶节点不要加入。

【输出】
只输出 JSON，不得输出 Markdown 或额外说明：
{
  "selected_leaves": [
    {
      "leaf_id": "目录中的叶节点 id",
      "tier": "required 或 optional",
      "reason": "该叶节点能回答哪个必要方面，不超过50字"
    }
  ],
  "branch_reason": "本分支整体为何相关或为何为空，不超过100字"
}
```

用户消息只序列化上述输入对象，不附加问题特例、金标准、已有选择结果或其他一级分支
信息。

#### 10.20.4 宿主校验

每次分支调用至少校验：

1. JSON 合法且未截断；
2. `selected_leaves` 是数组，`branch_reason` 是非空字符串；
3. 每个选择项必须包含 `leaf_id`、`tier`、`reason`，其中 `tier` 只能是 `required`
   或 `optional`；
4. 每个 `leaf_id` 在当前分支的 `leaf_directory` 中唯一出现；
5. 不得出现根节点、内部节点、其他分支叶节点或编造编号；
6. 模型返回总数为 0 时是合法的“本分支无相关叶子”，不能当作解析失败；
7. 出现未知 ID、父子节点混淆、重复 leaf_id 或非法字段时，本次分支运行记为失败，
   不得静默删除非法项后继续计分。

提示词中的 reason 字数上限是写作约束；原因是非空的硬条件，超过建议字数只记录警告，
不能因此丢弃合法叶节点选择。JSON 截断、非法字段和非法节点引用仍然是阻断错误。

一个问题的全局叶节点结果分别形成 `required` 集合和 `required + optional` 集合。任一
分支调用失败时，整个问题运行必须显式标记为不完整，不能用其余 23 个分支结果冒充完整
召回。

#### 10.20.5 观察指标

本轮沿用 §10.19 的必须叶节点集合和指标定义，但分别计算 `required only` 与
`required + optional` 两种返回集合，不进行父节点后代展开。记录：

- 每个分支返回的叶节点数和耗时；
- 24 个分支的联盟召回率、精确率、F1 和多余叶节点数；
- 哪些问题出现分支失败或空返回；
- 每个必须叶节点由哪个分支、经过哪些运行召回；
- 分支内漏项、全局跨分支漏项和边界误选的具体叶节点；
- 输入 / 输出 token、总延迟、实际并发和提示词哈希。

结果必须先判断该最小方案是否值得继续，再决定是否加入 description、分支审计或多轮

而是明显改变了答案空间。

48 个消失项按一级分支分布如下：

| 一级分支 | 消失的 required 数 | 代表节点 |
| --- | ---: | --- |
| K04 工具调用与互操作 | 1 | 异构工具生态互操作适配边界 |
| K06 知识检索与 RAG | 2 | RAG 运行时位置、离线准备与在线检索分层 |
| K07 多 Agent 协作 | 1 | 团队结构与角色分配 |
| K08 运行时与执行控制 | 2 | 代码执行沙箱、浏览器自动化执行环境 |
| K09 平台与基础设施 | 6 | 容器与 Kubernetes、Serverless、GPU、存储、消息队列、向量数据库 |
| K10 数据架构 | 2 | 查询接口契约、查询路由与访问路径 |
| K11 评估测试 | 1 | 提示注入与越狱测试 |
| K13 可靠性 | 2 | 失败影响范围、检查点与状态恢复 |
| K16 安全架构 | 2 | Agent 攻击路径与信任边界分析、执行环境隔离与沙箱架构 |

其中 `K08.05.01 代码执行沙箱` 和 `K16.06.01 执行环境隔离与沙箱架构` 在 required
与 optional 中均未返回，符合题面的明确排除；`K16.01.02 Agent 攻击路径与信任边界
分析` 从 required 降为 optional，原因写明“提供边界划分的分析视角”，但题面并未排除
信任边界分析，这一降级是否合理仍需人工判断。容器、Kubernetes、Serverless 等 K09
节点被模型当成沙箱或运行基础设施的同义扩展而移除，也不能仅凭“题面没列这些词”判为
错删。

新增的 28 个 required 主要来自以下方向：

| 方向 | 代表节点 |
| --- | --- |
| 人工监督与中断恢复 | 超时与取消控制、重试执行控制、人工介入中断与恢复 |
| 多 Agent 协作与共享状态 | 共享工作空间、共享状态一致性、协作协议与终止条件 |
| 数据与隐私治理 | 同意治理、数据主体权利、去标识化、保留策略、删除与销毁、跨境流动 |
| 审计与来源可信 | 审计记录完整性验证、审计事件来源认证 |
| 规划与风险控制 | 风险与应急规划、停止条件与计划完成判定 |

这说明模型执行了“排除已知项、继续枚举其他项”的语义操作。两个明确排除的沙箱叶节点
消失，同时新增人工监督、数据治理、审计和多 Agent 协作等原本属于 c13-003 关注范围的
边界。另一方面，137 个 required 中仍有大量相邻知识，例如参数校验契约、通用架构接口、
失败恢复和合规治理；这说明 `required` 目前仍是“优先召回集”，而不是严格的最小必要
答案集。尤其原 c13-003 的“上下文与记忆生命周期边界”在本轮主要落在 optional：
`K05.05.02 记忆遗忘与过期`、`K05.06.01 上下文预算分配`、`K05.06.02 上下文窗口裁剪
与优先级`。若这些属于 c13-003 的核心答案，则当前 required 仍存在漏项或分级偏差。

结论是：排除条件已经能稳定改变 required，但不能继续用通用 Q2 的 20 项金标准评价
排例题，也不应因为旧召回率降到 0.85 就回改提示词。下一步应为 c13-003 建立独立的
叶节点目标集，并逐项复核三类边界：明确排除而消失的节点、模型自行归入排除项的 K09
基础设施节点，以及从 optional 提升为 required 的数据治理、审计和人工监督节点。完成
这轮人工定标后，才适合判断是否需要二次必要性判定或调整 required 定义。

#### 10.20.13 增加“分别说明各限制什么”后的 required 变化

本节继续沿用 §10.20.12 的模型、提示词、24 个一级分支、620 个叶节点、仅标题输入和
关闭 thinking 的配置，只把问题进一步改成 c13-003 的完整表述：

```text
除了沙箱、虚拟机和出口控制，AI Agent 还有哪些隔离或控制边界？请分别说明各限制什么。
```

本轮表明，“请分别说明各限制什么”能把选择往可执行的控制机制上推，并让 reason 更接近
问题要求；但它没有解决 required 层级过宽的问题。模型仍会把任务分配约束、群体决策规则
和通用质量属性策略当作控制边界，同时把上下文预算、窗口裁剪和记忆过期稳定放在
optional。后三者正是 c13-003 已确认的核心组“上下文与记忆生命周期边界”，因此当前
主要风险已经从单纯多召回转为“弱边界升级、核心边界降级”的混合分类错误。

因此暂不根据这句话再次修改提示词。下一步应先按 c13-003 的 7 个核心组和 4 个扩展组
建立独立叶节点金标准，检查 `required` 是否稳定覆盖核心组，并用该目标集区分“合理扩展”
与“弱相关误升”。在新的目标集完成前，本节的 126～131 个 required 只能视为开放式求全
问题的候选答案集，而不是最小必需集。
