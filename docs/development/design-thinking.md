# 设计思考记录

本文件记录尚未完全定稿、但值得跨切片保留的设计观察、判断变化和待验证假设。

它不是设计基线，也不替代 ADR、设计文档或垂直切片记录。一个思考点形成稳定结论后，应
提升到对应的 `docs/design/` 文档、ADR 或切片，并在这里保留结果和链接。记录按 `T-NNN`
编号，不按日期维护流水日志。

## 记录格式

每个思考点至少记录：

- 状态：`讨论中` / `已吸收` / `已否决`
- 触发问题：为什么开始思考这个问题
- 当前判断：目前认为成立或需要验证的结论
- 边界与反例：哪些情况下结论不成立
- 未决问题：还没有确定的设计细节
- 关联记录：相关设计、切片、ADR 或实验

## T-001：Topic 身份有效性与知识充实度分离

- 状态：已吸收
- 触发问题：单篇文档只把 `long-term memory`、`middleware`、`skill` 等名称作为
  harness 组件列出，没有给出各自定义。是否应该因此删除这些“空壳”候选？
- 当前判断：不应删除。单篇抽取无法预知未来文档是否会补充定义、机制或用途；稳定名称
  和真实父级成员关系已经足以形成未来证据的挂接点。Topic 的身份有效性与当前知识充实度
  是两个不同状态。
- 边界与反例：空壳不表示可以随意制造摘要。摘要仍只能表达当前证据支持的内容；多个
  候选共享父级列表摘要时，不应伪造差异，也不应仅凭相同摘要合并 Topic。
- 关联关系：父机制、成员列表或结构位置不能只由 Group 保存。Group 可以因为检索语义
  重新划分，但最初的上下文关联必须继续从来源证据或独立关系记录中恢复。
- 未决问题：上下文关联最终采用来源 Block 推导、候选选择理由中的结构化字段，还是独立
  关系对象；空壳状态是否需要在产品界面显式展示；检索时应如何降低空壳对结果噪声的影响。

## T-002：预编译知识视角与查询视角之间存在结构性缺口

- 状态：讨论中
- 触发问题：当前检索能否答全，取决于预编译是否生成了与问题相关的 Group；但 Group 的
  划分受 Profile 和编译时取舍约束。以 `c13-003` 为例，“隔离与控制边界”不是一个
  Agent 领域的主分类，而是横穿执行环境、凭证、工具、外部内容、并行状态、上下文和子
  Agent 等功能切面。
- 当前判断：单一知识主划分无法覆盖用户从任意角度提出的问题。一个 Group 划分只是知识
  空间的一种投影；加入横切 facet 可以缓解视角错配，但不能消除问题。
- 结构性限制：即便建立多套横切 facet，它们仍然是预编译阶段选定的有限视角、有限粒度
  和有限组合。问答阶段可能出现新的功能切面、风险切面、生命周期切面或用户自定义角度，
  其理论空间无限；任何静态分类系统都只能近似覆盖。
- 当前架构顺序带来的实际风险：系统先选 Group，再展开 Topic、Aspect 和 Block。若正确
  证据分散在多个单独看只弱相关的 Group 中，后续 Aspect 和 Block 选择无法恢复第一层
  路由没有带入的内容。Group coverage repair 只能缓解已发现的覆盖缺口，不能证明完整。
- 候选方向：把 Group 定位为降低复杂度的快速路由层，而不是完备性权威；增加与 Group
  独立的多维 facet 召回平面；同时明确“答全”只能定义为相对于当前查询、Profile、facet
  契约和证据范围的覆盖，而不是对理论无限视角的绝对保证。
- 边界与反例：不能把覆盖槽位或 facet 直接升格为新的 Topic 身份，否则会重新制造入口
  膨胀和身份不稳定；也不能因为增加 facet 就声称解决开放视角问题。facet 本身仍是一种
  有损压缩，只是比单一主划分保留更多查询入口。
- 未决问题：Profile 应表达哪些稳定的 facet 轴；facet 由 Topic 派生、由 Block 派生，
  还是允许独立登记；有限 facet 与查询时受控扩展如何结合；如何为“相对于契约的覆盖”
  建立可执行验收；Group 路由与 facet 召回如何融合并共同控制噪声。
