## 控制契约

### 用户可观察目标

1. 连续提交多个入库任务时，同一时刻只执行一个任务，其余任务明确显示为排队。
2. 应用在入库过程中重启后，用户可以从操作记录找到中断任务并恢复或取消。
3. 部分成功任务在当前任务卡片和历史记录中都统一显示为“部分入库”，不显示成全部完成。
4. 用户通过正常界面即可继续创建新批次，并能持续看到全部非终态任务；不需要刷新页面或使用快捷键触发隐藏能力。

### 核心不变量

1. 任意时刻最多只有一个入库任务进入执行状态，所有任务共享同一串行调度顺序。
2. 恢复 interrupted 任务时保留 `next_source_index`、成功 job IDs 和失败清单，不重复处理已完成来源。
3. `succeeded + failed_sources > 0` 在任务卡片和操作记录中使用同一个“部分入库”语义。
4. 排队任务被取消后不得再启动；应用重启不得自动恢复未获用户确认的 interrupted 任务。
5. 页面刷新或重启后，queued／running／paused／interrupted 任务必须从持久队列恢复显示。

### 明确禁止

- 禁止两个任务同时调用 embedding 或发布 collection。
- 禁止在应用重启后静默自动重发可能已产生费用的请求。
- 禁止把 queued／paused／interrupted 任务显示成已完成。
- 禁止把 partial 任务的进度条和状态徽标显示成全部成功。

### 失败语义

| 场景 | 用户看到什么 | 系统保留什么 | 是否可恢复 |
| --- | --- | --- | --- |
| 提交时已有任务运行 | 新任务显示“排队中” | 完整来源队列和顺序 | 是 |
| 应用在任务运行时退出 | 重启后显示“已中断” | 下一来源索引、成功 job IDs、失败清单 | 是，需用户显式恢复 |
| 排队任务被取消 | 显示“已取消” | 取消记录，不进入执行 | 否 |
| 部分来源失败 | 任务显示“部分入库” | 成功 snapshot 和失败来源 | 可从失败来源重试，后续切片实现 |
| 调度器自身异常 | 当前任务显示失败或中断 | 已持久化进度和错误 | 视错误而定 |

### 人工检查点

- 编码前确认：两项 B 级决策——串行调度模型、历史恢复交互。
- 实现中途：提供两个任务连续提交的状态观察，确认第二个保持 queued。
- 完成后：人工重启应用并恢复 interrupted 任务，再检查 partial 状态展示。

### 决策预算

- 预计 B 级决策：3 项。
- C 级决策：无。
- 超过预算时：优先保留串行执行和恢复，拆分 partial UI。

## 目标

让后台入库任务的“串行、可恢复、部分成功可见”与现有设计和用户界面承诺一致。

## 输入与输出

输入：

- 一个或多个后台入库任务；
- 任务启动、暂停、取消、恢复请求；
- 应用重启后持久化的 queued／running／interrupted 状态。

输出：

- 单一执行的串行任务队列；
- 可从操作历史恢复或取消的中断任务；
- 当前卡片和历史记录一致的部分入库状态。

## 不包含

- 单篇文档删除、改名和跨来源合并；
- collection 回滚 UI；
- 只重试失败来源；
- embedding 成本和 token 统计；
- 历史记录分页、搜索和清理。

## 验收条件

- [x] 两个任务连续提交时，只有一个进入 running，另一个保持 queued。
- [x] 任意时刻 embedding 调用不会超过一个任务。
- [x] 应用重启后，历史中的 interrupted 任务可恢复或取消。
- [x] 恢复后的任务从原 `next_source_index` 继续。
- [x] partial 任务在当前卡片和历史记录中统一显示“部分入库”。
- [x] 失败任务的进度视觉不会表现为全部成功。
- [x] 当前任务运行时仍可在正常界面创建下一个任务。
- [x] 页面刷新后可以从后端恢复完整非终态任务队列。
- [x] 排队任务可以从界面取消。
- [x] 真实界面人工验收通过。

## 反向解释

1. 连续提交两个任务时，第二个任务为什么不能立刻开始？
2. 应用在 S5 中途重启后，恢复任务会不会重复处理已经成功的来源？
3. 一个任务已有成功 snapshot、但部分来源失败时，用户应该看到什么状态？

## 协作复盘

- AI 负责把多任务 worker 重构为单 dispatcher，并补齐状态展示函数。
- 人负责把“设计要求串行”提升为可观察不变量，并要求历史恢复入口和 partial 语义一致。
- 真正有效的控制点是“最大并发调用数”和“状态标签一致性”，不是只检查代码中是否有一个 dispatcher。
- 下次类似切片应同时给出机器可测的调度不变量和用户可判断的状态问题。
- 人工验收发现“只能靠刷新触发排队”的隐藏能力，证明后端已支持的能力不等于用户可达能力；控制契约必须包含正常操作路径。

## 已知风险与后续

- 单进程 dispatcher 不能覆盖用户同时启动多个独立应用进程的情况；若要支持多进程，需要额外文件锁或单实例机制。
- 恢复行为不能保证云端已发出的请求不重复计费，只能保证不自动重发和保留已记录进度。
