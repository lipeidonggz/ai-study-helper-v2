## 控制契约

### 背景与失败场景

- 触发问题：c13-003 原 R1/R2 的“核心边界／扩展边界”命名与内容存在交叉，`包括／例如`未说明是否为必选子项，R3 又依赖 R1/R2 的判定结果，无法作为独立 criterion 执行。
- 用户损失：同一答案可能因分类口径而不是知识覆盖质量被判 pass／fail，无法用于判断 Agent 是否真正完成跨文档找全。
- 现有流程不足：主判官只接收答案与单条 criterion，无法自行验证“文档事实依据”；虚构 citation 也无法靠生成判据稳定拦截。

### 用户可观察目标

c13-003 的核心知识点、扩展知识点和边界分别有明确覆盖规则；答案可以使用自己的分类和措辞，只要语义角色可辨认即可判定。

### 核心不变量

1. R1 的四个核心知识点必须全部覆盖，每类必须表达限制对象或作用；括号内示例均为可选示例。
2. R2 从四个扩展知识点中至少覆盖两类，每类必须表达限制对象或作用。
3. 一个机制可以支撑多个知识点，但答案必须分别表达对应的限制关系。
4. 删除依赖其它 criterion 的文档事实依据 R3；引用真实性由引用机制负责。
5. 删除无法仅凭答案判定的冒充文档 X1；来源可溯源由全局红线和引用机制负责。

### 明确禁止

- 不得把可选示例当成额外必选子项。
- 不得要求答案采用本用例的分类名称或层级。
- 不得让 X1 重复判定引用支持或来源可追溯。
- 不得在沛东复核前把新 revision 激活为 active。

## chat-v18 提示词试验

尝试用通用“证据范围／完整性责任”规则替换关键词触发的 coverage 规则，
并通过代码检查确认提示词不含“隔离”“worktree”“子 Agent”等本用例术语。
产品等价回放结果：

- run：`run_297cc332677943cb9c2204ae4d130be9`
- judgment：`evalrev_51181c45b6cb4a9c9f81c1efee22f8bd`
- R1：0 pass、10 fail。
- R2：9 pass、0 fail、1 pending。
- X2：10 pass、0 fail。
- 10/10 trace 仍为 `list_documents → get_outline → list_blocks`，均只读取一篇文档。
- 工具调用仍为 30 次；多文档检索样本仍为 0。

结论：chat-v18 的通用提示词没有改变检索范围决策，只增加了约 6% 输入
token，不能解决当前问题。已撤回 chat-v18，生产提示词恢复为 chat-v17；
本轮 trace 和判定保留供分析。

## chat-v19 降级依据试验

进一步尝试把 `finish.decision_summary` 从提示要求升级为协议必填，
并要求模型说明正常完成或降级的具体依据。定向协议与 Agent 测试通过，
但 c13-003 回放结果不成立：

- run：`run_a8c594adc94c42878dcffef974740d0d`
- judgment：`evalrev_e30939ea542b472e8c5c434fb575c73e`
- 10 个有效样本，7 个成功、3 个产品协议失败，并触发 1 次基础设施替换。
- R1：0 pass、10 fail。
- R2：10 pass、0 fail。
- X2：10 pass、0 fail。
- 工具调用：39 次；仍然没有任何样本读取第二篇文档。
- 模型调用：82 次；输入 814,170 tokens，约为 chat-v17 的 2 倍。

成功的样本都写出了结束依据，但依据主要是：

- “该文档范围内已完整覆盖”；
- “其它文档主题不相关，无需继续检索”；
- “未逐篇检查其它文档，因此降级为范围限定”。

这说明强制解释降级没有促使 Agent 先完成候选发现，只是为原有单篇停止
行为补充了合理化说明，并引入协议失败与显著成本。已撤回 chat-v19
及 `finish.decision_summary` 必填协议；保留其 trace 记录和
`app.decision_summary` 观测字段，生产提示词恢复为 chat-v17。
