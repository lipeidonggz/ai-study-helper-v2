## 控制契约

### 背景与失败场景

- 触发问题：窗口抽取只能看到局部 evidence；`Agent`、产品名和文档中心对象等合法锚点
  可能需要整篇文档才能确定。单纯要求名称锚点来自当前 candidate evidence，会把合法
  名称误判为无依据。
- 不处理时的用户损失：候选标题依赖正文或 summary 才能消歧，候选列表无法独立理解，也难以据此分析 Profile；
  模型还可能用翻译或括号释义冒充领域锚点。
- 现有流程为什么不足：discovery 按窗口和通道独立执行；名称生成时没有文档级共享上下文，
  audit 只能事后发现问题，不能从源头修正。
- 本切片负责什么、不负责什么：负责在窗口抽取和文档级精确去重后，用整篇文档 evidence
  对候选名称和 alias 做一次文档级锚定，并记录锚点来源；不负责候选合并、去重、
  canonical topic、全库命名或正式 build 审查处置。
- 什么情况下应停止或撤掉本切片引入的机制：如果真实回放显示文档级锚定持续增加
  不存在的锚点、降低证据支持性或无法在预算内稳定完成，则不进入后续实现，保留原名称
  和显式失败状态。

### 用户可观察目标

用户完成试抽取后，候选列表中的标题可以在当前 Profile 和整篇文档上下文中独立定位；
每个被文档级锚定修改的候选都能看到简短锚点理由和引用的原文块数量。预算超限或调用
失败时，用户明确看到该文档未完成锚定，已抽取候选仍可用于分析 Profile。

### 核心不变量

1. 文档级标题消歧只修改 final title、aliases 和消歧追溯信息，不修改 summary、selection reasons、
   source block IDs、候选数量或候选身份。
2. 文档级锚定可以读取整篇文档 evidence，但不得引入当前 Profile、整篇文档 evidence
   之外的实体或事实。
3. 翻译、同义释义、括号补充和文档组织标签不构成定位锚点；锚点必须增加实际对象、
   系统、产品、Actor 或作用范围。
4. 每篇文档最多一次锚定调用；候选数超过 150 或估算输入超过 64k tokens 时不得调用，
   必须记录显式状态，不截断、不摘要、不静默降级。
5. audit prompt、判定阈值和历史 Run 在锚定失败时保持不变。
6. `standalone_clear=false` 时必须记录缺失锚点类型并生成不同 final title；
   `standalone_clear=true` 时不得改名。

### 错误代价与非对称门禁

| 错误类型 | 具体例子 | 用户影响 | 处理分类 | 指标与阈值 |
| --- | --- | --- | --- | --- |
| 伪造锚点 | 正文没有 Agent 语境却生成 Agent 标题 | 名称看似清楚但事实关系错误 | 阻断 | 锚点来源必须属于当前文档 block；回放人工复核 |
| 锚点丢失导致标题歧义 | 仍输出 `blast radius` | 候选列表无法独立理解 | 可容忍但显式 | 标题审查必须继续可见 |
| 名称改动污染证据 | 修改 summary/source block | Profile 分析依据被静默改写 | 阻断 | 自动测试 100% 保持字段不变 |
| 超预算静默截断 | 只传部分文档却标记 completed | 用户误以为使用了整篇上下文 | 阻断 | 超限 run 必须为 over_budget |
| 无候选文档调用模型 | empty candidates 仍计费 | 成本和状态误导 | 阻断 | 0 calls，状态 not_needed |

### 明确禁止

- 不合并、删除、拆分或重新排序候选。
- 不修改 summary、selection_reason、source_block_ids、channel_ids 或 evidence 正文。
- 不用文档级锚定替代标题、名称含义或内容审查。
- 不静默截断整篇文档，不把摘要或 block 子集冒充“整篇 evidence”。
- 不在候选数或 token 预算超限时继续调用模型。
- 不把失败锚定伪装成 completed。

### 失败语义

| 场景 | 用户看到什么 | 系统保留什么 | 是否可恢复 |
| --- | --- | --- | --- |
| 无候选 | 状态 not_needed，不增加调用 | 原抽取结果 | 不适用 |
| 输入超过 64k | 明确显示该文档锚定超预算 | 原 provisional 名称和全部候选 | 可调整预算后重跑 |
| 候选超过 150 | 明确显示候选数超限 | 原 provisional 名称和全部候选 | 先处理候选膨胀后重跑 |
| 模型调用失败 | 显示 failed 和错误摘要 | 原 provisional 名称和全部候选 | 可重跑 |
| 模型输出非法 | 显示 failed，不部分采用 | 原 provisional 名称和全部候选 | 可重跑 |

### 人工检查点

- 编码前需要确认的契约或风险：直接使用整篇 evidence，不做结构化摘要；超预算显式跳过。
- 实现中途需要查看的可运行路径：先在合成文档上验证：整篇锚点、alias 校验、超预算跳过。
- 完成后需要人工执行的操作：同一 Profile、snapshot 和文档重跑，检查
  `blast radius`、`containment`、Pattern 标题、原始句 alias 和预算状态。

## 目标

在候选名称生成链路中增加一次文档级、可追溯、受预算约束的命名锚定。

## 输入与输出

输入：冻结 Profile、整篇文档 blocks、文档级精确去重后的候选、预算策略版本。

输出：provisional/final title、title kind、standalone clear、missing anchor types、
name changed、aliases、`name_anchor_source_block_ids`、`name_anchor_reason`、
每文档消歧状态、usage 和诊断。

## 不包含

- 候选 semantic merge/dedupe。
- 标题审查或名称含义审查规则修改。
- 长文档分段锚定和结构化上下文摘要。
- 正式全库抽取与 build。

## 协作复盘

- AI 明显加速的环节：把整篇 evidence 消歧、结构化输出校验、预算失败隔离和 UI 追溯一次实现并自动验证。
- 负责人失去系统模型的环节：未出现；负责人持续纠正“Preview Run 是 Profile 分析，不是正式审批”。
- 真正发现问题的控制点：整篇 evidence 与结构化 `standalone_clear` 判断，避免标题润色冒充消歧。
- 只有仪式感、没有产生判断价值的流程：未发现。
- 下一次准备调整的一到两项：在更多文档上观察标题消歧稳定性；必要时再评估长文档分段锚定。

## 已知风险与后续

- 未验证项：其它领域和更长文档上的标题消歧稳定性。
- 接受的风险：每篇文档增加一次模型调用。
- 后续待办或 ADR：超预算文档的分段锚定方案。

## 停止与推翻条件

- 文档级锚定反复生成无依据锚点或显著增加事实错误时，撤掉该机制。
- 如果 64k 内无法覆盖大多数普通文档，并持续需要复杂压缩，应重新设计文档上下文阶段。
