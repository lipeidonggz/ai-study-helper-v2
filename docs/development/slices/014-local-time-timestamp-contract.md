## 控制契约

### 用户可观察目标

1. 入库任务、当前知识库发布时间和文档版本时间与 Windows 当前时区一致。
2. 同一时间在操作记录、入库队列和文档详情中显示一致，不出现固定 8 小时偏差。

### 核心不变量

1. 后端持久化时间继续统一保存为 UTC，不把本机时区写入历史数据。
2. 所有由 SQLite 时间列生成的 API ISO 字符串必须携带明确 offset。
3. 前端根据浏览器／Windows 当前时区格式化，不硬编码任何时区偏移。
4. 修复只改变时间语义的表达，不改写已有数据库中的时间值。

### 明确禁止

- 不在前端固定加 8 小时。
- 不把无时区字符串继续当作 UTC 交给浏览器猜测。
- 不通过迁移重写已经持久化的历史时间。

### 失败语义

| 场景 | 用户看到什么 | 系统保留什么 | 是否可恢复 |
| --- | --- | --- | --- |
| SQLite 读取后丢失 `tzinfo` | 输出层按应用写入契约补齐 UTC offset | 原数据库值不变 | 是 |
| 时间字符串无法解析 | 前端显示原始值，不虚构本地时间 | 后端原始响应 | 是 |

### 人工检查点

- 自动化测试覆盖 SQLite 重新读取后的所有用户可见时间。
- 完成后刷新应用，对比“最近入库记录”与 Windows 当前时间。

## 目标

修复 SQLite 读取结果丢失时区后直接输出 naive ISO 字符串，导致浏览器按本地时间解释 UTC 数值的问题。

## 输入与输出

输入：

- SQLAlchemy 从 SQLite 读出的 UTC `datetime`，可能不带 `tzinfo`；
- 任务、collection、文档详情和文档登记 API。

输出：

- 带显式 UTC offset 的 ISO 时间字符串；
- 由前端现有 `Intl.DateTimeFormat` 按用户系统时区显示。

## 不包含

- 用户自定义时区设置；
- 历史数据库时间值迁移；
- 日期语言和显示格式改版。

## 验收条件

- [x] 任务历史中的 `created_at`、`started_at`、`finished_at` 携带 UTC offset。
- [x] collection 指针 `published_at` 和发布记录时间携带 UTC offset。
- [x] 文档详情的 `published_at`、版本时间和关联任务时间携带 UTC offset。
- [x] 文档登记响应中的文档与版本时间携带 UTC offset。
- [x] 完整质量门通过。
- [x] 真实界面时间与 Windows 当前时间一致。

## 反向解释

1. 为什么不在前端直接加 8 小时？
2. 修复后数据库里保存的时间值是否发生变化？
3. 为什么新写入后立即显示正常，不代表重启后仍正常？

参考解释：

1. 用户时区不固定，前端硬编码 `+8` 只适用于当前环境，也会破坏现有
   `Intl.DateTimeFormat` 对系统时区的支持。
2. 修复发生在读取后的序列化层，数据库仍保存原来的 UTC 时间值，没有执行迁移或改写。
3. 新写入对象在内存中仍可能带 `tzinfo`，只有 SQLite 重新读取后才会复现时区丢失，
   因此必须覆盖重启／重新查询路径。

## 协作复盘

- 实际界面验收发现了自动化测试未覆盖的跨层时间语义。
- 修复应验证 SQLite 重新读取路径，而不是只验证刚写入内存对象。

## 已知风险与后续

- 当前应用按单机 UTC 持久化设计，不提供用户自定义时区。
