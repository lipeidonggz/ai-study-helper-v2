## 控制契约

### 背景与失败场景

- 触发问题：通道由用户定义，无法保证完全正交；同一 evidence 可被多个通道以“具名对象、解释性概念、结构关系”分别抽取，形成不同名称的重复候选。
- 不处理时的用户损失：用户必须设计正交通道，否则候选膨胀、名称冲突，后续文档锚定和审查成本上升。
- 现有流程为什么不足：所有通道 discovery 独立并行，且同一通道的窗口也独立并行；后续窗口和后续通道都看不到之前已发现的对象，最终只按 primary name 精确去重，无法识别跨语言或不同措辞的同对象。
- 本切片负责什么、不负责什么：负责按“Profile 通道顺序＋通道内 window／batch 顺序”维护文档级候选账本，允许后续抽取批次对已有对象补充 summary、alias、source blocks 和 selection reason；不负责父级/子级语义判断、文档级名称锚定或跨文档 canonical topic。
- 什么情况下应停止或撤掉本切片引入的机制：若后续抽取批次经常错误归并不同粒度对象，或候选账本上下文显著增加成本而无法通过审查拦截，应停止串行累积，回到独立抽取加显式身份归并。

### 用户可观察目标

用户可以使用部分重叠的通道，而不必先证明通道完全正交。后续抽取批次发现同一对象时，原有候选会增加 alias、补充 summary、来源通道和 evidence，但候选数量不增加。

### 核心不变量

1. 只有当前 evidence 支持的内容才能加入已有候选；不得用附件中的 summary 充当新证据。模型返回当前窗口外 block ID 时，只保留当前窗口 ID；若某条 contribution 不再有当前证据，则丢弃该 contribution 并记录诊断，不使整个 Run 失败。
2. `existing_candidate_ref` 必须引用本通道调用附件中的候选；未知引用是阻断错误。
3. 同一引用下沿用已建立 name；模型提出不同 name 时保留原 name，并将可验证新名称作为 alias。
4. 新 summary 追加到 `summary_variants`，不覆盖原 summary；source blocks、channel IDs 和 selection reasons 按去重规则合并。
5. 不同对象或不同粒度必须返回 `existing_candidate_ref=null` 创建新候选，不得为去重牺牲合法知识对象。

### 错误代价与非对称门禁

| 错误类型 | 具体例子 | 用户影响 | 处理分类 | 指标与阈值 |
| --- | --- | --- | --- | --- |
| 错把不同对象归为同一候选 | blast radius 与 blast radius control | 丢失独立知识粒度 | 阻断 | 集成回放人工检查 |
| 未知 candidate_ref | 后续批次引用不存在附件 | 数据流不可追溯 | 阻断 | 未知引用 100% 失败 |
| 附件 summary 当证据 | 后续批次只复述旧附件事实 | evidence 绑定失真 | 阻断 | source 只能来自当前窗口 |
| contribution 混入旧窗口 source | 模型把附件里的旧 block ID 写回输出 | 证据 provenance 失真 | 可容忍但显式 | 丢弃旧 ID；无当前 ID 时丢弃该 contribution |
| summary 覆盖 | 后续批次 summary 替换原归纳 | 丢失已有贡献 | 阻断 | variants 保留全部 |
| 正常运行重复 | 后续批次忽略同一对象 | 候选膨胀 | 可容忍但记录 | 对比候选数与 alias 组 |

### 明确禁止

- 不把通道定义顺序解释成语义优先级。
- 不自动改写已建立候选的 primary name。
- 不使用附件里的 source blocks 替当前窗口生成候选证据。
- 不因 candidate_ref 相同就跳过 summary/alias 的证据校验。
- 不在未知引用、跨窗口越界或非法 alias 时静默创建新候选。

### 失败语义

| 场景 | 用户看到什么 | 系统保留什么 | 是否可恢复 |
| --- | --- | --- | --- |
| 未知 existing ref | Run 失败并显示协议错误 | 不发布该 Run candidates | 可重跑 |
| contribution 的 source 全在当前窗口外 | 该 contribution 被丢弃并显示诊断；Run 继续 | 已有候选、其它合法 contribution、诊断 | 可重跑 |
| 新名称不匹配已有名称 | 保留已有名称并记录诊断 | 新名称在 evidence 支持时转为 alias | 是 |
| summary 增加 | 原 summary 不变，补充归纳可见 | summary variants、source、reason | 不适用 |
| 通道仍返回重复新对象 | 后续内容审查发现 | 两个候选都保留 | 后续身份归并 |

## 目标

让用户定义的部分重叠通道通过运行时候选累积自然收敛，而不是要求用户手工做到完全正交。

## 输入与输出

输入：冻结 Profile 的通道顺序、当前窗口 evidence、文档级已积累候选附件。

输出：新候选，或对已有候选的增量 contribution；最终形成合并后的文档候选账本。

## 不包含

- 文档级名称锚定。
- 跨文档 canonical topic。
- 父级/子级和 typed relation 判断。
- 自动合并不同粒度对象。

## 协作复盘

- AI 明显加速的环节：把通道和窗口统一为串行累积链，并自动验证旧窗口 source 污染等失败路径。
- 负责人失去系统模型的环节：未出现；负责人纠正了“只通道串行、通道内窗口并行”的初始设计。
- 真正发现问题的控制点：同通道后续窗口回归测试和真实长文档回放。
- 只有仪式感、没有产生判断价值的流程：未发现。
- 下一次准备调整的一到两项：观察更多重叠通道的真实误合并率，评估附件 token 上限。

## 已知风险与后续

- 未验证项：更多领域下真实模型对“同对象”和“不同粒度”的识别稳定性。
- 接受的风险：通道及同通道窗口均串行会增加总延迟，附件增加输入 token。
- 接受的风险：同对象与不同粒度的判断属于 LLM 语义判断，无法确定性保证；确定性门禁只能校验引用、名称保护、证据来源和 alias 关系。
- 后续待办或 ADR：附件 token 上限和跨文档 canonical merge。

## 停止与推翻条件

- 后续抽取批次错误归并不同对象且审查无法可靠拦截时，停止自动补充。
- 全局串行累积带来的延迟或附件成本显著高于重复候选的处理成本时，重新评估架构。
