# 当知识地图也会漏：为什么“找全”需要双分面关系知识组织

> **摘要**：主题地图能回答“在哪里找”，却无法保证按某个关系视角找全。本文接续前文的 LLM Wiki 转向，提出知识对象域与关系分面的双分面模型，并明确尚未验证的边界。

> **30 秒判断**：如果你的 RAG 已经能找相关段落，却仍会漏掉“某类关系”的一部分证据，问题可能不在提示词或 Top-k，而在知识组织只建了“区域导航”，没有建“关系枚举维度”。这篇文章给出一次从 LLM Wiki、GraphRAG 继续向前的设计推演。

> **适合谁读**：正在做 Agentic RAG、LLM Wiki、知识图谱、主题综述和开放式找全问答的工程师与产品负责人。

## 1. 上一篇文章停在一个有条件的乐观判断

前文从一个具体问题出发：

> 在当前知识库中，除了沙箱、虚拟机和出口控制，AI Agent 还有哪些隔离或控制边界？

它看起来只是“查隔离”，实际要求跨文档找出文件、凭证、工具、外部内容、上下文、并行状态、子 Agent 等多个区域中的保护机制。块检索、查询展开、facet、审计、reranker 和章节路由都分别解决了一部分问题，但没有形成稳定的停止条件。

于是上一篇文章做了一个架构转向：从查询时现场搜索，转向入库时预先编译一层 LLM Wiki／主题证据地图。Wiki 负责告诉 Agent 应该围绕一个主题检查哪些方面，原始 block 继续负责事实和引用。

这个方向解决了“没有主题地图”的问题，却没有自动解决一个更底层的问题：

> **主题地图组织的是知识所在区域，不一定是用户指定的关系维度。**

用户可以从任意关系视角提问。“隔离”“前置条件”“失败恢复”“权限撤销”“信息来自哪里”都可能横切多个主题。如果知识层只预编译了主题、分组和页面，那么它仍然要依赖在线检索去临场发现这些横切关系。

这就是本文的起点。

## 2. 一组数字：相关词并不是关系本身

在固定 15 篇 HTML、526 个 block 的知识库中，`c13-003` 的跨文档金标准去重后包含 48 个目标 block。一次抽取运行能够找回其中 47 个候选原文，但检查词面后发现：

- 只有 13/48 个 block 直接出现 `isolation`、`isolated`、`isolating` 或 `boundary/boundaries`；
- 加上 `sandbox`、`control`、`bound` 等相关词，也只有 19/48；
- 其余核心证据通常只描述具体机制，例如 checkpoint、上下文清理、权限允许列表、凭证代理、子 Agent 上下文或 trace，却没有共同出现“隔离”“边界”这些词。

这是一组固定快照上的记录，不代表所有领域和语料的普遍比例。但它足以说明一个工程事实：

> “隔离和控制边界”不是原文里的一块统一主题，而是查询者施加在多种具体机制上的关系视角。

如果系统只做词面或向量相似度搜索，“隔离”与 checkpoint 之间没有必然的文本相似性；如果系统只做主题分组，checkpoint 又可能落在执行恢复主题，不会自动进入“控制边界”页面。

关系类别要解决的正是这件事：把“原文写了什么机制”映射到“这个机制在功能上建立了什么关系”。

## 3. 主题和 community 解决的是“在哪里”，不是“枚举什么”

GraphRAG 是理解这个边界的好参照。它会抽取实体和关系，再对实体图做层次化社区检测，为社区生成摘要；查询时可以利用实体邻域、文本单元和 community reports。[GraphRAG Indexing Dataflow](https://microsoft.github.io/graphrag/index/default_dataflow/)说明了社区检测与摘要的索引流程，[Local Search](https://microsoft.github.io/graphrag/query/local_search/)则展示了以实体为入口、同时读取邻接关系和社区报告的查询方式。

这说明 GraphRAG 并不是“没有关系”。它真正没有提供的是一种面向找全的显式关系分类目录：

```text
community 回答：知识属于哪一片区域
关系分类回答：在这片区域中要检查哪些关系
```

community 可以看作从图连接紧密度中产生的知识对象域候选，但社区边界由结构和权重决定，不由用户的问题视角决定。一个社区可能同时包含安全边界、执行恢复和职责设计；一个关系视角也可能跨越多个社区。社区摘要是有损压缩，跨社区的条件、例外和局部细节更可能在聚合中变弱。

LLM Wiki 的限制类似，只是层级更少。主题、分组和页面擅长组织“关于什么”的内容；当用户要求“找出所有满足某类关系的证据”时，系统仍然缺少一份可枚举的关系清单。

更准确的说法不是“它们答不了”：

> 它们可能答对一部分，但无法说明还应该枚举哪些关系，因此无法建立找全覆盖契约。

## 4. 第一版关系分类为什么会跑偏

最初我们的直觉很自然：既然关系重要，就先设计一套领域无关的关系类型。于是从 12 个一级家族出发，继续拆出约 40 个具体关系，又在语义审计后调整为 38 个候选。

但实验暴露了两个结构问题。

### 4.1 把两种轴混在了一起

有的候选确实在分类“关系语义”，例如：

- 使能；
- 约束；
- 分离；
- 持久保存；
- 恢复；
- 允许或禁止。

另一些候选更像在分类“知识属于哪个区域”，例如：

- 生命周期阶段；
- 系统组成；
- 主体与资源主题；
- 状态与过程场景。

它们并非毫无价值，只是分类对象不同。把两者放进同一套“一级家族”，会让同一组候选同时承担“知识在哪里”和“对象之间是什么关系”两种职责，导致范围边界和检索用途混淆。

一个关系类别只能把知识库缩小到某个比例。例如“所有隔离关系”依然可能横跨安全、职责设计、执行恢复和上下文管理；要进一步缩小范围，还需要知道当前问的是 AI Agent 的构建、运维，还是某个组成方面。相反，知识对象域告诉你“在哪一片知识区域里找”，关系分面告诉你“在这片区域里枚举哪些关系”。

### 4.2 多个关系同时判断会互相干扰

另一个问题来自模型调用本身。实践中最直观的方案是把几十个关系类别一起交给模型，希望一次抽全。实际运行时，加入第二、第三个关系类型会改变模型对整块的抽取密度，目标关系仍然可能被识别，但额外关系明显增加，语义边界也更难稳定。

当前实验收敛到：

1. 判断单位使用完整 block，而不是先拆句；
2. 每次只判断一个关系类别；
3. 关系类别由可版本化的关系卡描述；
4. 关系卡给出正向定义和证据推断边界；
5. 返回最小连续原文证据，逐字校验。

这不是最终架构，而是当前能够控制变量、定位错误的最小实验单元。

## 5. 实验如何修正了我们的判断

以下结果来自同一个 526-block 固定快照、`deepseek-flash`、temperature 0、thinking disabled 的实验口径。它们证明的是当前实现方向是否有效，不是对其他模型或数据规模的普遍保证。

| 路线 | 判断单位 | 有效“存在” | `c13-003` block 覆盖 | 观察 |
| --- | --- | ---: | ---: | --- |
| 句子级单关系 | 句子 | 463/526 | 66/68 | 召回高，但从句、例子和任务指令被大量放大 |
| 块级单关系 | 完整 block | 387/526 | 59/68 | 降低过切，但仍会把比较、配置选择宽解成关系 |
| 块级＋证据边界 | 完整 block | 327/526 | 单次约 55/68 | 误报方向改善；11 个语义组仍全部可达 |

这里最重要的不是“327 比 463 好”，而是三条互相约束的结论：

✅ 完整 block 比句子更适合作为关系判断单位，因为它保留跨句上下文，也减少把列表项和任务指令当成独立事实。

✅ 一次只判断一个关系，比把多个关系塞进同一调用更稳定。关系卡可以在类别之间复用，但语义竞争不应进入同一次判定。

🤔 召回、精确性和覆盖不能由单个总数裁决。块级判断仍存在明显宽解释；句子级虽然覆盖更多金标准 block，却带回大量切分噪声。一个高召回总数不能证明找全。

整篇文档一次输入也被验证过。它在 `D04` 的探索运行中显著减少了调用次数和输入 token，却没有保持逐块召回；在 `D14` 的单次探索中，整篇只找到 1/3 个人工确认的正确关系，分批后恢复到 2/3，逐块能够达到 3/3，但假阳性也最多。失败不是简单的 token 上限，而是长上下文下模型对逐块判断的覆盖和敏感度下降。

这些结果只支持一个保守判断：

> 当前做关系抽取，应先把“一个关系类别是否定义清楚、是否能稳定判断”解决好，再谈把几十个类别组合成完整地图。

详细实验见仓库中的[阶段 51 关系抽取记录](../development/experiments/2026-11-13-stage51-direct-relations.md)和[整篇文档约束实验](../development/experiments/2026-11-16-whole-document-constrain-probe.md)。

## 6. 关系必须成为一等知识对象

继续往下推，会遇到一个知识图谱里早已存在的问题：如果关系只是两个实体之间的一条无名边，它很难承载分类、证据、条件和再次参与关系的能力。

知识图谱中的常见做法是把关系实体化（reification）：给一条关系一个稳定身份，再把来源、时间、置信度、角色、条件等元数据附着在这个关系对象上。属性图的边属性、RDF reification、命名图、RDF-star 和事件节点，都是这一需求的演化。

我们的关系实例至少需要保存：

```text
关系实例
  参与角色
    每个角色上的知识对象
  自然语言命题
  原文证据
  关系分面标签
```

这样，“只有经过人工批准，Agent 才能访问外部网络”不必被压成两个普通实体之间的一个 `requires` 标签。它可以表示为：

```text
R1：Agent 访问外部网络
R2：R1 以人工批准为必要条件
```

`R1` 是动作或事件对象，`R2` 是作用在 `R1` 上的高阶关系。自然语言命题和原文证据继续保留完整语义，条件、否定、模态、时间和例外都不会因为分类标签而丢失。

这也迫使我们修正“实体域”的叫法。知识对象不只包括实体，还包括：

- 事件、动作和状态；
- 概念、命题和能力；
- 已经实体化的关系实例。

“记忆管理”不是某个实体，而是一个能力、职能或主题域；归入它的对象可以是记忆存储实体、写入动作、检索过程、保留策略和它们之间的关系。“一个行动被允许还是禁止”也不是普通实体关系，而是作用在行动对象上的规范关系。

因此，更准确的叫法是**知识对象域**。知识对象域轴一定领域相关；关系分面轴则尽量领域无关。

## 7. 双分面关系知识组织模型

把这些判断合起来，知识库不再只由“实体 + 关系边”组成，而分成事实层与两个正交的分面层：

```text
事实层
  知识对象
    实体
    事件、动作或状态
    概念或命题
    已实体化的关系
  关系实例
  自然语言命题
  原文证据

分类层
  知识对象域轴
    回答：在哪里找

  关系分面轴
    回答：找什么关系
```

### 7.1 知识对象域轴

知识对象域轴一定领域相关，并随知识组织目的变化。

面向 AI Agent 开发人员，根层可以按生命周期划分：

```text
AI Agent
  概念理解
  设计与开发
  发布
  运维
```

进入“设计与开发”后，下一层可以换成组成视角：

```text
设计与开发
  主循环
  记忆管理
  工具调用
  多 Agent 协作
```

进入“运维”后，又可能换成安全和可靠性视角：

```text
运维
  安全控制
  可观察性
  故障恢复
  成本治理
```

这里没有一棵对所有知识库都正确的固定主树。领域、读者和使用目的不同，根轴和各级切分轴都可能不同。GraphRAG 的 community 可以作为知识对象域的数据驱动候选，但不能替代按目的形成的领域结构。

知识域节点也不是普通实体。“记忆管理”是一个能力或职能域；域内才有记忆存储、写入动作、检索过程、清理策略等知识对象。

### 7.2 关系分面轴

关系分面轴从用户可能提出的关系视角，对关系实例做分类。它有明确的一级观察轴；轴内二级标签允许重叠，但所有标签的并集要覆盖该轴的适用范围，而且每个标签要有独立原文依据和可区分的检索价值。

例如，同一条关系可以同时进入多个观察轴：

```text
只有经过人工批准，Agent 才能访问外部网络

必要条件轴：条件控制
规范许可轴：允许
```

这不是重复抽成两条事实，而是同一条关系对象拥有两个分面标签。同一关系实例在单个轴内也可以拥有多个二级标签。查询侧用带 `AND`／`OR` 和求值作用域的表达式组合这些标签，不把标签集合本身当成完整查询语义。完整语义仍由命题和原文证据承担。

关系分面轴与知识对象域轴的区别可以压缩成一张表：

| 维度 | 分类对象 | 是否领域相关 | 主要职责 |
| --- | --- | --- | --- |
| 知识对象域轴 | 知识对象及其证据 | 必然相关 | 把候选对象和 block 缩小到目标知识区域 |
| 关系分面轴 | 关系实例的语义 | 尽量无关 | 给出可枚举、可检查的关系入口 |

## 8. 查询计划如何从“主题”变成“覆盖契约”

最终候选模型中的查询不只是一个主题字符串，而是一个结构化范围：

```text
查询
  资料范围
    当前知识库、快照，必要时限定文档

  知识对象域范围
    组织路径或子树

  查询锚点
    被域范围约束的目标知识对象或角色

  关系分面表达式
    一个或多个关系观察轴及轴内二级标签
    标签间 AND／OR 与求值作用域
```

资料范围是硬边界。用户说“只看这些文档”时，范围外证据即使相关也不能返回。

知识对象域范围通常约束查询锚点，而不是要求关系两端都在域内。查询是“AI Agent 构建中的隔离”时，Agent 是锚点，宿主或外部环境可以位于域外；只要关系描述的是 Agent 受到的隔离，它仍然相关。

当前阶段暂不实现知识对象域分类，整个知识库固定为一个完整的 AI Agent 域，因此实际实验只跑：

```text
当前快照
× AI Agent 全域
× 关系分面表达式
```

这样做是有意的。先把关系分面单独证明，才能判断后续增加知识对象域究竟带来了真实增益，还是只是让系统多了一层难以归因的结构。

### 8.1 用 `c13-003` 看差异

传统检索可能会把问题退化成关键词或向量查询：

```text
AI Agent 隔离 控制边界
```

双分面模型要求先把问题拆成可枚举维度。以当前讨论中的候选关系为例，它可能包含：

```text
资料范围：当前 15 篇
知识对象域：AI Agent（当前阶段固定为全域）
锚点：AI Agent
关系分面候选：
  分离／边界控制
  约束
  生命周期控制
  状态保存与恢复
  观察与审计
  来源与信任
```

这里的标签列表仍不是最终冻结目录，不能把它当成已经验证的答案。它要说明的是：系统不再只问“哪些 block 像隔离”，而会问“为了覆盖隔离这个关系视角，应该分别检查哪些二级标签、这些标签如何用布尔表达式组合，以及每个标签由哪些证据支持”。

这就是“覆盖契约”。找全不再是一个主观感觉，而变成一个联合条件：

```text
查询维度分解完整
∧ 所选同轴标签并集覆盖轴范围
∧ 每个二级标签有明确边界和独立检索价值
∧ AND／OR 运算符与求值作用域正确
∧ 每个标签完成候选抽取
∧ 结果合并去重
∧ 每条答案能回到原文证据
```

它仍然不等于“证明世界上所有相关事实都存在”。它证明的是：在当前知识库、当前组织和当前关系目录下，声明过的覆盖面都被检查过，未覆盖与不确定项能够显式暴露。

## 9. 哪些已经被验证，哪些还没有

这篇文章最容易犯的错误，是把一个正在形成的方法写成已经成功的方法。当前状态应当明确拆开。

✅ 已验证或已有项目运行证据：

- 主题和词面检索会漏掉横切多个主题的关系证据；
- 完整 block 比句子更适合作为当前关系判断单位；
- 一次注入一个关系比同时注入多个关系更稳定；
- 带定义和证据推断边界的关系卡已经能在“约束”关系上完成 526-block 全库回放；
- 整篇一次输入、连续分批和逐块输入在召回、误报、成本与时延上存在明确权衡；
- 关系实体化、原文证据和自然语言命题能够保留条件与高阶关系所需的信息。

🧪 已有部分可回归证据：

- 关系卡外壳、证据逐字校验、空结果与格式失败分离；
- “约束”关系的部分固定正例、负例和连续运行；
- 快照、提示词版本、运行产物和 token 记录的实验链路。

🤔 仍是当前设计与判断：

- 知识对象域轴和关系分面轴的组合能否在真实查询中稳定优于 LLM Wiki；
- 关系观察轴最终应有哪些，同轴二级标签能否形成覆盖并保持独立检索价值；
- 查询侧 LLM 能否稳定把问题映射到关系分面和查询锚点；
- 同一关系卡模板能否推广到“约束”之外的类别；
- 15 篇、526 block 上的方法能否扩展到 50 篇、1,000 篇；
- 知识对象域分类的生成、审核、增量和删除策略。

尤其要强调：目前只对“约束”做了相对充分的关系卡走查。其他关系仍处于分类评审、抽取探针或设计推演阶段。双分面模型给出了组织框架，不是“已经找全”的证明。

---

## 10. 下一步不是继续加提示词，而是验证覆盖契约

接下来真正需要验证的是三个逐级问题（这里就是本文留下的引子）：

### 实验一：关系轴能否被冻结

先在 AI Agent 全域中确定一组关系观察轴和二级标签，检查每个轴是否只回答一个稳定问题、同轴标签的并集是否覆盖适用范围、每个标签是否有独立原文依据和检索价值。关系轴不从 `c13-003` 答案反推，避免把单个问题的答案面固化成分类。

### 实验二：查询能否稳定映射到关系分面

冻结关系目录后，再用不参与轴设计的问题做映射测试，并检查模型能否产出正确的 `AND`／`OR` 和求值作用域。需要区分三类失败：

1. 用户问题没有对应关系类别；
2. 有标签，但查询没有选中，或表达式运算符／作用域错误；
3. 标签和表达式正确，但证据没有召回。

只有把这三类失败分开，才能知道问题出在分类、查询规划还是抽取。

### 实验三：找全结果是否真的改善

在固定快照上比较三类路线：

- 主题／Wiki 检索；
- 关系分面检索；
- 关系分面检索后增加知识对象域范围。

验收不能只看最终答案“像不像”。还要看关系标签覆盖、表达式与作用域正确率、证据 block 覆盖、跨文档来源轮转、误报、调用成本、时延，以及证据是否可回源。只有在不看当前金标准调提示词的前提下做回放，结果才有产品意义。

当关系分面本身被证明有效之后，再引入知识对象域轴。否则，一次改善无法判断来自关系分类、领域缩小，还是只是减少了输入上下文。

## 11. 可复用的检查清单

如果你也在做“主题式 RAG 已经能找相关内容，但始终无法稳定找全”的系统，可以先问这几个问题：

1. 用户问题要求的是“相关主题”，还是“某一类关系的完整枚举”？
2. 当前知识组织回答的是“在哪里找”，还是也能回答“应该检查哪些关系”？
3. 一个关系类别是否正在同时承担领域分类和关系分类两种职责？
4. 关系是否有稳定身份，能否单独承载证据、条件、角色和分类标签？
5. 同一关系轴内的二级标签能否共同覆盖限定范围？重叠标签是否各有原文依据和独立检索价值？
6. 多个关系类别是否被塞进同一次模型判断，导致相互干扰？
7. 查询范围是主题词，还是“资料边界 + 知识对象域 + 锚点 + 关系表达式”？
8. 所谓找全，是在证明世界完备，还是在证明声明过的覆盖面都已被检查且缺口可见？

这些问题不会替代检索、模型或评测，但它们决定系统有没有可能构建一个真正的停止条件。

## 12. 一页速查

- 前文的选择：Agentic RAG 找不到主题级停止条件，于是引入可回源的 LLM Wiki 证据地图。
- 本文发现的缺口：Wiki 和 community 擅长区域导航，不提供横切关系的显式枚举维度。
- 关键证据：在固定 526-block 快照中，48 个 `c13-003` 金标准 block 只有 13 个直接出现 isolation／boundary 词面，加上相关词也只有 19 个。
- 实验结论：完整 block 优于先拆句；单关系调用优于多关系联合判断；整篇输入降成本但会显著损失覆盖。
- 关系地位：关系必须实体化为带角色、命题、证据和分面标签的一等知识对象。
- 对象范围：知识对象包括实体、事件／动作、状态、概念、命题和关系实例；“记忆管理”是知识域，不是普通实体。
- 双分面：知识对象域轴回答“在哪里找”，一定领域相关；关系分面轴回答“找什么关系”，尽量领域无关。同轴标签允许重叠，但必须覆盖轴范围并保持可区分。
- 找全契约：资料范围 + 知识对象域 + 查询锚点 + 带作用域的关系布尔表达式 + 原文证据，而不是一个主题相似度分数或裸标签列表。
- 当前边界：双分面模型仍是候选设计，只有“约束”关系完成了较完整的单关系实验，端到端找全尚未验证。
- 下一步：先冻结关系轴，再做不看金标准调参的跨文档回放，最后接入知识对象域范围。

如果前文的结论是“找全需要一张主题地图”，那么本文的结论是：

> **只有区域导航还不够。要回答按关系视角找全的问题，知识库还必须知道有哪些关系维度需要枚举，以及哪些原文证据已经覆盖了每个维度。**
