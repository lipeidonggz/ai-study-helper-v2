# 对外文章写作规范

本规范用于《学习问答助手Agent实践》系列及其他对外技术文章。目标是保存有复用价值的工程判断，不以复述功能、流水账记录开发过程或追求营销效果为目标。

## 选题标准

优先选择同时满足以下条件的主题：

1. 有真实设计或实现证据，不以推测代替项目经验；
2. 能回答一个反直觉或容易做错的问题；
3. 能提炼出跨项目可复用的边界、契约、方法或检查清单；
4. 与已发布设计文和既有文章有明确差异；
5. 失败案例能够支撑更大的工程结论。

不要把以下内容单独写成对外文章：

- 一眼可见的 UI 对齐、错别字或配置遗漏；
- 没有形成系统判断的普通编码错误；
- 单纯的框架 API 用法或功能说明书；
- 只复述已发布设计文；
- 尚未实现，却被写成已经验证的设计。

低级错误并非绝对不能出现，但只能作为更大主题的证据。例如，调度竞态应服务于“有效样本如何保证可比较”，不应成为文章主线。

## 文章定位

每篇实现复盘至少回答一个问题：

```text
设计承诺了什么？
落地后哪里被现实修正？
修改后的契约为什么更可靠？
```

优先写“设计到实现的差异”，不要重新解释设计已经讲过的基础概念。

文章应明确区分：

- 设计已确认；
- 实现已完成；
- 仅通过确定性测试；
- 已经过真实运行；
- 尚未实现或尚未验证。

## 固定开头

标题之后立即给出不超过 100 字的摘要：

```markdown
> **摘要**：用一句话说明问题、证据和核心结论。
```

摘要之后按需提供：

- `30 秒判断`：给时间有限的读者说明文章价值；
- `适合谁读`：限定目标读者；
- `系列位置`：链接已发布设计文和相关前文；
- `代码库`：链接公开仓库；
- `结构速览`：列出主要章节；
- `证据标记`：统一解释 ✅／🧪／🤔 等标记。

证据标记的含义保持稳定：

- ✅ 项目实测：有真实运行、真实 trace 或真实界面证据；
- 🧪 可回归：已有确定性自动化测试；
- 🤔 当前判断：由当前机制推导，不声称已经量化验证。

## 正文结构

推荐结构：

1. 从一个具体现象、冲突或设计变化开始；
2. 还原证据和系统状态；
3. 解释为什么直觉方案不成立；
4. 给出最终契约和关键源码；
5. 说明测试、真实运行和剩余边界；
6. 提炼可复用检查清单；
7. 用“一页速查”收尾。

正文避免：

- 用“最佳实践”包装单个项目经验；
- 把模型行为解释成主观意图；
- 把一次偶发现象写成长期发生率；
- 用大量术语代替因果解释；
- 让读者必须读完前文才能理解一个专有名词。

## 证据要求

技术结论必须能回溯到至少一种证据：

- 设计文档或 ADR；
- 源码；
- 自动化测试；
- 真实运行 ID 与 trace；
- 人工验收记录；
- 明确的失败探针。

涉及数字时写清口径，例如：

```text
10 个有效样本
30 条生效 Judgment
2 个失败 attempt
1 次真实运行
```

不要用“多数”“经常”“很稳定”等模糊表述代替数据。

只观察到一次的行为，应写成：

> 这是一次已记录的失败模式，不代表长期发生率。

## 源码与链接

正文可以嵌入少量关键源码，一般每篇 3～6 段。每段只服务于一个判断，不贴大段实现。

源码要求：

- 优先展示契约、状态转换、失败分支和关键断言；
- 删除无关字段时必须说明“为便于阅读，省略无关代码”；
- 概念化代码不能冒充源码原文；
- 代码块使用正确语言标记；
- 代码附近提供可继续阅读的源码入口。

公开文章不得使用本机绝对路径，例如：

```text
/D:/.../backend/app/example.py
```

应使用固定 commit 的 GitHub permalink：

```text
https://github.com/lipeidonggz/ai-study-helper-v2/blob/<commit-sha>/<path>#L<line>
```

要求：

1. 使用固定 commit，不使用会漂移的 branch 链接；
2. 链接目标文件必须存在于该 commit；
3. 行号必须指向对应函数、规则或证据；
4. ADR、测试和真实运行证据与源码使用同样的固定版本；
5. 定稿前逐项检查文件存在性和行号。

## 图示与表格

只在关系比散文更难直接理解时使用图示或表格：

- 多对象之间的数据流；
- 多个状态或失败语义的对比；
- 设计前后契约变化；
- 多种执行者之间的职责划分。

不用表格重复普通段落，也不为了视觉丰富增加无信息图示。

## 系列关系

系列文章之间使用稳定的逻辑关系：

- 设计文回答“为什么这样设计”；
- 实现复盘回答“落地时改变了什么”；
- 故障复盘回答“哪个边界被击穿，怎样修复”；
- 方法文章回答“这些案例能提炼出什么通用判断”。

新文章必须链接相关设计文或前文，但只提供必要上下文，不要求读者按顺序读完。

文章发布后，将仓库内相对链接替换为公开文章 URL；已发布文章 URL 同时记录在 [文章索引](./README.md)。

## 定稿检查

- [ ] 标题能直接说明冲突、问题或实现结果。
- [ ] 标题后存在不超过 100 字的摘要。
- [ ] 文章与原设计文有明确差异。
- [ ] 设计、实现和未验证内容已分开。
- [ ] 每个关键技术结论有源码、测试、ADR 或运行证据。
- [ ] 源码片段短而完整，省略内容和概念化代码已标明。
- [ ] 所有 GitHub 链接使用固定 commit。
- [ ] 所有链接文件存在，行号指向正确内容。
- [ ] 正文没有本机绝对路径、API Key、token 或敏感数据。
- [ ] 一次观察没有被写成长期发生率。
- [ ] Markdown 代码围栏成对，表格可渲染。
- [ ] `git diff --check` 通过。
- [ ] 结尾有“一页速查”，并留下一个清晰的核心判断。
