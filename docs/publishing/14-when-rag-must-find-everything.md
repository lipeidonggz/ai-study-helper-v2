# 当 RAG 开始“找全”：从现场查询展开，到 LLM Wiki 预编译

> **摘要**：“找全”的瓶颈不是 Top-K 大小，而是无法稳定发现并验证主题的全部证据面。查询展开只能扩大候选；工程上应预编译可回源、可增量维护的证据地图，再用现场检索补齐缺口。

> **30 秒判断**：如果你的 RAG 只是回答“哪几个块与问题最相关”，块检索加 Agentic 已经够用；如果用户要求把某个主题的证据尽量找全，真正的难点会从相似度排序变成主题理解、语义面发现、证据判断和缺口闭合。本文记录我们从现场检索转向 LLM Wiki 的完整判断过程。

> **适合谁读**：正在做 Agentic RAG、知识库问答、主题研究、长答案检索或 LLM Wiki 的工程师和产品负责人。

> **系列位置**：本文接续 [05 · Agentic RAG 检索侧落地](./05-retrieval-design-to-implementation.md)。那篇讲的是块级工具如何形成可靠的 Agent 检索链路；本篇讨论一个更窄也更难的问题：当块级检索已经能工作，为什么“围绕主题找全”仍然需要另一种知识形态。

> **代码库**：[lipeidonggz/ai-study-helper-v2](https://github.com/lipeidonggz/ai-study-helper-v2)

> **研究证据**：[065 主题覆盖实验](https://github.com/lipeidonggz/ai-study-helper-v2/tree/c7d69ba97a55395431b406e4893ed70fe79f5f6a) · [066 章节路由实验](https://github.com/lipeidonggz/ai-study-helper-v2/tree/528ff57d1f7fa85182afcfca745cbc5b9f740498) · [冻结 tag](https://github.com/lipeidonggz/ai-study-helper-v2/tree/research-topic-coverage-2026-10-31)

## 1. 我们最初为什么不直接做 LLM Wiki

这个项目一开始并没有把“建立 Wiki”作为默认路线。

当时的判断很朴素：产品有 18 个问答用例，核心需求是把正确、可追溯的 block 交给 Agent，再由 Agent 回答。块级索引加元数据已经支持：

- dense 检索找到语义相关的内容；
- BM25／FTS 找到专名、数字和具体术语；
- 文档、章节、快照过滤限定范围；
- Agentic 循环根据中间结果继续查询；
- 引用最终回到原始 block。

而 Wiki 需要额外编译，页面内容经过模型改写，还必须补一条“页面段落 → 原始 block”的回源链。它增加成本、版本和一致性负担，却不是 18 个用例的普遍前提。

[存储与检索策略](../design/05-storage-and-retrieval-strategy.md)因此做了明确取舍：

```text
先做增强的向量块 + Agentic 检索
↓
当实测出现“面状覆盖／跨页概念归集”缺口
且现有方案反复解决不了
↓
再引入 Wiki
↓
接入时必须带“页面段落 → 块”的引用
```

这不是在等技术潮流，而是先写下一个可被现实推翻的条件。后面要回答的，不是“Wiki 看起来是否更强”，而是“那个条件有没有真的出现”。

## 2. 大多数问题，块检索加 Agent 确实处理了

当前系统在检索侧的核心模型可以概括为：

```text
原始文档
→ SectionTree / BlockSet
→ dense + BM25 双索引
→ 冻结 collection 快照
→ search_blocks / get_outline / read_block 等工具
→ Agent 多轮选择与回查
→ 带原始 block 引用的回答
```

这套架构面对的不是抽象的“大量问题”，而是一组已经写成固定输入与证据判据的真实用例。几条代表它主要处理的形态如下：

- `c1-001`：
  > Anthropic《How we contain Claude》里提到过 MCP 吗？
- `c3-001`：
  > "用户批准了约 93% 的权限提示"这句在哪、前后文是什么？
- `c6-001`：
  > 沙箱、出口控制、虚拟机在 containment 里各挡什么、彼此怎么配合？
- `c8-001`：
  > OpenAI《Harness engineering》和 Anthropic《How we contain Claude》合起来，给"agent 时代的工程"画了什么整体图景？
- `c14-001`：
  > "MCP 是新的攻击面"这个说法，在 Anthropic《How we contain Claude》里有原文依据吗？还是模型补充的？
- `c15-001`：
  > 把Anthropic《How we contain Claude》里的三种隔离模式整理成一张表：模式／产品／机制／威胁模型／代价。

这些问题的共同点是：检索目标可以由一条或几条明确查询表达，相关性排序、局部回查和多轮补充足以解决。完整 18 条用例及其金标准见 [03 · 用例集与金标准](../design/03-cases-and-gold-standard.md)。

## 3. 为什么 `c13-003` 成为例外

上一节里最复杂的交叉问题也指明了文档范围或比较对象。到了主题覆盖这一类问题，我们使用更严格的跨文档回归探针 `c13-003`：

> 在当前知识库中，除了沙箱、虚拟机和出口控制，AI Agent 还有哪些隔离或控制边界？请分别说明各限制什么。

主 Agent 把它交给主题覆盖工具时，进一步把检索输入收敛为主题：

> AI Agent 隔离与控制边界

这一步不是在改写用户问题，而是在划分职责：主 Agent 保留“为什么问、最终怎么答”，覆盖工具只负责围绕主题收集证据。问题也正出在这里：一个短主题看起来明确，实际却要求形成一张跨文档的完整证据地图。

一次普通 Top-K 查询很容易找到：

- Agent 容器；
- 沙箱；
- human-in-the-loop；
- 身份和权限；
- 网络隔离；
- 资源限制。

✅ 项目实测中，检索仍然会漏掉几个具体机制：

1. 并行会话如何用工作区／worktree 隔离；
2. checkpoint 如何支持恢复；
3. 状态变更后如何评估恢复是否正确。

这些内容不是知识库里没有，也不是向量检索完全搜不到。问题在于：

- 它们分散在多篇文档和多个章节；
- 主题词不会稳定出现在每个证据附近；
- 同一篇文档里既可能有总览，也可能有非常具体的实现；
- 总览块看起来“都很相关”，但彼此高度重复；
- 找到了很多相关块，不等于覆盖了主题的不同证据义务。

这里的“证据义务”指：如果主题包含某个机制、状态、边界或关系，检索结果中应该存在能够回答它的证据。它不是一段漂亮的主题解释，也不是一组通用分类，而是一条可以被原始文本支持的覆盖要求。

因此，`c13-003` 暴露的不是“Top-10 太小”。即使把 Top-10 扩大到几十、几百个块，如果主题的语义面没有被识别，仍然可能返回大量总览，而具体机制继续缺失。

项目对这个工具的输入边界也做了明确限制：

```text
search_topic(topic)
```

它只接收主题，不接收当前问答的 `retrieval_goal` 或预期答案格式。原因是主题覆盖集合应当独立于某次回答的使用方式；覆盖完成后如何从中选择、综合和作答，属于主 Agent 的职责。

## 4. 第一反应：把主题拆成更多查询

最自然的方案是 query expansion：既然一条查询找不全，就先生成主题解释，再生成 subtopic、同义词、中英文表达和可能实现方式，让多条查询分别检索。

我们确实这样试过。

### 4.1 只把主题解释做向量查询，不够

历史实验里，解释文本被切成单独的 dense 查询。17 条查询、每轮约 76～107 个候选，三个回归目标只召回 0～1 个。

解释文本擅长描述主题“大概是什么”，却不自动产生知识库里真正存在的工程术语。它能帮助人理解主题，不能替代语料证据。

### 4.2 从解释里逐名词做关键词全文检索FTS，能找全，但没有筛选

如果继续把解释拆成名词，再用 FTS 逐项检索，确实能找到 3/3 个目标块。

代价是：

- 346 条查询；
- 召回 511/526 个 block；
- 几乎把整个小知识库都拿回来了。

这在数学上叫“高召回”，在产品上没有完成检索。没有筛选能力的找全，只是把筛选成本从检索阶段推给了阅读阶段。

### 4.3 从固定 facet 到语料锚定 facet

下一步是把主题发展成若干语义面（facet），每个 facet 都带：

- `scope`：它的语义边界；
- `evidence_obligation`：需要找到什么证据；
- `coverage_question`：找到证据后必须能回答什么；
- `required_relation`：证据必须表达的机制、条件或因果关系；
- `origin`：来自语料、假设还是两者；
- `seed_refs`：哪些真实 seed block 支持这个 facet；
- dense 查询和 keyword 查询。

这比“让模型列 20 个相关词”更接近可验证的覆盖契约。系统先从主题做 hybrid seed 检索，再把 seed block 全文和所属文档章节大纲交给模型，要求它观察当前语料如何表达主题，而不是只凭参数知识生成一套通用分类。

随后还有一个 facet audit，检查：

- 语料中的重要机制是否漏进任何 facet；
- 是否存在混合多个独立证据义务的过宽 facet；
- 是否有语义重复的 facet；
- 是否有缺少语料依据的 corpus facet；
- 是否被单一文档或单一解释框架带偏。


🧪 这条链路已有可回归测试，覆盖非法 facet、未知候选、reranker 结构化输出失败、快照边界和“失败时不得返回部分成功”。这些测试能证明失败语义没有静默降级，不能证明覆盖质量已经稳定。

完整契约、失败探针和实验数据见固定快照中的 [065 切片](https://github.com/lipeidonggz/ai-study-helper-v2/blob/c7d69ba97a55395431b406e4893ed70fe79f5f6a/docs/development/slices/065-corpus-grounded-topic-coverage.md) 与 [facet 稳定性实验](https://github.com/lipeidonggz/ai-study-helper-v2/blob/c7d69ba97a55395431b406e4893ed70fe79f5f6a/docs/development/experiments/2026-10-31-facet-contract-audit-stability.md)。

### 4.4 它解决了“能生成”，还没有解决“稳定生成正确的面”

✅ 项目实测里，问题仍然存在：在迭代过程中，同一主题在相同快照上生成过约 14 到 24 个 facets，展开约 136 到 192 条查询，返回约 53 到 75 个支持块；已知三个目标的召回出现过 1/3 到 3/3。它们并非同一提示词版本下的受控 A/B，因此这些数字只用于暴露规划波动，不能写成同版本稳定区间。

这不是简单调一个温度就能解决的波动，因为变量在数据流上游：

```text
seed 看到什么
→ 模型如何理解主题
→ 选择哪些语义面
→ 每个面生成哪些查询
→ 哪些候选进入短名单
→ reranker 如何判断证据义务
```

这里的 reranker 是判断一个 block 是否真正满足某条 facet 证据义务的模型。

每一层都可能改变下一层的输入。现场规划越复杂，最终集合的稳定性就越难证明。

## 5. 章节结构能不能成为一条独立检索面？

论文阅读和工程直觉都支持一个想法：文章的目录本身包含语义。

例如，块正文里未必出现“worktree”，但它所在章节可能清楚表达“如何并行运行多个会话”。如果先检索章节，再展开该章节的 block，就可能找到块级 embedding 漏掉的内容。

✅ 我们在当前 15 篇基准语料上做了一个初步章节索引实验。这个规模只用于验证方法，不是产品的 1,000 篇／10 万 block 目标规模：

| 指标 | 数量 |
| --- | ---: |
| 文档 | 15 |
| block | 526 |
| section-tree 节点 | 328 |
| 可路由 section | 286 |
| 是否满足 95% 映射门槛 | 是 |
| 286 个 section 的 embedding 输入 | 18,322 tokens |
| 索引构建耗时 | 7.9～10.8 秒 |

单次 topic 查询只需要一次 query embedding 和 286 次本地余弦比较，构建成本并不高。

章节索引的实现、边界和实验数据见固定快照中的 [066 切片](https://github.com/lipeidonggz/ai-study-helper-v2/blob/528ff57d1f7fa85182afcfca745cbc5b9f740498/docs/development/slices/066-section-first-topic-coverage.md) 与 [章节路由实验](https://github.com/lipeidonggz/ai-study-helper-v2/blob/528ff57d1f7fa85182afcfca745cbc5b9f740498/docs/development/experiments/2026-10-31-section-first-routing.md)。

### 5.1 它确实找到了块检索找不到的东西

为了只观察“候选来源”这一变量，下面不重新生成 facet，而是沿用上一阶段固定 plan 中的 20 个 facet 名称，分别做章节查询，再合并排名：

- 得到 80 个唯一 section；
- 展开 157 个 block；
- 找到了位于 `Automate and scale > Run multiple Claude sessions` 下的 `worktree` 证据；
- 这个目标同时被三个不同 facet 的章节路由命中，说明多语义面有互补性。

原始 topic 的 block hybrid Top-60 找到了 `checkpoint resume`，但没有找到 `worktree`。把 block 候选和 section 候选合并后，三个目标达到 2/3。

这是一个正向结果：章节路由可以作为独立候选来源，帮助找到“标题有语义、正文却没有直接关键词”的内容。

### 5.2 但它也复制了标题的局限

另外两个目标仍然失败：

- `checkpoint resume` 位于标题 `Production reliability and engineering challenges` 下；
- `checkpoint evaluation` 位于 `Appendix` 下。

`Production reliability...` 不能说错，但它过于宽泛；`Appendix` 更只是一个容器，不表达任何可检索主题。

因此，实验结果不是“章节结构没用”，也不是“LLM 把标题改写得更好就行了”。更准确的结论是：

> 人类章节结构是一条有价值的补充路由，但它只能帮助发现标题已经表达出来的语义面。

当章节标题只表达泛化主题，或一个 Appendix 中塞了多个独立机制时，只检索原标题会形成结构盲区。

更合理的后续形态是：

```text
原始章节标题
+ 编译标题／别名
+ 覆盖问题
+ 子点摘要
+ 必要时把大容器章节做语义切分
↓
仍然回指原始 section 和 block
```

这也解释了为什么单纯做 Section Index 仍不够。章节路由与 block 检索是互补关系，而不是替换关系。

### 5.3 留出主题说明候选面变宽了，但还不能证明正确

在两个未参与调优的留出主题（held-out）上，章节路由分别产生 158 和 172 个展开 block；与当前返回集相比，分别有 81 和 71 个“新候选”。

这些数字只能说明候选集合发生了变化，不能说明新增候选都正确。我们目前没有 block 级人工相关性全集（qrels），也没有证明章节路由提升了人工定义的 facet 覆盖率。

在只运行一次（N=1）的实验中观察到候选变宽，只能作为方案筛选证据，不能写成长期效果。

## 6. 最新研究在解决什么，又没有解决什么

为了判断“是不是我们实现得不够好”，我们查了近期几项直接相关的工作。结论是：大家都在回应同一个问题，但还没有谁提供一个现成的端到端答案。

### 6.1 CoveR：让向量检索器更偏向覆盖

[CoveR](https://arxiv.org/abs/2605.28522) 用子问题可回答性构造覆盖信号，训练覆盖感知双编码器。它在推理时仍然是把 query 编码成一个向量，在全库中按向量相似度检索文档。这里的 nugget 指答案应该覆盖的原子信息点。

它解决的是“embedding 训练目标只奖励相关性、不奖励覆盖”的问题。它没有直接优化一个互补文档集合，因此不能保证 Top-K 之间没有重叠，也不能证明集合已经覆盖了主题的全部证据义务。

这和我们观察到的现象一致：文档各自都相关，不代表放在一起就是完整证据包。

### 6.2 Decompose, Estimate, Select：把集合覆盖显式化

[Decompose, Estimate, Select](https://arxiv.org/abs/2610.40314) 更进一步：

1. 用 LLM 把查询分解成子问题；
2. 用覆盖训练双编码器排序；
3. 用覆盖交叉编码器预测“文档 × 子问题”覆盖矩阵；
4. 用贪心最大边际覆盖选择固定大小的上下文。

这篇论文说明“集合级覆盖”可以工程化，但它仍有明确边界：

- 实验在固定的 BM25 Top-100 候选池中重排；
- 最终选择固定 `k=10`；
- 需要训练两个模型组件；
- 提升检索覆盖，不自动等于提升答案覆盖。


### 6.3 TREC CAR：复杂主题覆盖不是一个新问题

[TREC Complex Answer Retrieval](https://trec-car.cs.unh.edu/) 从 2017 年开始研究“给定复杂主题，返回覆盖多个 facet 的段落”。它的任务形式和我们的目标很接近。

但 TREC CAR 通常由人工 outline 给出主题 facet。也就是说，它非常认真地把“覆盖评价”做成一个可测问题，同时把最难的 facet 发现过程留在了任务输入里。

这组研究给出了同一个判断：

> “找全”是一个由主题理解、语义面发现、候选召回、集合选择和证据评价共同组成的系统问题。单靠更强的相似度检索，无法自动闭合它。

## 7. 为什么继续堆现场查询，收益开始变小

到这里，我们并没有得出“RAG 无法找全”的结论。更准确的是：

> 在固定本地知识库、topic-only 输入、10 万 block 目标规模、证据必须完整且可追溯的约束下，我们还没有找到已经工程验证的一站式现场检索方案。

继续增加查询当然还能提高某些召回，但会遇到五个相互关联的问题。

### 7.1 语义面本身从哪里来

如果由模型完全凭主题生成，就会偏向通用安全分类；如果只看 seed 语料，又会被 seed 的抽样偏差限制。章节结构提供了一部分语料证据，但会受标题质量限制。

这不是“提示词写得再长一点”能完全解决的，因为模型必须同时完成：

- 理解主题；
- 发现当前语料特有的表达；
- 区分不同证据义务；
- 判断哪些面值得检索；
- 知道什么时候已经足够。

### 7.2 查询数量增长快于信息增量

一条 facet 可以生成多组 dense 和 keyword 查询。查询越多，候选越宽，去重和近重复压力越大。最终问题从“怎么搜到”变成“怎么证明新查询带来了新证据”。

如果没有每条查询的 unique evidence 贡献，查询数很容易成为成本指标，而不是覆盖指标。

### 7.3 每次提问都重新理解同一个主题

主题覆盖只依赖主题和知识库快照，理论上可以复用。但现场检索会在每次调用时重新做 seed、解释、facet、查询和审计。

缓存可以复用已生成的覆盖计划，但缓存不是根本解决方法。如果第一次规划就是错的，缓存只会把错误稳定下来。

### 7.4 很难判断什么时候“已经找全”

Top-K 有一个天然停止条件：返回 K 个。覆盖没有。

要判断是否找全，需要一个可检查的覆盖结构：

- 有哪些 facet；
- 每个 facet 的证据义务是什么；
- 哪些义务已有证据；
- 哪些只是潜在解释；
- 哪些冲突尚未解决；
- 哪些缺口值得再查。

这正是现场 query fan-out 缺少的“地图”。

### 7.5 评价和生成仍然是另外两层

即使建立了覆盖矩阵，还要回答：

- reranker 的覆盖判断是否准确；
- 主 Agent 是否使用了返回的证据；
- 最终答案是否覆盖了 facet；
- 高覆盖集合是否牺牲了答案连贯性。

因此，继续把所有职责塞进一个 `search_topic` 调用，会让一个工具同时承担主题地图、检索器、判据和回答规划，边界越来越难验证。

## 8. 原设计中的 LLM Wiki 触发条件已经成立

🤔 按当前项目判断，回看最初写下的触发条件，`c13-003` 已经满足的是：

- 出现了明确的“面状覆盖／跨页概念归集”缺口；
- 块检索、查询展开、corpus-grounded facet 和章节路由分别解决了一部分，却没有形成稳定闭环；
- 问题不是单个工具的 bug，而是知识库缺少一张可复用的主题证据地图。

因此，下一步不应再问“要不要做 Wiki”，而应问：

> 怎样把 Wiki 做成一套可检索、可回源、可增量更新、可删除、可回滚的知识层，并让原有 block 检索继续存在？

目标架构不是用 Wiki 替换 RAG：

```text
                 ┌─────────────────────┐
用户主题 ───────→│ LLM Wiki / 主题地图  │
                 │ 概念、别名、覆盖问题  │
                 │ 页面链接、证据义务    │
                 └──────────┬──────────┘
                            │ page / section refs
                            ▼
                 ┌─────────────────────┐
                 │ 原始 block 证据层     │
                 │ dense + BM25 + 快照  │
                 └─────────────────────┘
                            ▲
                            │ 缺口补查与回源
                            │
                     Agent / coverage tool
```

Wiki 负责“知道该找哪些面”和“面之间如何组织”；block 负责“给出真实原文与引用”。在线 Agent 仍然负责缺口补查、冲突处理和最终综合。

---

## 9. WeKnora 给了我们什么参考

WeKnora 的公开拆解文章 [《能增、能删，但不幂等：拆开 WeKnora 的 LLM Wiki 知识编译》](https://juejin.cn/post/7694866345338765350) 展示了一条值得研究的知识编译流水线。

在文章分析的 `v0.8.2` 版本中，核心是七个阶段：

1. 每篇文档抽取候选概念／实体；
2. 去重并做身份对齐；
3. 把概念匹配到原文 chunk；
4. 生成每篇文档的 summary 页；
5. 批级目录规划；
6. 按 slug 写页或重写页；
7. 注入页间链接并完成索引收尾。

它支撑增量更新的三根柱子尤其值得借用：

### 第一根：页面素材使用逐字原文 chunk

如果页面正文只来自自由生成，后续很难判断某句话是否仍被当前证据支持。逐字 chunk 让“删除哪段材料”至少退化成文本和引用判断。

### 第二根：页面到文档／chunk 的引用落库

这样才能在文档删除、重解析和页面重写时反查影响范围，也才能满足我们的可追溯红线。

### 第三根：slug 身份账本

同一个概念在增量入库时必须归一到同一种身份。身份漂移会制造孪生页，让旧页永远不会被正确更新。

WeKnora 的编译提示词还写了一句很重要的话：

> You are a COMPILER, not a creative writer.

这句话的价值不是措辞，而是角色边界。知识编译需要组织、去重、连接和压缩原文，不应把原文当成灵感来源重新创作。

## 10. 但 WeKnora 不能直接照搬

WeKnora 的公开实验同时暴露了这类系统的工程成本，而且这些数字来自对方特定语料和版本，不是我们的产品基准。

### 10.1 编译成本高

文章中的几次实测里，编译 token 约为源文的 25～42 倍，其中写页占 75%～82%。这说明页面不是免费的索引，而是一次独立的知识生产。

我们的目标是约 1,000 篇文档、10 万 block，不能把这种成本当成可忽略的后台步骤。

### 10.2 重编译不幂等

同一篇文档删除后重新入库，47 个被删 slug 只回来 27 个，并新增 16 个原本没有的 slug。目录和页面集合会发生漂移。

LLM 编译天然带有判断差异。我们的设计不能只假设“重跑会得到同一份 Wiki”，而必须记录版本、保留页面快照，并提供回滚与人工修复路径。

### 10.3 删除会留下结构残留

该实验中删除一篇文档后留下 19 条悬空链接。更关键的是，页面引用只记录到页级 chunk 集合，句子没有回指原始 block，所以多源页面里“这句话是否只来自被删文档”很难精确判断。

如果直接复制这种模型，我们的“可追溯”只到页面挂过哪些块，达不到句子或 claim 级回源。

### 10.4 别名没有完整进入召回

公开拆解发现，去重和链接候选主要依赖标题，别名没有稳定参与召回。中文标题加英文别名时，很容易形成概念孪生页。

我们的知识库跨中英文表达，别名必须进入：

- 概念消歧；
- 页面身份归一；
- dense／BM25 检索；
- 页面链接候选。

### 10.5 页面本身未必进入产品检索索引

该版本中，Wiki 页面没有稳定进入 dense／keyword 索引，Agent 更多通过正则式的 `wiki_search` 找页。阅读可以顺着页面链接继续跳，但“找页”本身不是一套现代混合检索。

如果页面不进入正式索引，所谓 Wiki 更像一份人工可读的中间产物，而不是 Agent 可稳定召回的知识层。

### 10.6 规模超过设计区间后会逐级退化

文章根据实现常数判断，WeKnora 当前方案较适合几十到几百个目录、几千页以内。目录超过阈值后会使用近似召回，单篇输入还有 32,768 字符截断。

这与我们的目标规模存在明显差距。可以借鉴编译流程，不能把当前实现当成已经验证到 10 万 block 的底座。

---



验证顺序应当是：

1. 固定 `c13-003` 的原始问题、主题输入和知识库快照，检查 Wiki 能否显式生成三种证据义务；
2. 检查页面／section 路由能否找到三个目标 block；
3. 检查每个页面证据能否回源到原始 block；
4. 检查删除一篇来源文档后页面与引用是否正确变化；
5. 用至少两个 held-out 主题观察泛化；
6. 最后才比较回答覆盖、token 成本和延迟。

只在 `c13-003` 上成功，说明回归探针通过；在 held-out 上也成功，才说明方法具有泛化能力。

## 11. 这次探索真正改变了什么

我们最初把“检索”理解成一次更好的查询，后来把它理解成 Agent 的多轮工具使用。这次之后，还需要再往前走一步：

> 对“找全”任务，检索对象不只是一组 block，而是一个包含主题、语义面、证据义务和来源关系的覆盖结构。

这带来四个可复用的工程判断。

### 判断一：不要用返回块数代替覆盖质量

返回 10 块可能是重复，返回 500 块也可能没有筛选。找全需要独立于 Top-K 的覆盖评价。

### 判断二：facet 必须绑定证据义务

“安全”“隔离”“可靠性”这种宽泛分类无法指导 reranker。每个 facet 都应该说明它要回答什么、证据必须表达什么关系。

### 判断三：章节结构值得用，但不能当完整知识地图

章节路由能找到标题表达出来的具体机制，是块检索的重要补充。对泛标题、无语义容器和跨主题 Appendix，仍需要编译语义或内容级二次检索。

### 判断四：预编译解决的是发现与组织，不是放弃原始证据

LLM Wiki 最有价值的地方，是把“围绕一个主题应该有哪些面”变成可复用结构；原始 block 仍然是最终证据。没有块级回源，Wiki 越流畅，产品风险反而越大。

## 12. 一页速查

- **最初的取舍**：18 个用例优先使用块、元数据、双索引和 Agentic 检索；Wiki 只在出现面状覆盖缺口时引入。
- **触发问题**：`c13-003` 需要跨文档、跨章节地覆盖多个具体机制，Top-K 和单次 query fan-out 会返回大量相关但重复的块。
- **已试方案**：主题解释、名词逐项检索、corpus-grounded facets、缺项审计、证据 reranker、章节路由。
- **实验边界**：当前主要是单主题回归探针和 N=1 候选实验，没有 block 级 qrels；新候选不等于正确覆盖。
- **章节结论**：章节路由可以补充召回，但无法单独解决泛标题和 Appendix 容器。
- **论文结论**：覆盖感知检索、集合覆盖选择和覆盖评价都已有研究，但主要解决候选池内排序、集合选择或评价，不是完整主题证据发现。
- **架构判断**：继续保留块检索，同时引入可回源的 LLM Wiki，作为主题发现、别名消歧和覆盖地图层。
- **WeKnora 可借点**：七阶段编译、逐字原文素材、chunk 引用和 slug 身份账本。
- **不能照搬的原因**：成本高、结构会漂、删除不彻底、引用可能只增不减、别名和页面未完整进入检索、规模边界有限。

🤔 最后留下一句核心判断：

> 我们不是从 RAG 转向 Wiki，而是从“用查询寻找证据”扩展到“先维护一张可回源的证据地图，再用查询补全它”。
