# 0009 · 单开发壳承载产品和评测，发布时编译期移除评测

- 状态：已接受
- 决定日期：2026-10-22
- 影响范围：Tauri 构建、前端入口、Python sidecar、评测工具分发、测试与发布检查

## 背景

08 原先把评测台定义为独立 Tauri 应用。产品和评测确实需要保持分别的数据根、分别的 Python sidecar，并且评测只作为开发工具，不进入普通用户发布包。

如果为此再维护第二个 Tauri 应用，会重复窗口生命周期、sidecar 管理、重启与清理、更新、日志、前端导航和构建脚本。开发者也需要在两个窗口之间切换，才能从产品 trace 进入评测诊断。

## 决定

1. 产品和评测使用同一个桌面宿主源码与同一个 Vue 前端源码。
2. 默认发布构建只包含产品功能、产品 sidecar 和产品数据根。
3. 显式评测构建启用 `eval-console` Cargo feature 和 `VITE_EVAL_CONSOLE` 编译标志，在开发壳中增加评测工作区。
4. 评测运行时仍启动独立评测 sidecar，并使用独立 `eval-data` 数据根和独立评测 SQLite。
5. 产品和评测复用同一 `AgentRuntime`、检索工具、prompt、预算和 trace 实现；评测不通过产品 HTTP API，也不依赖产品实例正在运行。
6. 评测 sidecar 按需启动；产品 sidecar 生命周期不受评测运行影响。
7. 发布构建必须通过产物检查，确认不包含评测前端资源、评测 Python 模块、评测 sidecar 和 `/api/eval` 路由。
8. 评测是否可用由显式编译 feature 决定，不能只依赖 `debug_assertions` 或运行时配置开关。

## 候选方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 两个完全独立的 Tauri 应用 | 不采用 | 物理隔离明确，但重复桌面生命周期和前端基础设施；开发切换成本高 |
| 单应用始终携带评测，仅隐藏入口 | 不采用 | 发布包仍包含评测代码和数据能力，隔离不可验证 |
| 单开发壳 + 编译期裁剪 + 独立评测 sidecar／数据根 | 采用 | 降低宿主维护成本，同时保留运行、数据与发布隔离 |

## 后果

- 开发构建比纯产品构建更大，并可能启动两个 Python sidecar。
- 构建系统必须明确区分产品发布构建和开发／评测构建。
- 前端评测入口必须使用可 tree-shake 的动态入口，产品发布构建不能包含评测页面。
- 产品后端代码不能依赖评测模块；评测 sidecar 可以单向依赖共享 Agent 核心。
- 发布会增加静态产物、进程清单和安装包内容检查。

## 验证

- 产品发布构建的导航和静态资源中不存在评测工作区。
- 产品安装包中不存在评测 sidecar、评测数据库初始化和 `/api/eval`。
- 开发评测构建中，产品与评测使用不同端口、启动令牌、进程和数据根。
- 从产品 trace 可进入评测工作区，但评测写入不改变产品 SQLite、collection 或 trace。
- 产品 API 和评测 runner 对同一输入复用同一个 Agent 执行服务，并有契约测试证明没有第二条问答链。

## 推翻条件

- 评测台需要作为独立产品分发给其他开发者；
- 单壳构建导致无法接受的包体积、权限面或进程复杂度；
- 编译期裁剪无法可靠验证，或评测代码多次意外进入发布包；
- 产品和评测需要不同 Tauri 权限、更新节奏或签名发行渠道。
