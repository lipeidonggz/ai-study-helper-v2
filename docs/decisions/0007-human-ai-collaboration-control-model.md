# 0007 · 人-AI 协同控制模型

- 状态：试行中（连续 3～5 个实质性切片后复核）
- 决定日期：2026-10-22
- 影响范围：需求讨论、切片设计、实现、验证、交付和文档记录

## 背景

本项目由项目负责人与 AI 编码代理共同完成。AI 显著提高了代码、测试和文档的生产速度，但也产生了新的控制问题：

- 负责人没有逐行编写代码，旧有的“读过实现就有掌控感”不再成立；
- 设计原则可能与实现算法脱节；
- 局部测试通过，跨切片用户流程仍可能错误；
- 决策记录在实现完成后集中出现，容易形成审批疲劳；
- 自动检查可以证明格式和已知行为，不能证明产品语义正确。

现有“垂直切片 + 决策账本 + 二次确认”提高了可追溯性，但仍不足以完全解决掌控问题。需要把控制点从“事后确认”前移到“事前契约、中途检查和可运行证据”。

人机协同没有可直接照搬的成熟标准。外部机构公开的实践报告提供的是特定团队、工具和任务分布下的经验证据；个人适配模式必须在自己的项目中持续试验、观察和调整。

因此本 ADR 记录的是当前阶段的试行策略，不是已经验证完成的方法论。

## 当前试行决定

### 1. 掌控感按四个能力定义

| 能力 | 判断标准 |
| --- | --- |
| 可预测 | 实现前能说明系统准备怎样变化 |
| 可解释 | 能从代码、测试和文档解释当前状态为什么如此 |
| 可干预 | 方向错误时能在成本可控时停止或改选 |
| 可恢复 | 失败后能定位、回滚并重新验证 |

代码阅读量、提交次数或文档字数都不是掌控感的替代指标。

### 2. 每个实质性切片先写控制契约

功能、数据、架构、安全或用户流程切片在编码前必须填写
[切片模板](../development/slices/TEMPLATE.md) 中的“控制契约”：

- 用户可观察的完成目标；
- 最多 5 条核心不变量；
- 明确禁止的行为；
- 主要失败语义；
- 预计人工检查点；
- 本切片允许承载的高价值决策数量。

纯文档修正、机械格式化和不改变行为的维护可以简化。

### 3. 决策按风险分级

| 等级 | 判定 | 人的控制方式 |
| --- | --- | --- |
| A | 不改变公开接口、数据语义或用户行为，有明确设计依据且可自动验证 | AI 可自主执行，在交付中列入审计摘要 |
| B | 设计有方向但缺具体算法，影响当前切片且可回退 | 记录决策账本，完成后集中确认 |
| C | 删除或覆盖数据、安全边界、不可逆变化、高风险依赖或突破硬约束 | 执行前必须停止并请求负责人选择 |

所有实质性自行决策仍必须记录；分级改变的是确认强度和时点，不是是否可以留下无记录决定。

如果一个切片出现超过 5 个 B 级决策，应优先拆分切片、重新收敛范围，或明确说明为什么必须一起审查。

### 4. 关键切片要有中途可运行检查点

涉及数据流、任务状态、存储、安全或用户主流程的切片，不等全部完成后才展示。第一条主路径可运行时，应检查：

- 数据实际流经哪些状态；
- 用户会看到什么；
- 失败后会留下什么；
- 实现是否仍符合控制契约。

### 5. 完成后提交证据包

除“测试通过”外，交付必须提供：

- 可运行入口和操作步骤；
- 自动化命令和结果；
- 关键不变量的测试映射；
- 真实失败样本或失败探针；
- 仍需人工执行的验收动作；
- 已知风险、未验证项和待确认决策。

证据必须来自实际执行，不能用设计推断代替运行结果。

### 6. 负责人做反向解释

高风险或高复杂度切片交付时，AI 提供 3～5 个行为问题，由负责人独立回答，例如：

- 连续操作两次后系统状态是什么？
- 某一步失败会不会删除旧状态？
- 回滚后新的写入以什么为基线？
- 哪些数据被删除，哪些配置被保留？

如果负责人无法回答，不能把“点了确认”当成已经建立掌控。

### 7. 人机职责保持显式

| 角色 | 主要责任 |
| --- | --- |
| 人 | 产品定义、非目标、安全边界、数据删除、核心不变量、最终语义验收 |
| AI | 方案探索、实现、测试、文档草稿、失败分析和可运行证据 |
| 共同 | 架构取舍、根因判断、验收标准和“完成”的定义 |

### 8. 外部实践只作为假设来源

外部实践按用途分为三类：

| 类别 | 采用方式 |
| --- | --- |
| 硬约束 | 可以本地验证后直接采用，例如数据不可静默丢失、凭证不得落盘、失败不得伪装成功 |
| 工作假设 | 在自己的切片中试行，例如中途检查、证据包和决策分级 |
| 个人偏好 | 根据负责人的认知方式、任务节奏和维护成本持续调整 |

OpenAI Harness engineering、其他团队公开的 Agent 协作经验，以及本系列之前的设计文章，都作为高上下文案例和候选假设使用。采用前必须检查：

- 对方团队规模、工具链和任务类型；
- 对方产品阶段与风险边界；
- 当前项目是否具备相同前提；
- 试行后是否真的改善预测、解释、干预和恢复。

外部实践不能替代本地验证，也不能因为写进公开文章就自动成为本项目规则。

### 9. 协作模式可以随任务切换

不存在适用于所有任务的一种固定模式：

| 任务 | 更适合的协作方式 |
| --- | --- |
| 产品定义、边界与非目标 | 人主导，AI 做反方和结构化整理 |
| 架构探索 | 人机共同讨论，AI 提供候选和失败预演 |
| 已定契约的实现 | AI 主导，人检查关键不变量 |
| 复杂故障定位 | 结对调试，AI 管理证据，人确认根因 |
| 文档与文章 | AI 起草，人决定价值、取舍与叙事 |
| 删除、迁移、发布 | 人明确批准，AI 提供验证与恢复路径 |

需要学习的是“当前任务应进入哪种模式”，而不是寻找一套永远不变的总流程。

### 10. 每个切片记录协作复盘

除产品和技术复盘外，每个实质性切片还要回答：

- 哪一步 AI 明显加速；
- 哪里负责人失去了系统模型；
- 哪个控制点真正发现了问题；
- 哪个流程只有仪式感、没有产生判断价值；
- 下一次准备调整哪一到两项。

协作复盘不追求长篇总结，重点是比较“预期帮助”和“实际帮助”。

### 11. 流程规则必须有生命周期

新增规则必须记录：

- 要防住的具体失败；
- 适用任务与风险等级；
- 使用成本；
- 当前有效证据；
- 复核时点；
- 继续、调整、降级或删除的决定。

同类失败重复出现、后果不可逆或风险很高时才增加长期硬规则。单次低风险摩擦优先通过局部判断解决，避免每次事故都为流程增加一层永久负担。

## 候选方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 人逐行阅读所有 AI 代码 | 不采用 | 无法随项目增长持续，也不能单独证明运行时语义 |
| 完全相信设计与自动测试 | 不采用 | 已有连续操作和跨切片语义失败的反例 |
| 只做事后集中二次确认 | 作为过渡保留 | 可追溯但介入太晚，容易审批疲劳 |
| 控制契约 + 风险分级 + 中途检查 + 证据包 + 反向解释 | 当前试行 | 同时覆盖预测、解释、干预和恢复，但成本和长期收益仍需验证 |

## 后果

- 切片开始时间略微增加，但方向错误更早暴露。
- B 级决策从长表格变成有限的高价值审查。
- AI 需要提供可运行证据，而不只是实现总结。
- 负责人仍需投入时间理解关键行为，不能把责任委托给 AI。
- 这套模型本身仍处于实验阶段，后续必须用实际切片检验其成本与收益。
- 每个切片增加简短协作复盘；连续 3～5 个切片后统一评估规则，而不是每次不适就叠加新流程。
- 外部实践只作为输入；与当前上下文不匹配的建议可以记录、试用或拒绝。

## 验证

- 下一个实质性切片必须包含完整控制契约。
- 决策账本必须标记等级和确认方式。
- 交付说明必须包含证据包与反向解释问题。
- 若出现跨切片语义错误，必须同时检查控制契约是否遗漏了对应不变量。
- 连续 3～5 个实质性切片后，汇总协作复盘，评估每条新增规则是否保留。
- 负责人应能说明协作模式与任务类型的匹配关系，而不是只知道一套固定操作。

## 推翻条件

- 流程成本长期显著高于发现问题的收益；
- 对低风险切片造成不必要的审批负担；
- 反向解释和证据包无法帮助负责人建立更准确的系统模型；
- 试行后流程成本持续明显高于发现问题、减少返工或提高理解的收益；
- 外部实践与本地条件差异过大，继续套用会造成虚假确定性；
- 项目进入多人或多 Agent 协作后，需要更强的权限、评审或责任人模型。
