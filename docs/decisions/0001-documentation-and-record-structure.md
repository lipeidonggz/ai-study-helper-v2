# 0001 · 文档与实现记录结构

- 状态：已接受
- 决定日期：2026-10-20
- 影响范围：`docs/`、`AGENTS.md` 和后续实现流程

## 背景

项目准备开源，设计文档已经从手写 HTML 迁移为 Markdown，并将已审核的产品与架构设计整理为 `01–09`。

进入实现阶段后，还会持续产生技术取舍、垂直切片过程、实验数据和运维说明。如果把这些内容都继续塞进 `docs/design/`，设计基线会不断变化，贡献者也难以区分：

- 哪些是已经审核、必须遵守的设计；
- 哪些只是实现过程中的一次判断；
- 哪些是一次实验的结果；
- 哪些属于安装、排障或日常运维；
- 哪些只是临时任务进度，不值得长期维护。

## 决策

文档按用途分类，不使用一个按时间排列的总日志：

| 位置 | 保存内容 | 命名与规则 |
| --- | --- | --- |
| `docs/design/` | 已审核的产品、架构与行为设计基线 | 现有 `01–09` 保持稳定；只有形成新的稳定设计主题时才继续编号 |
| `docs/decisions/` | Architecture Decision Record（ADR，架构决策记录） | `NNNN-短描述.md`，独立从 `0001` 编号 |
| `docs/development/slices/` | 每个垂直切片的实现记录 | `NNN-短描述.md`，按切片而不是按天或会话编号 |
| `docs/development/experiments/` | 性能、质量、兼容性和技术验证实验 | `YYYY-MM-DD-短描述.md` |
| `docs/operations/` | 安装、排障、备份、升级和诊断说明 | 按长期使用场景组织 |

GitHub Issue、Project 和 PR 用于临时任务、进行中状态和讨论。只有得出可长期复用的结论时，才整理进 `docs/`。

## 每类记录的边界

### ADR

记录“为什么选择这个方案”，至少包含背景、候选方案、决定、后果、验证方式和推翻条件。ADR 可以指向设计文档，但不复制整篇设计。

### 垂直切片

每个切片记录目标、范围外事项、输入／输出、失败语义、验收条件、关联版本、关键转折与根因、验证证据和遗留问题。只记录有解释价值的过程，不保存逐轮流水账、模型内部思考或无关操作。

### 实验记录

记录固定配置、版本、样本、测量结果、结论和复现方式。大型数据库、trace、artifact 和原始评测产物仍保存在本地或被忽略的目录中，不直接提交进 Git。

### 运维文档

面向实际使用和故障处理，优先写可执行的步骤、前置条件、预期结果和回滚方式。

## 后果

- `docs/design/01–09` 成为稳定基线，不会因为一次普通实现决定而持续扩张。
- 架构取舍、切片过程和实验结果各自有固定入口，便于搜索和维护。
- 临时进度继续留在协作系统，减轻仓库文档负担。
- 需要维护少量分类规则，但比以后拆分一个混合型总日志成本更低。

## 推翻条件

如果项目长期只有单人开发、文档分类带来的维护成本明显高于收益，或者现有协作系统无法承担临时进度记录，可以重新评估。重新评估必须以实际使用问题为依据，不以“目录更多”为理由。
