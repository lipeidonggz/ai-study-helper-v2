- 状态：已接受（2026-11-27，沛东人工确认）

- 影响范围：领域知识框架生成、离线证据挂接、查询期叶节点选择、主 Agent 候选证据接入、评测与 trace
- 设计正文：[16 使用角色驱动的领域知识组织（v1.0）](../design/16-使用角色驱动的领域知识组织.md)

## 背景

固定关系轴、语料主题聚类和单一路径 Wiki 都容易受术语、语料覆盖和预定义关系限制。当前项目需要优先解决开放式、多方面的“求全类”问题：既要找到回答问题所需的完整知识范围，又要让每个知识范围能够追溯到原文 block。

更底层的两项判断是：第一，在当前产品对“找全”的定义下，问答 Agent 直接面对没有面向目标组织的文档集合，无法证明自己已经覆盖全部必要方面；它仍可能给出有用答案，但不存在可枚举、可审计的完整知识面和覆盖判定单位。第二，同一知识库可形成多种自洽组织，同一实体和关系在不同视角下可能具有不同语义身份、职责边界和证明义务，因此知识组织必然视角相关；相对稳定的底座是原文证据，组织层则是视角化的映射。

这两项判断分别要求预先编译知识和按视角编译知识。当前产品 v1.0 以角色作为用户必须选择的视角锚点；这不排除未来其他产品采用任务、监管职责或问题类型作为视角，但不能据此弱化当前设计中角色选择的必要性。

角色驱动路线已经在固定 15 篇快照上跑通“角色与任务框架生成 → 冻结叶节点目录 → 全量 block × leaf 证据挂接 → 查询时按一级子树选择叶节点 → 候选原文接入主 Agent”的完整链路。c13-003 真实运行达到 24/24 个分支调用成功，旧混合相关证据集合召回为 34/35，唯一缺口已复核为背景概览块；候选证据成本、回答证据选择和跨样本泛化仍未达标。

因此需要把此前边探索边记录的 16 号草稿收敛成可执行、可追溯、可验收的 v1.0 设计基线。旧稿保留为历史实验材料，不再作为实现依据。

本设计的核心指导思路是“先定义应知，再证明已知，最后闭合覆盖”：角色与任务定义知识面，当前 snapshot 原文证明知识是否成立，查询期完整执行状态约束本次结果能够承诺的覆盖范围。三者分别对应知识面、证据面和覆盖状态，不能被主题摘要、检索分数或模型自我判断互相替代。

## 决定

1. 采用“使用角色与履职任务决定知识视角”的领域知识组织路线，作为当前 v1.0 设计基线。
2. 框架生成不读取当前知识库内容；知识库证据通过独立的离线挂接阶段关联到冻结叶节点。
3. 知识框架先冻结一级目录，再逐一级分支展开叶节点；框架 revision、hash、生成模型和提示词必须可追溯。
4. 运行时支持关系保持二值；人工评测使用 `no_support`、`weak_support`、`direct_support` 三档，`weak_support` 不升级为额外运行时等级。
5. 离线挂接完成全部计划的 `block × leaf` 判定；只有完整性校验通过的不可变账本才能标记为 `sealed_complete` 并对查询发布。
6. 查询时按冻结框架的一级 root 分别选择叶节点，再合并、去重并从同一版本的账本和 collection 快照中物化候选 block。
7. `complete` 只表示全部分支调用成功、输出合法且未截断，不表示现实知识绝对完整；任一分支失败、非法或截断都必须使整体为 `partial`。
8. 当前 24 个 root 和 `kf_c1b79b163bfcb2a93844` 是当前框架 profile 的兼容与回放约束，不是永久产品常量。
9. 金标准按 `core_required`、`supporting`、`overview`、`irrelevant` 分层。核心召回使用 `core_required` 作为硬分母，概览块不得与核心必答块混入同一个硬召回指标。
10. 知识编译输入是当前知识库 snapshot 和领域边界，不是预先给定的角色。单知识库通常对应单一领域；出现多领域时应先拆分领域边界。
11. 领域边界可由用户提供，也可由系统根据知识库元数据和内容推断。角色候选由 LLM 根据领域生成并归并，用户必须从中选择本次编译使用的角色。
12. 在具体知识库的知识编译流程中，选择角色是唯一必须由人完成的前置动作。主要任务、任务树、知识框架、叶节点展开和叶节点审计均可自动生成并通过自动门禁；对具体生成内容的人工复核是可选的，但项目级提示词、金标准、工具行为契约等基础件仍遵循既定人工确认规则。
13. 文档、框架、领域、角色、任务和判定配置变化应支持显式 delta、精确失效、staging 合并和原子发布。该增量编译模型属于设计支持的能力，当前尚未实现和验证，不得宣称已经具备自动增量能力。
14. 当前 v1.0 的 `coverage_status=complete` 只覆盖冻结知识框架内的叶节点选择与候选物化。知识框架缺口可从“挂接后较多 block 不支持任何叶节点”和“全局类问题召回很少或出现明显未覆盖方面”形成待审反馈；LLM 可辅助分类，人工判断是否进行版本化框架修订。该闭环尚未实现，不得把 `complete` 外推为框架完备或现实问题已经找全。

## 候选取舍

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 使用角色与任务驱动的知识框架 | 采用 | 知识视角与履职任务直接相关，可先建立内容无关目录，再挂接当前语料证据 |
| 单一固定关系轴作为唯一索引 | 不采用为唯一路线 | 容易受术语和预定义关系限制，不利于开放范围发现 |
| 从任务树直接生成知识树 | 不采用 | 任务需求和知识身份会混合，难以稳定覆盖与复核 |
| 一次生成完整知识森林 | 不采用 | 结构漂移和局部失败不可控，先冻结一级目录再逐分支展开 |
| 多叶最终支持判定合并为一次调用 | 不采用 | 叶节点之间会竞争注意力，无法得到稳定的一对一证据关系 |
| 一级树初筛加逐叶最终判定 | 采用 | 初筛只排除整棵子树明确无关，真实支持关系仍由逐叶判定产生 |
| 只用固定 Top-k 候选宣称找全 | 不采用 | 数量上限不是语义覆盖，容易产生静默漏挂和假完整 |
| 24 个一级子树并行选叶 | 当前采用 | 分支隔离、失败可解释，并可在宿主层统一去重和排序 |

## 后果

- 知识目录、挂接账本和原文证据具有明确的版本与身份关系，可以复现、解释和回滚。
- 查询期可以按一级分支检查完整性；失败不会被伪装成合法的空结果。
- 离线挂接的计算成本较高：固定 15 篇、526 个 block 的计划产生 121,742 次候选 `block × leaf` 调用。
- c13-003 当前会返回约 365 个去重候选 block，工具结果约 167,624 token；默认 100,000 上下文只能返回 `partial`，提高到 200,000 才成功。
- 全量挂接关系不等于最终回答证据包；后续必须按问题意图、支持类型、代表性和边际覆盖进行证据选择。
- 角色框架本身需要持续维护；新增领域、角色变化和大量文档增量都需要重新评估框架与挂接版本。
- 选择角色是当前产品必须保留的人工控制点；其余生成内容可以采用自动校验，但自动通过只代表满足当前门禁，不等同于人工质量背书。
- 框架缺口反馈仍是独立缺口；当前完整声明只能限定在冻结框架和成功执行的分支范围内。

## 推翻条件

- 一级树初筛在未参与调参的样本上持续误排除核心证据，且回退机制无法恢复；
- 在默认产品预算下，证据选择和上下文压缩无法把端到端成本降到可接受范围；
- 角色框架在未参与调参的领域、角色或文档集合上无法稳定覆盖核心知识；
- 挂接账本、框架 revision 和 collection snapshot 无法保持版本一致或可靠回滚；
- 正式扩大样本后，核心证据召回率、`partial` 正确率或假完整率持续不达验收门禁。
