## 0. 这篇怎么用

**一句话：Agent 虽然是带智能的，但它仍然是一个系统。** 所以架构设计的老办法照样适用——先用**功能属性**定义"做什么"， 再用**质量属性**定义"做到什么程度"；而**架构的形状，基本由后者决定**。

问题在于：功能需求通常写得很清楚，**质量属性却常常整条不在需求文档里**。 01 §4 写了 8 条质量属性（正确性、可信、覆盖、诚实、一致、表达、边界、速度）， **成本、安全、隐私、可靠性、可观测性、可维护、可复现、易用性、可安装性／可运维性／资源占用这些一条都没有**。 所以做架构的第一步不是画结构，而是**把它们挖出来、摆到桌面上，逐条给一个处置**。

**读法**：先看 [§2 表 B](#attr-gap)——那是需要你拍板的地方（01 没考虑过的质量属性 ＋ 建议的处置）； §1 是方法本身，方便以后复用；§3 是下一步。

**本版不做什么**：不选技术、不定通道、不画架构图——那些是这套方法下一步的产物。

## 1. 通用架构设计方法（六步）

这套步骤与业界"质量属性驱动的架构设计"同源（SEI 的 ADD／ATAM、Bass《Software Architecture in Practice》的质量属性清单、 ISO/IEC 25010 的产品质量模型），按本产品的语境裁剪过。

1. **A. 输入：功能属性 ＋ 约束。** 功能属性＝系统要提供的能力（本项目：01 的 15 类问题 ＋ 03 的 18 条用例与金标准）。 约束＝不是目标、但限定了方案空间的硬条件（本项目：单人开发、本地部署、非生产系统、单用户＋单知识库、单轮对话）。
2. **B. 质量属性盘点（重点步骤）。** 拿一份通用清单当起点，逐条对着本产品问三问：① 它在我们这里**意味着什么**（用用户能听懂的话说）？ ② 它**会不会改变我们的结构**？③ **不管它**会出什么事？ 然后每条给一个处置，三选一——**要设计满足**／**只观测记录**（暂不设目标，跑批时记着看）／**显式忽略**（写清为什么）。
3. **C. 筛出架构驱动因素。** 判据只有一条：它会逼我们**选择或放弃某种结构**吗？是，就是驱动因素；不是，降级为设计约束或观测项。
4. **D. 驱动因素 → 设计战术。** 每条驱动因素找对应手段（例如：成本 → 预算与调用上限；安全 → 最小权限、输入不可信、出站限制； 一致性 → 多次取样与抖动预算；可观测 → trace 与对账），并明确它**施加在哪一层**。
5. **E. 候选结构 ＋ 取舍。** 至少列两个候选，逐条对驱动因素比对，并写明**代价由谁承担**（用户的时间？开发成本？答案质量？）。
6. **F. 决策记录 ＋ 推翻条件 ＋ 验证方式。** 每条记四件事：决定什么／依据什么／判定它够用的**判据**／什么信号出现就**推翻**它，以及怎么测出来。

>  **三条纪律**：<br> ① **"不知道"不算处置**——质量属性不要求量化（成本可以只写"设一个上限、超了就报警"），但每条都得有明确处置； **忽略也要留理由**，否则半年后没人知道当时是想过还是没想过。<br> ② **产品视角第一性**——先问用户会怎么体验，再谈工程约束（延迟、token、实现复杂度是约束，不是出发点）。<br> ③ **每条决策都要能指回它服务的用例**；指不回去的，就是技术本位主义。

## 2. 本产品的质量属性盘点

### 表 A · 01 已经覆盖的（Q1–Q8，共 8 条）

| # | 质量属性 | 在本产品的含义 | 架构敏感？ |
| --- | --- | --- | --- |
| Q1／Q2 | 正确性／可信（可核对） | 讲的东西与材料一致；关键说法能回查到出处 | **是**——决定要不要做"原文块可溯源"这一层 |
| Q3 | 完整性（覆盖）＋ 遗漏透明 | 该说的说到；说不全要具名讲清漏了哪类 | **是**——决定要不要"全集／枚举"能力 |
| Q4 | 诚实性（不编造） | 不知道就说不知道，**不把模型补充说成文档内容** | **是**——与 Q1 的排除性那一半同源 |
| Q5 | 一致性（稳定） | 同一个问题问几次，答案不该翻来覆去 | **是**——决定要不要多次取样与抖动预算 |
| Q6 | 表达合适 | 讲得清楚，形态贴合问法 | 否——主要靠提示词与输出形态，不改变结构 |
| Q7 | 边界合规 | 越界请求按任务类型处理，不是一律拒答、也不是有求必应 | **是**——决定拒答／转任务的路径 |
| Q8 | 响应速度 | 等太久就不好用（已定＝首字延迟上限，见 03 §4） | **是**——决定要不要流式、检索要不要挡在首字之前 |

| 质量属性 | 在本产品的含义（用户视角） | 架构敏感？ | 处置与理由 |
| --- | --- | --- | --- |
| **成本** | 问一次要花多少（模型调用、token）；把一批文档编译进来要花多少时间与调用。用户视角：等得起吗？这套东西跑得动吗？ | **是**——它决定"一轮评测能不能跑完"（18 条用例 × N＝10 ＝ 180 次问答，外加固化语料的编译） | **要设计满足**（设上限 ＋ 观测，不设优化目标）。理由：这里成本不是钱的问题，是**实验可行性**。实测量级：单篇编译分钟级；多文件大源折算约 500 次调用／1–1.5 小时（0028 记录） |
| **安全** | ① **文档是"不可信输入"**——加进来的文章里可能藏着指令（提示注入）；② agent 能动的工具要**最小权限**（只读优先，写要有边界）；③ 出站限制 | **是**——决定工具集与权限模型 | **要设计满足（最低限度）**。理由：单用户本地、威胁模型弱，但"用户会把网上抓来的文档丢进来"是真的；且 01 §3.1 已要求"自称来自文档的必须真能找到"，注入会直接破坏这一条 |
| **隐私／数据主权** | 用户文档去了哪：是否发给第三方模型服务、本地留存多久、能不能删 | **是**——若在意，会逼出"本地模型 vs 云模型"这条通道选择 | **显式忽略**。理由：自用，语料都是公开文章，无个人信息。**但写清：一旦面向他人使用，这条必须重估**（它会影响整条模型通道） |
| **可靠性／降级** | 模型超时、检索为空、解析失败、答案被截断时，系统要干什么——**不许静默** | **是**——决定要不要"否信号"与降级路径 | **要设计满足**。理由：02 §3 的"静默失败""没有否信号"是已经踩过的坑（丢 19% 报告而指标全绿） |
| **可观测性** | 能不能解释"这个答案是怎么来的"：检索证据、提示词、token、工具调用；失败时能不能白盒归因到检索／引用／提炼哪一步 | **是**——决定每个环节都要留可读产物 | **要设计满足**。理由：没有它，失败样本的**根因闭环**做不了——那是 02 §1.2 第 ⑤ 步的前提 |
| **可测试／可评估** | 这套系统自己能不能被考：判官、用例集、统计口径——判官是基础设施 | **是**——它决定"改动之后你怎么知道变好了" | **要设计满足**（正在做：[03](03-cases-and-gold-standard.md)） |
| **可复现性** | 同输入同配置能否重放：模型名与版本、温度、提示词版本、语料版本 | **是**——决定语料与提示词要不要版本化 | **要设计满足（最低限度）**。理由：金标准里的精确数字与引文就绑在语料版本上（03 §4 的"冻版"） |
| **可维护／可演进** | 换模型、加语料、改提示词、重编译，各自要付什么代价 | 部分 | **只观测记录**：记下"改一处要重跑什么"，不设目标 |
| **可安装性／可运维性／资源占用** | 从干净环境完成安装，只需少量本地依赖即可启动；升级、备份和排障不需要管理员长期维护；低配置机器可关闭可选能力，核心问答仍可用 | **是**——决定运行时要依赖哪些服务、哪些能力必须可选、数据与配置放在哪里，以及升级和回滚能否保住用户数据 | **要设计满足（最低限度）**。理由：产品定位是**单机个人版**，部署复杂度会直接成为用户能否实际使用的门槛；功能再完整，如果只有开发机才能安装和维护，也达不到产品目标 |
| **易用性** | 界面与交互 | 否 | **显式忽略**：练手／自用产品，界面不是重点；只保留最小的追问与提示能力 |
| **性能（吞吐／并发）** | 多人同时用的承载力 | 否 | **显式忽略**：01 已明确单用户＋单知识库，不做多用户与多知识库 |

>  **处置三分法的含义**：**要设计满足**＝它会进架构决策； **只观测记录**＝暂不设目标，但跑批时记着看； **显式忽略**＝明确不做，并留下理由。 **忽略项不该在后面偷偷回来**——要回来就明说重估。

## 3. 下一步

1. **表 B 的处置逐条拍板**（尤其标了"显式忽略"的三条：隐私、易用性、并发）。
2. **走 C–F 步**，产出两样东西： ① 一张「类 → 能力需求 → 原语 → 候选通道 → 判据 → 成本 → 结论」对照表； ② 一组决策记录，每条带**推翻条件**。
3. **凡"两条通道都可能行"的地方，不靠推理**——做离线对比实验（复用已有编译输入）， 并用三问过滤器收口：闭卷基线是多少？差距有没有超过抖动？这个便宜是不是语料偶然给的？

顺序提醒：第 ④ 步（架构决策）产出的是"每类问题走哪条通道、承载层背多少'全'的责任"， 不是技术选型；而且它不是一次定终身——02 §1.2 第 ⑤ 步的失败模式可以推翻它。
