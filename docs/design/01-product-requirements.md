# 01 · 文档学习问答 · 产品需求文档（PRD）

**本文是产品需求文档（PRD）**：定位 → 用"用户以学习为目的会问哪些问题"推导**问题空间（15 类）** → **范围与边界（产品视角，含「两类特殊问题：照答但金标准不同」）** → **质量属性与验收标准**。

## 1. 产品定位

允许**以学习为目的**的用户**添加各种文档**，然后**基于这些文档以及大模型内化的知识**，提供**学习方面的知识问答能力**。

|   | 内容 |
| --- | --- |
| **做** | ① 接受用户自带的文档（多份、各种形态）；② 基于「**用户文档 ＋ 模型内置知识**」回答学习类的知识问题；③ 允许用模型内置知识补全；**不要求每条答案逐句标注来源**，但用户问起时必须能说清哪句来自文档、哪句是模型补充，且**不得把模型补充说成文档内容** |
| **不做** | ① **不做学习方向／学习规划的指导**（"先学什么、按什么顺序学"不答）；② 不做操作执行（不写代码、不改文件）；③ 不做导航／办事类（不是搜索引擎，也不是任务代理） |

**与前版的差别（这是本次的收窄）**：旧路子把"学习过程主线（初步 → 内化 → 产出）"当作**产品骨架**，并承诺覆盖多个学习环节——那等于要产品对"学习本身"有主张。新版只承诺一件事：**基于「文档 ＋ 模型内置知识」的知识问答**。学习阶段不再是骨架，只作为"用户为什么要问"的背景。

## 2. 需求分析：从产品定义推导问题空间

### 2.1 定义锁定了四个结构

| 定义里的要素 | 它锁定了什么 |
| --- | --- |
| **以学习为目的的用户** | 用户**目的恒定**（只为学）⇒ "问答目的"这一维在本产品里基本是**常量**，不构成分类依据 |
| **添加各种文档** | 语料是**用户自带的、多份的、形态各异的**——不是我们准备的固定集合 |
| **基于这些文档以及大模型内化的知识** | **两个知识来源并列**：文档内 ／ 模型内置 ／ 两者（这句话本身送出了一把现成的刀） |
| **问答能力（且不做学习指导）** | 只出答案：不执行操作、不规划学习路径 |

### 2.2 「以学习为目的」改变了什么

它**不增加"取信息"类的问题**（纯查数据的用户也会问），它改变的是问题的**层次**：

| 纯查数据的人 | 以学习为目的的人 |
| --- | --- |
| 问"有没有／是什么／在哪" | 问同样的问题，但要的是"**能理解的说法**"，不是一个孤立的数值 |
| 不会问 | **为什么／怎么做／什么关系**——要求解释与连接，而不是一个点 |
| 不会问 | **有哪些／整体是什么／有没有冲突**——要求覆盖、整合与发现分歧 |
| 不会问 | **这个说法对吗／哪个对**——要求带依据的判断 |
| 不会问 | **这句是文档说的还是你补的**——要求来源分明 |

一句话：**学习目的的作用是"从取用升级为理解、判断、成体系、辨来源"**。

### 2.3 问题空间：15 类

分组只为好读，不是分类轴。每类给 3 个示例，尽量在「单篇／跨篇、事实／机制、直接问／情境问」上拉开；示例都尽量锚在真实的 Agent 学习语料上，后面可直接当用例候选。

**示例的指代口径**：示例问句**默认指代明确**（点篇名或作者）——用户要对比、追问时，心里本来就知道是哪两篇。**模糊只留给刻意设计的消歧题。** **经验**：题面只给「一篇 OpenAI 的、一篇 Anthropic 的」而库里有多篇时，系统会选错对象（**错在对象，不在质量**）——所以模糊只应出现在刻意设计的消歧题里。同一原则也适用于锚点列里的「某一篇」：那是类型描述，不是问句。

## 3. 范围与边界（产品视角）

本节只按**产品定位**说话：这个产品承诺什么、不承诺什么。**不引入「当前实现到什么程度」**。

### 3.1 承诺范围

| 维度 | 承诺 |
| --- | --- |
| 输入 | 用户**以学习为目的**添加的**各种文档**（多份、形态不限）；它与模型内置知识共同构成"可回答的范围" |
| 输出 | **知识问答**：回答问题、给出依据；**用户问起时区分来源**；**答案里不给裁决结论，也不替用户做学习安排** |
| 知识边界 | 答案可以来自 ①用户文档 ②模型内置知识 ③两者；**来源可分辨**（用户问起时必须能说清，**不要求每条答案逐句标注**） |
| 形态 | 单轮问答（一问一答）；**多轮对话＝下个迭代计划项** |
| 使用边界 | **单用户 ＋ 单知识库**：一个用户就自己的一批文档提问；不涉及多用户协作，也不涉及多库并存与跨库检索 |
| 产品能力 | **查证入口**：用户对答案里某个说法有疑义时，可一键检索相关段落。它是质量属性 Q2（可信性）的落地方式——**它是能力，不是一种问题类型**（作为问题，它已被 §2.3 的第 3、14 类覆盖） |

**来源口径（2026-10-16 定）**：不要求每条答案逐句标注来源；**用户问起时必须能准确归属**（见 §2.3 第 14 类）；**自称来自文档的必须真能找到**（§4.2 红线）。这三句话合起来才是"来源"这一条完整的口径——"来源要分明"是能力，不是每条答案的格式要求。

### 3.2 明确不做

| 不做 | 产品理由 |
| --- | --- |
| **学习方向／学习规划的指导**（"我该先学什么、按什么顺序学"） | 那是**学习安排**，不是知识问答；本产品只对材料里的知识负责 |
| **多用户与多知识库**（账号体系、协作／分享／权限；多库并存、库间切换、跨库检索） | 产品只服务"一个人问自己的一批文档"这一场景；多用户与多库是另一层的事，不属本产品边界 |
| 操作执行（写代码、改文件）；导航与办事类（搜索引擎、任务代理） | 与"知识问答"无关 |

注：还有两件事容易被误读成"不做"，其实不是——**不替用户下结论**、**不承诺代做成品**。它们是**答案形态与金标准的边界**，问题照答，见 §3.3。

### 3.3 两类特殊问题：**照答，但金标准不同**（不是"不做"）

这两类用户**一定会问**，产品也**一定回答**。它们的特殊性不在"做不做"，而在**金标准的合格线画在哪**——不是"给出结论"，而是"把得出结论所需的材料摆清"。

| # | 类型 | 照答什么 | 金标准与其它类的差别 |
| --- | --- | --- | --- |
| **11** | 哪个对（两边冲突时该听谁的） | 两方**各自怎么说** ＋ 各自的**依据**（＝ 9 指出分歧 ＋ 10 各自主张） | **不判「选了哪边」**；判「分歧是否被正确指出、双方依据是否准确」。产品不把裁决写进答案，也不把「选边选得对」当作通过条件 |
| **15** | 换个形态（整理成表格／清单／checklist） | 内容本身（按 1–14 类的方式正确给出） | 判**内容的重述是否忠实、完整、正确**；**不判工件形态**（排版、清单完备度等留待后续迭代） |

一句话：**这两类问题照答，差别只在合格线画在哪**——其它类画在"答案对不对"，这两类画在"材料摆得全不全、准不准"。

**另有两处边界的口径（保持现状）**：<br> · **10「对吗」留在范围内**：它问的是「**按某篇的观点**这个说法成立吗」，答案可引原文，属**知识核对**，不是替用户裁决。<br> · **7「有哪些」与 15「换形态」的区分成立**：**7 的清单是答案的自然形态**（用户问的就是"有哪些"），**15 才是把已知内容按用户指定格式重排成工件**——前者的内容与完整性在本迭代的验收范围内，后者的"工件形态"不在。

## 4. 质量属性与验收标准（产品视角）

本节只回答三件事：**要满足哪些质量**、**每条是红线还是可度量**、**红线具体是什么**。<br> 具体**指标与阈值**取决于"每个用例考什么、考到什么程度"，属**用例与金标准设计**，不写在本文；<br> 而**判定规则**（把多次测量结果折成"通过／不通过"）**写在本文 §4.3**。

### 4.1 质量属性

| # | 质量属性 | 用户视角的含义 | 性质 |
| --- | --- | --- | --- |
| Q1 | **正确性** | 讲的东西是**对的**（与材料／事实一致） | 可度量（覆盖性）＋ **见下注** |
| Q2 | **可信性（可核对）** | 关键说法**能回查到出处**（用户问起时能定位；自称来自文档的必须真能找到） | 能力（查证入口）＋ 红线（见 4.2） |
| Q3 | **完整性（覆盖）** | 该说的**说到**；说不全**要讲清漏了什么** | 可度量 ＋ **红线**（遗漏透明） |
| Q4 | **诚实性（不编造）** | 不知道就说不知道；**不把模型补充说成文档内容** | 红线（见 4.2） |
| Q5 | **一致性（稳定）** | 同一个问题问几次，答案不该**翻来覆去** | 可度量 |
| Q6 | **表达合适** | 讲得**清楚**，形态贴合问法（问定义给定义、问对比给对照、问清单给清单） | 可度量 |
| Q7 | **边界合规** | 越界请求**按任务类型**处理（不是一律拒答，也不是有求必应） | 红线（见 4.2） |
| Q8 | **响应速度** | 等太久就不好用 | 可度量（目标值未定） |

**Q1 的两半（重要边界）**：<br> · **覆盖性**（该有的都有）——**能逐点核对**：要点清单是有界的；<br> · **排除性**（不该有的不能有）——**只能按「已知错误类型清单」验，不追求全**。理由：错误空间是开放的（任何没被材料支持的内容被说出来都算错）， 「**排除了所有错误**」这件事**本身无法验证**——这是本质限制，不是工具问题。<br> 可行的形态：把高风险错误写成**显式的事实边界断言**（用例里的 `boundary_claims`，例如「某文未以某命名其主张」），逐条核对； **错误类型清单从真实失败样本回填**（如「概念嫁接」那一类：两个来源各自都真，错在把两者说成同一机制——**逐点核验抓不到它**）。<br> ⇒ 因此产品承诺必须**明说「未知类型会漏」**，不得暗示「内容一定正确」。

### 4.2 红线（必须满足；违反即不合格）

1. **引用无伪证**：凡给出引用承诺，来源必须真实存在、归属正确、内容与原文吻合。
2. **来源可溯源**：凡自称来自文档的说法，必须真能从文档找到——**不得冒充**（这一条同时管住"编造"）。
3. **遗漏透明**：面对"要全"的问题（§2.3 的第 7、13 类），若没列全，**必须具名说清漏了哪一类**。
4. **边界合规**：越界请求按任务类型处理。

### 4.3 判定规则 （已定）

**为什么需要它**：这个系统的回答是**概率性**的——同一个问题问两次，答案可能不一样。所以**任何单次结果都不能当结论**，必须先把"多次结果"折成一个判断。

**规则分两层**：

1. **单用例判定**：同一用例跑 **N** 次，其中 **≥ K 次满足该用例的金标准** ⇒ 该用例**判定通过**。<br> "满足金标准"＝该用例的**必选全满足**、**边界零违反**（边界含通用边界，即 §4.2 的四条红线）。
2. **用例集准出**：整套用例集需**同时**满足三条——<br> ① **红线类用例必须全过**（标为必须通过的，一条都不能不过）；<br> ② **每一类问题都要有代表用例达标**（不能靠整体平均掩盖某一类崩塌）；<br> ③ **整体通过率达到目标**（目标按类分别定，不设一条笼统的总分线）。

**三条原则（为什么这样定）**：

- **不看单次**：单次结果只作观测，不作结论；
- **分类看，不看总分**：平均分最容易掩盖的正是"某一类全崩"；
- **红线不可平均**：红线是"零违反"，不能折算成"违反率 5% 也算过"。

**同时要报抖动**：除了"通过／不通过"，还要报同一配置多次之间的**结果波动**——波动本身就是 Q5（一致性）的读数，也决定了 N 要取多大才可信。

**待定数值**：N（跑几次）、K（几次算过）、各类目标值——都由**用例与金标准设计**给定（每个用例考什么，决定它跑几次、几次算过）。本节定的是**规则的形状**。

连带提醒：引用一旦不强制溯源（见 4.1 Q2 与 4.2 的措辞），"说错了但没引"就完全压在 Q1（正确性）上；而 Q1 的**排除性那一半本就验不全**（见 §4.1 注）——所以引用不能当作"内容正确性"的兜底。
