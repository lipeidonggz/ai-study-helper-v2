## 0. 文档定位与当前结论

### 0.1 文档范围

本文定义当前 v1.0 主路径：在单一知识库、单一领域的产品边界内，从知识库 snapshot 与领域边界出发，经用户选择角色、生成任务与知识框架、离线挂接原文证据，到查询期覆盖检查和回答接入的完整设计。

本文是设计契约和当前验证基线，不是逐轮探索日志。形成当前基线的复现指标、关键失败语义和最终取舍写入正文；逐轮提示词对照、已经排除的中间方案和探索细节保留在实验文档与 [v0 探索草稿](../development/experiments/2026-11-27-role-knowledge-design-v0-draft.md)。

### 0.2 一句话设计

```text
知识库 snapshot + 领域边界
→ LLM 生成并归并角色候选
→ 用户选择角色（唯一必需的人工前置动作）
→ 自动生成主要任务、任务树和角色知识框架
→ 对冻结叶节点执行全量 block × leaf 证据挂接
→ 查询期按全部一级子树选择叶节点并物化候选原文
→ 主 Agent 基于候选原文作答
```

在当前固定 15 篇快照上，这条链路已经完成一次端到端运行，证明可以形成可追溯的框架、证据账本、查询覆盖状态和原文引用。它尚不是产品规模承诺：默认上下文成本、问题感知证据选择和跨领域泛化仍未解决。质量基线见 §6.7、§9.5，限制见 §14.1。

### 0.3 系统输入与派生对象

本产品的知识编译输入不是角色，而是当前知识库 snapshot 和领域边界。对于当前“单用户、单知识库、单一领域”的范围，一个知识库通常对应一个明确领域；如果知识库跨越多个领域，应先拆分领域范围，不能用一个笼统领域强行生成统一知识框架。

| 对象 | 性质 | 来源与约束 |
| --- | --- | --- |
| 知识库 snapshot | 外部事实底座 | 入库产生；框架、账本、候选和查询都必须绑定具体 snapshot |
| 领域边界／领域卡 | 编译范围输入 | 可由用户提供，也可由系统根据知识库元数据和内容推断；推断只用于确定领域边界，不得反向生成知识目录 |
| 角色候选 | 视角候选 | 由 LLM 根据领域生成，可多轮生成并归并 |
| 已选角色 | 本次编译使用的观察视角 | 由用户选择；这是本产品唯一必须由人完成的编译前置选择 |
| 主要任务与任务树 | 角色履职覆盖审查工具 | 由已选角色自动生成并通过结构校验；人工复核可选 |
| 知识框架 | 当前领域和角色下的应知知识面 | 自动生成、归并、覆盖审查和叶节点审计；人工复核可选 |
| 证据账本 | 原文证据与叶节点的支持关系 | 由当前 snapshot 和冻结框架挂接产生 |

人工边界需要区分两个层次：选择角色是具体知识库编译流程中的必要输入；主要任务、任务树、知识框架和叶节点展开均可自动生成并通过自动门禁，对具体生成内容的人工复核不是每次运行的必需步骤。项目级系统提示词、金标准、工具行为契约等基础件仍按项目规则接受人工确认，这两类“人工确认”不能混为一谈。

## 1. 问题、立论与目标

### 1.1 问题不只是“检索到相关内容”

普通事实问答主要优化“候选内容与问题是否相关”。本设计面对开放式、多方面的求全类问题：回答必须覆盖多个不一定共享关键词的知识方面，并且每个方面能够回到当前知识库中的原文 block。

因此，一个候选方法至少要回答三个问题：

1. **知识面在哪里？** 系统是否有一张独立于当前查询措辞的知识范围，用来判断还有哪些方面应当检查；
2. **证据面在哪里？** 某个知识方面是否已经有当前 snapshot 中的连续原文作为直接证据；
3. **什么时候可以停止？** 停止条件是否来自可枚举、可复核的覆盖状态，而不是模型认为“应该差不多了”。

仅提高 Top-k 召回率、增加关系图、生成主题摘要或扩大上下文窗口，通常只能改善其中一部分，不能自动形成这三层闭合。

### 1.2 前提一：没有有效组织边界，无法证明“已经找全”

“找全”不是一堆文档自身固有的属性，而是当前问题、知识组织范围、证据关系和执行状态共同定义的结论。原始文档即使具有章节、段落和 block 结构，也只提供文本容器，不等于提供了一张面向当前任务、有限且可枚举的知识面。

问答 Agent 直接面对文档集合时，可以完成局部检索、阅读候选和继续补充查询，但它没有一张独立于临时检索结果的清单来判断“应当检查的方面一共有哪些”。因此它无法区分：

- 已经找到全部必要证据；
- 只是当前查询词碰巧命中了这些证据；
- 某些方面因为术语不同、路径较远或查询尚未想到而根本未被搜索；
- 模型因为上下文、时间或自我置信度而提前停止。

即使把全部文档放入足够大的上下文，系统仍可能组织出一份看似合理的回答，却没有外部知识面证明它覆盖了用户真正需要的全部方面。准确表述不是“Agent 绝对找不到有用答案”，而是：**没有明确知识面和覆盖判定单位时，系统无法证明、也无法审计自己已经找全。** 这是可判定性和可问责性问题，不只是 Top-k 或上下文预算问题。

要恢复可判定性，必须把“找全”转化为有限检查：当前视角下有哪些知识节点、每个节点是否有当前 snapshot 的原文证据、本次问题需要检查哪些节点、全部必要查询分支是否执行完成。

### 1.3 前提二：知识组织必然依赖观察视角

同一批文档可以从不同使用目的、职责、问题、粒度和知识本体出发形成多种自洽组织，不存在脱离使用目的的唯一自然目录。同一个实体或术语在不同视角下可能进入不同上位范畴、承担不同职责、连接不同关系，并具有不同边界；同一个原文关系也可能在一种视角下只是属性，在另一种视角下需要实体化为独立知识对象。

需要区分两个层次：

- **原文证据层相对稳定。** 当前 snapshot 中的 block、连续 quote、来源和可定位性不随查询视角改变；
- **知识组织层必然视角相关。** 哪些对象组织在一起、哪些关系需要显式化、粒度到哪里、什么算完整，都取决于系统试图支持谁完成什么任务。

因此，“先做一份通用知识地图，再让所有问题共用”并不能自动解决歧义。一个没有声明视角的目录会把多个视角强行压成一套路径，隐藏概念冲突、职责差异和证据边界。

当前产品选择“角色与履职任务”作为视角锚点：角色候选由系统生成，用户必须选择本次编译使用的角色，选择记录进入框架 revision。未来产品可以采用任务、监管职责或问题类型等其他视角，但不能因此弱化当前产品中角色选择的必要性。

| --- | --- | --- | --- |

这些路线并非无效。它们分别适合相似度召回、关系导航、二次归纳、动态查询和局部证据阅读，本设计也继续使用 dense／BM25、模型结构化判断、主题导航和 Agent 工具循环。真正的区别是：它们没有把“角色履职需要哪些知识、每个知识叶节点是否有原文证据、全部查询分支是否执行完成”定义为首要产品契约。

### 1.5 项目探索收敛出的判断

前期探索逐项排除了若干看似可行、但无法证明找全的路径：

1. **仅扩大主题和关系目录仍不够。** 阶段 5.1 关系抽取、14 号双入口和 15 号双分面模型证明了关系入口的价值，也暴露出固定分类的身份、边界和覆盖义务难以仅从当前语料稳定推导。
2. **任务树不能直接改写成知识树。** 直接生成主题森林会把任务动作、交付物和验证步骤写成知识节点；结构合法也不代表跨任务覆盖完整。
3. **LLM Wiki 解决了导航和回源，没有解决页面目录完备性。** 页面来源仍需预先选择，完整 Topic 目录进入上下文后，模型也不一定形成覆盖决策。
4. **Agentic RAG 的反思不能替代覆盖账本。** 强模型能找到不少主要证据，但“还缺不缺”仍依赖它临时想到哪些同义机制和相邻方面，且未执行分支不会留下可审计记录。
5. **找全必须同时绑定知识面和原文证据。** 只定义框架会得到“应该回答什么”，却没有可信证据；只做 block 级相似检索会得到“可能相关什么”，却无法证明知识方面已经完整。

本设计不声称 GraphRAG、LLM Wiki 或 Agentic RAG 在一般场景中无法工作，也不声称角色知识框架能够自动发现现实世界中的全部知识。它只针对当前产品目标作更强承诺：在声明领域、已选角色、冻结框架和完整挂接账本范围内，系统能够解释选了什么叶节点、对应哪些原文 block、哪些查询分支失败，以及哪些核心证据仍未覆盖。

### 1.6 两条直接结论：预先编译，按视角编译

1. **必须预先编译知识。** 查询前建立版本化知识框架和 `block × leaf` 证据关系，把模糊的“去文档里找全”转化为有限知识面上的覆盖检查；编译产物不是文档摘要，而是可枚举、可回溯、可验证的组织与证据结构。
2. **必须按视角编译知识。** 不构建声称对所有问题都通用的单一知识真相，而是在明确领域、角色和任务下生成框架并建立证据关系。相同 snapshot 可以拥有多个视角的编译结果，它们共享原文事实底座，但各自保留独立的知识身份、边界、版本和覆盖记录。

### 1.7 指导思路：先定义应知，再证明已知，最后闭合覆盖

> 先从角色履职任务定义“应该知道什么”，再以当前知识库原文证明“实际知道什么”，最后按冻结框架和完整执行状态判断一次回答“已经覆盖什么、仍然缺什么”。

**“应知”是规范性知识面。** 角色、主要任务和任务树回答一个承担该职责的人或 Agent 应当理解和处理哪些领域知识。任务树只用于审查履职覆盖，不直接复制成知识节点；知识框架也不读取当前语料主题、聚类或测试问题来反推边界。叶节点存在只表示该方面值得检查，不表示知识库中一定有材料。

**“已知”是当前 snapshot 的证据事实。** 模型生成的框架只是待验证假设；叶节点是否被当前知识库覆盖，必须由连续原文 block 直接证明。挂接阶段保存可定位 quote、支持类型和关系账本，主题页、图边和模型理由可以辅助导航，但不能替代原文成为事实源。

**“覆盖”约束本次查询能承诺什么。** 查询期沿冻结框架选择相关叶节点、检查全部一级分支、从封存账本物化候选原文，并显式保留失败、非法输出、截断和预算不足。`coverage_status=complete` 只表示工具侧覆盖检查无技术错误地执行完成，不表示框架完备、答案真实或现实领域完整；最终回答完整性和失败状态仍需单独判定。

| 缺失的层 | 系统会退化成的形态 | 核心后果 |
| --- | --- | --- |
| 缺少“应知” | 从语料主题、图社区或相似度聚类反推知识结构 | 只能发现材料里已经显露的知识，无法系统指出应存在但材料缺失的方面 |
| 缺少“已知” | 把模型生成的知识框架或摘要直接当作知识库事实 | 结构可能完整，但结论不可回源，无法区分原文事实与模型补全 |
| 缺少“覆盖” | 依赖 Agent 多轮检索和自我反思决定何时停止 | 召回可能不错，但无法说明每个一级分支是否执行、哪些必要叶节点未检查 |
| 三层同时成立 | 框架定义知识面，证据账本证明已有知识，覆盖记录约束本次承诺 | 能解释“应该找什么、实际有什么、这次检查了什么”，形成可复现、可回查、可报告缺口的求全闭环 |

后续任何结构、提示词、检索或评测改动，都应先回答：它改善的是知识面定义、原文证据接地还是查询覆盖闭环；是否把模型生成内容错误提升为事实；是否用固定 Top-k、静默截断或自评“差不多”掩盖未检查范围；`complete` 是否仍绑定明确的 snapshot、框架、账本、查询分支和执行状态。

### 1.8 三层如何落到系统对象

| 层次 | 回答的问题 | 默认单位 |
| --- | --- | --- |
| 领域边界 | 这个知识库属于什么领域 | 领域卡、collection snapshot |
| 角色与任务 | 从哪个职责视角组织知识、完成什么工作 | 已选角色、主要任务、任务树 |
| 知识框架 | 该角色应掌握哪些领域知识 | 知识节点、叶节点 |
| 证据挂接 | 哪些原文能支持哪个叶节点 | `block × leaf` 关系 |
| 查询覆盖 | 回答当前问题需要检查哪些叶节点 | 叶节点选择结果 |
| 回答综合 | 哪些候选原文构成最终回答证据包 | 原文 block |

领域和已选角色共同决定知识视角；任务和知识框架决定“去哪里找”；挂接账本决定“每个叶节点下能取到哪些原文”；查询期选叶决定“本次要检查哪些范围”；最终回答仍必须基于原文 block 综合和引用。

### 1.9 目标、非目标与“找全”的定义

本文中的“找全”限定为：在当前冻结知识库快照、已选角色、冻结框架和声明资料范围内，尽可能找出所有可用于回答当前问题的核心原文证据，并明确报告无法确认的缺口。

它不是：

- 证明现实世界中的领域知识已经完整；
- 要求返回知识库中所有共享关键词的相关文本；
- 要求每一个背景块或章节导览块都进入回答；
- 仅凭全部一级分支调用成功就宣称答案完整。

完整声明若要在产品层成立，还需要同时考虑叶节点选择、证据挂接、候选物化、知识框架反馈闭环和回答覆盖。当前 v1.0 的 `coverage_status` 只覆盖冻结框架内的分支执行；回答流程的回退和输出状态也必须在回答层独立记录。知识框架缺口的反馈来源和未完成设计见 §5.8，不能用工具侧 `complete` 替代最终回答质量判断。
## 2. 设计原则与不变量

### 2.1 设计原则

以下原则是把“先定义应知，再证明已知，最后闭合覆盖”转化为工程设计时必须保持的约束，而不是另一套并列目标：

1. **高召回优先，但不用噪声冒充覆盖。** 漏掉核心方面通常比多返回少量可筛选候选更严重；候选多不等于答案完整，必须继续做证据选择。
2. **框架内容与当前语料解耦。** 领域边界确定后，角色候选、任务和知识框架生成不读取当前知识库、测试问题、答案或金标准，避免具体语料反向定义“应该知道什么”。领域边界自身的识别可以使用知识库元数据和内容，但不得把文档中的主题直接当作知识框架。
3. **框架、挂接和查询分层。** 知识节点表示知识身份，挂接表示原文支持关系，查询选择表示本次任务需要，三者不得互相替代。
4. **结构由宿主确定，语义由模型判断。** 模型负责角色、知识、支持关系和叶节点选择；宿主负责 ID、版本、结构校验、去重、预算、状态和持久化。
5. **失败不得伪装为空结果。** 调用失败、输出非法或截断必须进入显式失败状态，不能等同于“没有相关叶节点”或“没有证据”。
6. **不针对单个问题写个案规则。** 提示词、知识树和挂接修正必须由系统性语义根因驱动，并通过固定样本、跨样本和产品等价回放验证。
7. **数量不是质量目标。** 一级节点数、叶节点数、任务数、每叶证据数和固定 Top-k 都不是覆盖质量本身；数量只由知识身份、任务和边际证据决定。

### 2.2 核心不变量

| 编号 | 不变量 |
| --- | --- |
| I1 | 查询时只能读取与当前 collection snapshot、框架 revision、框架 hash 和挂接 manifest 相互绑定的 `sealed_complete` 账本。 |
| I2 | 原文证据只挂接叶节点；父节点覆盖由后代叶节点汇总，不在祖先链重复存储同一证据。 |
| I3 | 一个 block 可以支持多个叶节点，一个叶节点可以拥有多个 block；不得为了唯一性只保留“最相关”关系。 |
| I4 | `coverage_status=complete` 只表示所有一级子树调用成功、输出合法且未截断，不表示答案在现实世界中绝对完整。 |
| I5 | 任一级子树失败、非法输出或截断必须使整体为 `partial`；成功返回空叶节点集合可以作为合法分支结果。 |
| I6 | 主 Agent 只接收候选原文 block 和覆盖状态；叶节点、支持类型、内部理由和内部相似度不得暴露为回答可直接引用的证据。 |
| I7 | 所有模型调用、重试、token、缓存命中和失败原因必须进入 trace 与预算。 |

## 3. 术语与系统模型

### 3.1 核心对象

| 术语 | 定义 |
| --- | --- |
| 领域卡 | 领域名称、说明和边界的版本化描述；是角色生成和知识框架生成的领域范围输入。 |
| 角色候选 | 系统根据领域生成的候选角色卡，包含名称、区分性任务和已有知识；用户必须从中选择当前使用的视角。 |

| 主要任务 | 角色必须交付或维持的完整职责结果。 |
| 任务树 | 把单项主要任务拆成可独立完成、可检查结果的工作树；只用于覆盖审查，不直接变知识节点。 |
| 角色知识框架 | 特定领域和角色下，由一级、中间和叶节点构成的知识范围树。 |

| 原文 block | collection snapshot 中带文档、章节和稳定 ID 的连续原文单位。 |
| 支持关系 | 一个 block 中至少一条可定位原文直接支持一个叶节点知识身份的版本化关系。 |
| 挂接账本 | block 与叶节点支持关系、block/leaf 覆盖和冲突的不可变事实源。 |
| 候选 block | 查询期由选中叶节点反向取得的原文候选，不自动等于最终回答证据。 |
| 查询覆盖记录 | 本次查询的全部一级子树调用、选叶、块物化、失败和预算信息。 |

### 3.2 逻辑关系

```text
Domain
  └── Role
       ├── PrimaryTask[] → TaskTree[]
       └── KnowledgeFramework
             └── KnowledgeNode[]
                   └── Leaf[]
                         └── BlockLeafSupport[] ── Block

Query
  → select leaves per root subtree
  → selected leaves
  → BlockLeafSupport
  → candidate blocks
  → answer evidence package
  → answer
```

### 3.3 版本绑定

一次可复现的知识库查询至少需要绑定：

- `snapshot_id` 与 collection manifest hash；
- `framework_revision_id` 与框架文件 hash；
- `attachment_run_id`、manifest hash 和账本文件 hash；
- 生成、挂接、叶节点选择和回答提示词版本及 hash；
- 模型 ID、温度、thinking、输出上限、并发和重试策略；
- 原始模型输出、校验结果和 usage。

任何知识节点、叶节点目录、提示词或模型语义变化都形成新版本，不静默覆盖旧结果。

### 3.4 当前提示词与调用配置基线

## 4. 数据契约

### 4.1 知识节点

```json
{
  "node_id": "K08.05.04",
  "title": "工具执行运行时隔离与中断恢复",
  "description": "该范围覆盖……",
  "exclusions": ["不属于当前范围的相邻知识"],
  "children": []
}
```

- `node_id` 由宿主分配，模型不得自行改写最终路径编号。
- `title` 脱离父路径后仍应能识别知识范围。
- `description` 直接说明知识内容和边界，不写学习动作、项目步骤或交付物。
- `exclusions` 只记录容易混淆且属于相邻节点的知识；没有明确边界时可以为空。
- `children=[]` 的节点是叶节点。固定深度和固定叶节点数不是设计目标。

### 4.2 单叶支持关系

```json
{
  "block_id": "doc_...#v0001#c1#b00006",
  "leaf_id": "K08.05.04",
  "evidence": [
    {
      "quote": "block.text 中的连续逐字原文",
      "support_types": ["mechanism"],
      "target": "从叶节点范围中识别出的支持目标",
      "reason": "该原文如何直接支持 target"
    }
  ]
}
```

运行时支持状态由 `evidence` 是否为空确定性派生：

- 非空且通过结构、ID、叶节点归属和原文连续性校验：支持；
- 空数组：不支持；
- 调用失败、JSON 非法、截断或无法定位 quote：失败，不得降格成“不支持”。

`support_types` 只允许：`definition`、`structure`、`capability`、`mechanism`、`condition`、`method`、`instance`、`effect`、`evaluation`。它说明证据以什么形态支持叶节点，不要求穷尽 block 内所有方面。

离线人工评价另使用 `no_support`、`weak_support`、`direct_support` 三档。`weak_support` 只用于金标准与稳定性分析，不是运行时新增的支持等级。

### 4.3 挂接账本

挂接账本至少包含：

- `supports.jsonl`：每条支持关系及 evidence；
- `block-coverage.jsonl`：每个 block 的初筛 root、候选叶节点数、支持叶节点数和完整性；
- `leaf-coverage.jsonl`：每个叶节点的候选和支持状态；
- `conflicts.jsonl`：非法 ID、quote 不可定位、不可恢复失败和重复关系；
- `manifest.json`：版本绑定、计数、文件 hash、状态和运行配置。

manifest 状态：

| 状态 | 含义 |
| --- | --- |
| `building` | 运行中，可续跑；不可作为活动账本。 |
| `sealed_complete` | 计划范围全部完成且完整性校验通过；可原子发布活动指针。 |
| `partial` | 范围未完成或存在未解决失败；不得宣称完整覆盖。 |
| `failed` | 完整性校验失败；保留诊断，不更新活动指针。 |

### 4.4 查询工具输出

`search_coverage_blocks` 对主 Agent 返回：

```json
{
  "blocks": [
    {
      "block_id": "稳定 ID",
      "doc_id": "文档 ID",
      "doc_title": "文档标题",
      "section_path": ["章节路径"],
      "source_label": "来源标签",
      "text": "完整原文"
    }
  ],
  "coverage_status": "complete"
}
```

公共输出不包含知识树、叶节点 ID、support type、内部相似度或挂接理由。分支选择细节只进入 trace。
## 5. 角色知识框架生成

### 5.1 生成链路

```text
知识库 snapshot + 领域边界
→ LLM 多轮生成并归并角色候选
→ 用户选择角色视角（必需）
→ 自动生成并归并主要任务
→ [可选] 人工复核主要任务
→ 每个主要任务独立生成任务树
→ 多轮生成一级知识框架候选
→ 按知识身份归并
→ 使用完整任务树审查覆盖
→ LLM 依据结构化缺口修复并复审
→ 冻结一级目录
→ 逐一级分支独立展开
→ 全量叶节点颗粒度审计
→ [可选] 人工复核知识框架
→ 冻结角色知识框架 revision
```

生成阶段按“先全局一级目录、后逐分支展开”执行。一次模型调用不同时承担全局覆盖、多级组织、叶节点粒度和最终证据判断。

### 5.2 角色

系统根据知识库的领域边界多轮独立生成角色候选，每个角色至少包含名称、区分性任务、已有知识和区别理由。候选按履职对象、核心问题和问题边界归并，允许合并、拆分和显式 `needs_review`。

角色候选可以自动归并，用户必须选择本次编译使用的角色视角；未选择角色时不得生成并发布该视角下的知识框架。用户可以在选择前合并、拆分和调整候选，但这些操作属于可选的候选整理，不是自动运行的必要人工步骤。每个已选角色独立生成后续任务和知识框架；角色变化不得静默复用旧框架。

### 5.3 主要任务与任务树

主要任务是角色必须交付或维持的职责结果，必须包含：

- 任务名称；
- 可检查的完成状态；
- 属于任务的主要结果与责任；
- 容易误并入的相邻职责；
- 无法判断的职责边界问题。

主要任务候选按职责结果归并，并允许单例保留。任务生成和结构校验可以自动完成，人工复核是可选的；未人工复核时，系统按自动校验结果继续生成任务树，并在 revision 中明确记录 `auto_validated` 状态。每项主要任务独立生成任务树，避免多个根任务在同一调用中竞争输出预算。

拆分单位是可独立完成并检查结果的实际工作。共享同一文档、矩阵、Schema 或交付物不构成停止拆分理由；固定深度、固定叶节点数和树形美观不是质量目标。

任务树只作为知识框架履职覆盖审查的锚点，不直接被复制成知识主题。

### 5.4 一级知识框架

一级框架候选只使用规范领域名称和角色名称生成，不读取当前语料、测试问题、金标准或外部资料。领域说明不进入一级候选生成，以免摘要限定知识的发现边界。

一级候选的结构由宿主校验：

- 只输出一级知识范围；
- 节点标题脱离父路径仍可识别；
- `description` 明确知识内容，不写任务步骤；
- `exclusions` 可空，但不得与当前范围同义；
- 模型不得生成永久节点 ID。

多轮候选按知识身份归并。两个节点只有同时满足“核心研究对象基本一致、核心问题基本一致、主要知识边界基本一致”才可合并。每个来源必须有明确去向：`equivalent`、`contained`、`split` 或 `needs_review`。

### 5.5 任务覆盖审查与修复

归并后的框架使用完整任务树审查每项任务完成所需的知识是否已经被节点明确承载。审查输出为 `covered`、`partial` 或 `missing`，并给出匹配路径和缺口。

存在缺口时，LLM 在完整框架上执行结构化修复；宿主校验结构、节点 ID 和来源账本。修复后重新审查全部任务，不只复查原缺口。迭代终止条件必须显式记录：

- 全部任务 `covered`；
- 进展停滞；
- 调用或结构失败；
- 达到异常保护迭代上限。

“为了通过覆盖而增加宽泛节点”“把任务动作写成知识节点”和“灾难性节点膨胀”均属于质量失败。

### 5.6 逐一级分支展开

一级目录冻结后，每个一级节点独立展开。单次调用只能展开目标一级节点，根节点字段原样保留，不得侵入其他一级分支。

节点表示知识范围，不表示任务、项目、交付物、产品方案或实现步骤。一个范围仍包含多个可分别命名、分别检索和分别判断证据覆盖的知识身份时，应继续生成子节点。

叶节点不以固定深度定义。一个范围如果能脱离父路径作为独立检索目标，就应形成叶节点；如果只能作为同一知识身份的属性、定义、作用或边界出现，就留在该节点描述中。系统不保留独立 `aspects` 层。

展开后必须执行全量叶节点颗粒度审计。`split` 必须返回完整替换子树，不能只给建议标题；失败或 `uncertain` 必须显式保留，不得默认通过。审计、修复和结构校验属于自动运行门禁；人工复核可以补充质量和边界判断，但不是每次编译的前置条件。

### 5.7 冻结

冻结 revision 至少绑定：

- 知识库 snapshot、领域卡、角色候选来源、已选角色及用户选择记录；
- 主要任务和任务树版本；
- 自动校验状态，以及可选的人工复核记录和复核者；
- 一级生成、归并、覆盖审查、修复和展开提示词；
- 节点 ID、路径、标题、描述和排除边界；
- 模型与 thinking 配置；
- 原始输出、任务覆盖审查和叶节点审计记录。

当前验证 revision 为 `kf_c1b79b163bfcb2a93844`，包含 24 个一级分支、620 个叶节点和 847 个总节点，最大深度 3。这些数字是当前回放结果，不是生成目标或永久产品常量。

### 5.8 框架缺口反馈与离线完善（当前未实现）

已冻结框架不能由挂接结果或单次查询直接改写。系统需要一个独立的“框架缺口反馈”阶段，用来收集当前组织和当前 snapshot 之间可能存在的错配，再决定是否形成新的知识框架 revision。当前已明确两个候选触发来源，但完整流程尚未设计完成：

1. **挂接侧未挂接 block 聚集。** 全量挂接完成后，如果较多 block 无法支持任何叶节点，不能直接认定它们都没有价值，也不能直接据此新增叶节点。可以由 LLM 辅助判断这些 block 是否只是背景内容、是否属于领域排除范围、是否其实支持已有叶节点但发生挂接错误，或是否形成了当前框架无法承载的有价值知识；候选结果再交由人工判断。
2. **查询侧全局问题低召回。** 开放式或全局类问题如果只选中少量叶节点、只能物化很少候选原文，或回答阶段明确识别出大量未覆盖方面，也进入同一反馈路径。该现象可能来自框架缺项、叶节点选择错误或知识库本来就没有对应证据，必须分类而不能一律解释为框架缺失。

“较多”和“很少”目前没有确定阈值，不应先写死数量。阈值需要结合未挂接率、候选聚集、问题宽度、叶节点覆盖、证据可得性和跨样本稳定性另行校准。

每条框架缺口反馈至少应绑定 snapshot、框架 revision、挂接运行或 query、候选 block／问题方面、触发信号和证据。LLM 可以辅助把候选归为“无价值或领域外”“已有叶节点但挂接遗漏”“已有叶节点但查询选择遗漏”“当前框架缺少承载范围或边界错误”或“仍不确定”，但最终是否改建框架必须经过人工判断；在自动审核策略尚未验证前，系统只能保留待审反馈，不能自动发布框架修订。

经人工判断，或未来经独立验证的自动审核，可以产生的动作包括：不修改、修复挂接、修正查询选叶、对已有节点移动／拆分／合并、新增叶节点或标记 `needs_review`。任何知识结构变化都创建新的框架 revision，并按 §11.3 重新计算受影响的挂接关系；旧 revision 和旧账本保持可追溯，不在活动中静默修改。

普通知识库编译仍然只需要用户选择角色；本节是异常触发的可选维护流程，不是每次编译都必须人工审核。查询暴露的问题、答案和金标准也不得直接反向写进当前框架，只能形成带来源的离线反馈。

## 6. 离线知识库证据挂接

### 6.1 挂接目标

挂接阶段回答一个存在问题：当前 block 中是否存在至少一条连续原文，仅凭当前 block 就能直接支持当前叶节点的知识身份。

它不是要求：

- 为 block 做完整语义标注；
- 枚举 block 内所有相关叶节点或所有证据方面；
- 要求一个情况或实例覆盖叶节点的全部变体；
- 为父节点重复保存同一证据。

### 6.2 一级树初筛

对每个 block，先使用当前框架的一级、二级、三级标题骨架排除整棵明确无关的一级树。初筛只缩小最终判定范围，不形成支持关系。

失败语义：

| 情况 | 处理 |
| --- | --- |
| 初筛调用失败、超时、非法输出或覆盖不完整 | 保守回退全部一级树，记录原因 |
| 初筛合法完成后返回完整空集合 | 接受为当前 block 无候选叶节点 |
| 任一下游逐叶调用失败 | 该 block 不能封存为 `sealed_complete` |

### 6.3 单叶最终判定

初筛保留的每个 `block × leaf` 单独调用模型。输入包含：

- `block.section_path` 和 `block.text`；
- `leaf.path`、`leaf.title`、`leaf.description`、`leaf.exclusions`；
- 固定的支持类型定义和 JSON 输出契约。

模型在 `evidence` 数组中返回 quote、支持类型、target 和理由。只要一条合规证据成立，就判为支持；叶节点整体是否覆盖充分由多个 block 汇总判断。

支持关系必须满足：

- quote 是 block.text 的连续原文；
- quote 不借助 block 外知识补造对象、机制、因果或关系；
- target 保留路径和标题规定的知识身份及关系限定；
- quote 直接陈述该关系，不能只提供该关系可使用的对象、能力、背景或相邻现象；
- quote 的核心对象、关系或职责不落入叶节点 `exclusions`；
- 模型输出的 leaf ID 必须属于本次输入。

### 6.4 支持类型

| 类型 | 允许证据说明的内容 |
| --- | --- |
| `definition` | target 的规范定义 |
| `structure` | target 内部组成、角色、层级和组成关系 |
| `capability` | target 能执行的动作、提供的功能或允许/拒绝/限制规则 |
| `mechanism` | target 借助什么过程、因果链或工作原理产生功能或变化 |
| `condition` | target 之外必须先成立的事实 |
| `method` | 建立、操作、使用或处理 target 的方法、步骤、策略或流程 |
| `instance` | target 的具体样例、案例、实现、产品或场景 |
| `effect` | target 产生、导致、避免或改变的结果、影响 |
| `evaluation` | 评价 target 的指标、判据、标准、权衡或优缺点结论 |

支持类型帮助审核 quote 与 target 的关系是否自洽，不表示必须对 block 做穷尽分类。

### 6.5 校验与修复

宿主对每个候选关系执行确定性校验：

- JSON 结构、必需字段和类型；
- 叶节点 ID 存在且属于当前 block 候选树；
- 同一 `framework_revision_id + block_id + leaf_id` 不重复；
- quote 可映射回原文连续子串；
- evidence 为空与调用失败的语义区分。

当前 15 篇运行中共 13,446 条 quote 精确连续匹配，9 条经排版归一化后定位，不可定位为 0。修复只能来自已保存的原始模型输出，不得改写语义。

### 6.6 账本封存与发布

运行时必须支持中断续跑。staging 结果按条 flush；计划中的全部 `block × leaf` 完成后执行完整性校验。只有失败数为 0、覆盖记录齐全和文件 hash 一致时才写 `sealed_complete`，并原子更新活动指针。

新运行失败不能使旧活动账本失效。`partial` 或 `failed` 结果可以用于诊断，但不能对查询宣称完整覆盖。

运行时索引是账本的派生产物，至少提供 `block_id → leaf_ids` 和 `leaf_id → block_ids`。删除索引后必须能够从不可变账本重建。正式 SQLite schema 不在本版本冻结。

### 6.7 当前挂接基线

固定快照 `s_6b787258ba7d700c` 的挂接运行 `att_20261126T144721347314Z`：

| 指标 | 结果 |
| --- | ---: |
| 文档 / block | 15 / 526 |
| 候选 `block × leaf` 调用 | 121,742 |
| 支持关系 | 7,843 |
| 无支持 block | 67 |
| 空叶节点 | 94 |
| 一级初筛回退全部 root | 0 |
| 冲突 | 0 |

单叶提示词在 `b00008` 的 253 叶样本上完成 10 轮回放：必挂召回 99.12%，硬负例误挂 4.35%，灰区支持 88.95%。未参与提示词调参的 `b00007` 也完成了 149 叶 × 10 轮跨 block 回放（rev3）：必挂召回 94.44%，灰区支持 78.57%，硬负例误挂 10.00%。该结果支持二条件提示词作为当前主路径，同时暴露高召回与硬负例精度之间的系统性权衡；`b00007` 仍有 11 个稳定 10/10 硬负例误挂和 1 个稳定必挂漏判，不能视为跨 block 泛化已经完成。

全量挂接必须保留精确的无支持 block 集合。某个 block 没有支持叶节点只说明当前框架和挂接判断下没有承载位置，不能直接判定为无价值或框架缺项；当前 v1.0 只保存该事实用于诊断，尚不自动触发 §5.8 的框架缺口反馈。

### 6.8 核心证据与背景相关证据

挂接账本只用 `block × leaf` 支持关系记录“这个原文能够支持这个知识身份”。金标准另需区分：

- **核心必答证据**：直接提供回答某个必需方面所需的定义、结构、机制、能力、方法、效果或评价；
- **支持／连接证据**：补充边界、条件、例子或关系，但缺失不一定使核心答案不完整；
- **概览／背景块**：只说明章节安排、后续主题或文章范围，不直接提供所问知识。

`b00006` 这类块可以保留在“背景相关召回”集合中，但不能因为未进入回答就直接改写为挂接错误，也不能与核心必答证据共用同一个硬召回分母。

## 7. 查询期叶节点选择

### 7.1 工具边界

主 Agent 使用一个宏工具 `search_coverage_blocks`。工具接收用户完整问题，在宿主内部完成叶节点选择和候选原文物化，返回候选 block 与覆盖状态。

工具描述必须说明：它适合需要完整覆盖多篇文档或多个方面的开放式问题；返回原文候选，不直接生成答案；`partial` 表示检查不完整。

第一版中，旧的四个 Wiki 工具退出主 Agent 工具列表，避免与新路径竞争。普通单点事实、精确原文定位和已知 block 补全继续使用基础检索工具。

### 7.2 一级子树隔离调用

查询时从冻结框架动态读取全部一级 root，并针对每棵子树独立调用一次叶节点选择模型。调用之间互不传入其他分支结果。

每次输入只包含：

- 用户完整问题；
- 当前一级子树的 `node_id/title/description/exclusions/children`；
- 固定的叶节点选择提示词。

模型只能返回当前子树内的叶节点 ID。输出中的空 ID、父节点 ID、其他分支 ID 或改写 ID 使该分支失败。返回数组无需排序和去重，宿主统一处理。

### 7.3 选择语义

当前叶节点选择契约要求：

1. 选择所有可能为完整回答问题提供必要知识或证据的叶节点，不只选一个最相关节点；
2. 同时考虑问题中的对象、方面、关系、条件、限制、比较维度和列举要求；
3. 使用路径、标题和描述确定知识范围，用排除边界做消歧；
4. 不因关键词偶然重合而选择，也不因某个节点看似次要而省略补充节点；
5. 不增加当前子树之外或不是叶节点的 ID；
6. 无相关叶节点时返回空数组。

当前提示词版本为 `coverage-leaf-selection-v2`，输出顶层唯一字段为 `leaf_ids`。根节点数量和并发数从冻结框架派生；当前兼容 profile 要求 revision `kf_c1b79b163bfcb2a93844` 和 24 个 root，这只是当前适配约束，不是永久写死的产品常量。

### 7.4 合并与块物化

宿主完成以下确定性步骤：

1. 校验每个分支的 `leaf_ids` 都属于该 root；
2. 按叶节点 ID 去重并稳定合并；
3. 通过封存账本取得 `leaf_id → block_id[]`；
4. 按 block ID 去重；
5. 按文档和原文顺序读取完整 block；
6. 聚合模型调用、重试、token 和缓存数据；
7. 返回候选 blocks 与 `coverage_status`。

同一 block 被多个叶节点选中时只返回一次。

### 7.5 完整性与失败语义

| 情况 | `coverage_status` | 用户可见行为 |
| --- | --- | --- |
| 所有 root 调用成功、输出合法、无截断 | `complete` | 可以说本次覆盖检查完成，但仍按证据内容限定结论 |
| 任一 root 失败、非法或截断 | `partial` | 必须说明检索不完整，不得宣称找全 |
| 分支合法返回空数组 | 不单独降低状态 | 空结果与调用失败严格区分 |
| 所有分支均无法完成 | 工具失败 | 主 Agent 显式报告工具失败，不生成无依据的完整回答 |

`complete` 是检索执行状态，不是答案真实性或现实领域完备性的最终证明。

查询侧发现全局问题低召回或明显未覆盖方面时，应生成绑定当前 snapshot、框架和 query 的待审反馈，进入 §5.8 的框架缺口流程。该反馈不得修改当前活动框架，也不能把本次 `complete` 升级为框架完备性证明。

## 8. 回答接入

### 8.1 候选块不是最终证据包

`search_coverage_blocks` 返回的是完整覆盖检查形成的候选原文。主 Agent 仍需：

- 阅读候选块；
- 合并相同或重叠结论；
- 区分定义、机制、例子、条件、效果和评价；
- 删除与问题无关的候选；
- 检查候选之间是否存在冲突；
- 识别候选已经覆盖的方面和仍未覆盖的方面；
- 只对实际支持回答内容的 block 产生引用。

不得把“工具命中”直接写成事实，也不得因为候选很多就声称已经找全。

### 8.2 主 Agent 与完整状态

主 Agent 提示词必须把工具语义、资源边界和失败处理写清楚：

- 开放式多方面问题优先调用 `search_coverage_blocks`；
- `coverage_status=partial` 时必须显式告知用户；
- 工具失败、上下文预算不足或回答被截断时不得标记完整；
- 资源上限只用于异常保护，不得通过固定截断候选来伪装完整。

### 8.3 当前上下文与引用限制

c13-003 的候选工具结果已经超过默认 100,000 上下文，Harness 在 post-tool 检查时返回 `partial`；只有提高预算后主流程才成功。这个差异说明当前候选集合过大，不是提示词可以单独解决的问题。候选规模和成本拆分见 §11.2。

后续必须设计“全量挂接关系”和“单次回答证据包”的分离：

- 挂接账本保留可追溯的证据全集；
- 查询期按问题意图、支持类型、代表性、唯一性、冲突和边际覆盖选择进入回答的证据；
- 不设固定 Top-k 冒充语义完整；
- 输出选择数量、省略数量和省略理由，必要时继续补查。

## 9. 金标准与评测

### 9.1 三层金标准

三类判断不能用同一个布尔值表达：

| 层 | 判断对象 | 必要信息 |
| --- | --- | --- |
| 块相关性 | block 对当前问题是否有帮助 | 核心、支持、概览或无关 |
| 叶节点支持 | block 是否直接支持某个叶节点知识身份 | `no_support`、`weak_support`、`direct_support` |
| 回答覆盖 | 最终答案是否覆盖全部核心方面并正确引用 | 核心方面集合、证据、缺口和假完整状态 |

“块相关”不等于“支持任意当前叶节点”，“支持当前叶节点”也不等于“必须进入最终回答”。三层必须分别统计。

### 9.2 核心、支持与概览证据

求全类问题的块级金标准至少区分：

- `core_required`：直接提供某个必需答案方面所需知识；缺失会使答案不完整；
- `supporting`：补充条件、边界、例子、背景或连接关系，能改善答案但不构成核心缺失；
- `overview`：章节导览、文章安排、主题预告或范围说明，缺少后对当前问题几乎没有实质损失；
- `irrelevant`：与问题无关。

核心召回使用 `core_required` 作为硬分母；支持召回和概览召回单独观察。该分类用于评价，不应被模型当作待枚举输出，以免增加调用复杂度。

`known_relevant_block_ids` 如继续保留，必须明确其包含的层级；不能把概览块与核心块直接合并成一个必召回率。

### 9.3 指标

必须分别报告：

**知识框架**

- 结构合法率；
- 主要任务覆盖审查通过率；
- 叶节点颗粒度审计完成率；
- 拆分、未决和失败数量；
- 人工抽样中的重复、任务式节点和错误边界。

**证据挂接**

- `direct_support` 必挂召回率；
- `no_support` 硬负例误挂率；
- `weak_support` 稳定率和覆盖率；
- quote 可定位率；
- 调用失败率、冲突率和完整运行耗时；
- 输入、输出、缓存命中和未命中 token。

**查询选叶与候选物化**

- 必要叶节点召回率；
- 核心、支持和概览块召回率；
- 候选 block 数量、token 和成本；
- 一级分支失败率与 `partial` 正确率；
- 不同运行之间的集合稳定性。

**回答**

- 回答核心方面覆盖率；
- 核心证据召回率；
- 假完整率；
- 引用完整率和语义支持率；
- 首字延迟、总耗时和请求预算；
- 无法验证或仍为 `pending` 的阶段必须单独报告。

单次 100% 通过不作为冻结条件。稳定性和泛化必须通过多个 block、多个问题、不同主题宽度和未参与调参样本验证。

### 9.4 防泄露

运行时不得向模型提供：

- 答案组名称、方面标签或隐藏必要叶节点；
- 金标准 block ID；
- 已选叶节点；
- 针对具体问题的检索词映射；
- 其他一级分支的内部选择结果。

知识框架生成、提示词调参和查询使用必须遵循样本隔离。c13-003 可用于阶段验收，但不能反向进入框架生成或形成问题特例规则。

## 10. 失败语义与可观测性

### 10.1 失败分类

| 阶段 | 失败 | 必须行为 |
| --- | --- | --- |
| 框架生成 | 结构非法、截断或字段缺失 | 显式失败；不得用部分节点冻结 |
| 任务覆盖 | 迭代停滞或未覆盖 | 保留未通过任务和证据；不得宣称框架有效履职 |
| 叶节点审计 | `uncertain` 或调用失败 | 保留未决；不得默认通过 |
| 一级树初筛 | 调用失败、非法或覆盖不完整 | 回退全部 root |
| 单叶挂接 | 调用失败、JSON 非法或 quote 不可定位 | 记冲突；账本不能 `sealed_complete` |
| 账本封存 | 覆盖缺失、hash 不符或重复关系 | 保持 `partial`／`failed`，旧活动指针不变 |
| 查询分支 | 失败、非法或截断 | 整体 `partial`，保留成功结果 |
| 上下文预算 | 候选结果超出限制 | 显式 `partial`；禁止静默截断伪装完整 |
| 回答输出 | 截断或未结束 | 标记不完整，并告知用户 |
| 引用标注 | 调用预算耗尽 | 保持 `pending`；不得写成成功 |

### 10.2 trace

至少记录：

- query 和工具调用；
- 每个一级 root 的选择输入摘要、输出、状态、重试和 usage；
- selected leaves 只在内部 trace 中记录；
- block 数、token 估算、上下文预算决策；
- ledger、snapshot、framework 和 prompt 版本；
- 主 Agent 工具轮次和回答完整性；
- 引用标注的分批结果、预算和 pending 状态。

trace 用于根因分析，不用来向用户证明模型内部正确。

## 11. 成本、规模与增量生命周期

### 11.1 当前规模

当前已验证规模为 15 篇文档、526 个 block、24 个一级分支和 620 个叶节点。产品目标约 10 万 block，当前方法尚未在该规模验证。

当前全量挂接固定使用 `deepseek-flash`，thinking 关闭，temperature 0，最大输出 8,192 token；一级初筛并发 25，逐叶判定并发 20，单请求最多 3 次尝试。模型 ID、thinking、输出上限、并发和重试策略都是挂接结果可追溯的一部分，不能只记录提示词版本。

全量离线挂接的主要成本来自 `block × candidate_leaf`：

- 当前候选判定量见 §6.7；成本随 block 数、叶节点数和初筛保留率增长；
- 输入 token 142,531,463，输出 token 2,387,933；
- 真实耗时约 1.513 小时。

该成本证明首版可以完成固定语料挂接，不证明可以在每次入库或每次查询中重复执行。

已实验过对初判支持项开启 thinking 做二次校准。`b00008` 的 593 个初判支持实例在 `deepseek-flash`、thinking 开启、temperature 0、最大输出 8,192 token、并发 16 下重判后，硬负例误挂由 4.35% 降至 1.10%，硬精确率由 79.48% 升至 93.75%，硬 F1 由 88.22% 升至 95.38%，二元精确率由 85.33% 升至约 95.45%；但直接支持召回由 99.12% 降至 97.06%，弱支持命中由 88.95% 降至 69.47%～70.00%。这 593 次调用耗时 511.862 秒，消耗输入 756,539 token、输出 1,230,344 token，另有 1 次输出截断。考虑到当前首要目标是高召回，以及二次调用带来的时间和 token 成本，thinking 二次校准暂不纳入默认挂接路径，只保留为诊断与未来选择性复核方向；启用前必须另行设计触发条件，并在未参与调参的 block 上验证。

### 11.2 查询成本

当前 c13-003 的候选集合产生约 167,624 token 的工具结果。该成本来自“全量候选进入主 Agent”的实现，不是最终回答所必需的最小证据包。

默认 100,000 上下文时，Harness 因候选过大返回 `partial`；提高到 200,000 后成功。资源上限只用于异常保护，不能作为长期方案：

- 不得固定截断候选并宣称完整；
- 不得为通过而一味提高全局预算；
- 应先实现问题感知的候选证据选择和分组阅读；
- 保留完整账本和回查能力，以便选择阶段遗漏时恢复。

### 11.3 增量编译模型与当前实现状态

本设计要求文档、框架、视角或判定配置发生显式变化时，只重算能够证明已失效的 `block × leaf` 关系，并通过 staging 账本与原子切换发布新 revision。变化输入必须来自显式 delta manifest，不能把“本次输入中未出现”解释为删除。

v1.0 冻结的是增量失效原则、发布不变量和后续验收口径；正式增量执行器、失效传播、staging 合并以及与等价全量重建的对照尚未实现。因此当前版本不得宣称已经支持自动增量编译；在实现和验证完成前，正式入库仍以可追溯的完整重建为准。

#### 11.3.1 变化类别与失效范围

| 变化类别 | 最低失效或重算范围 | 必须保持的约束 |
| --- | --- | --- |
| 无变化 | dirty set 为空，复用当前活动账本，不创建新的语义 revision | no-op 不得产生挂接调用或伪造变更 |
| 新增文档或 block | 对新增 block 执行候选叶节点初筛和 `block × leaf` 判定 | 新 block 发布前不得被宣称已覆盖 |
| block 内容修改 | 按内容 hash 使该 block 的旧支持关系失效并重新初筛、判定 | 新内容不得复用旧 quote 或旧支持理由 |
| block 删除 | 只接受显式删除输入；退休该 block 的全部支持关系 | 不得从候选集合缺项推断删除 |
| 新增叶节点 | 对历史 block 补充候选初筛和挂接；若做局部挂接，必须先证明候选 block 集合完整 | 新叶节点不得因“没有历史关系”被当成空叶节点 |
| 叶节点 path、标题、描述或 exclusions 改变 | 使该叶节点的支持关系失效并重判；相关祖先摘要、身份去重和受影响兄弟节点必须重新校验 | 语义边界变化不得静默沿用旧关系 |
| 叶节点删除、合并或移动 | 通过 lineage 迁移、退休或重建相关关系，更新祖先和叶节点身份 | 不允许产生悬挂关系或把旧 ID 关系隐式映射到新知识身份 |
| 领域、角色或任务变化 | 形成新的知识框架 revision；按受影响分支重编，无法证明局部等价时全量重建框架与挂接 | 视角变化不得复用旧视角的知识身份和证据关系 |
| 模型、挂接提示词或支持协议变化 | 明确标记旧关系不可作为新配置下的等价结果；按影响范围重判 | 不同判定语义的账本不得混用或只更新版本标签 |

#### 11.3.2 执行与发布流程

1. 从旧活动账本和显式 delta manifest 计算 dirty document、block、leaf 和 lineage 集合；
2. 仅复用 block 内容 hash、叶节点语义 hash、祖先路径语义、模型、提示词、支持协议和解析语义均未变化的关系；
3. 对 dirty `block × leaf` 重新初筛和逐叶判定；
4. 将保留关系与重判结果写入新的 staging ledger，不修改当前活动账本；
5. 执行完整性、版本绑定、quote 定位、叶节点身份和冲突校验；
6. 校验通过后原子切换活动指针；失败时旧活动账本继续服务，不发布半成品。

增量结果必须在固定样本上与同 snapshot、同框架、同判定配置的等价全量重建对照。核心必挂关系、block／leaf 覆盖单位和完整性状态必须一致；允许模型非确定性带来的边缘支持差异，但差异必须逐条列出并完成复核，不能只比较总数。

## 12. 设计决策登记与未采用路线

### 12.1 已确定决策

| 决策 | 当前选择 |
| --- | --- |
| 知识组织主路径 | 角色和任务驱动的知识框架；关系轴只作为生成和查询辅助视角 |
| 编译输入 | 当前知识库 snapshot 和领域边界；单知识库通常是单一领域，跨领域时应先拆分 |
| 框架生成与语料 | 框架生成不读取当前知识库，先形成独立知识疆域，再挂接证据 |
| 角色来源 | LLM 根据领域生成并归并角色候选，用户必须选择本次编译使用的角色 |
| 人工边界 | 选择角色是具体知识库编译中唯一必须由人完成的前置动作；领域推断、任务与框架生成、叶节点审计可自动完成 |
| 生成内容复核 | 主要任务、任务树、知识框架和叶节点的具体人工复核可选；未人工复核时由自动门禁和 `auto_validated` 记录约束 |
| 一级生成 | 先冻结一级目录，再逐分支展开，不让单次调用生成整棵树 |
| 叶节点判定 | 一个 block 对每个候选叶节点逐叶判定；运行时不输出“部分支持” |
| 评测支持分级 | `no_support`／`weak_support`／`direct_support` 仅用于评测 |
| 挂接事实源 | 不可变、版本绑定的 `sealed_complete` 账本；运行时索引可由账本重建 |
| 查询结构 | 每个一级 root 独立调用，分支之间不共享中间选择结果 |
| 主 Agent 工具 | `search_coverage_blocks` 返回候选原文和覆盖状态，不暴露知识树 |
| 失败语义 | 分支失败、非法或截断使整体 `partial`，空结果是合法结果 |
| 根节点数量 | 从框架动态读取；当前 profile 的 24 root 是 revision 兼容约束，不是永久常量 |
| 框架缺口反馈 | 挂接侧多个 block 无法承载或查询侧全局问题低召回时形成待审反馈；LLM 可辅助分类，人工判断是否改建；当前未实现自动闭环 |
| 增量编译 | 设计支持显式 delta、精确失效、staging 与原子发布；当前尚未实现和执行验证，不得宣称已具备自动增量能力 |

### 12.2 主要未采用路线

| 路线 | 未采用原因 |
| --- | --- |
| 单一固定关系观察轴作为唯一索引 | 适合关系枚举，但容易漏领域对象和开放主题，多义性成本高 |
| 从任务树直接生成知识主题 | 容易把工作步骤、交付物和方案写成知识节点 |
| 单次生成完整知识森林 | 全局覆盖、层级和叶节点粒度在同一调用中相互竞争 |
| 多个叶节点一次完成最终支持判定 | 容易互相竞争和漏判；一级目录批量初筛可保留，但最终支持仍需逐叶 |
| 只返回 Top-k block 并宣称找全 | 数量上限不是语义覆盖，容易产生假完整 |
| 把全部叶节点放进一次查询调用 | 注意力稀释，分支效果和失败语义不可解释 |
| 根据测试问题修改知识树或提示词 | 会形成不可泛化的个案补丁 |
| 模型直接决定节点 ID、最终版本或账本状态 | 结构、身份和持久化必须由宿主控制 |

## 13. 验收门禁

### 13.1 框架门禁

- 全部一级和叶节点结构合法；
- 主要任务完成覆盖审查，未通过项显式保留；
- 全部叶节点完成颗粒度审计；
- 不存在已知任务式节点、重复知识身份或未处理复合叶节点；
- revision、hash、模型和提示词可追溯；
- 框架能够追溯到领域边界、角色候选来源、已选角色及用户选择记录；
- 自动校验通过且无人工复核时，框架可以按 `auto_validated` 状态通过门禁；不得把人工复核记录伪造成运行必需条件或质量通过证据。

### 13.2 挂接门禁

- 所有计划 `block × leaf` 调用完成；
- quote 可定位率为 100%，无法定位进入冲突且阻止封存；
- `direct_support` 必挂召回达到当前约定基线；
- `no_support` 硬负例误挂不出现不可接受退化；
- `sealed_complete` 通过完整性校验并原子发布；
- 运行失败不得被记为不支持。

### 13.3 查询门禁

- 所有一级 root 均产生独立调用；
- 非法 ID、跨分支 ID 和截断被识别；
- 任一分支持续失败时正确返回 `partial`；
- 空叶节点集合不被当成调用失败；
- 账本、快照和框架版本绑定一致；
- 同一 query 多次运行的核心叶节点和核心证据集合达到约定稳定性。

### 13.4 回答门禁

- 回答覆盖声明的全部核心方面；
- `partial` 和失败状态对用户可见；
- 引用只能指向实际工具返回的 block；
- 引用完整性和语义支持按当前评测规则报告；
- 公开检索结果中不出现隐藏金标准或已知答案标签。

### 13.5 规模门禁

- 固定 15 篇闭环通过后，再验证更多文档和 block；
- 10 万 block 的成本、吞吐、存储和失败恢复必须有单独实验；
- 不允许仅凭 15 篇成功宣称达到产品规模。

### 13.6 增量门禁

本节在增量执行器进入实现后生效；当前不得用设计说明替代实现验证。

- no-op 输入产生的 dirty set 为空，不创建新的语义结果；
- 新增、修改、删除、移动、合并和配置变化均能从显式输入精确分类；
- 所有复用关系都能由内容、语义、模型、提示词、协议和解析版本共同证明；
- staging 结果通过完整性校验后才能原子切换，失败时旧活动账本继续服务；
- 固定样本上的增量结果与等价全量重建满足 11.3.2 的对照要求，所有允许差异均已列明和复核。

## 14. 已知限制与后续设计

### 14.1 当前限制

1. c13-003 已完成一次真实端到端运行，但尚未形成多轮 N/K、核心证据全量和最终假完整率的正式结论。
2. 当前候选证据包在默认 10 万上下文下无法容纳，具体规模与成本见 §11.2。
3. 挂接账本记录支持关系全集，尚未实现问题感知的单次回答证据选择。
4. 挂接基线只在调参样本 `b00008` 和未参与调参的 `b00007` 上完成 10 轮验证；`b00007` 仍存在 11 个稳定硬负例误挂和 1 个稳定必挂漏判，不能视为已在足够多 block 上泛化。
5. 一级树初筛存在误排除风险；15 篇运行中没有出现回退，不等于跨领域无误排除。
6. 叶节点证明义务尚未完全分类：某些叶节点支持一个机制即可，某些要求类别实例、整体结构或完整过程。
7. 引用标注后的回答仍可能因预算停止，当前评测不能把 `pending` 当作成功。

```text
【任务】
1. 本次调用只接收一个已审核主要任务 approved_primary_task，输出必须恰好包含一个与其对应的根节点；
```

```text
  description 和 exclusions。

过窄的知识片段。

【判断知识身份的方法】
1. 两个候选节点属于同一知识身份，必须同时满足：核心研究对象基本一致、

2. 标题同义、近义、缩写展开、中英文译法不同，或仅更换了组织措辞的，属于

3. 两个节点只因为共享领域名称、岗位用途、上位类别、横向主题或同一应用场景，

4. 上位范围与下位范围不是重复。若下位范围属于某个一级范围，应将其知识身份

   范围的核心问题不同，并且需要成为独立的高层检索入口，则保留为独立节点。
5. 同一个候选节点包含多个互不从属、需要分别检索的知识身份时，应拆分到多个
   归并节点，不能为了少生成节点而强制合并。
6. description 中列举多个具体内容，不代表必须拆分。只有这些内容分别形成
   独立知识身份，并且需要成为不同的高层检索入口时，才进行拆分。

1. 候选框架中的全部知识身份都必须有明确去向：进入某个归并节点、作为该节点

2. 低频出现的有效知识同样需要保留。一个范围只出现一次，不是删除它的理由。
3. 归并后的 description 必须综合各候选的有效信息，不能只采用出现次数最多的

5. 一级节点数量不设目标。数量由归并后的知识范围决定，不得为了凑数拆分，也

target_node_ids 使用归并节点的 node_id。split 可对应多个 node_id；

reason 用一句话说明判定依据。

【输出要求】

domain 和 role 必须与输入逐字一致。
```

```text
- role_name：岗位角色名称；
- primary_tasks：已经审核的一级任务，每项包含 task_id、task、

对 primary_tasks 中的每项任务执行覆盖审查：
1. 根据任务的 completed_when、inclusions、exclusions、任务本身和角色职责，
   推导完成该任务及其关键判断所必需的知识范围。
2. 检查当前知识框架的一级节点标题、description 和 exclusions，判断这些知识

3. 为每项任务给出 covered、partial 或 missing，并记录提供覆盖的节点和缺失

3. missing：当前框架没有任何节点覆盖完成该任务所需的主要知识身份。
4. 一级节点可以较宽。不能因为一个节点包含多个知识身份就判定 covered 或

   所需要的知识身份。
5. 一级节点较窄也不能自动判定 covered。必须确认该节点确实能够支持任务的
   全部主要知识需求。
6. 同一个知识身份可以支持多项任务。不要因为多个任务都需要它而生成多个重复
   缺口。
7. 不要求每项任务对应一个或多个独立一级节点。知识身份可以存在于宽节点的
   description 中，也可以跨越多个节点，只要范围明确且没有遗漏。
8. 任务名称是审查锚点，不是知识名称。不能直接复制任务名称作为缺口名称，也

9. primary_tasks 是已经审核的职责边界。不要增加新的角色职责；发现跨任务
   共用的知识需求时，将其关联到所有确实需要它的 task_id。
10. 不要用固定知识清单代替判断，也不要因为某个知识范围出现次数少、看起来
```

```text
9. title、description 和 exclusions 必须说明该知识范围研究什么、包含什么以及
```

```text
只有当 query 本次需要的知识属于 exclusion，并且该叶节点没有其他知识可服务本次问题时，
才不选择该叶节点。
5. 不得因为某个叶节点看似主要、其他叶节点只是补充，就省略补充叶节点。
6. 不得增加当前子树中不存在的叶节点，也不得改写 node_id。
7. 只返回当前子树内、确实属于叶节点（children 为空）的 node_id。
8. 如果没有叶节点与 query 相关，返回空数组。

返回的叶节点 ID 无需排序去重。

【输出】

只输出一个 json 对象，不得输出 Markdown、解释或额外说明。顶层必须且只能包含 leaf_ids 字段：

{
  "leaf_ids": ["leaf_id_1", "leaf_id_2"]
}

不得输出 selected_nodes、nodes、type、response_format 或其他顶层字段。

```

```text
<role>
你是“文档学习问答 Agent”，基于用户添加的文档和模型内置知识，回答学习类的知识问题。
</role>

<tools>
{{TOOLS}}
</tools>

<collection_status>
{{COLLECTION_STATUS}}
</collection_status>

<runtime_contract>
{{RESPONSE_POLICY}}
</runtime_contract>

<scope>
1. 只回答学习方面的知识问题。
2. 不制定学习计划，不替用户安排学习路径，不执行代码或文件操作。
3. 请求越界时，直接在最终回答中说明能力边界，不调用工具。
</scope>

<grounding_rules>
1. 工具返回的 block 是候选原文材料，不自动构成证据。只有其内容确实直接支持拟写入答案的文档主张时，才构成该主张的证据；无证据支持的内容不得作为文档事实或文档观点呈现。
2. 数字、对象、时点、范围、归属和限定词必须与证据一致，不得混用相近指标，也不得把概括说成原文原句。
3. 因果、条件、比较、取舍和让步关系必须保持原文的语义角色和方向。
   不得交换原因与结果、前提与结论、收益与代价、作用者与承受者，
   也不得反转增加／减少、允许／禁止、拦截／漏过、误拦／漏检等方向。
   可以使用不同句式和语序，但不能改变各事实在关系中的角色。
   转述收益与代价、目的与让步、条件与结果时，应分别写出双方角色，
   例如“收益是……；代价是……”。不得用含糊的单向连接词压缩双方关系，
   也不得用同一个词同时指代收益端和代价端。
4. 回答前先区分“通用知识”和“文档事实”，并明确内容属于文档直接表述、基于原文的推断还是模型补充。
   文档没有提供或不足以解释时，可以使用模型内置知识补齐通用背景，
   但应说明“以下是通用背景，不是原文表述”；模型补充不得冒充文档原文。
5. 问题询问文档是否说了某事、原文数据、作者立场或出处时，不能用模型知识代替文档证据；
   用户询问某说法是否有原文依据时，应分别判断是否存在原文原句以及核心命题是否被原文直接支持。
   “不是原句”不能直接判为“没有原文依据”；合并多个陈述或加入模型知识时，
   必须标成“基于原文的推断”或“模型补充”。
6. 某次相关度检索没有返回结果，不能证明文档、章节或知识库中不存在相应内容。
   否定判断或“没有相关内容”的结论，只能依据指定范围内明确完成的字面扫描、完整枚举
   或其他可核验的完整检查。工具表示检索过程完整，也不自动等于现实知识已被穷尽。
7. block.section_path 只描述该 block 在规范化章节树中的当前位置，
   不是完整文档目录或章节数量声明。判断章节深度、子章节或章节总数时，
   必须使用工具随 block 返回的 section_context；不得从单个 section_path 推导整篇结构。
   描述位置时使用工具返回的章节名或 section_path，不得自行改写成“文章开头”等顺序判断；
   只有工具结果明确给出可核验的先后关系时，才能描述位置先后。
</grounding_rules>

<coverage_rules>
1. 回答前先识别用户问题明确要求说明的对象、方面、关系、条件、比较维度和列举范围，
   并把它们作为最终回答必须逐项交代的内容；
   不得只覆盖其中最显眼的一项。
2. 候选原文、Top-k 结果或当前已读到的 block 不能自动代表全集。
   只有指定范围已经完整检索，或工具明确返回该范围内的完整枚举时，
   才能使用“全部”“完整覆盖”等表述。
3. 工具表明检索未完整完成、结果被截断、部分结果无法进入上下文或某些来源不可用时，
   最终回答必须说明哪些范围没有完成，不得把部分检索表述为完整检索。
4. 已发现与问题相关且足以影响回答的内容，却没有写入最终答案，视为回答覆盖遗漏；
   证据不足、结论冲突或无法确认时，应说明缺的是哪一部分。
5. 比较多个来源或多个对象时，应分别交代每个被点名对象的对应信息；
   一个来源或对象证据充分，不能替代其他来源或对象的覆盖检查。
6. collection_status.completeness=partial 时，只能基于成功入库的文档作答，
   并必须声明 failed_documents 中缺失的来源；不得声称当前知识库完整。
</coverage_rules>

<answer_rules>
1. 答案形态跟随问题：定义给定义，原因给因果链，步骤按顺序，
   比较使用同一组维度，清单给清单。
2. 用户明确要求表格、清单、矩阵或指定字段时，按该结构组织答案；
   不得只保留结构外壳而省略已经确定的内容。
3. 对“哪个更好／该听谁的”类问题，陈述双方观点、前提和依据，不替用户裁决。
4. 最终回答使用 GitHub Flavored Markdown；可使用段落、列表、粗体和表格，
   禁止输出原始 HTML、脚本或把整段回答包进代码块。
5. 最终回答只呈现已经确定的内容、必要澄清和覆盖检查发现的缺口；
   不输出“来源”、block_id、引用角标或引用占位符，也不展示内部运行轨迹。
   后置引用标注由 Harness 基于本次真实工具证据独立完成。
</answer_rules>
```
