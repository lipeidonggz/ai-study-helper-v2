0053 · 如何做一个 Agent：方法 + 知识面

一句话：做好一个 Agent，有两块东西是基础的——① 正确的方法（测试驱动升级版）； ② 知识面（架构判断与技术内核理解）。前者决定"你怎么不走偏"，后者决定"你判断得对不对"。

本文用途：作为产品重启的指导文件。先在这套方法 + 知识面的指导下重新推导， 再决定这个"文档学习问答"产品怎么做——过去这段时间的所有记录都是知识经验，不是产品基础。

1. 第一块基础：正确的方法

1.1 为什么 Agent 开发需要"测试驱动升级版"

传统软件开发的测试，测的是"确定行为"：输入定了，输出就定了。 Agent 不一样——它是一类带智能的系统：同一个问题、同一份材料，跑两遍， 结果可能不一样；同一个答案，"对不对"也往往不是一个布尔值 （可能覆盖了要点但漏了扩展主题，可能内容对但引用锚不住， 也可能引用了原文，却把两篇文章的关系说成同一套框架）。

这意味着不能用"跑一遍、看结果对不对"来衡量系统功能质量—— 单次结果可能只是运气。衡量这类系统的质量，必须引入统计方式： 跑多次、看通过率与分布，用"稳定通过"代替"碰巧通过"。

而一旦改用统计方式，测试工作量就是数量级的上升：一个用例要跑 N 次， 还要跨模型、跨配置、跨版本对照，并且要能复现。靠人工跑，既贵又不稳—— 人会疲劳、标准会漂移，何况自己抽读还会自我说服（我们有过一次实测： 人工抽读认为答案通过，判官按事实边界判为失败）。所以测试必须自动化。

自动化评测又不能只是一段"跑得动"的脚本——它必须先回答两个问题： 测什么、什么算对。这就是用例集（测试集）与金标准。 没有它们，自动化只能告诉你"程序跑完了"，判不了"结果对不对"。

所以 Agent 开发变成了"测试驱动升级版"：不是"先写代码、后补测试"， 而是先把用例集与金标准立起来，让架构决策和代码优化既有依据、也有验证器。

用例的两个角色： 它暴露的失败模式，是架构调整与代码优化的依据——告诉你哪里不对、该往哪改； 它的通过率，是这两类改动的验证器——告诉你改完到底有没有变好。 需要补一句：架构决策的依据不止失败模式一处——第一版架构要先由 产品定义、问题形态、数据形态与硬约束推出；失败模式只有在系统能跑之后才存在， 它负责修正，而不是唯一来源。

1.2 五步流程

步骤做什么
① 产品定义 回答"这是什么产品、给谁、解决什么、明确不做什么"；用户 / 产品视角第一性，工程约束刻意降权。
② 需求 / 问题空间 从产品定义正推"用户会问哪些类型的问题"，而不是从已有实现反推；只谈问题域，不混解决域。
③ 用例 + 金标准 各类问题都要有代表用例；金标准要能回答"满足什么即通过、什么情形判失败"；含概率指标与判定规则。某一类若写不出"什么算对"，别硬写——那是产品定义有洞，回头补定义（见 §3）。
④ 架构决策 只在宏观层判断：知识承载层要背多少"全"的责任，智能执行层要背多少；不追最新范式，只对问题形态。怎么做见 0055。
⑤ 实现 + 统计判质量 按用例集执行，用统计指标判断系统质量。这一步不是一次性的终点检查，而是一个迭代过程： 每一轮失败都要走"红 → 根因定案 → 探针 → 修复 → 回归"； 新暴露的问题既可能回填用例（回到 ③），也可能推翻第 ④ 步的架构判断—— 例如发现瓶颈不在检索，而在输出预算；或发现"取齐"缺的是结构，而不是模型。 所以第 ④ 步不是一次定终身：架构决策必须能被第 ⑤ 步的失败模式推翻并重做。

顺序不能倒：先定义问题、再定验收、最后才定架构。反过来做，就会变成"技术上能做什么，产品就做什么"。 但顺序不能倒不等于只能走一遍——第 ⑤ 步的失败会带着证据回流到 ③／④，整个流程是一个可以反复回环的循环。

1.3 配套纪律（各自保护五步中的哪一步）

这三条不是第 ⑤ 步之外的另一组方法，而是前面五步各自的护栏——每一条都能指回它保护的那一步。 没有它们，流程看起来还是走完了，但结论很可能是错的。

纪律落在哪一步内容为什么
基础件人工复核 ③ 用例 + 金标准 金标准、判官提示词、系统提示词、工具行为契约——AI 可起草、可提议，但不得自审自合入。 基础件错了，③ 之后的所有统计都在朝错误方向优化。AI 看不见自己的盲区，自检无效； 出现"补丁摞补丁"，往往是少了这步。
根因闭环 ⑤ 实现 + 统计判质量 红 → 根因定案 → 先补"该不变式的代表探针"（仍红）→ 机制修复（绿）→ 全量回归。 探针必须钉住唯一根因类；每个根因类只留代表用例，防套件膨胀。
概率指标 + 红线 ③ 定义 ＋ ⑤ 执行 单用例跑 N 次、≥K 次满足判据才算通过；红线（引用无伪证、来源可回锚、遗漏透明、边界合规）零违反。 模型每次生成都带随机性：同一个问题、同一份资料，跑两遍结果可能不一样—— 单次通过可能只是运气好，单次失败也不代表系统不行。所以要跑 N 次、要求 ≥K 次达标， 用"稳定通过"代替"碰巧通过"。

但红线不能按比例算：引用造假、来源对不上、该声明的遗漏没说、越界—— 只要出现过一次就不通过，不能用平均分把它盖过去。

2. 第二块基础：知识面（架构判断与技术内核）

这一块分四层：模型能力（天花板）→ 知识承载（能不能确定全）→ 智能执行（能不能拿全）→ 验收体系（你知不知道系统在哪）。 每层给几条能直接拿去用的判断法则。

2.1 能力层：LLM 是真正的变量，但"更强"≠更好用

  • 能力上限由模型决定。模型能理解、能推理、能遵守指令到什么程度， 决定了产品能力的天花板；架构与工程改进只能让系统逼近这个上限，不能越过它。
  • "更强"不等于"更好用"。 实测 换更强的模型是否带来增益，必须用对照实验验证，不能靠参数规模、榜单或直觉默认。 模型变强可能只改变一部分行为，也可能把原来的平衡打破。
  • 输出预算是能力边界，不是格式细节。 实测 上下文窗口与输出上限直接决定"能不能把一件事做完"；撞到上限会出现内容被截断， 而且可能是静默的（系统报告完成，答案却停在句中）。评估能力时必须把它当成变量。
  • 采样参数（温度等）影响需要实测。 实测（小样本） 不同系统、不同任务下，同一组参数的效果并不一致；它属于要固定、要对照的实验配置， 不能默认取值，也不能照搬别人的结论。

2.2 承载层：编译层是索引，不是事实源

  • 原文单元永远是事实源；编译产物只能是地图 / 索引。 否则引用真实性审计链在编译处断裂——这是硬约束，不是保守。 已定口径。
  • 图也是索引层，不是事实源。 边的 chunk_id 由证据句定位而来，事实在 chunk； 方向 / 极性错误会让边指向错的 chunk，属索引层的正确性红线。 已定口径。
  • Wiki 是投影，图是不变量。 投影的完备性边界是"角度集合"（不可枚举）；不变量的完备性边界是"事实集合"（有界、可建金标准）。 落点：事实层要有结构（断言 + 出处 + 归属标签），呈现层可以很 Wiki； 页面不承担"成员清单载体"。 推断 / 已定口径。
  • 编译噪声要锁死在"路由"层。 结构性噪声由程序校验拦，语义性噪声由判官 / 引用审计当自动门 + 抽样； 关键是噪声进不了"事实"。 实测。
  • 语料相关的坑要提前想：跨语言、符号与指代（C_reason、Eq. 3、the former）、 元主语告警（论文的 we propose / our method）、 section 标题在论文里没有信息量。 实测。

2.3 四种知识组织形式的判断表

形式解决的问题做不到什么前置成本什么时候够用
块向量 相似度选点；细节 / 单点问题 枚举、跨源连接、关系；要"全"的场景 最低（入库即用） 点状问题、定义型问题、模型不会时的兜底召回
段落主题标签 受控小词表下的范围枚举 细粒度关系、按条件取齐 一遍 LLM（可复用编译输入） 面状覆盖、需要"按主题取一组"的场景
LLM Wiki 入口网 + 跨源概念归集 + 页面遍历 条件取全的原语、可查询的关系 编译一层（页 + 链接） 面状覆盖（本次实测支持：Wiki 基本够用）
知识图谱 枚举 + 跨源连接 + 关系查询 开放域理解；它替代不了 LLM 的语义判断 编译 + 抽实体 + 建边（最高） 有条件可枚举、需要跨源连接或关系查询的场景

这张表的用法：先按问题形态确定"要不要全、要不要关系、要不要跨源"， 再决定组合。不要反过来"因为上了图谱，所以去找图谱能回答的问题"。

陷阱：技术本位主义。决定"上图谱"时没从产品需求与约束出发， 方案便宜的"前提"其实是语料偶然给的（那两篇博客的 section 标题自带语义总结）， 而产品要覆盖的论文标题基本没有信息量。 定架构前先问：这个信号是语料偶然给的，还是方法本身要产出的？

2.4 执行层：工具集决定能力边界，契约决定行为下限

  • 工具集决定能力边界，不是"检索质量"决定。 实测 smart 没有页导航、wiki 没有块入口、hybrid 两样都有； 三条路线的能力边界由工具集决定。
  • 提示词写了 ≠ 会执行。 实测 三份提示词都写"精确引用要回原文核对"， 但只有能拿到原文块的路线做得到。
  • 契约 + 显式输出槽必须配对。 实测 软性自然语言契约在义务真正触发时 0/1； 只有槽位没契约，模型会直接填"未覆盖：无"。 槽位负责"必须交一份覆盖清单"，契约负责"不许搪塞、缺项必须具名"。
  • 静默截断是最危险的失败。 实测 一次实测里，答案落库 16,964 字，停在句中、带着未闭合标签， 而 is_completed=True、无提示——对全景题等于"讲一半、不声明"。 输出预算与"被截断要声明"应是契约的一部分。
  • "收尾式"要求最先被截断吃掉。 实测 + 产品形态决策 披露不要放结尾，要嵌进列举结构—— "详述完主要几项后，用一句话把没展开的项具名带出来"。
  • 没有"否信号"，成本就没有上限。 实测 块级检索几乎不返回空（0.5%），agent 提的每个问题看起来都有结果； 页级检索有 48.6% 返回 0，所以 wiki 更容易止损。 同一道 4 跳题连跑 8 次，token 差 19 倍，最贵的几次几乎正好撞在 max_iterations 上。
  • 路由要有可观测信号；纠错要有回灌。 实测 + 推断 跳数在提问时不可观测，"按预期跳数路由"前提不成立； 被测系统的问题台账全库 0 条—— 只有记录、没有回灌的纠错机制，实际使用里没人会去写。

2.5 验收层：判官、基线、抖动与"覆盖 vs 排除"

  • 判官是基础设施。 实测 一次实测里，人工抽读认为答案通过，判官按事实边界判为失败； AI 抽读会自我说服——判官的价值正在这里。
  • 绝对分不能当能力刻度。 实测 先量闭卷基线，分成"记忆可解 / 记忆不可解"两档； 两档方向相反，混在一起算平均会得到一个谁都不像的结论。
  • 多轮 + 抖动；差距小于抖动就当它不存在。 实测 本实验单轮结论翻了四次 （重排、"hybrid 最差"、换模型、换模型后单轮领先）； 同一个 0.006 换口径会翻号；同一道题连跑 8 次成本差 19 倍。
  • 覆盖 vs 排除是两回事。 本质限制 覆盖性（该有的都有）有判据、可逐点核对； 排除性（不该有的不能有）错误空间开放，只能按"已知错误类型清单"验， 未知类型会漏——产品必须明说这一点。 可行形态＝事实边界断言（用例 boundary_claims）； 错误类型清单从失败样本回填（如"概念嫁接"：两来源各自都真，错在说成同一机制）。
  • 要区分"模型本来就会的"和"检索补上的"。 实测 先量闭卷底分，再谈检索增益；底分高时上检索要先做好"分数可能下降"的心理准备。
  • 一个好的测试集本身要体检。 实测 4 跳 10 道题里 8 道本身有问题（定指不唯一 / 关系错配 / 同名混用）； 判断一道题站得住的最快探针是"题面预设"层—— 一道题只依赖"知识库事实 + L1 术语与指代"，才算站得住。

3. 架构陷阱清单（反面清单）

陷阱表现怎么防
技术本位主义 先定技术方案，再找它适用的产品问题；用"实现容易"当架构理由。 先问"这个信号 / 前提是语料偶然给的，还是方法本身要产出的"。
把均值当能力 用公开数据集的绝对分推"我的系统能到什么水平"。 先量闭卷基线分档；公开 benchmark 只当相对参照。
单轮定论 跑一次就说"方案 A 更好"。 多轮均值 + 抖动；差距小于抖动当不存在。
用近似物当精确判据 字面匹配判幻觉、拿 A 的清单比 B、用汇总指标判"漏没漏"。 判据必须标来源与边界；跨语言 / 跨字段 / 跨层默认失效。
契约只写在提示词里 提示词写了"必须声明遗漏"，模型不照做。 契约 + 显式输出槽配对；红线用程序核，软性用判官核。
静默失败 截断、丢页、解析失败、少生成 19% 报告，而系统报成功。 失败要可观测：截断声明、缺项声明、对账；指标要覆盖产出层，不只调用层。
没有否信号 检索永远有结果，agent 不知道"这里没有"，反复搜索不收敛。 设计"找不到"的信号；给成本上限并声明；把"正确拒答"和"答错"分开记。
纠错没有回灌 有台账、有工具，但没人用，也不影响下一轮。 把反复犯的错写成约束，回灌下一轮编译 / 生成。
用长度绕开义务 答案越长，覆盖越全，判官越绿——但用户看不完，越界风险也更高。 看 pass 率时同时看长度与义务触发情况；产品目标不是"一次给全"。
把编译产物当事实源 引用指向编译页，而不是原文块；审计链在编译处断裂。 原文单元永远是事实源；编译层只做索引 / 路由。
金标准写不出来就硬写 某一类问题说不出"什么算对"，却在措辞上反复打磨、硬凑一条判据。 那是产品定义有洞——回头补定义，别在金标准里凑（本项目"整体图景"类第一次就是写不出来，补了"总纲＋若干支撑面＋核心概念必须覆盖"才成形）。

4. 拿它来重启这个产品

产品定义已经收窄： 允许以学习为目的的用户添加各种文档，基于这些文档以及大模型内化的知识， 提供学习方面的知识问答能力；单用户 + 单知识库；单轮；不做学习规划指导。

4.1 动作顺序

  1. 确认产品定义：产品的定位与做 / 不做表，先冻结。
  2. 冻结问题空间：已经推导出的 15 类问题，逐类确认"这一类是不是用户真会问的"， 并给每类确定取材范围。
  3. 用例集先行：每类问题至少一条代表用例；各类必须先齐全，数量可以后补； 金标准要写清"满足什么即通过"，并标出红线。
  4. 确定判定规则：判定规则的建议稿（跑 N 次、≥K 次满足且红线零违反；用例集按类达标）； N / K 与各档阈值在用例层定。
  5. 再做架构决策：按上面 §2.3 的判断表，决定每一类问题走哪条通道、 承载层要背多少"全"的责任；方法与质量属性盘点见 0055。
  6. 实现后按统计指标判质量，失败样本按根因闭环回填用例与错误类型清单。

4.2 第一批要补的用例（当前缺口）

  • "按一个确定条件取齐"类：已有的用例里一条都没有； 已有一批候选题面（A–F 六组）等待纳入。 这是"图谱 vs Wiki"能否被实测回答的关键缺口。
  • 关系查询类：Wiki 页里关系是叙事文本，没有可枚举、可遍历的关系原语。
  • 排除性防线类：概念嫁接等"两来源各自都真、错在说成同一机制"的错误， 需要专门的边界断言用例。
  • 跨源消歧类：口语模糊题面在多源库里会选错文档对； 需要有"库里多一篇同域干扰文档"的代表用例。

4.3 暂缓 / 不做

  • 多轮对话：下个迭代计划项，本迭代单轮。
  • 多用户 / 多知识库：不做账号、协作、权限、多库并存、跨库检索。
  • 预编译一层：在"答案要解决哪件事"说清楚前，不先上图谱 / 不先上 Wiki 编译。
  • 学习方向 / 学习规划指导：明确不做。
一句话收束：结构决定"能不能确定全"，智能决定"能不能拿全"，验收决定你看不看得见真相。 凡是"看起来更好"的结论，先问三件事： 闭卷基线是多少？差距有没有超过抖动？这个便宜是不是语料偶然给的？
